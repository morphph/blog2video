# Video 1: Claude官方揭秘：为啥你不需要多Agent架构？

[SLIDE 1: cover] (0:00 - 0:30)

现在多 Agent 架构很火，那么什么时候该使用它？今天我们来精读 Claude 官方发布的工程博客：《Building multi-agent systems: when and how to use them》。很有意思的是，它不是在教你如何构建多智能体，而是在教你如何尽可能不使用它。

[SLIDE 2: principle] (0:30 - 2:30)

Claude 官方分享了一个真实的教训：他们见过有些团队投入数月时间构建复杂的多智能体架构，结果却发现，改进单智能体的提示词就能达到同等效果。多智能体系统，在现有的条件下，本质上是一种"代价昂贵的工程权衡"，而不是对单智能体能力的升级，是在用"成本"换取"能力"。

为什么这么说？想象一下，你是经营一家小餐馆。原本你一个人就是主厨，切菜、炒菜、摆盘样样精通，这就是"单体 Agent"。虽然忙一点，但你心里非常有数，所有信息都在你脑子里，没有任何沟通成本。

现在，你听说"多智能体"很火，于是你招了三个助手：一个专门切菜，一个专门炒菜，一个专门摆盘。看起来很豪华，对吧？但现实是：你需要花大量的时间去协调他们。那个洋葱切丁不是切丝！菜炒好了盘子怎么还没来？这就是"通信开销"。

Claude 的工程师在实战中发现，盲目上多体的代价是非常昂贵的。首先是 Token 成本。每个 Agent 都要维护自己独立的上下文，这就像每个人都要发一份完整的"员工手册"，消耗通常是单体的 3 到 10 倍。其次是延迟。多一个 Agent，就多一次网络请求，也就多了一个潜在的故障点。

所以，第一条原则就是：尽量先使用单 Agent，如非必要，勿增实体。除非使用多 Agent 有明确的正收益。

[SLIDE 3: comparison_cards] (2:30 - 6:00)

原文总结了三种"多智能体能持续跑赢单体"的特定场景，能获取明确的正收益：

第一，上下文保护，解决的是"噪音"问题。来看一个客户服务的例子。假设你的 Agent 需要处理一个用户的技术故障，为了搞清楚状况，它需要先去查询用户的历史订单。结果 API 一下子返回了 5000 字的完整日志。如果你把这几千个 Token 的"高噪声材料"直接塞进上下文，Agent 的注意力瞬间就被冲散了。它可能本来要解决"无法登录"的问题，结果看完日志后，开始一本正经地分析"为什么上个月的快递慢了"。

这一类场景要成立，必须同时满足三个条件：子任务会产生大量上下文内容；这些信息大部分与主线任务无关；这些信息在被使用前，必须先经过筛选或过滤。

第二，并行化，解决的是"覆盖度"问题。这里有一个常见的误解：很多人以为并行是为了"快"，但在 Agent 领域，并行的核心收益，其实是"全"。比如，你需要回答一个极其复杂的研究问题，如果你只用一个 Agent，它只能按顺序看前几页搜索结果。这就像一个人在图书馆找书，能翻阅的数量是极其有限的。在并行架构中，我们可以同时启动十个子智能体，分头行动。虽然总 Token 消耗会上升到 3 到 10 倍，但换来的是对搜索空间的"全覆盖"。

第三，专业化分工，解决的是"能力稀释"问题。当一个 Agent 被赋予过多且差异很大的工具时，系统的整体可靠性反而会下降。实践中，一个常见信号是：新增工具，不仅没有提升能力，反而削弱了它在原有任务上的表现。

但专业化并不是免费的。它引入了额外的路由和协调成本。只有在任务边界清晰、职责划分明确，且路由决策本身不模糊的前提下，才会产生正收益。

[SLIDE 4: checklist] (6:00 - 7:30)

到这里为止，我们讨论的都是：在什么问题结构下，多智能体是正收益的。但还有一个更现实的问题：你现在是否已经被逼到必须使用多智能体？

你可以检查一下你的系统是否出现了以下三个信号：

信号一：上下文触顶。如果只是觉得记性不够用，但还没到必须隔离的地步，先别急着拆 Agent。先试试上下文压缩技术。

信号二：工具过载。如果你只是工具多，但职责并没有冲突，先试用 Tool Search，让 Agent 在运行时自己去搜该用什么工具。官方数据显示，光是这一招，就能减少 85% 的 Token 消耗。

信号三：任务天然可并行。在任务天然独立的前提下，并行架构确实能带来显著的速度提升。

[SLIDE 5: summary] (7:30 - 8:00)

最后总结一下。构建 Agent 系统，不要一上来就做多 Agent。默认先从单体出发。如果遇到瓶颈，先检查是不是可以通过 Tool Search 或上下文工程技术来解决。如果不能，再考虑多 Agent。只有当你确认问题符合那三个正收益场景——上下文需要强隔离、任务需要高覆盖，或者职责发生强冲突时，再最终切换到多智能体架构。
