# 给模型加 CRITICAL 没用, 加工具才有用

## Hook

Anthropic 自己刚把"怎么写 prompt"拆成了一份 4 层方法论。一份官方文档 + 一门内部课 + 一位应用 AI 工程师的内部演讲，被一个博主压成了 29 万阅读的长帖。我读完最被打到的，是 Anthropic 工程师在演讲里亲口点穿的那条判断——你给模型加 CRITICAL、加 ALWAYS、加 NEVER，全都没用。指令不等于能力。

## 99% 的人为什么一直改不对 prompt

先把这件事讲透。大多数人写 prompt, 流程是这样的: 想到一句话, 敲下去, 模型答得不行, 加几个词, 再不行就加 CRITICAL, 再不行就把 ALWAYS 和 NEVER 一起堆上去, 像在跟模型吵架。

Anthropic 自己的文档里有一句直接点名这种姿势——"打一句模糊的话, 按回车, 然后祈祷, 然后纳闷为什么输出又泛又虚"。这不是讽刺, 这是 99% 的人每天在干的事。

问题不是你不够卷, 是你在错的地方卷。这篇文章给了一个很冷静的判断: prompt 不是一句话, 是一个四层的系统。新手只写第二层, 然后停在那里。专业的人四层一起搭, 而且有顺序。

## 把四层快速过一遍

四层是这样的。

第一层叫 Parseable, 让模型读得懂。XML 标签把角色、政策、数据、示例分开。Claude 是被专门训练过认 XML 结构的, 这不是审美, 是模型的母语。

第二层叫 Direction, 给模型指方向。给它一个 role, 把任务说清楚, 给一两个例子, 让它把思考过程写出来。

第三层叫 Capability, 给它真的去做这件事的能力。这层是大多数人完全没意识到的地方, 等下专门讲。

第四层叫 Verification, 你怎么知道它真的对了。写一组 test case, 跑一遍, 改一处, 再跑一遍。没有 eval, 你不是在调 prompt, 你是在猜。

四层叠起来的关键不是哪一层最重要, 是顺序。结构在前, 方向次之, 能力再次之, 验证压底。跳层就废。

## 这篇文章最戳我的那条: 指令不等于能力

回到 Hook 里那个客服 bot。它给客户算 prorated 账单, 算得稀里糊涂。工程师做的第一件事, 跟你我一样, 改 prompt。原话已经是 "CRITICAL. Always calculate any prorated amounts correctly. Never give a vague answer." 没有比这更强硬的措辞了。

结果没用。它永远不会有用。

为什么？因为你在让一个不擅长心算的人, 用更大的声音再算一遍。声音再大, 算的还是错的。

真正的解法是给它一个计算器。在工具系统里定义一个 calculator, 告诉模型什么时候用它, 后端把数学逻辑写好。换完之后, 所有 test case 全过。

这就是我读完这篇最被震到的判断。Prompt 失败的时候, 别急着改字, 先问自己一个问题——这是个 direction 问题, 还是个 capability 问题？

Direction 问题的修法在第二层, 换个 role, 加个例子, 让它把思路写出来。

Capability 问题的修法在第三层, 给它一个工具, 或者给它更大的推理预算。

这两条路完全不一样。99% 的人把所有问题都当 direction 问题来调, 在第二层里改一个礼拜, 改的全是同一个意思的不同说法。真正卡住他们的, 是第三层的能力缺口。改字解决不了能力缺口, 这件事光听一遍可能没感觉, 真正写过 prompt 的人会一拍大腿。

## 顺手送一个 30% 的便宜钱

讲完最贵的那条, 顺手讲个最便宜的。

Anthropic 长上下文文档里写得很明白——把长文档放 prompt 顶部, 问题放 prompt 底部。同一个 prompt, 同一个模型, 只是换个顺序, 长上下文任务的质量可以提升百分之三十。

我第一次看到这个数字的时候, 是不信的。模型不就是把整段 prompt 一起看吗, 顺序怎么会差出百分之三十。但这就是真事。模型注意力在长输入里有衰减, 问题贴在长文档后面比贴在前面更容易被关注到。

这是 prompt 工程里最便宜的一刀。不写代码, 不调工具, 不加 token, 把问题挪到最后, 拿百分之三十。如果你今天只能改一件事, 改这个。

## 你的 prompt 只给了一面, 模型就只往那一面优化

第二条最容易踩的坑, 是单边指令。

同一个客服 bot 还有一个 bug: 客户账单错了, 它就是不肯升级处理。工程师翻 prompt, 翻到这么一行——"avoid escalating unless absolutely necessary — it costs about $8 and counts against our metrics." 翻译过来就是, 尽量别升级, 一次升级花八块钱, 而且影响我们的指标。

模型把这条执行得完美无缺。

问题是这条 prompt 只写了升级的代价, 没写不升级的代价——客户拿错了答案、要退款、信任掉一截。你只给一面, 模型就只往那一面优化。

这条洞察的可怕之处在于, 模型越聪明, 这件事越严重。弱模型理解不到位, 单边指令可能还不那么照做。强模型理解得越深, 越会把你给的单一目标硬刚到底。你以为升级模型会让 prompt 更稳, 实际上你的 prompt 漏洞被放大了。

写每一条 "尽量别 X" 的时候, 把另一边的代价也写出来。这是越强模型越值钱的小动作。

## 去年的补丁, 今年的毒药

第三个坑, 我觉得是这篇里最反直觉的一条。

那个客服 bot 还有最后一个怪症状: 客户问套餐细节, 它明明账户数据里就有答案, 却回答 "去网站看看吧"。把已经在手里的信息藏起来。

工程师追根溯源, 找到一行老 prompt: "never give wrong plan details, point them to the URL." 永远不要给错套餐细节, 让用户去看 URL。

这条当年有道理。当年的模型会幻觉, 编套餐细节, 加这一行就是为了堵幻觉。

问题是新模型不幻觉了。可这条补丁还在。新模型只会更认真照做——它不分辨数据在不在手里, 看到指令就让你去看 URL。当年救命的补丁, 今年变成了把客户挡在门外的毒药。

这条洞察我自己读完愣了一下。我们写 prompt 都是往里加, 没有人养成往外删的习惯。但模型在迭代, 你为旧 bug 加的补丁, 在新模型上往往会反噬你。

这件事的解法不是改 prompt, 是改流程。把 prompt 当代码版本控制起来, 每加一条防御性指令记一句为什么加。模型升级的时候, 翻出来一条一条问——还有用吗？没用就删掉。

这是这篇文章最值钱的工程纪律。大部分团队不做, 然后下一次模型升级整体翻车。

## 5 个 test case 不嫌少

最后说第四层, verification。

Anthropic 工程师演讲里展示的内部 eval suite, 只有 5 个 test case。你没听错, 5 个。

不是说 5 个就够, 是说 0 跟 5 的差距, 比 5 跟 50 的差距大得多。重点不在数量, 在覆盖。三类 case 各拿几个就行: control case, 永远应该通过, 它一旦挂, 说明你刚改的东西出大事了; edge case, 历史上挂过的 bug, 每条都是一次 regression 防御; boundary case, 该交给人或该拒答的地方, 测的是模型知不知道自己的边界。

跑一遍, 改一处, 再跑一遍。这一刻你不再是改完 prompt 看一个例子说 "好像变好了", 你是在知道它变好了。这是 prompt 工程从猜测变成工程的那条线。

## Synthesis

我把这篇收尾一下。Prompt 不是你写的一句话, 是你搭的一个系统。四层有顺序, 结构在前, 方向在次, 能力再次, 验证压底。

碰到 prompt 不工作的时候, 别再一头扎进第二层改字。先问自己: 这是结构问题、方向问题、能力问题, 还是没验证问题？这一句多花的三十秒, 经常省下你三个小时。

如果非要我从全篇压一句话出来——你 prompt 失败时改的不是字, 是层。99% 的人活在第二层, 你升一层, 就赢一半的人。

## Closing

今天回去做一件事就够: 找一条你最依赖的 prompt, 拉出来, 不要急着改字, 先按四层走一遍——它的结构清楚吗？方向明确吗？该有的工具有吗？有没有 test case？哪一层最薄, 就补哪一层。

AI 世界很吵, 精读一篇, 胜过刷一百条。我们下期再见。
