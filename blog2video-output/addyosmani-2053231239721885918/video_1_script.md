# Video 1: 模型不再决定 Agent 的胜负

[SLIDE 1: cover] (0:00 - 0:30)

Google Cloud AI 的人，公开说模型已经不是 Agent 的胜负手了。

写这话的是 Addy Osmani，Google Cloud AI 与 Gemini Agents 的 Director，之前还管过 Chrome 的工程。他完全可以替自家 Gemini 站台。但他没有。他写了一篇叫《Agent Harness Engineering》的长文，832K 阅读，将近 8 千人收藏。今天我不聊"模型不重要"这个老结论，只聊这位模型方内部人士，给整个行业埋了哪些新框架。

[SLIDE 2: principle] (0:30 - 1:45)

你想想这个画面有多怪。

一个掌管 Gemini Agent 业务线的 Director，在公开博客里告诉所有人：你换什么模型不重要，重要的是包在模型外面那一层东西。这跟苹果出来说"你买什么手机不重要"是一个量级。

但 Addy 不是在谦虚，他是认真的。他说，相同模型放进定制 Harness 里跑，和放进开箱即用的框架里跑，benchmark 分数会出现剧烈差距。剧烈这个词是他用的，不是我加的。

过去两年，所有人都在比模型。哪家最聪明，哪家写 React 最干净，哪家幻觉最少。这些话题确实有意义，但 Addy 说，这些话题只盖到了系统的一半。模型只是 Agent 运行时的一个输入。其余的部分，才是真正决定行为的地方。

所以这事的信号在哪？模型厂商自己开始承认，下一阶段的竞争，不在模型那张卡上。

[SLIDE 3: principle] (1:45 - 2:35)

先把名字定下来。Harness 这个词由一个叫 Vtrivedy 的工程师在今年提出，Addy 这篇文章是给它做的工程化注解。

Harness 不是工具，也不是框架。它是包在模型外面、所有不是模型本身的东西。系统提示、CLAUDE.md、AGENTS.md、Skills、子 Agent 指令、文件系统、沙箱、Hook、压缩策略、可观测性——这些加在一起才是 Agent。

Addy 给了一个特别简洁的判断。Agent 等于模型加 Harness。如果你不是模型，那你就是 Harness。

所以你在用的 Claude Code、Cursor、Codex、Aider、Cline——这些全都是 Harness。底层模型可能一模一样，你体验到的差别，几乎完全来自外面那层。

[SLIDE 4: principle] (2:35 - 4:55)

这一段是这篇文章我觉得最值钱的部分。

Addy 给 Harness 工程定了一个核心动作，他叫它 Ratchet，棘轮。棘轮的意思是只往一个方向走，永远不退回去。

具体怎么用？假设你的 Agent 不小心提交了一个被注释掉的测试，PR 被人合并了。这就是一次输入。你下一步要做三件事。AGENTS.md 里加一行：绝不注释测试，要么删，要么修。pre-commit hook 自动 flag 掉所有 `.skip(`。Reviewer 子 Agent 加一条阻断规则。

注意这三件事一件都不靠模型的记性，全部是机制。下一次同样的失败再出现，根本到不了模型的判断这一步，被外面三道闸门先拦下来了。这就是棘轮。

听起来挺普通。但 Addy 紧接着的判断很狠。他说，一份好的系统提示，每一行都必须能追溯到一次具体的历史失败。

读到这里我停了几秒钟。

意思是反过来——如果你的 AGENTS.md 里有一条规则，你想不起来它是哪次翻车留下的，那这条规则就该删掉。约束只在你观察到真实失败后才加进去，也只在某一代更强的模型让它变成多余时才删掉。规则不是凭空写的，是疤痕。

这跟我们以前理解的 prompt 工程完全是两件事。Prompt 工程关注的是"怎么把话说清楚"。Harness 工程关注的是"如何把每一次翻车永久编码"。

所以 Addy 才说，Harness 不是一个框架，是一种纪律。一份属于你这套代码库的失败史。他还顺手扔了一个比喻——CLAUDE.md 这种文件，应该当成飞行员清单来对待，不是风格指南。清单的特点是每一条都是用事故换来的，没有一条是为了好看。

[SLIDE 5: principle] (4:55 - 6:25)

第二个新框架，叫 Working backwards from behavior。

普通做法是这样：我先把 Agent 搭起来，让它跑，然后看哪里不对再补。Addy 反着说：你应该先描述你要的行为，再去设计能交付这个行为的组件。

更狠的是后半句。他说，每一个 Harness 组件都必须能对应一个具体行为。如果你说不出某个组件存在的理由——它解决的是哪个具体行为问题——那这个组件就该被删掉。

我看完心里默默盘了一下我自己平时配的几个工具，凉了一半。我们很多人加工具不是因为需要，是因为"看到别人都加了"。这是 Addy 想纠正的。

他还顺手定了一个 Hook 设计的原则，我觉得特别值得记。Success is silent，failures are verbose。意思是类型检查通过的时候，Agent 听不到任何声音，安静地继续往下走；只有失败的时候，错误信息才被原样塞回它的下一轮上下文，逼它自己改。这是一个特别工程师的设计直觉，很多人写 hook 习惯成功也广播一句"完成"，那其实是污染上下文。

[SLIDE 6: principle] (6:25 - 7:50)

第三个框架更反直觉。

你的直觉一定是：模型变强，外面就要写得越来越少。Addy 说，不对。模型变强不让 Harness 消失，只让它往上挪一层。

他举的例子是，最近一两代模型升级，让那些缓解上下文焦虑的小机制变得没必要了。你以前要小心翼翼地压缩 token，现在窗口大了，那一类脚手架可以拆掉。

听上去 Harness 不就是变小了吗？没有。因为 floor 升高的同时，ceiling 也升高了。以前你不敢让 Agent 做的多 Agent 编排、自我 trace 修复、动态工具拼装——这些以前根本碰不到的任务，现在变成了你必须解决的新失败模式。

Addy 的判断是：Harness 的每一个组件，本质上都在编码一个"模型现在还做不了什么"的假设。模型变了，那个假设就要重写，但新的假设永远会出现。

这是个挺残酷的结论。意思是 Harness 工程不是一次性投入，它是一份要持续维护的资产。你不能写一次写完。

[SLIDE 7: image] (7:50 - 9:40)

这一段是技术圈外面的人不太会注意到的，我觉得是整篇里最有内部视角的部分。

Addy 透露了一件事：今天的模型在 post-training 阶段，就把特定的 Harness 拉进了训练循环。也就是说，模型不是先训练好，再被 Harness 调用——而是训练的时候，就已经在某种 Harness 里跑过了无数遍。

这意味着什么？意味着模型会对它在训练时见过的那些动作过拟合——文件操作、bash、子 Agent dispatch 这些被 Harness 设计者优先优化的动作，模型用起来会异常顺手。

反过来呢？如果你切换到一个训练时没见过的 Harness 模式——比如你自己发明了一套奇怪的子 Agent 协议，或者一种不常见的工具调用约定——模型的表现可能会突然下降，而你查不出原因。表面看是模型变笨了，实际上是它没在训练里见过你这套用法。

这就把"换 Harness"这件事的成本拉得很高。它不再是单纯的工程切换，它是在跟"模型训练时见过什么"博弈。

也意味着先把某种 Harness 范式做大的玩家，会在下一代模型上拿到天然的优势。这不是阴谋，这是训练流程的物理结果。Claude Code 之所以越用越顺手，跟模型本身的训练有多重视它，是绑在一起的。

[SLIDE 8: principle] (9:40 - 10:45)

第四个框架。

Addy 说，行业正在从"建在 LLM API 上"转向"建在 Harness API 上"。SDK 卖的不再是 completion——一个字一个字吐出来的那种 API——SDK 现在直接卖 runtime。

runtime 包括什么？包括 loop，包括工具，包括上下文管理，包括 Hook，包括沙箱。整套 Agent 骨架开箱即用。

他给这个范式取了个名字，叫 Harness-as-a-Service，简称 HaaS。

这话出自 Google Cloud AI 的 Director 之口，含义就有点深了。它隐含的预测是：未来你跟模型厂商签的合同，不会是按 token 算钱，而是按 runtime 实例算钱。模型在这个交易里，变成 runtime 的一个内部配件。

代价是什么？Addy 没明说，但我帮你说出来。HaaS 把"换 Harness 框架"变得跟"换数据库"一样痛苦。loop 生命周期、压缩策略、子 Agent 协议——这些一旦绑定，你的失败历史就沉淀在这套抽象里，再想搬家成本极高。

[SLIDE 9: quote] (10:45 - 11:55)

文章最后这句判断，我反复读了几遍。

Addy 说，今天市面上最强的几个 coding Agent，它们彼此之间，比它们用的模型还像。

这句话翻一下就是：表面看 Cursor、Codex、Claude Code 还在拼模型，但实际上它们的 Harness 模式已经在快速收敛到同一组承重脚手架。文件系统加 git、bash 加沙箱、AGENTS.md 加 Hook、子 Agent 加 trace——这些核心组件正在变成行业标配。

收敛到一定程度，模型差异在缩小，Harness 差异也在缩小。剩下什么是真正的差异？Addy 没明说，但顺着他的逻辑往下推——剩下的就是你这套 Harness 上沉淀的失败记录。一份只属于你这套代码库、你这个团队、你这种任务类型的，几年积累的疤痕。

这个东西不能抄，不能买，也没法外包。它是 Harness 工程时代真正的护城河。

[SLIDE 10: principle] (11:55 - 13:00)

回到开头那个画面。一个掌管 Gemini Agent 业务的 Director，跟全行业说模型不重要。

不是谦虚，是预告。

预告的事情有四件。第一件，Harness 工程会变成一种独立纪律，每一条规则都要绑定一次翻车，没有抄作业这回事。第二件，Harness 不会消失，只会随着模型变强不断往上挪，永远在搭新的脚手架。第三件，HaaS 会取代 LLM API，模型成为 runtime 里的一个零件，被卖给开发者的是整套运行环境。第四件，顶级 Agent 们会越来越像，模型也会越来越像，真正的差异沉淀在你的失败历史里。

模型是 Agent 的输入，不再是 Agent 的胜负手。胜负手是这份只属于你的失败记录。

[SLIDE 11: summary] (13:00 - 14:00)

如果你今天在用 Claude Code、Codex 或者 Cursor，回去打开一下你那份 AGENTS.md 或者 CLAUDE.md，从上到下扫一遍。问自己一个问题：每一条规则，我能不能想起来它是哪次具体翻车留下来的。

想不起来的，删掉。想得起来的，留下，并且把它编码进 Hook 或者 Linter，让它机械执行，不再靠模型自觉。这是 Addy 给的最小可执行动作，几分钟就能做完，但它的复利会一直累积下去。

剩下的事情，慢慢做，做几年。等下一代模型出来，再回过头来盘一次，看哪些规则可以删，哪些新失败模式需要加新规则。Harness 就是这样长出来的。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
