# 你能开 20 个 Agent，但只有一个你

[SLIDE 1: cover] (0:00 - 1:06)

你同时开着 20 个 Agent 在跑，dashboard 满满当当，感觉自己一个人在干一个小团队的活。但晚上关电脑你比谁都累，今天 merge 的代码你其实没看明白几个。

这条诊断不是别人下的，是 Google Cloud AI 的总监、Gemini Agents 负责人 Addy Osmani 在 Google I/O 现场说的。

他给这件事起了个名字，叫 Orchestration Tax，编排税。今天不聊"教你怎么开更多 Agent"——只聊为什么你越用越累，而且这笔账你已经在付了。

[SLIDE 2: principle] (1:06 - 2:39)

先说一个 Addy 在 panel 上抛出来的矛盾。

他说：我从来没觉得自己的工具这么强过，但我也从来没这么累过。

这两句听起来像是情绪发泄，其实是同一个原因。当时旁边坐着的 Richard Seroter 当场给这种状态命名——"You can't manage twenty agents successfully in your own brain."——你的脑子撑不住二十个 Agent 同时跑。

Addy 把这件事拆开了。他说这不是态度问题，不是你心态没调整好，也不是你纪律不够。这是一个架构问题。

什么意思？意思是你不是用错了工具，你是被错放在了系统里错的位置。这个错位有一个具体的代价，每天都在收，只是你看不见。这就是 Orchestration Tax。

[SLIDE 3: comparison_cards] (2:39 - 4:37)

Addy 指出一个大家平时不会停下来想的事实。

开一个 Agent 几乎不要钱。一个 keystroke，一句话 prompt，它就跑起来了。所以你很容易开到 5 个、10 个、20 个，反正成本看起来是零。

但关这个 Agent 的环——也就是 close the loop——一点都不便宜。

什么叫 close the loop？就是 Agent 跑完了把东西交回来，得有人判断它写得对不对、跟其他几个 Agent 改的地方有没有冲突、能不能 merge 进主分支。这件事没人能替你做。模型不能替你做，因为它没有你对整个架构的理解。另一个 Agent 也不能替你做，因为最后还是要有人拍板。

所以这里有一个非常不对称的结构。开口是零成本，收口是高成本，而收口的那个人只有一个——就是你。

Addy 说，当你开始把多 Agent 工作流当成一个并发系统来看，你会发现一件不太愉快的事。你不是系统的指挥官，你是系统里的一个组件。而且是那个最慢的、串行的组件。

[SLIDE 4: quote] (4:37 - 5:55)

讲到这里 Addy 用了一个特别精确的类比，我觉得这是全篇最值得停下来想的一段。

写过 Python 的人都熟悉一个东西叫 GIL，全局解释器锁。Python 允许你开任意多的线程，但同一时间只能有一个线程真的在执行 Python 代码，因为它必须先抢到那把锁。

Addy 说：你就是你所有 AI Agent 的那把 GIL。

Agent 之间可以并行存在，可以同时在 20 个 worktree 里改东西。但只要哪一个 Agent 的产出需要真正的架构理解、需要解决 merge 冲突、需要判断要不要 ship，这件事就必须排队，排到你这把锁前面。锁只有一把，你拿着。

[SLIDE 5: principle] (5:55 - 8:03)

你可能听过 Amdahl 定律，性能工程里的老结论。它说一个系统的加速比，是被它里面"无法并行的那一段"卡死的。串行部分占 20%，你就算上一万核也突破不了 5 倍加速。

在 Agent 开发里，那个无法并行的部分就是判断力。Addy 说得特别狠：开 8 个 Agent 不会让你的判断时间变快，它只会让排在你判断力前面的队伍变得更长。

这是个性能工程里反复被验证、但每次都让人惊讶的事实——优化非瓶颈环节不会提高系统的吞吐量。它只会在瓶颈前面堆出更高的待办堆。整个系统的真实产能，等于瓶颈那一步的产能。一字不差。

Orchestration Tax 就是这里来的。它是你的 Agent 写出来的代码，和你真的能 merge 进主分支的代码，二者之间的结构性差距。Addy 用一句话给它下了定义——It's what happens when you put a single-threaded resource in charge of a concurrent one. 当你让一个单线程资源去管一个并发系统，必然会出现这个差距。

[SLIDE 6: image] (8:03 - 10:30)

讲到这一步，那种"用 AI 反而更累"的感觉就有了一个明确解释。

Addy 说，那种累有一个非常具体的来源。它是一个串行处理器被拉到 100% 利用率、还不留任何 slack 的体感。

每次你去 check 一个你刚离开过的 Agent，你都在付一笔 context switch 的代价。你得清空当前脑子里装的东西，重新冷加载另一个上下文。CPU 做这件事是微秒级的，架构师还在拼命想办法避免它。你做这件事是分钟级的，而且你永远 reload 不到 100%。

所以 5 个 Agent 不是"1x 工作量做 5 遍"。Addy 算得很清楚——它等于 5 次冷加载，外加一个一直在你脑子后台跑的进程，那个进程的任务就是焦虑"我下一个该去看谁"。

这个时候光"再努力一点"是没用的。结构限制不会因为你努力就消失。这个税你不主动付，它就换一种方式让你付——付的方式是你的 code review 变浅了，是你开始接受 Agent 写的代码不是因为它对，而是因为你已经没有注意力去形成自己的判断了。Addy 给这种状态起了个名字叫 cognitive surrender，认知投降。

这是这篇文章里我觉得最扎心的一句——你要么主动付这个税，要么让它悄悄毁掉你对自己系统的理解。

[SLIDE 7: principle] (10:30 - 11:36)

讲到这里你可能会以为他要劝大家少用 Agent。不是。Addy 是 Google Cloud AI 总监，他不是反 AI 的视角。

他的观点是——既然你的注意力是这套并发系统里唯一不能复制的串行资源，那就把它当一个真实的稀缺资源来做架构。你不会随便设计一个分布式系统而不考虑瓶颈，那对自己的脑子也得有同样的尊重。

他给了几条他自己反复验证过的做法，我把它们串起来讲。它们看起来是 5 条独立建议，其实是同一个原则——把你的注意力当稀缺资源做架构——的不同应用面。

[SLIDE 8: checklist] (11:36 - 14:50)

第一件事，并发系统里有个概念叫 backpressure，反压。说的是 producer 必须减速来匹配 consumer，否则队列就无限增长。在你这套系统里，Agent 的数量是 producer，你能真正 review 的速度才是 consumer。大多数人对得上的并行 Agent 数，是低个位数。Addy 说一句很犀利的话——AI 工具会很乐意让你 spawn 20 个，但那只是个 UI feature，不是它在建议你这么做。

第二件事是把任务分两堆。一堆是隔离的、可以丢给云端 background Agent 跑的活——这种你只在终点把个关就行。另一堆是判断本身就是工作的活，比如怪 bug、架构设计。最大的错误是想把第二堆并行化。并行做多个复杂判断不会让你的产出翻倍，它只会让你那把锁被反复抢来抢去，最后每件事都做得更差。

第三件事是 batch review，攒一批再看。Context switch 是单价很贵的开销，看一个走开再回来冷启动那种代价远高于一次性看 4 个。给 Agent 长一点的绳子，让活攒一攒，一次性处理。

第四件事，把你的锁只花在真正需要判断的地方。能让 Agent 自己写一个通过的测试、生成一张截图自证的，就让它自证。无聊的那 80% 它自己搞定，你的注意力只花在真正需要人类判断的那 20%。

最后一条 Addy 说得几乎像在劝慰——保护你的串行时间。瓶颈需要你最好的几个小时，不是夹在两次 Agent check-in 之间的零碎分钟。有时候最高杠杆的动作，是关掉那个开了一堆 Agent 的笔记本，把那把锁攥在手里，只对着一个问题狠狠想。

[SLIDE 9: quote] (14:50 - 15:19)

他说了一句话我特别想转述给你：orchestrating is not the real work. It's the overhead around the work. 编排不是真正的工作，它只是工作周围的开销。

[SLIDE 10: image] (15:19 - 17:15)

这篇文章里有一段我读完后愣了一下。

Addy 说这个失败模式最可怕的地方是——你从内部完全感觉不到它发生了。

20 个 Agent 在跑、dashboard 满满当当、什么都在动，这给你一种产能爆棚的感觉。但这种感觉是和"今天真的 ship 了好代码进主分支"完全脱钩的两件事。你可以最大化地忙，同时几乎什么都没真正做出来。从内部看，这两种状态长得一模一样。

同 panel 的 Ciera Jaspan 还提了一个补刀——Margaret-Anne Storey 关于 cognitive debt 的研究。讨论里 Addy 总结说：Orchestration Tax 不付，你是在同时累积技术债和认知债。

你 merge 进去的代码自己其实没看懂，你对整个 codebase 的心智模型在悄悄过期。dashboard 上今天看不见这件事。它会在某天 production 炸了你打开系统、发现自己已经认不出自己写的东西的时候，一次性结账。

[SLIDE 11: summary] (17:15 - 19:29)

把整篇拉回到一句话。

Addy 真正想说的是——开 Agent 不是技能。能开 20 个 Agent 不算什么，谁都能开。真正的技能是给那个不能被复制、不能被并行的串行资源——也就是你自己——做架构设计。

你过去做分布式系统的时候是怎么想瓶颈的，对自己的脑子也得那么想。它有一个具体的、低的、可测的吞吐量。系统要么尊重这个数字，要么它就偷偷给你降低标准——表现就是你的 review 越来越浅，你越来越愿意接受不太对的代码。这两种结果只能选一个。

我读完这篇最大的感受是——这是 Google Cloud AI 总监自己跳出来给整个"多 Agent 万岁"的叙事踩了一脚刹车。它不是反 AI，它是给"什么时候并发、什么时候单线程"画一条分界线。

并发的部分留给 Agent，串行的部分留给你。这条界画错的时候，付的不是显性账单，是你对自己代码库的理解。

下次你又想开第 11 个、第 20 个 Agent 的时候，停一秒问自己——这件事 close the loop 谁来做？如果答案还是你，你已经在付这笔税了。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
