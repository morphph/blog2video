# 你能跑 20 个 Agent，但你只有一个大脑

这里是精读AI。今天读的这篇博客来自 Google 那位常年写性能工程的人——他刚在 Google I/O 的 panel 上被同台的同事现场点名，命名了一种他自己天天在付的"税"。我把这件事完整想穿了，挑出真正会改变你工作流的那一刀。

## Hook

大家都在比谁能开更多 Agent。我看下来，这条赛道根本不在 Agent 数量上，在你手里那把唯一的锁上。

你以为你在指挥它们。其实它们都在排队等你。

今天我要论证一件事——感觉很忙和在产出，已经是两件完全不同的事了。仪表盘满屏在动，跟 main 分支真的进了代码，从你的体感里分不出来。这才是问题。

## 我的论点

我看下来这件事的真正本质是这样的——你不是 Agent 的指挥官，你是它们的 GIL。

什么意思？Python 里有个东西叫 Global Interpreter Lock，全局解释器锁。你可以开任意多个线程，但同一时刻只能有一个真的在跑——它们必须排队抢这把锁。

你和你那一票 AI Agent 之间，是一模一样的关系。它们可以同时启动，没问题。但只要任何一个走到需要"真正理解架构"或者"解决 merge 冲突"那一步，它就得拿锁。

锁只有一把。在你手上。永远只有一把。

这件事最锋利的地方在哪？它不是纪律问题。不是你不够拼。是结构。再多自律，撬不动一个并发系统里只有一个串行处理器这个事实。我以前也以为多开几个 Agent 就是产能翻倍，直到我开始看自己一天结束时 main 分支接进去的东西——根本对不上。

## 启动便宜，收尾不便宜——这条不对称大多数人没在定价

并发系统里最贵的，从来不是产生任务的那一端。是消化任务的那一端。

启动一个 Agent，一个键盘快捷键，或者一句 prompt——零成本。但收尾呢？得有人验证它写的对不对，得有人去看它和另外几个 Agent 改的代码会不会冲突，得有人决定要不要合进去。

这个"有人"，全是你。而你只有一个。

我看下来这个不对称是 orchestration tax 的物理基础——producer 端零边际成本，consumer 端不可并行。任何一个学过并发的人都知道这种系统的归宿——consumer 前面那条队伍会无限增长，直到整个 pipeline 烂掉。

你现在做的，就是亲手在搭这种系统。区别只是 producer 是 Agent，consumer 是你的判断。

## Amdahl's Law 这一刀，把"多开几个 Agent"的幻觉直接斩断

要把这件事讲清楚，得请 Amdahl's Law 出场——性能工程里最老、最不浪漫的那条定律。

它说什么？你做并行化能拿到的加速比，被你那段没法并行的串行工作的比例死死卡住。pipeline 里有一大块串行段，你往上堆多少核都顶不破那个天花板。

把它套到 Agent 工作流——串行段是什么？是判断。

我读到这里的时候停了一下。这一刀比"Agent 编排很难"那种泛话直接太多了。它说的是——开 8 个 Agent，不会让你判断更快。判断的速度不变。只会让喂给判断的那条队伍变得更深。

这是性能工程里一条让人反复意外的老事实——优化非瓶颈段，不会让吞吐变大。只会让瓶颈前面那堆未完成的活儿堆得更高。

多 Agent 这件事，优化的就是从来不是约束的那一段。整个系统的吞吐，等于 review 那一步的吞吐。一字不差。

我现在的判断是——orchestration tax 这个词起得已经够好了，但底层公式其实更冷：你的产能 = 你能合进去的代码量 = review 吞吐。前面再多 Agent，都是噪声。

## 累不是因为活多，是因为单线程在百分之百占用率下跑

这一段我读完最有体感。它把一种很多人在感受但说不清的累，归到了一个具体物理原因。

不是活多。是一颗串行处理器以百分之百占用率、零 slack 在跑的那种体感。

每次你切到一个你刚离开过的 Agent，你都要付一次上下文切换的钱。清空脑子，从冷态重新加载一个完全不一样的上下文。CPU 干这件事是微秒级，架构师都还在使劲躲开它。你呢？分钟级。而且永远没法把上下文完美加载回来。

5 个 Agent，不是 1 倍工作量乘 5。是 5 次冷加载，加上一个在后台一直跑的进程——这个进程在持续焦虑"我现在该看哪一个"。

最扎我的是接下来这一段——结构性的限制，靠拼修不了。这个税你怎么都要付。

要么你主动付——少开 Agent、批量 review、把锁花在判断上。要么它就悄悄地、看不见地从你身上扣——以 cognitive surrender 的形式扣。认知投降。你开始无脑接受 Agent 写的代码，因为形成你自己的判断这件事本身要花注意力，而你账上已经没了。

我看下来最关键的一刀是这个——orchestration tax 的失败模式不是"做不完"，是"你悄悄接受了你不该接受的代码，而且自己不知道"。

## 反方质疑——那如果我就是能管 10 个呢

我得替你抛出这场辩论里最有力的反驳。

你可能会说——别拿平均值压我。我个人状态好的时候、活儿之间独立性高的时候，我管 10 个 Agent 是没问题的。你这套是把所有人都拉到那个最弱的水平。

这个质疑有它的道理。我承认——确实有些类型的活儿，并行 10 个 Agent 是合理的。比如批量重命名变量、批量修一类已知模式的小 bug、批量加文档。这些任务的判断含量极低，几乎是机器自己就能验证完。

但请注意——这恰恰说明这套框架是对的，不是错的。

那 10 个 Agent 之所以能并行，不是因为你的 review 吞吐变高了。是因为这些活儿压根不需要拿锁。machine 自证 80% 那部分，本来就该让 machine 自己 prove——写测试、出 screenshot。它们都没排到锁那一步。

真正的考验是判断密集任务。怪 bug、架构选择、跨模块重构。你试试在这种活儿上并行 10 个 Agent——锁会被疯狂抢，每一个都被打断得乱七八糟，每一个出来的东西都更差。

所以我的修正是——并行度不是看你自我感觉，是看任务结构。任务越靠"机器能自证"那一端，并行越多没事。任务越靠"判断本身就是工作"那一端，并行就是在自残。

## 我的 take

有一句话我非常同意——architecture 是现在最 urgent 的技能。

我想往前再补一刀。

你不只是在为系统做架构。你是这个系统里的一个组件。一个串行吞吐已知的、低的、不可克隆的组件。这个系统要么尊重这个数字，要么就绕过它——通过悄悄降低你的标准。

模型在变快，Agent 数量在变多。有一样东西，不会被克隆，不会被并行——是你这一个人，握着这把唯一的锁。

所以真正的技能不是"我能开几个 Agent"。真正的技能是——围绕那个唯一的串行资源去设计你的工作系统。Agent 数量是 producer，你的 review 吞吐是 consumer。两者必须用 backpressure 绑死，否则前面那条队伍会一直堆，直到 dashboard 上一切看起来都在动，但 main 分支什么都没接住。

记住这一句——你以为你在指挥 Agent，其实 Agent 们都在排队等你这把唯一的锁。

## Closing

今晚回去你能做的最小动作——看一眼此刻同时在跑的 Agent 数量。砍到你真正能认真 review 完的那个数字。多半是 2 到 3 个。

剩下的让它们排队。最高 leverage 的那个动作有时候反而是——关掉笔记本，安安静静想一个问题，把锁握满一个小时。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
