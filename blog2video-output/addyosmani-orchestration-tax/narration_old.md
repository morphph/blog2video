# 你能跑 20 个 Agent，但你只有一个大脑

## Hook

你开了 20 个 Agent，仪表盘满屏在动，感觉自己产能炸裂。但等你回头看 main 分支——这一天合进去的代码，根本对不上你忙的程度。

这件事 Google 的 Addy Osmani 上周在 I/O 的 panel 上被现场点了名。同台的 Richard Seroter 给它起了个名字，叫 orchestration tax。今天不聊怎么用 Agent——只聊一件事：为什么你越开越累，产出却越来越虚。

## 这件事的本质，不是纪律问题，是架构问题

Addy 在 panel 上被问到——开发者今天应该改掉的一件事是什么？他说，他这几个月反复在想的就是这一句话：感觉很忙，跟在产出，是两件事。你可以跑 20 个 Agent，感觉完全在忙。但那不是 20 个 Agent 量的产出。

Richard 接过去说，这就是 orchestration tax。你没法在自己脑子里成功管 20 个 Agent。

Addy 把这件事拆得很狠。他说，这不是一个纪律问题。这是一个架构问题。你以为你不够自律、不够专注，所以管不过来。错。是你这个角色，在系统里本身就是个瓶颈，再多自律也撬不动这个事实。

他在 panel 上随口说的一句话，他自己后来一直在想——开多个 Agent，并不意味着有多个你。

## 启动一个 Agent 很便宜，收尾一个 Agent 一点都不便宜

文中有一个不对称，作者认为大多数人没意识到。

启动一个 Agent，几乎是零成本——一个键盘快捷键，或者一句 prompt。但收尾一个 Agent，成本一点都不低。它跑完之后，得有人看看它写的东西对不对，得有人去对一下它和其他几个 Agent 改的代码会不会冲突。这个人是你。而你只有一个。

Addy 上个月还写过一篇前置博客，叫 "Your parallel Agent limit"，讲的是那种隐隐的焦虑——你不知道你那几个并行的线程里，是不是有一个在悄悄出问题。这一篇是这个焦虑底下的实际形状。

他说，当你开始把 Agent 开发当成一个并发系统看的时候，你才会意识到——你这个人，其实是这个系统里的一个组件。是那个慢的、串行的组件。

## 你就是你 AI Agent 的 GIL

如果你写过并发代码，作者说你其实早就有这个直觉，只是你一直把它套在了系统的错的那一段上。

Python 里有个东西叫 GIL，Global Interpreter Lock，全局解释器锁。你可以开任意多个线程，但同一时刻只能有一个真的在执行 Python 字节码——因为它们必须先拿到这把锁。

Addy 说，你就是你那帮 AI Agent 的 GIL。它们可以同时跑，没问题。但当它们里头任何一个，需要真正理解你这套架构、或者要解决一个 merge 冲突的时候——这个活儿，必须先拿到锁。

锁只有一把。在你手上。

这个类比有意思的地方在于，它把"管 Agent"这件事直接还原成了一个并发编程问题。你管 20 个线程，你不会说你管得过来——你会去算每个线程的 lock contention。但管 20 个 Agent，大家就以为是意志力问题。错。

## Amdahl's Law 给你算清楚了这个账

作者接着把 Amdahl's Law 搬出来。这是性能工程里的老法则——你做并行化，能拿到的加速比，被你那段没法并行的串行工作的比例死死卡住。如果你的 pipeline 里有一大块没法并行，那不管你往上堆多少核，最后还是会顶到一个硬天花板。

在 Agent 开发里，那段串行工作，就是判断。

作者说得很狠——你开 8 个 Agent，并不会让你判断更快。它只会让喂给你判断的那个队伍变得更深。

这里他拎出了一个老的性能工程事实，他说一直让人意外——优化非瓶颈的那一段，不会让吞吐变大。你只是让瓶颈前面那堆未完成的活儿堆得更高。

加 Agent，优化的是从来就不是约束的那一段。约束是 review 那一步。你整个系统的吞吐，就等于 review 那一步的吞吐。这就是 orchestration tax 的真正定义——你能产生的代码，跟你能合进去的代码，这中间的那条结构性鸿沟。

你把一个单线程资源，放进了一个并发系统里去当总开关。

## 不是不够拼，是结构上撞墙

作者说他在 panel 上还讲过一句——他从来没觉得自己工具用得这么爽过，但他也从来没这么累过。两边都是真的，而且是同一个原因。

这种累，他说有一个非常具体的来源。它就是一颗串行处理器以百分之百占用率、零 slack 在跑的体感。

每次你去看一个你刚离开过的 Agent，你都要付一次上下文切换的钱。你得清空脑子，从冷态重新加载一个完全不一样的上下文。CPU 干这件事是微秒级的，架构师们还在使劲想办法躲开它。你呢？你是分钟级的。而且你永远没法把上下文完美加载回来。

5 个 Agent，不是 1 倍工作量乘 5。它是 5 次冷加载，加上一个一直在后台跑的进程——这个进程在持续焦虑"我现在应该去看哪一个"。

然后作者说出了那句最扎心的判断。结构性的限制，靠拼不能修。这个税你怎么都要付。

如果你硬要靠拼撑——这个限制会以两种方式显形。一种是你 code review 变浅，扫一眼就放过。另一种他叫 cognitive surrender，认知投降——你开始无脑接受 Agent 写的代码，因为形成你自己的判断这件事本身要花注意力，而你账上已经没了。

要么你主动地、有意识地付这笔税。要么它就悄悄地、不知不觉地吃掉你对自己系统的理解。

## 把你的注意力，当成系统资源去架构

所以怎么办？作者说，你得把你的注意力，当成它本来该是的那种稀缺串行资源去对待。

你设计一个分布式系统的时候，你不会不认真想瓶颈。给你脑子同样的尊重。

他给了几条对他自己有用的做法。

第一条，他叫 scale fleet to review rate, not the UI。一个好的并发系统，会用 backpressure 来防止队列无限膨胀——producer 要降速去匹配 consumer。你的 Agent 数量是 producer，你的 review 吞吐是 consumer。所以正确的并行 Agent 数量，是你能真正认真 review 完的那个数量。对绝大多数人来说，这个数字是个位数低位。AI 工具会很高兴让你开 20 个，但那只是 UI 的事，不是物理事实。

第二条，Sort the work。给任务分堆。作者说他自己有两堆——一堆是 isolated 的活，可以丢给云上的后台 Agent 跑，跑完最后我把一道关就行。另一堆是判断本身就是工作的复杂任务，比如怪 bug、架构设计。他说大多数人的错，是去并行第二堆。同时干多个复杂任务，不是把产出乘以 N，是让那把锁被疯狂抢——所有任务都做得更烂。

第三条，Batch your reviews。批量评审。上下文切换很贵，每切一次都要钱。在一次坐下里同时 review 4 个 Agent，比看一个、走开做点别的事、再冷着回来看下一个，便宜得多。给 Agent 长一点的绳子。让活堆一会儿，再批量处理。

第四条，Only spend the lock on judgement。只把锁花在判断上。别让你的脑子做机器自己能验证的事——让 Agent 自己写一个能 pass 的测试，让它自己生成一张 screenshot。它能自己证明无聊的那百分之八十。你的注意力只花在真正需要人来判断的那百分之二十上。

第五条，Protect your serial time。保护你的串行时间。瓶颈需要的是你最好的几个小时，不是 Agent 一轮一轮 check-in 之间的零碎几分钟。有时候最高 leverage 的动作，反而是停下编排——合上那台跑满 Agent 的笔记本，就好好想一个问题，把锁一直握在手里。编排不是真正的活儿。它是真正的活儿的额外开销。

panel 上 Aja 还点了一句——architecture 是现在最 urgent 的技能。知道什么该塞进一个 Agent，什么对一个 Agent 来说太大。作者补了一句——你自己也是这个系统里的一个组件。你的注意力有一个已知的、低的串行吞吐。这个系统要么尊重这个数字，要么就绕过它——通过悄悄降低你的标准。

## Busy 和 Productive 是两件事

这件事真正可怕的地方，作者说，是失败模式对你自己是隐形的。

20 个 Agent 在跑，给你一种巨大的产能错觉。仪表盘满了，一切都在动。但这种感觉，和你真的合好代码进 main 这件事，已经完全解耦了。你可以最大化地忙，几乎什么都没产出——从里面体感上，完全分不出来。

panel 上 Ciera 提到了 Margaret-Anne Storey 关于债的研究。他们讨论了技术债和认知债。orchestration tax 你不付，就是同时在攒这两种债。你合了你自己没认真读的代码进去。你脑子里那套 codebase 的心智模型一点一点完全过期了。dashboard 上看不见这一切。等它显形，是 production 出事的那天——你看着这个系统，发现你已经完全不知道它是怎么工作的了。

所以真正的 takeaway 在这里。开 Agent 不是技能。谁都能开 20 个。真正的技能是——围绕那个没法被克隆、没法被并行的串行资源，设计你这套系统。这个资源是你的注意力。像架构其他任何你在生产环境里依赖的东西一样去架构它。

## Synthesis

让我把这件事压成一句你能记住的话。

你以为你在指挥 Agent，其实 Agent 们都在排队等你这把唯一的锁。

仪表盘上跑的 Agent 数量，不是你的产能指标。你的 review 吞吐才是。盲目把 producer 数量往上推，只是在把 consumer 前面那条队伍堆得越来越高——所有人都在等你判断，没有人在被处理。

模型在变快，Agent 数量在变多。但有一样东西不会被克隆，不会被并行——是你这一个人，握着这把唯一的锁。

## Closing

今晚回去你能做的最小动作——看一眼你现在同时在跑的 Agent 数量，砍到你真正能认真 review 完的那个数字。多半是 2 到 3 个。

剩下的，让它们排队。或者干脆关掉笔记本，安静想一个问题，把锁握满一个小时。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
