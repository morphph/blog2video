# Insight Memo: Claude Code Agent View Docs（操作层）

## title_zh
Claude Code 把 session 当进程管，不当 tab

## one_sentence_thesis
Agent view 表面是一张"快捷键 + 状态表"，但真正的设计赌注藏在两处：颜色和图标形状是**两条独立的状态维度**，以及 supervisor 是一个常驻进程而非一个 UI 模式——session 因此变成了系统里的对象，而不是终端里的标签页。

## why_this_video_exists
博客那条视频讲的是"并发 Agent 的瓶颈是注意力调度、inbox 不是 dashboard"——是高维度判断。这条视频的价值是：文档里有一组**只有翻 docs 才看得到的具体设计选择**——状态机的两层 indicator、Haiku 每 15 秒刷一次行总结、supervisor 把进程从终端剥离、filter 框直接复用 dispatch input——这些是博客没讲、但暴露了团队真实工程取舍的细节。看完观众应该意识到：这不是一个 TUI，是一个**会话管理系统**。

## judgment_lines

- "颜色管语义，形状管生死——agent view 是双层 indicator，不是一层颜色码" — 来源：docs 明确把 state（working/needs-input/idle/completed/failed/stopped）的颜色编码和图标形状（`✻` 进程活着 / `∙` 进程已退出但状态可恢复 / `✢` `/loop` 在 sleep）分成两张独立的表
- "supervisor 是一个架构决定，不是 UX 装饰：session 因此脱离终端而存在" — 来源：docs 写明 supervisor 是 per-user 常驻进程，会监视磁盘上的 Claude Code 二进制并在 auto-update 后自动 restart into the new version；session 不挂任何终端也继续跑
- "dispatch input 复用成 filter input，是用一行预算换两个功能" — 来源：同一个底部输入框，输入 prompt 是派单，输入 `a:<name>` / `s:blocked` / `#<PR>` 是筛选——这条交互压缩节省的不是按键，是屏幕空间
- "每个 prompt 都是一个新 session，回车不是 follow-up——这是把 session 当对象、不当对话窗的关键证据" — 来源：docs 明确说"Every prompt you enter here starts its own new session"，且每个 session 独立消耗订阅 quota
- "行总结由 Haiku 跑、每 15 秒一刷——团队愿意为'扫一眼就懂'付一个独立的小模型调用账单" — 来源：docs 写明"generated by a Haiku-class model", "refreshes at most once every 15 seconds, plus once when each turn ends", "billed and handled under the same data usage terms as the session itself"

## evidence_map

- [具体事实] 状态颜色维度：Working=animated / Needs input=yellow / Idle=dimmed / Completed=green / Failed=red / Stopped=grey；Stopped 专指被 `Ctrl+X` 或 `claude stop` 停掉的
- [具体事实] 图标形状维度（与颜色正交）：`✻`/`✽` 进程活着可立即回复；`∙` 进程已退出但仍可 peek/reply/attach，Claude 会从中断点续起；`✢` 是 `/loop` session 在两次迭代之间 sleep，行内显示 run count 和 countdown
- [具体数字] 行总结刷新节流：最多每 15 秒一次，外加每个 turn 结束触发一次
- [具体事实] PR 状态点 4 色：黄=等 checks/review 或 checks 失败；绿=checks 过且没有 review 阻塞；紫=已 merge；灰=draft 或 closed。一个 session 开多个 PR 时显示数字，颜色取最需要注意的那一个
- [具体快捷键] Peek 面板：`Space` 打开 / 多选问题时按数字键选 / `Tab` 填入建议回复供编辑 / `!` 前缀走 Bash / `↑↓` 在相邻 session 间 peek / `→` attach
- [具体快捷键] 组织视图：`Ctrl+T` pin / `Ctrl+S` 按目录分组 / `Ctrl+R` rename / `Ctrl+G` 在 `$EDITOR` 里编辑 prompt / `Shift+↑↓` reorder / `Ctrl+X` 停 + 两秒内再按一次 = 删除（含 worktree 清理）
- [具体语法] Filter 三种：`a:<name>` 按 agent / `s:<state>`（含 `s:blocked`）按状态 / `#<number>` 或 PR URL 按 PR
- [具体语法] Dispatch 修饰：首词匹配 subagent 名 = 当主 agent 跑；`@<agent>` 显式提及；`@<repo>` 跑在该 repo；`/<skill>` 触发 skill；`Shift+Enter` 派单并立刻 attach
- [具体命令] Shell 入口：`claude --bg "<prompt>"` 直接派后台；`claude --agent code-reviewer --bg "..."` 指定 subagent；session 内 `/background` 或 `/bg` 把当前会话转后台
- [具体命令] Shell 管理：`claude agents` / `claude attach <id>` / `claude logs <id>` / `claude stop <id>` / `claude respawn <id>` / `claude respawn --all`（机器睡眠/关机后批量恢复）/ `claude rm <id>`
- [具体路径] 状态持久化在 `~/.claude/jobs/<id>/state.json`；supervisor 日志 `~/.claude/daemon.log`；运行列表 `~/.claude/daemon/roster.json`
- [架构事实] supervisor 是 per-user 常驻进程，watch 磁盘上的 binary，auto-update 后 restart into the new version；background session 是 detached processes，能跨 supervisor 重启存活；空闲约 1 小时后 supervisor 杀掉 session 进程，下次 attach/peek/reply 时从磁盘 state 重启
- [架构事实] file edit 隔离：默认进 `.claude/worktrees/` 下的 git worktree 写；不在 git repo 里则不隔离，并发派单要避开
- [边界事实] subagents 和 teammates 不单列行；交互 session 不出现在 agent view 直到被 background；session 在所有项目里跨目录可见，不取决于你从哪开 agent view
- [Quota 事实] 每个 background session 独立计入订阅 quota；`bypassPermissions` / `auto` 模式必须先在交互 session 里接受过一次才允许通过 `--permission-mode` 传入 `--bg`

## non_obvious_points

- **状态颜色和图标形状是两条独立维度** — 为什么这不显而易见：表面看像 6 个状态 + 3 个图标共 18 种组合，但其实是"语义状态（出了什么事）"× "进程是否活着（能否立刻回话）"的笛卡尔积。一个 Completed 的 session 既可以是 `✻`（进程还在）也可以是 `∙`（进程被回收了，但状态可恢复）——观众如果不看 docs 永远只会以为颜色变化就是全部。
- **supervisor 自动 watch 二进制并 restart into the new version** — 为什么这不显而易见：这意味着 background session 必须设计成可以被无感重启的——状态必须能从 `~/.claude/jobs/<id>/state.json` 完整重建。它不是一个"长跑进程"，而是"可随时被 cold-start 的对象"。auto-update 这条线把 supervisor 和持久化绑成了一个隐含合约。
- **dispatch input 同时是 filter 框，是一种"上下文相关解释"的设计** — 为什么这不显而易见：输入 `a:foo` 不是派一个叫 `a:foo` 的 session，是触发 filter 模式。这种"一个输入区根据语法 prefix 切换语义"的做法跨过了"再开一行搜索框"的诱惑，但代价是要求用户记住几个 prefix 规则。
- **每个 prompt 都是新 session、background session 之间不能 follow-up** — 为什么这不显而易见：观众的本能模型是"agent view 是个聊天室，回车继续对话"。文档要专门补一句"Typing another prompt and pressing Enter launches a second session alongside the first rather than sending a follow-up to it"——说明这是反直觉的，团队也意识到了。

## tradeoffs_and_limits

- **Haiku 行总结是一笔独立账单** — 具体表现：每 15 秒一次（外加每个 turn 结束）的 Haiku-class 调用走的是你自己的 provider，按 data usage terms 走和 session 同样的账。开 10 个并发 session 等于 10 路独立计费的 Haiku 在背景跑。
- **每个 background session 独立吃订阅 quota** — 具体表现：docs 在 quick start 第二步就警告"Each session uses your subscription quota independently, so see Limitations before dispatching many at once"。并发派单的真实瓶颈是订阅配额，不是机器。
- **不能 follow-up 是硬约束** — 具体表现：想给已有 session 加 instruction 必须 peek/attach 进去，不能在底部输入框里"再聊一句"。底部输入框只做两件事：派新 session 或筛选。
- **supervisor 复杂度的代价是排查路径变长** — 具体表现：troubleshooting 一节就出现了"agent view 列出 subagents 而不打开"、"Bedrock/Vertex/Foundry 环境上历史版本不支持"等环境性失败；状态散在 `~/.claude/daemon.log` / `daemon/roster.json` / `jobs/<id>/state.json` 三处，不是一个文件能看全。
- **worktree 删除即数据丢失** — 具体表现：`Ctrl+X` 两次（或在 group header 上按）会清掉 worktree 包括未提交改动。docs 反复强调 push/commit before delete——这是 worktree 隔离的副作用，便利和危险绑在同一个键。
- **机器睡眠/关机会停掉所有 session** — 具体表现：需要 `claude respawn --all` 来批量恢复。supervisor 不能跨机器重启幸存，它只能跨 auto-update 幸存。

## what_to_leave_out

**不该进入的素材：**
- 完整快捷键表——观众不会跟着 22 个 binding 学，列 4-5 个就够；不要把整段做成 cheatsheet 的复读
- Troubleshooting 节（Bedrock/Vertex/Foundry 环境差异、`disableAgentView` 设置）——和核心 thesis 无关，留给读 docs 的人
- 模型选择细节（`/model` / `--model` / subagent frontmatter `model` 字段三种路径）——是配置项不是设计判断
- 文件路径配置（`CLAUDE_CONFIG_DIR` 改变 supervisor 实例隔离）——太细节
- worktree 完整规则（不在 git 仓内时如何 fallback、`isolation: worktree` frontmatter）——和"看一眼 docs 学到什么非显然设计"无关

**应避免的叙事方向：**
- 不要重复博客视频的"inbox 不是 dashboard / 并发瓶颈是注意力调度 / --bg 暗示默认形态翻转"——那条已经讲过
- 不要写成"agent view 使用教程"——观众不是来学操作的，是来看团队做了哪些非显然决定
- 不要把整片框架建立在"快捷键好多"这种数量感上——这是表层观察
- 不要把 supervisor 讲成"daemon 而已"——重点是它和 auto-update、state.json 持久化绑成了一个隐含合约
- 不要把状态机讲成"6 种状态"——必须讲清是"6 颜色 × 3 形状"两条独立维度

## signature_line
Agent view 不是给你看 session 在干嘛，是把 session 从终端里抽出来变成可被管理的对象——颜色告诉你它在想什么，形状告诉你它还活不活着。
