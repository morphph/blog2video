# 并发 Agent 的终点不是 tmux

## Hook

Anthropic 刚给 Claude Code 加了个看起来很普通的小功能，叫 agent view。一句话说，就是把你所有正在跑的 Claude session 摊在一个列表里。今天不聊它有几个快捷键，也不教你怎么打开——只聊一件事：为什么这个看起来无聊的小更新，其实是 Agent 工作流的一个拐点。

## tmux 的终结

最有意思的是 Anthropic 自己的措辞。他们在发布稿第二段直接承认了一件事：在这个功能之前，用户要并行跑多个 Agent，靠的是什么？多个 terminal tab，一个 tmux 网格，再加上自己脑子里那本随时可能漏的待办账本。

注意，这是官方文案。等于 Anthropic 自己在说，tmux 是临时方案，是用户硬撑出来的脚手架。这件事其实挺关键的。一个公司愿意在产品发布稿里写"我们以前让你受了苦"，意味着他们已经把这种用法当成默认假设，而不是少数极客的边缘玩法。

## 瓶颈不是模型，是你的注意力

我读完最大的感受是这个：并发 Agent 的真正瓶颈，从来都不是模型能力，是人类的注意力调度。

模型能不能同时跑十个 session？早就能了。难的是你怎么知道哪个在等你回话，哪个还在干活，哪个已经交活了。这是个调度问题，不是算力问题。以前没人正面解决，是因为大家默认"一个用户管一个 Agent"。agent view 的潜台词是：N 等于 1 的时代已经过去了，N 大于 1 已经成为常态。

## inbox 不是 dashboard

agent view 最值得讲的设计，是它的三个状态：waiting，working，done。waiting 是在等你输入，working 是还在跑，done 是干完了。

这三个状态的顺序就是优先级。最显眼的位置留给 waiting——谁在等我。这不是监控面板的思路，这是邮件 inbox 的思路。

差别在哪？dashboard 关心的是"系统现在的全貌"，inbox 关心的是"谁在卡我"。如果你把它做成 dashboard，最显眼的会是已经完成的产物。但 Anthropic 选了反过来——把"卡点"置顶，因为卡点会阻塞其他所有 Agent 推进。这是个有立场的产品判断。

## --bg 这个 flag 比你想的重要

发布稿里塞了一个 flag，`claude --bg`，意思是直接以背景模式启动一个新 session，跳过前台。

听起来只是个开关，但它暗示了一件事：默认形态正在翻转。以前我们的直觉是"前台跑一个，偶尔 detach 到后台"，前台是默认；这个 flag 在说，未来的默认可能反过来——"所有 session 默认在背景跑，前台只是你恰好选中的那一个"。

你不是在操作一个 Agent，你是在调度一池 Agent。前台只是这池子里你此刻看的那个窗口。

## 什么时候这个功能没意义

诚实讲，这个产品不是普惠的。它的价值曲线是非线性的。

如果你一次只开一个 Claude Code，agent view 反而是负收益——多了一层导航，没解决任何问题。session 数从 1 涨到 3，收益一般；从 3 涨到 10，才指数级上升。

还有一个隐性代价。以前 tmux 帮你"忘掉"那些后台 session——它们在别的 tab 里，你看不见就不焦虑。现在所有东西都摊在一个 inbox 里，你必须主动决定：哪个值得派到背景跑，哪个必须前台盯着。这是新的认知负担，agent view 没替你回答。

## 我的判断

所以我的判断是这样的。这个功能不是一次 UI 改进，是 Anthropic 在产品上承认了一件事：一个人管多个 Agent 已经不是高阶玩法，是默认场景。

以前 Agent 在每个 terminal tab 里各跑各的，靠你脑子串起来。现在 Anthropic 把那个"脑子里的账本"做成了产品。并发的边界，不再是模型能跑几个，而是你愿不愿意让所有 session 都进同一个 inbox。

下一个问题就来了：当 inbox 里堆满二十个 Agent 的时候，谁来帮你决定先回哪一个？那大概是下一代 Claude Code 要回答的事。
