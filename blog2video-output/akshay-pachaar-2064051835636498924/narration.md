# 你的 AI Agent，应该自己修自己

## Hook

今天聊一个正在被严重低估的概念——self-improving agent，会自我进化、能自己修自己的 AI Agent。

什么意思？想象一下：你的 Agent 在生产环境里出了故障，可这一次，你没有熬夜翻日志，没有手写补丁，也没有改完一处又提心吊胆别的地方会崩——它自己把自己修好了。修完之后，它还比出问题之前更难被打破。

听起来是不是有点像 PPT 上的吹牛？可这恰恰是 Akshay Pachaar 一篇深度文的核心判断，背后站着 Comet ML 和开源项目 Opik 的实战主张：一个真正成熟的 AI Agent，本来就应该会自己修自己。

那它到底怎么成立？我们不聊怎么搭监控，只拆一件最关键的事——怎么让你的 Agent，从「每次出错都要你来救」，变成「每次出错都让它自己变得更强」。

## trace 给你的，和没给你的

先回到今天的现实。你的 Agent 在生产环境里挂了，你打开监控，一条干干净净的 trace 摆在面前。每一次模型调用、每一个触发的工具、每一步花了多久、烧了多少 token，全都清清楚楚。

但你真正想知道的三件事，它一个都没回答。它为什么坏了？哪一处改动能修好它？还有最关键的——怎么保证下周不会再坏一次？

这些它都不管。于是你开始干那件最熟悉的活：一个 span 一个 span 往下翻，慢慢拼出一个假设，手写一个补丁，然后祈祷别把原本好好的地方改坏。

补丁打完，你松一口气。可过几周，一个新模型上线，带来一整批新的失败模式。于是你把刚才那套手工流程，从头到尾，再跑一遍。

## 瓶颈不在监控，在虚线右边

这里有一个很值得停下来想的画面。把整个调试流程画成一张图，中间拉一条虚线。

虚线左边，全是自动跑完的：trace、span 树、延迟、token 成本，监控平台一键给你。虚线右边呢？为什么坏、怎么修、保证不复发——全靠你自己的时间。

而生产环境里的调试，真正住的地方，恰恰是虚线右边。

所以真正的瓶颈，从来不是可观测性本身。是 trace 落到你屏幕之后，必须发生的那一切。监控只是把问题端到你面前，它没解决问题，它只是让你看见了问题。

## 同一个模型，差距在那层脚手架

为什么这件事这么重要？因为决定 Agent 好坏的，越来越不是模型本身。

Cursor 公开聊过，他们在 Agent 外面那层 harness 上投入了多少工程。所谓 harness，就是包在裸模型外面的那一层——prompt、工具、各种检查。同一个模型，换上一套更好的 harness，结果好得多。而这活儿，永远干不完。

这就是症结。每升级一次模型，多一批新失败模式。每加一个工具，多一批新的边界情况。harness 越长越复杂，复杂的速度，比任何团队手工追踪和修复的速度都要快。

你一个人，追不上它。

## 调试循环为什么反复重开

更扎心的是，这个循环之所以一次次重开，是因为它从来没被记住过。

你这次熬夜修好的那个 bug，知识就藏在你脑子里、藏在那个一次性的补丁里。修完，它就丢了。下个模型一来，一切归零，你又从看 trace 开始。

每一次调试，都是一次性消耗品。你付出的时间，没有沉淀成任何能复用的资产。这才是循环反复重开的真正原因——不是 bug 太多，是经验留不住。

那要怎么让它停下来？答案是，得想办法把这个手工循环，变成一个能自己闭合的回路。

## 让失败自动变成回归测试

第一个关键转折，听起来像个小功能，实际改变的是整套工作流的数学。

把每一个你调试过的失败 trace，自动变成一条新的测试用例。

你品一下这件事的份量。普通的测试集，是有人提前坐下来，凭想象写一堆合成场景。而这套机制里，测试集是从真实的生产失败里长出来的。每修复一个真实事故，测试套件就自动多硬一分。

于是出现了一句很关键的话：每转一圈，这套 harness 就更难被打破一次。

它不再是漏一个补一个的消防队。它在变成一个越用越结实的东西。你过去丢掉的那些经验，现在全都被锁进了测试里，永远帮你守着。

## 用大白话写断言，而不是比浮点数

第二个转折，关于怎么判断一个回答到底行不行。

传统做法是研究员那一套：标一个数据集，定一个数值指标，然后比浮点数。这套对做研究很有效。可它压根不是工程师判断质量的方式。

工程师脑子里想的不是分数，是一句很朴素的话：这个回答必须包含具体的成交细节，不能只给个数字。或者：这个回答绝对不能泄露未授权的信息。

那就直接用大白话把它写成断言。底层再把每一条转成 LLM-as-a-judge，也就是让一个模型去当裁判，给出干净的通过或者不通过。

这里要诚实说一句代价。让模型去判模型，本身是有可靠性边界的——裁判也会看走眼，也要花成本。但它换来的，是让质量标准回到工程师真正思考的那个层面，而不是逼你把判断硬塞进一个浮点数里。

## 测的是整张图，不是单次 prompt

第三个转折，关于你到底在测什么。

大多数所谓的 playground，本质是 prompt playground。你改一句系统提示词，重跑一次模型调用，看输出变了没有。

可这回答的是个错问题。生产环境真正要问的是：我改了这一处，整张 Agent 图会怎么反应？

差别巨大。一个 Agent 不是一次模型调用，它是一整张图——多个步骤、多个工具、彼此牵连。你只重跑单次 prompt，看到的是局部；你要看的，是改动顺着整张图传下去之后，整个系统的反应。

所以正确的做法，是把完整埋好点的 Agent，端到端跑一遍，盯着改动在整张 span 树上引起的连锁反应。这才叫测试一个 Agent，而不是测试一句话。

而且还有个附带好处：这种沙箱里的测试足够安全，产品经理、领域专家、做 QA 的人都能进去调配置、试方案，完全不用碰一行 git。

## 飞轮转起来是什么样

把这三件事串起来，循环就闭合了。

一行装饰器把 Agent 埋上点，声明一下配置。生产环境出故障。一个内置的编程 Agent——在 Opik 里它叫 Ollie——读 trace、读你的源码，走遍整张 span 树，定位根因，给你一份 diff。

注意，整条路径里只有一个手动步骤：你批准。没有你的显式批准，它不改任何代码，不动你的 git。这一步既是安全闸，也意味着这个回路并非全自动——规模化的时候，人就是那个吞吐瓶颈。这是个真实的取舍，不是缺点也不是噱头。

你一批准，它就用原始失败 trace 里一模一样的输入，把 Agent 重跑一遍，把新 trace 流式推给你做并排对比。通过了，这个修复就存下来，原始那个失败，被锁成一条回归测试。

然后,下一个失败,进入同一个循环。

## Synthesis

回过头看，这套思路的精髓，其实跟 trace 本身没多大关系。

它真正做的，是把「调试」这件事，从一次性的手工消耗，变成一个能自我修复、还越用越硬的飞轮。失败不再是负担，失败变成了让系统变强的燃料。

Opik 是把这套回路自动化的一个具体实现样本。但你哪怕一行它的代码都不用，这套范式也值得刻进脑子里：失败 trace 要自动沉淀成回归测试；质量断言要用大白话写，而不是比浮点数；要测的是整张 Agent 图被改动后的反应，而不是单次 prompt 的输出。

你的可观测性工具能告诉你 Agent 出了什么事，但「为什么坏、怎么修、保证不再坏」这三件最耗命的活，至今还压在你一个人肩上。真正的瓶颈，从来都在 trace 落屏之后。

## Closing

所以下次再有人跟你说「我们上了可观测性」，你可以反问一句：那看见之后呢？谁来修，修完怎么保证它记住？

监控让你看见问题，是 2023 年那个还算合理的终点。可一旦 Agent 真正进了生产，活才刚刚开始。能把虚线右边那段自己跑完的系统，才是接下来真正值钱的东西。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
