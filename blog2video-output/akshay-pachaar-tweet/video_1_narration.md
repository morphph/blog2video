# Agent 80%的能力不在大模型里？

## Hook

今天我们把全球最主流的 Agent 公司——Anthropic、OpenAI、LangChain 等的 Agent 框架拆开，看看它们的 Harness 到底是怎么造的。拆完之后我发现一件意外的事：这几家底层循环几乎一模一样。真正拉开差距的不是模型本身，而是模型周围那套系统该怎么设计。

## Brand Intro

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。

今天我们精读的是 Akshay 的一篇长推文：《The Anatomy of an Agent Harness》。他把五家主流 Agent 框架的架构拆开，做了一次横向解剖。

## 裸模型就是没有操作系统的 CPU

先说一个核心类比。大模型本身是无状态的。每次调用之间，它什么都不记得。你可以把它理解成一块裸 CPU——算力很强，但没有操作系统，没有文件系统，没有驱动程序。你没法直接用它干活。

Harness 就是这个操作系统。RAM 对应 Context Window，就是模型当前能"看到"的信息容量。硬盘对应 Vector DB，也就是向量数据库这类持久化存储。设备驱动对应 Tool Integration，就是工具集成。而用户看到的 Agent，是跑在这个操作系统上面的应用程序。

这个类比的价值在于：它把"Agent 为什么有时候很蠢"这个问题，从模型能力转移到了系统架构。模型可能一样强，但如果操作系统不行，跑出来的应用就是不行。

## 三层壳，不是一层壳

Harness 不是一个笼统的 wrapper，它有三层同心环结构。

最里面那层叫 Runtime，运行时。干的是最脏最累的活：把 Prompt 拼好、调模型、把模型吐出来的东西解析成结构化数据、出错了帮你兜住。没有这层，模型连启动都启动不了。

往外一层叫 Capabilities，能力层。工具调用在这层，记忆系统在这层，上下文管理也在这层。你可以理解为：Runtime 让模型能跑，Capabilities 让模型有手有脚。

最外面一层叫 Safety and Scale，安全与扩展层。输入输出过滤、验证循环、子 Agent 编排、工具权限控制。这是防护栏，也是天花板。

用户请求从最外层进入，经过安全检查才能到达模型。模型的工具调用从内层往外走，同样要过安全检查。进来一道关，出去一道关。每一层职责分明。

## 七步循环：机械上简单，工程上不简单

所有 Agent 的核心都是一个循环，拆开来看是七步。Prompt 组装，模型推理，输出分类，工具执行，结果打包，上下文更新，然后回到第一步。

关键在第三步：输出分类。模型的回答要么是最终答案，要么是工具调用请求。如果是最终答案，循环结束。如果是工具调用，就继续往下走。这个分支决定了整个循环是继续还是停止。

这里有一个容易被忽略的设计细节。第五步"结果打包"的时候，工具执行的错误信息也会被回传给模型。不是悄悄吞掉，不是只返回成功结果，而是把报错原样喂回去。为什么？因为模型的纠错能力，恰恰来自让它看到失败。吞掉错误等于剥夺了模型自我修正的机会。

退出条件有四个：达到最大轮次、Token 预算用完、安全护栏触发、用户中断。没有它们，Agent 可能陷入无限循环，一直调用工具，永远不停。

这个循环，mechanically simple, complex in every step。一张图就能画完，但每一步背后都是大量的工程细节。

## 五大框架：同一个循环，不同的赌注

这是整篇文章最有价值的部分。把五个主流框架放在一张表里对比，维度是循环方式、状态管理、多 Agent 策略和设计哲学。

先说循环方式。Claude Agent SDK 用的是"笨循环配聪明模型"。OpenAI 用 Runner 类。LangGraph 用状态图。CrewAI 用顺序或层级结构。AutoGen 用对话驱动。五种实现，但底层都是那个七步循环。

状态管理的分歧更有意思。Claude SDK 用 git commits 来做状态管理。OpenAI 提供四种策略让你选。LangGraph 用 typed dicts 加 checkpoints。同一个问题，三种完全不同的工程实现。

但最核心的分歧是哲学层面的。Anthropic 和 OpenAI 押注 thin harness，也就是薄壳策略：尽量少写控制逻辑，信任模型自己做决策。LangGraph 和 CrewAI 押注 thick harness，也就是厚壳策略：用代码显式编排路由和流程。

这不是技术选择，是信仰赌注。你越相信模型会持续变强，Harness 就应该越薄。你越担心模型犯错，Harness 就应该越厚。

## 脚手架比喻：会拆掉的才是好架构

这里有一个很精准的比喻。Agent 是用户看到的建筑物。大模型是建筑工人。Harness 是脚手架。

脚手架不盖楼。但没有它，工人够不到高层。关键是：脚手架是临时的。楼盖完了，脚手架要拆掉。模型越强，需要的脚手架越少。

但这里有一个不显而易见的陷阱。工人是在这套脚手架上训练出来的。你换一套脚手架，工人的表现会下降。原话是：the worker was trained on THIS scaffolding, change it and performance drops。

这意味着模型和 Harness 之间存在隐性耦合。你以为模型能力是通用的，可以随便换框架。实际上，换框架可能直接导致性能回退。

而且这个耦合是动态的。每次模型升级，旧的脚手架可能变成技术债。今天正确的 thick harness，在下一代模型发布后可能需要拆掉重建。这不是一次性的架构决策，而是持续的维护工作。

## 三个最值得记住的设计决策

原文总结了七个关键设计决策。我挑三个张力最大的说。

第一个，推理策略选 ReAct 还是 Plan-and-Execute。ReAct 灵活，每一步都能临时调整方向，但每一步都要推理，Token 开销大。Plan-and-Execute 先制定计划再执行，数据显示快三点六倍，但碰到意外情况适应性差。这不是"哪个更好"的问题，是"你的任务有多确定"的问题。

第二个，工具范围控制。这个被严重低估了。直觉上，给模型越多工具越灵活。但现实是反的。按步骤最小化工具集，Vercel 的数据是减少了百分之八十的冗余工具调用。百分之八十，这不是微调，这是量级差别。工具太多，模型反而选不好。

第三个，验证方式。Computational verification，比如跑测试、跑 linter，结果是确定的，对就是对，错就是错。Inferential verification，用另一个 LLM 来判断，灵活但不确定。一个是考试有标准答案，一个是开卷由老师主观打分。两者成本和可靠性完全不同。

七个维度，每个都没有标准答案。但这三个的取舍方向，可能对你的系统影响最大。

## Synthesis

回过头来看，这篇文章最大的贡献不是告诉你哪个框架更好。它做的事情是把"选框架"这个问题重新定义了。你不是在选一个工具，你是在做七个架构赌注。每个赌注背后都是对模型能力的判断、对任务特性的理解、对成本的容忍度。

而且这些赌注有保质期。今天押对的厚壳策略，半年后可能因为模型升级变成技术债。今天信任模型的薄壳策略，碰到下一个能力瓶颈可能需要加回控制逻辑。Harness 架构不是一锤子买卖，它需要跟着模型一起迭代。

大模型是建筑工人，Harness 才是脚手架。你以为在选模型，其实在选操作系统。而这个操作系统，还有保质期。

## Closing

如果你正在搭建 Agent 系统，建议先回答一个问题：你对当前模型的信任度是多少？信任度高，从 thin harness 开始，少写控制逻辑。容错率低，用 thick harness 兜底。

但不管选哪个，记住工具范围控制这个杠杆。百分之八十的冗余消除，是最低成本的性能优化。
