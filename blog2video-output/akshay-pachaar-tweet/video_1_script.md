# Agent 的真正大脑不是大模型，是你看不见的那层

[SLIDE 1: cover] (0:00 - 1:17)

最近我看到一张架构图，把五大 Agent 框架的核心循环拆开对比。结论让我很意外：它们的底层循环几乎一模一样。真正的分歧不在模型，而在一个大多数人忽略的东西——Harness。今天只聊一个问题：为什么你选 Agent 框架，本质上是在选操作系统。

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。

今天我们精读的是 Akshay 的一篇长推文：《The Anatomy of an Agent Harness》。他把五家主流 Agent 框架的架构拆开，做了一次横向解剖。

[SLIDE 2: principle] (1:17 - 2:51)

先说一个核心类比。大模型本身是无状态的。每次调用之间，它什么都不记得。你可以把它理解成一块裸 CPU——算力很强，但没有操作系统，没有文件系统，没有驱动程序。你没法直接用它干活。

Harness 就是这个操作系统。RAM 对应 Context Window，就是模型当前能"看到"的信息容量。硬盘对应 Vector DB，也就是向量数据库这类持久化存储。设备驱动对应 Tool Integration，就是工具集成。而用户看到的 Agent，是跑在这个操作系统上面的应用程序。

这个类比的价值在于：它把"Agent 为什么有时候很蠢"这个问题，从模型能力转移到了系统架构。模型可能一样强，但如果操作系统不行，跑出来的应用就是不行。

[SLIDE 3: image] (2:51 - 4:15)

Akshay 把 Harness 拆成三层同心环。最内层是 Runtime，运行时。它负责最基本的事：组装 Prompt、调用模型、解析输出、处理错误。这是引擎层。

第二层是 Capabilities，能力层。工具调用、记忆系统、上下文管理、状态管理，都在这一层。这是让模型"有手有脚"的层。

第三层是 Safety and Scale，安全与扩展层。输入输出过滤、验证循环、子 Agent 编排、工具权限控制。这是防护栏。

用户请求从最外层进入，经过安全检查，到达模型。模型的工具调用从内层往外走，同样经过安全检查。每一层职责分明，不是一个笼统的"wrapper"。

[SLIDE 4: image] (4:15 - 5:03)

所有 Agent 的核心都是一个循环。Akshay 拆成了七步。Prompt 组装，模型推理，输出分类，工具执行，结果打包，上下文更新，然后回到第一步。

关键在第三步：输出分类。模型的回答要么是最终答案，要么是工具调用请求。如果是最终答案，循环结束。如果是工具调用，就继续往下走。这个分支决定了整个循环是继续还是停止。

[SLIDE 5: checklist] (5:03 - 5:50)

退出条件有四个：达到最大轮次、Token 预算用完、安全护栏触发、用户中断。这四个条件缺一不可。没有它们，Agent 可能陷入无限循环，一直调用工具，永远不停。

原文说得很准确：mechanically simple, complex in every step。循环本身一张图就能画完，但每一步背后都是大量的工程细节。

[SLIDE 6: comparison_cards] (5:50 - 7:21)

这是整篇文章最有价值的部分。Akshay 把五个主流框架放在一张表里对比，维度是循环方式、状态管理、多 Agent 策略和设计哲学。

先说循环方式。Claude Agent SDK 用的是"笨循环配聪明模型"。OpenAI 用 Runner 类。LangGraph 用状态图。CrewAI 用顺序或层级结构。AutoGen 用对话驱动。五种实现，但底层都是那个七步循环。

状态管理的分歧更有意思。Claude SDK 用 git commits 来做状态管理。OpenAI 提供四种策略让你选。LangGraph 用 typed dicts 加 checkpoints。同一个问题，三种完全不同的工程实现。

[SLIDE 7: principle] (7:21 - 8:19)

但最核心的分歧是哲学层面的。Anthropic 和 OpenAI 押注 thin harness，也就是薄壳策略：尽量少写控制逻辑，信任模型自己做决策。LangGraph 和 CrewAI 押注 thick harness，也就是厚壳策略：用代码显式编排路由和流程。

这不是技术选择，是信仰赌注。你越相信模型会持续变强，Harness 就应该越薄。你越担心模型犯错，Harness 就应该越厚。

[SLIDE 8: quote] (8:19 - 8:53)

原文用了一个我觉得很精准的比喻。Agent 是用户看到的建筑物。大模型是建筑工人。Harness 是脚手架。

脚手架不盖楼。但没有它，工人够不到高层。关键是：脚手架是临时的。楼盖完了，脚手架要拆掉。模型越强，需要的脚手架越少。

[SLIDE 9: principle] (8:53 - 10:18)

但这里有一个不显而易见的陷阱。工人是在这套脚手架上训练出来的。你换一套脚手架，工人的表现会下降。原文原话：the worker was trained on THIS scaffolding, change it and performance drops。

这意味着模型和 Harness 之间存在隐性耦合。你以为模型能力是通用的，可以随便换框架。实际上，换框架可能直接导致性能回退。

而且这个耦合是动态的。每次模型升级，旧的脚手架可能变成技术债。今天正确的 thick harness，在下一代模型发布后可能需要拆掉重建。这不是一次性的架构决策，而是持续的维护工作。

[SLIDE 10: checklist] (10:18 - 11:22)

最后，Akshay 总结了七个关键设计决策。每一个都是取舍。

单 Agent 还是多 Agent。单体更简单，调用更少。多体有隔离和专业化优势，但协调成本高。

推理策略选 ReAct 还是 Plan-and-Execute。ReAct 灵活但贵。Plan-and-Execute 快三到六倍，但适应性差。在确定性任务上选错策略，速度差距是数倍级别的。

上下文策略。激进压缩省 Token，但可能丢信息。保留丰富上下文效果更好，但更贵。

[SLIDE 11: image] (11:22 - 12:00)

工具范围控制是一个被严重低估的杠杆。全量工具随时可用，灵活但性能差。按步骤最小化工具集，Vercel 的数据是减少了百分之八十的冗余工具调用。百分之八十，这不是微调，这是量级差别。

还有权限策略、验证方式、Harness 厚度。七个维度，每个都没有标准答案。

[SLIDE 12: summary] (12:00 - 13:33)

回过头来看，这篇文章最大的贡献不是告诉你哪个框架更好。它做的事情是把"选框架"这个问题重新定义了。你不是在选一个工具，你是在做七个架构赌注。每个赌注背后都是对模型能力的判断、对任务特性的理解、对成本的容忍度。

大模型是建筑工人，Harness 才是脚手架。你以为在选模型，其实在选操作系统。

如果你正在搭建 Agent 系统，建议先回答一个问题：你对当前模型的信任度是多少？信任度高，从 thin harness 开始，少写控制逻辑。容错率低，用 thick harness 兜底。

但不管选哪个，记住工具范围控制这个杠杆。百分之八十的冗余消除，是最低成本的性能优化。
