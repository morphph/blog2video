# 你用 Claude 的方式，决定了它的 90%

## Hook

Claude 已经出来两年了，每天用它的人，还在用它的百分之十。Anatoli Kopadze 这条爆了一千九百万阅读的长贴，把矛头指向了一件更尴尬的事——不是你不知道功能在哪里，是你用 Claude 的姿势本身就在浪费它。今天不聊它有什么功能。只聊那剩下的百分之九十，到底是怎么被你亲手扔掉的。

## 上一期讲的是"在哪里"，这一期讲的是"怎么用"

我们上一期刚讲过这个作者另一篇文章——Claude 有十七个功能，大部分人一个都没开。那是一份功能地图，告诉你东西在哪里。

但他这一篇更狠。他说：就算你把这些功能全部打开，你打开 Claude 的方式还是错的。

他把这件事拆成了十八个步骤。我不打算按一到十八念给你听——那是 PPT 目录。我想挑里面最反直觉的五六个出来，让你听完今天就能动手改。

## 第一个反转：Claude 不是搜索引擎

大部分人用 Claude 的方式，跟用谷歌一样。打开一个新对话，扔一句"什么是 prompt caching"，等它把定义吐出来。

原作者一句话定性了这种用法："你把它当搜索引擎用的那一刻，它的价值就被你砍掉了百分之八十。"

为什么砍掉百分之八十？因为 Claude 不是检索工具，它是一个会推理、会综合、会跟你辩论、会基于上下文继续往下想的伙伴。你问它"什么是 X"，它就给你背一个定义。你问它"我在做一个每次会话调用 Claude 二十次的工作流，prompt caching 在我的场景里能不能真的省钱"——它就跟你一起把这件事想清楚。

同一个话题，两个问法，输出质量天差地别。

## 第二个反转：让 Claude 反问你

这是十八条里面，我个人觉得性价比最高的一条。

大部分人的直觉是，我要把问题问得越清楚越好。这话没错，但不够。真正的杠杆是反过来——在 Claude 开始任何复杂任务之前，让它先反问你五个最重要的问题。

原作者给的 prompt 短得吓人："在你开始之前，先问我五个最重要的、能帮你把这件事做好的问题。我回答完，你再开始。"

不到三十个字，但它改写了整个交互结构。因为 Claude 自己挑出来的五个问题，是它**最缺的那五个信息**。这比你猜它需要什么准得多。没有这一步，Claude 默默替你做假设，然后你花一堆时间在纠正本来一次就能对的东西。

## 第三个反转：让 Claude 帮你写 prompt

如果你不知道怎么 prompt，就让 Claude 自己帮你写 prompt。听起来废话，但几乎没人这么做。

逻辑很直接：Claude 自己最清楚什么样的指令能拿到什么样的输出。这是它的元知识。你把任务描述给它，让它生成一份包含角色、上下文、格式、约束的完整 prompt，然后立刻执行那个 prompt。

这是少数让 AI 自己来优化使用 AI 的环节。一开始你可能觉得绕，但一旦养成习惯，你 prompt 的平均质量会被它一次次地拉上去。

## 第四个反转：删掉那一堆没人要的开场白

每条 Claude 回复，默认都会先来一句你没要的话。"好问题，让我帮你分解一下。"或者把你刚才说的话重新复述一遍。或者一段免责声明。或者结尾再总结一遍它刚说过的东西。

你都没问。但它在那里。它在烧 token，也在烧你的时间。

原作者给了一行规则，加进 Custom Instructions 就永久生效——"永远不要用开场白、附和、或者重复我的问题开头。直接给答案。我没问就不要加结尾总结。除非话题真的需要，不要加免责声明。"

这是少数"写一次、终身受益"的设置。在这个 Project 里，它再也不出现。

## 第五个反转：指定输出长度，砍掉一半 token

Claude 的默认是"我觉得多写一点更稳"。所以它写得啰嗦。

加一句"用三句话回答，最多"——他给了一个让我惊讶的数字——大部分任务的 token 消耗会被砍掉百分之四十到六十，而你真正需要的价值一点没少。

但更重要的不是省钱。是省你的注意力。你读不完的那部分内容，本身就是噪声——它不光浪费 Claude 的输出能力，也在浪费你的接收能力。一句"最多三句话"同时优化了两端。

## 第六个反转：风格克隆，但只克隆表层

如果你让 Claude 替你写东西，没给它你自己的样本，它就会用它自己的腔调写。结果就是那种"语法都对、味道全错"的 AI 文——你能闻到。

正确的做法是给它三到五段你自己写过的东西，让它分析你的句长、节奏、用词偏好、你怎么开段怎么收段、你避免什么。然后告诉它，从今往后写任何东西，都按这个模式来。

但这里有一个我必须告诉你的代价：风格克隆克隆得了表层模式，克隆不了你的判断力。它能学会你怎么写，学不会你为什么这样写。所以克隆出来的稿子读起来像你，但说不出你会说的话。它适合邮件、社媒草稿这种大量低决策的输出，**不适合代表你立场的核心稿件**。

## 一个容易用错的点：sparring partner 不等于 thinking partner

原文里有两个看起来很像的 prompt，但作者把它们分到了两个完全不同的位置，我得跟你说清楚。

一个叫 sparring partner，让 Claude **攻击**你的方案——不是 critique，是 attack。找出每一个错误的假设、每一种失败可能、用最狠的角度反驳你。原话是"不要客气、不要加限定，就攻击。"

另一个叫 thinking partner，让 Claude 在给建议之前，先提问、先理解你说的话、先反馈它听到了什么——然后才说它真正的想法。

这两件事的差别，是**决策心态**。当你信心很足、要拍板了，叫 sparring partner，让它把你打醒。当你还在迷茫期，刚开始想一件事，叫 thinking partner，让它陪你把问题想清楚。

用错了会出问题。脆弱期叫一个 sparring partner 上来，你不是被打醒，是被打垮。这个区分原作者写在那里了，但很多人不会去看，照搬第一个 prompt 就开始用。

## Synthesis：所有这些技巧，其实是同一件事

如果你听完前面这些，会发现一个隐藏的共同点。

"让 Claude 反问你"、"让 Claude 帮你写 prompt"、"删掉 preamble"、"指定输出长度"、"换新话题就开新 chat"——这些动作看起来很散，本质上都在做同一件事。它们都在管理 Claude 看到的上下文：哪些信息要进来、哪些不要、用什么形式进来、不用的时候要怎么扔掉。

这件事有个名字，叫 Context Engineering。我们之前讲过 Anthropic 工程师怎么在百万行代码库里做 context engineering，那是基础设施层的玩法。但这十八步，是 context engineering 在个人使用层的具象化——你也是在做 context engineering，只是大部分人没意识到自己在做。

而一旦你这么去看待它，原作者那句结论才真正落得下来：Claude 不是比你聪明，它没有比你更好的想法。它有的是无限耐心、广博知识、和从你没想过的角度切问题的能力。但前提是，你得让它**理解你**——理解你是谁、你要什么、什么时候该多说、什么时候该闭嘴。这件事一次性投入半小时设置好，剩下每一次会话都在收回报。

## Closing

如果你今天只做一件事，做这一件：打开一个 Project，把"永远不要用开场白和复述"那一行规则写进 Custom Instructions。三十秒。然后这个 Project 之后所有的对话，你都会觉得清爽一截。

设一次，永久换掉你和 Claude 的工作方式。
