# Claude 点击不准？多半是你截图开太大了

## Hook

你的 Claude 在 Computer Use 里点不准？大概率不是模型蠢——是你截图开太大了。Anthropic 刚把这些"以为没问题"的工程默认值，全部摊出来。今天挑三个最反直觉的点跟你聊。

## 反直觉一：截图分辨率越高，点击越不准

先讲第一个反直觉的事，也是这篇博客花最多篇幅讲的事——分辨率。

你的直觉一定是：截图清晰度越高，模型看得越清楚，点得越准。对吧？但 Anthropic 在这篇博客里直接告诉你：错。点击不准的头号嫌疑人，根本不是模型推理能力，而是图像被偷偷压缩了。

Claude 的 Computer Use API 内部对图像尺寸有硬限制。4.6 这一代模型，长边最大 1568 像素，总像素不能超过 1.15 兆。Opus 4.7 放宽了一点，长边 2576 像素，总像素 3.75 兆。听起来挺宽对吧？但你算一下，1920×1080 的全高清截图，总像素已经超过 2 兆了——4.6 接到这张图，会怎么办？

它不会报错，也不会提醒你。它会**静默地**把图缩小到限制以内，然后送进模型。问题就出在这里。模型看到的，是缩小后的图。它根据缩小后的图返回坐标。但你的 harness 拿到坐标，要点的，是原始尺寸的屏幕。坐标系彻底错位了。

更阴的是 macOS 用户。Mac 的 device pixel ratio 默认是 2，你随手一截图，得到的是屏幕逻辑分辨率的两倍。你以为自己截了张正常图，实际上传给模型的是一张超大图，被悄悄降采样，然后坐标全错。

Anthropic 给的起步推荐特别朴素：4.6 用 1280×720，大概占像素预算的百分之八十。Opus 4.7 起步用 1080p。低于 960×540 也不行，细节丢太多。这中间有个很窄的甜点区间，你得自己找。

还有一个小细节很有意思——他们发现，把文字指令放在图像**前面**而不是后面，准确率会提升。一句话顺序的事，但很多人不知道。

更反常识的一点：Anthropic 内部试过三种"听起来很合理"的做法，结果一个都没用——把图切成小块、叠加坐标网格、换 resize 算法。全是白做工。真正有用的就两件事：选对分辨率，把文字放在图前面。

## 反直觉二：思考预算开到顶，是在烧钱

第二个反直觉的点，关于 thinking effort——也就是思考预算。

你可能下意识觉得，让模型多想想总是好的，对吧？尤其是复杂任务，开 max 准没错。但这篇博客原话是这么说的：UI 自动化任务，跟写代码、解数学题，根本是两码事。大部分 Computer Use 的动作是**感知加机械**——认出那个按钮在哪、点下去——这不是逻辑推理任务。

Anthropic 给的数据特别直接。Opus 4.7 用 high effort，成功率已经非常接近 max effort，但输出 token 大概只有一半。4.6 家族更夸张，medium 是甜点位，加上失败重试，效果跟 high 几乎打平。他们直接写在文档里：**不要用 max**，对准确率没好处，纯粹多花钱。

这件事翻译成大白话就是：你让一个会点鼠标的人多想三分钟，他不会点得更准，他只会想得更多。多想出来的那部分逻辑，对感知任务没有杠杆。

还有一个我觉得很有意思的判断——Sonnet 和 Opus 谁更适合做 Computer Use？官方答案是 Sonnet 4.6 机械点击更精准，Opus 的优势是推理。Opus 4.7 把点击精度拉到差不多了，但默认推荐还是从 Sonnet 4.6 开始。换句话说，给 Agent 当"点击工"用最强模型，是错配——你要找的不是最聪明的，是手最稳的。

## 反直觉三：上下文管理不是省钱，是生死线

第三个，我认为是这篇博客里最重要的判断——上下文管理。

很多人把上下文压缩当成"省 token 的优化"。但在 Computer Use 这个场景，它不是优化，是生死问题。

为什么？算一笔账。每一次操作都会生成一张新截图，一张截图消耗一千到一千八百 token。200k 的上下文窗口，不到 100 步就撑满了。100 步是什么概念？让 Agent 帮你订一张机票，从打开浏览器到最终确认，可能要点二三十次。一个稍微复杂点的工作流，几十步就上去了。你不做上下文管理，Agent 就跑不过 100 步——这不是慢，是直接停。

Anthropic 给的默认方案叫"滚动缓冲"。听名字很复杂，原理特别简单——只保留最近 3 张完整截图，再往前的换成文字占位符。但这里有个非常工程的细节，我必须讲一下：**必须批量裁剪**。

为什么？因为 API 的 prompt caching 靠的是消息数组字节级一致。你每跑一步就裁一张，每一次消息序列都变了，缓存就废了。Anthropic 的做法是攒一批再裁——默认 keep_n 等于 3，interval 等于 25。意思是保留最近 3 张高清截图，等总数超过 28 张了，一次性把最老的 25 张全替换成占位符。这样在两次裁剪之间，消息序列字节完全一致，缓存断点持续命中。

这就是我说的 tradeoff：滚动缓冲不是"该删就删"，而是"忍着不删，攒一批再删"。直觉相反，但工程上是对的。

更长的会话还要叠一层 LLM 压缩。把更早的对话整段交给一个 summarizer 模型，让它写一份摘要，记下用户原话、任务模板、做过的动作、踩过的错、当前状态、下一步。摘要替换原始历史，最近几张截图保留。这就是为什么 Anthropic 给长任务的推荐配方是组合拳——一个 cache breakpoint 放系统提示，三个 breakpoint 放最近的工具结果，滚动缓冲打底，服务端 compaction 在 150k token 左右触发。听起来繁琐，但少一环 Agent 就跑不远。

## 关于安全：Prompt Injection 是结构性风险

剩下两点我快速过一下，不展开，但值得你知道。

第一是安全。Computer Use 这个范式天然就是不安全的——它每一帧屏幕、每一个网页、每一个 UI 元素，都可能藏着对抗指令。看不见的隐藏文字、被改过的图、伪装成系统对话框的钓鱼弹窗，全是攻击面。这不是偶尔出现的 bug，是结构性风险。

Anthropic 内置了实时分类器，扫描每一帧内容里有没有注入指令。原话是"几乎零延迟、零额外成本"——但有个坑：分类器**只**在你用官方 Computer Use 工具时自动跑。你要是自己实现了一套自定义工具，分类器不会自动启用。这个边界要记住。

不管你用不用官方工具，几条底线都得守：高风险动作要有人工确认、Agent 权限要收窄、所有动作要记日志、所有网页内容都当不可信处理。

## 演示回放：与其改 prompt，不如演一遍

第二是这篇博客最后讲的一个新思路——teaching Claude。

老路子是反复改 prompt，把流程写成一长段文字告诉模型怎么做。新路子是：你自己操作一遍，系统把每一步的截图、点击位置、键盘输入、甚至你的语音解说全录下来，下次让 Claude 照着这份录像做。

但这不是死板复制坐标。Claude 会把演示当**参考**，结合当前 UI 状态自己判断。按钮挪位置了，菜单改版了，它会找等价元素，不会瞎点原坐标。

这里有个 tradeoff 要讲清楚。回放有三种模式：strict、adaptive、goal-oriented。Strict 模式严格按步骤来，UI 一旦变化太大就直接停——这对合规场景是好事，但对经常改版的网站就是灾难。Adaptive 是默认推荐，把演示当指南，灵活适应。Goal-oriented 只看终点，步骤当提示。你得根据场景选——把 strict 当万能解，UI 一改 Agent 就罢工，反而不如纯 prompt。

## 一句话总结

把这篇博客摊开来看，Anthropic 其实在传一个反常识的判断——Computer Use 在生产环境跑不起来，主要不是模型推理不够强，是一连串"以为没问题"的工程默认值在拖后腿。

你以为分辨率越高越好，其实超出限制会被静默压缩，坐标系崩了。你以为思考开 max 准没错，其实感知任务不吃推理预算，开 max 就是白烧钱。你以为上下文够大不用管，其实 100 张截图就满，不做滚动缓冲 Agent 跑不过 100 步。三件事的直觉解法，全都恰好是错的。

如果你现在正在做 Computer Use，三条可执行建议——把截图分辨率降到 1280×720 起步、思考预算从 high 或 medium 开始而不是 max、长任务一定上滚动缓冲加批量裁剪。这三件事调对，比换模型管用得多。
