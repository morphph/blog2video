# 30个工具的Agent，输给了7个工具的它？

## Hook

整个 Agent 领域吵到现在，连最基础的一个问题都没对上号：一个 Agent 到底该配多少个工具。Codex 和 Claude Code 各自塞了三十来个，另一个叫 Pi 的只配七个，整整差出四倍。而真正在对冲基金里被认作最准的那个表格 Agent，叫 Shortcut，它的作者押了个更极端的注——只给模型一个工具。今天我们就来精读他这篇文章，聊清楚他凭什么这么干，还赢了。

## 没有人知道一个好 Agent 长什么样

先说说为什么这篇值得读。

现在网上讲"怎么搭一个 Agent"的内容，已经多到泛滥了。一个 while 循环套着模型，模型不停调工具，直到任务做完，给它一个文件系统，给它一个命令行，剩下的它自己折腾。这套东西一个下午就能写出来，大部分人也都写过了。

但你发现没有，几乎没有人在讲"怎么搭一个**好**的 Agent"。

差距就在这里。我前面说的那个四倍分歧不是笑话。当市面上最流行的几个产品，在"该配多少工具"这种最基础的问题上都能差出四倍，这本身就是一个信号——这个领域根本没有公认的原则。大家都是各凭手感。

写这篇文章的人,花了将近一年打磨 Shortcut 这个表格 Agent。它被广泛认为是市面上最准的表格 Agent，部署在全球四大多策略对冲基金里的三家。在那种地方，算错一个数字代价非常高，没人会给你的成绩放水。他们没有微软或者 Anthropic 那种铺天盖地的渠道，靠的就是一件事——这个 Agent 出错更少。所以"怎么让 Agent 更准"，是他每天都在琢磨的问题。

他把答案浓缩成一句话：一个好的 Agent，是它所处理任务分布的一次忠实压缩。

这句话听起来抽象，但接下来全是它逼着你去造的具体东西。

## 真正在调的，只有上下文质量

我们一步步来拆。

假设你既没有训练那个模型，也不拥有它运行的环境。那留给你设计的，其实只剩三样东西：系统提示词、工具、还有各种素材，比如 skill、整理好的文档、参考资料。

而这三样本质上是同一样东西——Agent 的上下文。

于是游戏规则就变得很清楚了。模型固定不变的前提下，准确率就是上下文质量的函数。上下文塞太满，信号会被噪声埋掉；上下文缺东西，模型只能靠猜。这两头都在扣你的准确率。

而准确率，恰恰就是你卖的东西。这里有个反直觉的点——它跟价值不是线性关系。一个能做到百分之99的任务，价值是只能做到百分之95的那个的十倍。差的就是那四个百分点，但它值十倍。

所以你不能不在那点脏活上较真。

## 用户给你的，是一条长尾

但麻烦在于，用户拿来的问题，从来不是均匀分布的。

他们给你的是一条长尾。每次打开你的 Agent，绝大多数时间在做的，是那几样最家常的操作，这是又高又胖的头部。然后是一些重要但偶尔才用一次的能力。最后是长长的尾巴——每一件都很罕见，但这种事多得是，而且每一件都还得能做对。

Agent 必须把这整条尾巴全接住。可它又不能一次性把所有东西全塞进上下文里——那就是前面说的，上下文塞太满，信号被埋掉。

所以真正的目标比"什么都备着"要更锋利一点：在整条任务分布上平均下来，让每个任务花掉的上下文最少。

这个问题，其实 CPU 早就遇到过。

一个程序可能要碰到好几个 G 的数据，但紧挨着处理器的那块存储非常小。所以计算机把内存分了层：一小块、瞬间就能拿到的缓存，叫 L1；下面是更大但更慢的 L2、L3；再往下才是主内存和硬盘。这套为什么管用？因为访问也是长尾的——把最热的那批数据放在最快那一层，只有碰上罕见的东西，才下沉去慢的那几层捞。

而当你要的东西不在快的那一层、得花代价去慢层取，这就叫一次"缓存未命中"。这恰恰是你在常用路径上拼命想避免的成本。

Agent 应该长成一模一样的结构。把你的上下文，造成 L1、L2、L3 三层。

而每一项优化，几乎都是在做同一笔交易：信息压缩，换发现速度。放进 L1，它瞬间可用，但代价是每个任务无论用不用，都得为它付出提示词的 token。推到 L3，平时一分钱不花，可真要用的时候，得花好几次工具调用才能找到它。

你的活儿，就是把每一项能力，放到那个能让全分布上总成本最低的层。这就是全部的手艺。

## 整套地基，只有一个工具

在讲三层之前，得先说清楚这套东西踩在什么地基上。

所有这些表格操作——每一次读、每一次写、每一次查文档——背后都是同一个工具在执行代码。模型写代码，代码调用他们的函数，函数去碰那张表。没有什么读取工具、写入工具、画图工具。从头到尾，就一个工具，API 全活在代码里。

为什么这么干？

因为他们自己的实验一次次显示：工具加得越多，模型反而越蠢。

这违反直觉。我们的常识是能力越多越强。但你想想，每加一个工具，就是往提示词里多塞一份 schema，多一块能让模型犯迷糊的表面，多一种选错的可能——尤其当几个工具的职责还互相重叠的时候。

一个 execute_code 工具，把这一堆乱七八糟全收成了一个决策——写代码就完事。而且模型还能用一门编程语言的完整表达力去组合能力，而不是去拼接一堆僵硬的工具调用。

注意，这不是"工具越少越好"的口号。他真正在做的，是把"该选哪个工具"这个决策本身，当成噪声源给删掉。

这件事对那三层很关键：因为模型永远在写代码，所谓 L1、L2、L3，无非就是它知道自己能调哪些函数、以及它为了找到这些函数费了多大劲。

## L1：读和写，本身就是一次压缩

第一层，L1，是那百分之80的家常活——读单元格，写单元格。

如果连读写单元格都做不到极致，后面全是空谈。所以他们在这一层砸了荒谬的、不成比例的功夫。我们就看一次读取，背后到底发生了什么。

先说读。你可能以为，读一段两百行的表格，不就是把数据搬出来吗？不是的——读取本身，就是一次压缩。

它做了三件事。

第一件，公式别名。一列五百行的公式，A2 乘 B2、A3 乘 B3，这么排下去，是五百个几乎一模一样的公式。他们把每个公式归一化成一种相对写法，于是这五百个全长成同一个样子，然后数一数，凡是出现超过十次的模式，就折叠成一个短别名，比如就叫 F1。模型看到的，是重复的 F1 加上一行图例，而不是五百个公式。token 省掉一大截，信息零损失。

第二件，免费的行列上下文。当模型读一片光秃秃的数字，它怎么知道这些数字是什么意思？他们会自动向左扫出行标、向上扫出表头——表头还是靠投票选的，看附近哪一行的文字单元格最多。于是模型白白拿到了"地区、销量、单价、营收"这种上下文，再也不用去猜一堆数字到底代表什么。

第三件，样式压缩。格式本身也是信息——一个加粗的红色单元格在告诉你点什么。但要是把每个单元格的完整样式都列出来，数值就全被淹了。所以他们按相同样式把单元格分组，每组折叠成一块连通区域，一组只打一行。

最后的效果是这样的：六百个公式，变成一行图例；四百个带样式的单元格，变成两行。而那个模型压根没主动要的表头，就乖乖躺在底下。整张表，无损地，塞进了原始 dump 几分之一的 token 里。

每一个，都是那笔"压缩换发现"的交易，在最常用的场景上被赢得干干净净。

## 写回的反馈，是一个内建的纠错员

读完，再说写。写比看起来难。

因为一次执行代码，可能改掉上百个单元格，而 Agent 得知道自己到底改了什么，又不能把整张表重读一遍。所以代码跑完之后，他们会递回来一份结构化的 diff，列出每一个被改动的单元格。但关键不止于此——他们还把这份 diff 做了压缩和分诊。

怎么压缩的？分组、采样，而不是一股脑全倒出来。两百次写入，被归成寥寥几行，但 Agent 还是知道总数。

更妙的是分诊。干净的写入，归在"没问题的改动"那一栏。而任何看起来可疑的东西——一个无效公式、一个没标注的硬编码数字、一个藏在公式里的硬编码、一个离谱到不真实的百分比——都会被单独拎进"需要复查"那一栏，最严重的，直接标上"必须修复"。

举个例子。两百个单元格改下来，第57行冒出来一个 #REF! 的报错。这要是淹在一整片绿色的正常 diff 里，太容易被漏掉了。但在这套机制下，它被顶到最上面，贴着一个"必须修复"的标签。

所以这个反馈循环，给的不是"你改了什么"，而是"你改了什么、以及你大概率搞错的是哪一处"。这相当于给 Agent 自己的每一次编辑，内建了一个纠错员。

L1 一句话总结：处在频率曲线最陡那一段的操作，都被做成了特征工程过的、token 压到极致的、还会主动汇报后果的包装层，而且永久住在提示词里。它们造起来很贵，但你还是得造——因为 Agent 每一个任务都在为它付代价。

## L2：整理好的英文文档，按需取用

但你不可能把所有东西都塞进 L1。

像条件格式、数据透视表、图表、数据校验、复制移动这些操作，每一样都重要，每次会话里都会冒出来那么几次，但每一样又都有足够多的细节，要是全写进系统提示词，就会拖累所有用不到它的任务。这就是典型的第二层，L2。

他们的做法，是把这些能力写成一份份整理好的英文规范，按需才取，就跟 skill 文档一模一样。模型在自己写的代码里调一句，就能把对应的文档拉进来。

但注意，这些不是把函数签名堆在一起的类型说明。它们是手写的散文，每份几百行，讲的是把一件事做对的那条正确路子，包括那些原始 API 永远不会告诉你的知识。

拿数据透视表那份规范来说。它不只是列方法，它是按正确的顺序，把整套配方教给你。它会告诉你一些你本来只能靠反复栽跟头才学得到的事：比如你必须用一对挂起和恢复布局的命令，把这一批改动包住，否则每改一次，整张表就重建一次；再比如，聚合方式得传一个裸整数进去——比如8代表求和——因为运行时根本就没有那个友好的枚举值给你用。

这些都不是什么古怪的坑，这就是把透视表做对，本来该有的样子，只不过被一个已经替你踩过坑的人，提前写下来了一次。

而它最妙的性质是：在任务真正需要它之前，它一个 token 都不花。一个从不碰透视表的任务，永远不必为透视表的文档买单。调一句话，就是它全部的发现成本——一次缓存未命中，很快就被服务掉了。

## 同样这招，也用在可执行的工具上

L2 不只用在文档上。同样这套思路，他们原封不动地搬到了那些"延迟加载的工具"上——网页搜索、网页抓取、生成网站这些。

它们的 schema 不会一直待在提示词里。取而代之的，是一道元工具组成的墙。模型得先用一个查询命令，把某个工具的 schema 取出来，这个工具才会被标记成"已加载"。而如果你没先取就想直接调用，系统会直接拒绝你。

已经取过的那批工具，本质上就是一个会话级别的缓存。模型加载一次 schema，从此它就常驻了。同样是"压缩换发现"那笔交易，同样的解法：把提示词保持得很小，真要用某个能力时，才付一次"未命中"的代价。

这里作者点了一句很值得记的话——这跟 Claude 上的"延迟工具加载"是同一个思路，但他们没有被绑死在某一家厂商的工具加载功能上，照样能拿到这个行为。

## L3：七万行的原始大全，和那份教你 grep 它的 skill

然后，就是那条长尾了。

那种你从没包装过、也没写过规范的、孤零零的冷僻需求。它没法被预料到——这是长尾的定义决定的。但 Agent 还是得有路能走到那儿，否则它就一头撞墙，任务失败。

比如"给每一行加一个小折线图，概括它的趋势";比如"把图表的次坐标轴设成对数刻度，只给第三组数据重新上色";比如"从这个单元格插一个超链接到那个命名区域,再把这几个图形组合起来"。这些都是真实存在、但极少被碰到的 API 角落。

所以第三层 L3，就是那份完整的原始 API——整个 Office.js，或者整个 SpreadJS，全部倒到磁盘上。这是一份机器生成的参考文档，足足七万行长。它包含了一切。但它也彻底没法当上下文用——你绝不可能把它整个贴进提示词。

那怎么办？

诀窍是：你给它配一份 skill，一张简短的地图，教它怎么用 bash 的 grep 去挖这本大全。

这份 skill 大概一百行。它说清楚：这本大全是什么结构、每条方法和每个类型长什么样、针对每一类问题该用哪条 grep 命令去捞。有了它，Agent 就从"几万行我根本读不了"，变成了"三到六次 grep，精准捞出我要的那个签名"。这就是 L3 的访问成本——真实存在，但有上限，而且只有那些罕见到要往这么深处探的任务，才需要付。

系统提示词里还把这条逃生通道写得明明白白，让模型知道这条路存在、也知道什么时候该走它。原话大意是：永远不要猜，把文档完整读一遍;如果包装好的 API 做不到，就用原始 API，别将就。

这最后一句，才是 L3 全部的意义所在。Agent 永远不该被卡死。它可以在 L1 没命中，掉到 L2;就算整理好的规范也没写，它还能下沉到那本原始大全里去,最后用一个还算理智的调用次数，把答案捞出来。

## 把整个预算拆开，正好镜像那条曲线

值得看一眼 token 到底花在哪了，因为这套分层会直接体现在系统提示词的形状上。

提示词的主体是 L1，量级大概是几百行——核心读写操作、execute_code 的约定、关键的几个类型、还有几乎每个任务都会用到的那一小撮方法，外加执行和安全准则。这部分每次调用都常驻，所以也是他们拼了命要压紧的地方。

L2 是叠在上面薄薄一层，大概五十行。注意，这五十行不是规范本身,而是一份"祝福过"的方法白名单,加上几个指针——告诉 Agent 那些文档存在、什么时候该去取。规范的实际内容，在被调出来之前，根本不进提示词。

L3 基本就五行——那份 skill 文档的名字和描述，外加散落别处的一些参考指引。而那份七万行的原始参考，整个躺在磁盘上,永远不碰提示词。

所以你看，整个预算，正好镜像了那条频率曲线：绝大部分提示词花在百分之80的常用场景上,一点点用来给那百分之15立路标,几乎没有花在长尾上。这恰恰就是缓存分层那套框架，一开始就预言的分配方式。

## 这套配方，搬到你的领域

表格只是他的例子。这套结构，能迁移到任何领域。

那些系统提示词、那些整理好的规范里的压缩，本质上是在编码你的用户、以及他们要做的任务的分布——而在你自己的领域里,这个分布,你比任何人都懂。

所以你的活儿，就是回答三个问题。

第一，什么东西包进 L1？是频率曲线最陡那一段、最家常的操作。把它们做到 token 效率极致、速度极快，还要会汇报后果。在这儿砸不成比例的功夫，因为 Agent 每个任务都在付这个代价。

第二，什么东西推到 L2？是那些重要但偶尔才用的能力。把它们写成整理好的、英文的、带着各种坑的提醒的规范，一步就能取到。编码进去的是那条正确路子和各种约束，而不只是函数签名。

第三，你的逃生舱 L3 是什么？是那份原始的、完整的底层素材，再加一份教 Agent 去挖它的 skill。它不需要好用,它只需要能到达、足够完整、并且能在有限步数内被找到。

这三个位置放对了，你就造出了一个在常用场景上飞快、在偶发场景上够用、在罕见场景上也永远卡不死的 Agent——同时还把上下文保持得足够小，让模型一直保持锋利。

## 分层不会消失，它只会往下滑

最后一个观察，我觉得是全篇最值得记住的判断。

什么东西算 L1，并不是固定的，它会随着模型变强而漂移。

早年那些弱模型，需要小小的、单一用途的工具，每件事都得给它掰开揉碎。今天的模型，能一口吞下一份更大的 L2 规范,能直接在更多的 L3 原始细节上推理而不噎住。

所以随着模型变强，昨天的 L3 会变成明天的 L2，昨天的 L2 会塌进 L1。Agent 的责任范围向外扩张，整个层级，往下滑一级。

但你可能会觉得——模型越强、上下文窗口越大，这套分层的脚手架不就该被淘汰了吗？

恰恰相反。分层本身，永远不会消失。因为相对于"你能往里塞的一切",上下文永远是稀缺的;而噪声，永远在扣你的准确率。没有哪个模型大到，能让"在对的时间、把对的东西、放到它面前"这件事，不再重要。

更大的上下文窗口，总在诱惑人们往里贴更多东西。但更好的本能，是 CPU 几十年前就想明白的那一个：摘要放缓存,细节按需取,原始素材留作最后一招。

把你 Agent 的上下文，造得像一套内存分层。准确率，自然就跟上来了。

## Synthesis

回过头看这一整套，你会发现它真正颠覆的不是"工具数量"这个表面问题。

别人忙着给 Agent 加到三十个工具，真正赢的那个只给了一个。但他赢，不是因为工具少,而是因为他想清楚了一件事：Agent 的上限,不在它能调多少工具,而在你有没有把任务分布,像 CPU 缓存一样,分层压进它的上下文里。

热的常驻在 L1，温的在 L2 按需取，冷的留一条能 grep 到的逃生舱。

一个好的 Agent，就是它所处理任务分布的一次忠实压缩。这句话，到这里，应该不再抽象了。

## Closing
