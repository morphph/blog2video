读完,再说写。
写比看起来难。
因为一次执行代码,可能改掉上百个单元格,而 Agent 得知道自己到底改了什么,又不能把整张表重读一遍。
所以代码跑完之后,他们会递回来一份结构化的 diff,列出每一个被改动的单元格。
但关键不止于此——他们还把这份 diff 做了压缩和分诊。
怎么压缩的?
分组、采样,而不是一股脑全倒出来。
两百次写入,被归成寥寥几行,但 Agent 还是知道总数。
更妙的是分诊。
干净的写入,归在"没问题的改动"那一栏。
而任何看起来可疑的东西——一个无效公式、一个没标注的硬编码数字、一个藏在公式里的硬编码、
一个离谱到不真实的百分比——都会被单独拎进"需要复查"那一栏,最严重的,直接标上"必须修复"。
举个例子。
两百个单元格改下来,第57行冒出来一个 #REF! 的报错。
这要是淹在一整片绿色的正常 diff 里,太容易被漏掉了。
但在这套机制下,它被顶到最上面,贴着一个"必须修复"的标签。
所以这个反馈循环,给的不是"你改了什么",而是"你大概率搞错的是哪一处"。
这相当于给 Agent 自己的每一次编辑,内建了一个纠错员。
L1 一句话总结:处在频率曲线最陡那一段的操作,都被做成了特征工程过的、token 压到极致的、还会主动汇报后果的包装层,而且永久住在提示词里。
它们造起来很贵,但你还是得造——因为 Agent 每一个任务都在为它付代价。
