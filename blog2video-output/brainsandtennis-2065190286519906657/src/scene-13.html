然后，就是那条长尾了。
那种你从没包装过、也没写过规范的、孤零零的冷僻需求。
它没法被预料到——这是长尾的定义决定的。
但 Agent 还是得有路能走到那儿，否则它就一头撞墙，任务失败。
比如"给每一行加一个小折线图，概括它的趋势";比如"把图表的次坐标轴设成对数刻度，只给第三组数据重新上色";
比如"从这个单元格插一个超链接到那个命名区域,再把这几个图形组合起来"。
这些都是真实存在、但极少被碰到的 API 角落。
所以第三层 L3，就是那份完整的原始 API——整个 Office.js，或者整个 SpreadJS，全部倒到磁盘上。
这是一份机器生成的参考文档，足足七万行长。
它包含了一切。
但它也彻底没法当上下文用——你绝不可能把它整个贴进提示词。
那怎么办？
诀窍是：你给它配一份 skill，一张简短的地图，教它怎么用 bash 的 grep 去挖这本大全。
这份 skill 大概一百行。
它说清楚：这本大全是什么结构、每条方法和每个类型长什么样、针对每一类问题该用哪条 grep 命令去捞。
有了它，Agent 就从"几万行我根本读不了"，变成了"三到六次 grep，精准捞出我要的那个签名"。
这就是 L3 的访问成本——真实存在，但有上限，而且只有那些罕见到要往这么深处探的任务，才需要付。
系统提示词里还把这条逃生通道写得明明白白，让模型知道这条路存在、也知道什么时候该走它。
原话大意是：永远不要猜，把文档完整读一遍;如果包装好的 API 做不到，就用原始 API，别将就。
这最后一句，才是 L3 全部的意义所在。
Agent 永远不该被卡死。
它可以在 L1 没命中，掉到 L2;就算整理好的规范也没写，它还能下沉到那本原始大全里去,最后用一个还算理智的调用次数，把答案捞出来。
