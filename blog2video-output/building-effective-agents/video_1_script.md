# 最成功的 Agent，都没用框架

[SLIDE 1: cover] (0:00 - 0:36)

你以为跑通生产的 Agent，背后一定是套精密复杂的框架。恰恰相反。Anthropic 陪着几十个团队做了一年 Agent，得出一个反直觉的结论。最成功的那批实现，全都没用复杂框架。它们靠的是简单、可组合的小模式。这篇官方工程博客，就是把这个结论掰开揉碎讲给你听。

[SLIDE 2: principle] (0:36 - 1:36)

很多人把 Agent 挂在嘴边，其实脑子里是一锅粥。这篇文章上来先做了一个特别重要的切分。

它把所有能自己动手的系统统称为 agentic 系统。但里面分两种。一种叫 Workflow，工作流。就是大模型和工具，按照你事先写死在代码里的路径一步步走。另一种才叫 Agent。模型自己决定下一步用什么工具、怎么完成任务、走几步。

差别在哪？Workflow 的路是你铺好的，模型只是在上面跑。Agent 是模型自己找路。记住这个区分，后面全靠它。

[SLIDE 3: principle] (1:36 - 2:33)

这篇文章最克制、也最值钱的一句判断是这个。用大模型做东西，先找最简单的方案，只有在真正需要的时候才加复杂度。

什么意思？很多场景你根本不需要 Agent。Agent 这东西，是拿延迟和成本，去换更好的任务表现。这笔交易不是每次都划算。

对很多应用来说，把一次大模型调用优化好，配上检索、配上几个示例，就足够了。你没必要一上来就搭个自主系统。这跟市面上教你搭越来越复杂系统的调子，正好反过来。

[SLIDE 4: image] (2:33 - 3:57)

顺着这个思路，文章问了下一个问题。框架要不要用？

市面上框架不少。Anthropic 自己的 Agent SDK，AWS 的 Strands，还有 Rivet、Vellum。它们的好处很明确。帮你把调用模型、定义解析工具、串联调用这些底层脏活累活包起来，让你快速起步。

但代价也很实在。框架会多出一层抽象，把底层真正发给模型的 prompt 和模型的响应给挡住了。出了问题你很难 debug。而且它会诱惑你，在其实更简单就够用的时候，忍不住去加复杂度。

文章给的建议很直接。先直接调 LLM 的 API，很多模式几行代码就实现了。真要用框架，也一定要搞懂它底层在干什么。对引擎盖下面发生的事情做错误假设，是客户出错最常见的来源。

[SLIDE 5: image] (3:57 - 5:00)

讲清楚该不该用，文章开始搭台阶。从最简单的积木，一级一级加复杂度。

最底层那块积木，叫增强版大模型。就是给模型配上三样东西：检索、工具、记忆。模型可以自己生成搜索查询、自己挑合适的工具、自己决定哪些信息该记住。怎么接这些外部能力？一个办法就是 MCP，模型上下文协议，让模型接入一个不断长大的第三方工具生态。

往上一级，是 Workflow。文章列了好几种，我们不挨个念，那样就成教科书目录了。挑两个你就懂这个复杂度阶梯了。

[SLIDE 6: comparison_cards] (5:00 - 6:06)

最简单的一种叫提示链。把一个任务拆成固定的几步，每一步的输出喂给下一步。中间还能加个检查关卡。比如先生成营销文案，再翻译成另一种语言。适合那种能干净拆成固定子任务的活。

再看一种更聪明的，叫路由。先给输入分个类，再送到专门的处理流程去。举个特别实在的例子。简单的问题，就交给便宜快速的 Claude Haiku 4.5。难的问题，才送给更强的 Claude Sonnet 4.5。这样成本和性能就平衡了。

注意，这些还都是 Workflow。路径都是你写死的。

[SLIDE 7: image] (6:06 - 6:48)

阶梯往上，有一种叫编排器-工人。一个中心模型，自己把任务拆开，分派给下面的工人，再把结果汇总。它跟前面并行处理最大的区别是，子任务不是你预先定好的，是这个编排器临场决定的。写代码就是这样，要改几个文件、改成什么样，完全看任务本身。

再往上，那条线终于越过去了。就是 Agent。

[SLIDE 8: principle] (6:48 - 7:54)

Agent 听起来很玄。文章却说了句大实话。Agent 能干很复杂的活，但它的实现往往简单得出人意料。

说穿了，它就是一个大模型，拿着一组工具，根据环境给的反馈，在一个循环里转。

它怎么工作？先从人这里拿到一个指令，或者跟人聊清楚要干什么。任务明确了，它就自己规划、自己执行。执行过程里最关键的一点，是每走一步都要从环境里拿到真实反馈。工具返回了什么、代码跑出了什么结果。靠这些真实反馈来判断自己进展如何。卡住了或者到了检查点，它可以停下来问人。

[SLIDE 9: checklist] (7:54 - 8:47)

这里必须泼盆冷水。文章自己也说了，这份自主性是有代价的。

Agent 自己做主，意味着更高的成本，还有误差累积。一步错，可能步步错，错误会滚雪球。所以文章反复强调，一定要在沙盒里大量测试，加护栏，还要设停止条件，比如最多循环多少次。不加这些，它就失控了。

Agent 适合的是那种开放式问题。你预测不了要走几步，也没法把路径写死。这时候才轮到它上场。

[SLIDE 10: principle] (8:47 - 9:53)

如果这期你只记住一件事，记住这个。文章最后抛出了一个大多数人都忽略的胜负手。

所有人的精力都砸在打磨 prompt 上，把工具当成写死的 API，懒得管。但 Anthropic 说，工具的定义，值得你投入和整体 prompt 一样多的心思，甚至更多。他们造那个解决真实 GitHub issue 的 SWE-bench Agent 时，花在打磨工具上的时间，超过了打磨主 prompt。

而且有个特别反直觉的点。该选什么工具格式，不取决于对程序员来说规不规整，而取决于模型写起来累不累。

[SLIDE 11: image] (9:53 - 11:02)

文章里有个具体的 bug 场景，比任何比喻都锋利。

他们发现，当 Agent 离开了根目录，再用相对路径去指文件，模型就开始出错。你猜他们怎么修的？没去改 prompt，没去骂模型笨。他们改了工具本身。把工具改成强制要求用绝对路径。改完之后，模型零失误，完美地用对了。

你品品这个细节。解决出错，有时候根本不是让模型更聪明，而是把接口设计成让模型更难犯错。这就是文章说的，给工具做防呆。把工具描述写得像给初级程序员的一份好文档。把自己代入模型的处境，想想它用起来到底顺不顺手。

[SLIDE 12: summary] (11:02 - 12:32)

绕了一圈，文章把三条核心原则拍在桌上。第一，让你的 Agent 设计保持简单。第二，把模型的规划步骤明明白白亮出来，别藏。第三，认认真真打磨那个 Agent 和计算机之间的接口。

这三条背后是同一个判断。别急着造更聪明的系统，先造对的系统。最强的 Agent，往往把最多的时间，花在怎么让模型少犯错上，而不是花在怎么让模型更聪明上。

所以如果你正准备做 Agent，这篇文章给你的可执行建议其实特别朴素。先从最简单的 prompt 起步。用评估去优化它。只有当简单方案真的不够用了，才一步步加上多步的自主系统。框架能帮你快速起步，但真到了生产环境，别舍不得把那些抽象层砍掉。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
