# Video 2: 手把手教你造Claude技能包：从规划到测试的完整流程

[SLIDE 1: cover] (0:00 - 0:30)

上期我们聊了 Skill 是什么。一个文件夹，一个 SKILL.md，就能让 Claude 永久记住你的工作流。但知道"是什么"和"怎么建"，中间隔着一条巨大的鸿沟。很多人打开编辑器，第一行就卡住了。

这里是 AI 精读。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。今天我们继续精读 Anthropic 的 Skill 构建指南，聊聊从零开始建一个 Skill 的完整流程。

[SLIDE 2: principle] (0:30 - 2:30)

很多人一上来就开始写 SKILL.md 的正文。错了。官方指南第一句话就说了：写代码之前，先想清楚两到三个具体用例。

为什么？因为 Skill 不是通用工具，它是专用工具。你得先搞明白它要解决什么问题，才能写出有效的指令。

Anthropic 观察到，好用的 Skill 基本上只有三大类。

第一类，文档和资产生成。比如自动生成前端组件、设计稿、PPT。像官方的 frontend-design 技能，就是专门生成高质量前端界面的。

第二类，工作流自动化。把多步骤的流程编排成一键触发。比如官方的 skill-creator 技能，能交互式引导你一步步创建新 Skill。

第三类，MCP 增强。给 MCP 工具服务器加上工作流指导。比如 Sentry 的代码审查技能，能自动从 Pull Request 里分析并修复 Bug。

打个比方。这三类就像厨师的三个分工。第一类是做菜的，直接产出成品。第二类是管后厨流程的，确保出菜顺序不乱。第三类是把食材供应商和菜谱打通的，让原料和做法无缝衔接。

先确定你的 Skill 属于哪一类，后面的设计才有方向。

[SLIDE 3: comparison_cards] (2:30 - 4:30)

用例想好了，接下来才是最关键的一步：写 YAML description。

没错，不是 SKILL.md 的正文，而是顶部那一小段 YAML 里的 description 字段。这个字段决定了 Claude 什么时候触发你的 Skill。写得好，它该出现时就出现。写得不好，要么从不触发，要么乱触发。

你可以把它想象成便利店的招牌。写"24小时营业便利店，卖零食饮料日用品"，顾客一看就知道要不要进。但如果你写"综合性零售服务机构"，路过的人根本不知道你是干嘛的。

官方推荐三段式写法。第一句说它做什么。第二句说什么时候用。第三句列核心能力。

好的 description 长这样："分析 Figma 设计文件并生成开发交接文档。当用户上传 fig 文件，或要求生成设计规范、组件文档时使用。"

坏的 description 长这样："帮助处理项目。" 太模糊了，Claude 完全不知道什么时候该触发。

还有一个容易踩的坑。description 不能超过 1024 个字符，不能包含 XML 标签。而且文件必须叫 SKILL.md，大小写敏感。文件夹必须用 kebab-case 命名，比如 notion-project-setup 是对的，Notion Project Setup 是错的。

[SLIDE 4: checklist] (4:30 - 6:20)

Skill 写好了，怎么知道它行不行？官方给出了一套三层测试法。

第一层，触发测试。就是检查：该触发时触发了吗？不该触发时没触发吧？你至少准备五个相关提问和五个无关提问。比如你的 Skill 是做项目初始化的。"帮我搭建新的 ProjectHub 工作区"应该触发。"今天天气怎么样"不应该触发。目标是百分之90的查询命中率。

第二层，功能测试。触发了之后，输出对不对？流程有没有走完？有没有报错？

第三层，性能对比测试。这一层很多人忽略了。你要证明：有 Skill 确实比没 Skill 强。官方给了一组数据。没有 Skill 时，完成同一个任务需要 15 轮对话、3 次 API 报错，消耗一万两千个 Token。有 Skill 之后，自动完成，只问了 2 个确认问题，零报错，Token 消耗降到六千。

测试完了，肯定会发现问题。怎么迭代？官方总结了三种常见症状和对应的药方。

触发不足，就是 Skill 太"内向"了。解法：在 description 里加更多关键词和细节，让 Claude 更容易匹配到它。

触发过度，就是 Skill 太"社牛"了。解法：加负面触发条件。比如写上"不要用于简单的数据浏览"，让它学会说"这事不归我管"。

执行出错，输出不对。解法：改正文指令，补充错误处理逻辑。官方还有一个进阶技巧。关键校验别用语言描述，直接放一个脚本。代码是确定性的，语言解读有歧义。

[SLIDE 5: summary] (6:20 - 7:00)

总结一下。造一个好用的 Skill，不是一上来就写 Markdown。正确的流程是三步走。第一步，想清楚用例，确定它属于文档生成、工作流自动化、还是 MCP 增强。第二步，用三段式写好 YAML description，这是整个 Skill 的灵魂。第三步，三层测试加迭代，触发、功能、性能，逐层打磨。

你现在就可以做一件事。打开你已有的 Skill，用三段式重写 description。第一句说它做什么，第二句说何时触发，第三句列核心能力。然后分别用五个相关和五个无关的问题测一测。十五分钟搞定。
