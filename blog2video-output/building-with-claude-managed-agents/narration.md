# Agent 上线为什么要把大脑和手拆开？

## Hook

Anthropic 刚发布了 Claude Managed Agents，同一天他们的 Applied AI 团队放出一篇长文，直接承认了一个架构判断：Agent 想真正跑上生产，大脑和手必须分开。这里的大脑指调用 Claude 的 harness，手指跑代码、动文件、访问系统的沙箱。他们把这两件事塞进同一个容器已经塞了两年，现在自己把它拆开了。

## 从 tokens in tokens out 说起

这篇长文的作者是 Anthropic Applied AI 团队的两位技术成员。他们不做研究，也不做产品，卡在中间——一边看模型能力怎么演化，一边看客户到底怎么把 Claude 塞进生产系统。

他们开头就丢了一句话，我读的时候直接停下来了：把一个 Agent 送上线，缺的不是好 prompt，是基础设施。

这句话看起来很朴素。但你把它翻过来想——如果一个真正做过大量客户落地的团队说，模型能力早就不是瓶颈，那瓶颈到底在哪？

他们回顾了一下时间线，很短。二零二三年 API 刚开放的时候，契约极其简单：tokens 进，tokens 出。你发一段 prompt 过去，Claude 返回一段补全，剩下的全是你的事。这在很长一段时间里够用。文档摘要、工单分类、文本改写，这类活儿一次模型调用就能干完，你不需要循环，不需要状态，不需要沙箱。

但慢慢地，人们想让 Claude 干的事变了。不再是回答一个问题，而是接一个任务从头做到尾——查一下、动一下、看结果变没变、再决定下一步。而且要在你原本的系统里干活，你的代码仓库、你的内部 wiki、你的工单系统。

一旦任务变成这种形态，只有 API 就不够了。

## 你得自己造一个循环

在只有 API 的年代，把 Claude 变成 Agent，意味着你要自己写那个循环。问模型下一步干嘛，跑工具，把结果喂回去，再问，再跑，一直到任务完成。听起来简单，但这个循环外面要包一层一层的东西：怎么管上下文、怎么处理工具失败、怎么在模型迭代之后重新调参。

Anthropic 自己在二零二五年发布 Claude Code 的时候，就写了他们自己版本的这个循环。里面有工具执行、有子 agent、有上下文管理、有一大堆让 Claude 变成真·编码 agent 的机制。这套东西他们叫 harness。

开发者看到了就说，能不能让我也用这套 harness？于是有了 Claude Agent SDK，把 Claude Code 内部那套机器暴露出来，你不用再从零写循环，直接站在他们调好的 harness 上盖自己的 agent。

到这一步，很多团队觉得，行，Agent 可以做了。

## 六个绕不过去的坑

但 Applied AI 团队在这里踩了一脚刹车。他们说，就算有 harness，把 Agent 送上生产依然有一堆事绕不过去。他们列了六个。

第一个是 hosting 和 scaling。Agent 到底跑在哪台机器上？一个多小时的任务，进程能不能一直活着？用户量涨上来了，怎么横向扩？

第二个是 session management。一次 run 的历史和进度存在哪？如果中间断了，能不能续上继续跑？想回头看上周那次 run 到底干了什么，找不找得到？

第三个是文件系统。Agent 干活是要产出的——改代码、写文件、生成文档，这些东西落到哪里？两次 run 之间这个工作区怎么办？

第四个是执行隔离。Claude 写出来的代码总要有地方跑。跑错了炸多大？在生产环境里你敢让它在哪一层落地？

第五个是凭证。Agent 要连你的系统，那 token 怎么给它？怎么保证它不会把 token 泄给自己生成的代码？

第六个是可观测性。Agent 自己跑了一小时，中间做了件出人意料的事，你能不能把它每一步都还原出来？

这六个坑，每一个都不是模型问题，全是基础设施问题。

## 隐藏在 harness 里的一笔债

Agent SDK 解决了一部分，但没解决全部。而更麻烦的事情，还不在这六条里。

作者讲了一个内部事故，我觉得是全篇最有意思的一段。

Claude Sonnet 4.5 上线的时候，他们观察到一个奇怪的 bug——agent 快跑到 context 上限的时候，会突然开始草率收尾，不再充分利用剩下的空间。他们给这个行为起了个名字，叫 context anxiety。

修法是给 harness 加了一个 context reset 的机制，等于是在 harness 里塞了一个假设：Claude 到了 context 边缘会慌，我要提前帮它稳住。

然后 Opus 4.5 上线，这个行为消失了。Claude 自己就不慌了。而之前打的那个补丁，从功能变成了纯粹的 overhead——白白多做一遍事。

这个案例的意义远远超过它自己。作者点破了一个残酷的事实：自己维护 harness 是一笔跟模型代际相关的技术负债。每换一代模型，就有一批过去的补丁失效，同时可能冒出新的怪癖需要新补丁。

你以为 harness 写一次就一劳永逸，实际上你订阅了一个跟 Anthropic 模型迭代速度赛跑的义务。而对绝大多数团队来说，harness 根本不是产品差异化的地方，它是被迫维护的基础设施。

## 关键判断：把大脑和手拆开

问题追到源头，作者给了一句非常重的话。

这些困难里的大多数，来自一个共同的架构决定：harness 通常跟它操作的文件系统跑在同一个容器里。

意思是，让 Claude 思考的那部分代码，跟 Claude 生成的代码执行的地方，物理上住在一起。听起来没什么，但这一个决定造成三笔隐性成本。

第一，容器要冷启动，Claude 才能开始想事情，用户就要多等一段。

第二，agent 跑的代码跟你的凭证挤在同一个进程边界里，一次 prompt injection 就可能让模型读到自己的环境变量，把 token 打出来。

第三，容器一死，整个 run 就死了。你没有办法从中间恢复，因为思考进程本身就没了。

Managed Agents 的做法，就是把这个耦合正面拆掉。调 Claude 的 harness 单独跑一份，跑代码的沙箱单独跑一份，中间用一条 append-only 的 session 事件日志把两边连起来。

结果是三件事同时被解锁：Claude 可以在任何容器出现之前就开始推理；沙箱离你的凭证很远；一次完整的 run，任何时刻都能从事件日志里重建。

这就是那句 signature——decouple the brain from the hands. 大脑跟手，拆开。

## 三个抽象和它带出的效应

拆开之后，Managed Agents 只留下三个抽象。

一个是 agent，等于一份配置：用哪个模型、用什么 prompt、给哪些工具、加哪些护栏。

一个是 environment，就是执行上下文：沙箱容器长什么样、网络规则怎么定、预装了哪些包。可以跑在 Anthropic 的云上，也可以跑在你自己的基础设施上。

一个是 session，一次具体的 run。它把一个 agent 和一个 environment 组合起来，拿到一个独占的沙箱实例，然后把这次 run 里所有的模型调用、工具调用、结果，全部作为事件写进日志。

看起来只是三个概念，但作者点了一下——正是因为 session 被设计成事件日志，才带出来一批下游能力。

首 token 延迟先说。因为 Claude 不再等容器，只要用户发个问题过来，harness 可以立刻开始推理，环境在旁边并行 spin up。中位数下首 token 时间砍了大约六成，最慢那批场景砍了九成以上。这个数字来自他们自己的测试。

再说凭证。因为沙箱跟凭证物理分开了，MCP、CLI、GitHub repo 这些 token 都塞进一个独立的 vault，用信封加密存起来，一个 proxy 按需拉出来解密，凭证从头到尾不进沙箱。以前需要在同容器里做的护栏，现在从架构上就消失了。

再说 session 本身的持久性。因为每一步都以事件形式落盘，一次 run 可以中途 checkpoint、离线暂停、之后接着跑。你可以在开发者控制台里刷时间线，也可以基于同一份事件日志做 memory、做 dreaming。dreaming 是他们的一个功能，会定期回看你 agent 的会话和记忆，抽出模式、整理经验，让 agent 从反复犯的错和用户的偏好里越用越好。这些花活儿能成立，全都是因为架构底下有一条可回放的事件流。

## 交出去的东西

我不想只讲爽点。这个模式要用，是要交换东西的。

原文自己写了：如果你的 agent 需要完全自定义 loop 结构，Managed Agents 就不合适，那种情况自建循环仍然是对的。托管方案面向的是那种更可预测、复杂度更低的 agentic 场景。

第二个代价，是数据和执行边界的部分让渡。默认路径下，orchestration 和工具执行都跑在 Anthropic 云上。他们提供了 self-hosted sandbox 和 MCP tunnel，让"手"可以回到你自己的 VPC 里，但"大脑"那部分，也就是调 Claude 的 harness，本质上必须在 Anthropic 侧运行。对严监管行业，这是一个前置合规问题。

第三个代价，是绑定 Anthropic 的产品节奏。harness 随模型自动演进的好处是你省心，代价是你失去了"选择不跟进"的能力。哪一次模型或 harness 更新改了某个工具调度行为，你没办法冻结版本。

这三笔账我觉得要摆在桌面上。省下的那部分维护成本，换回来的是耦合方向的绑定。

## 已经在跑的案例

作者给了几个真在用的例子，我挑两个最扎眼的。

Notion 把他们的 Custom Agents 建在 Managed Agents 上。团队从看板里直接把任务派给 Claude，Claude 自动把这个任务相关的文档、会议记录、连接过的数据拉过来处理，然后把写好的代码、幻灯片、页面丢回工作区等审阅。几十个任务并行跑。他们描述过一个早期原型的效果——一个原本大概要十二小时的活儿，压到了二十分钟。

Sentry 把他们已有的 Seer debug agent 跟一个新的 Claude agent 配对，那个 Claude agent 负责写补丁、开 PR。这套东西一个工程师几周内就做完了，作者特意对比了一下，原来这类东西通常按月算。

这些不是 demo，是真在生产里跑的东西。共同点很明显——团队原本花在基础设施上的时间，现在全部转到了他们真正的差异化上：怎么管上下文，怎么把体验打磨到贴自己业务。

## Synthesis

回过头看这篇文章，它讲的其实不是一个新产品，讲的是一次架构承认。

从二零二三年的 API，到二零二五年内嵌 harness 的 Claude Code，到把 harness 打开的 Agent SDK，到现在把 harness 加基础设施整个托管起来的 Managed Agents——这条产品线是同一个判断在一步一步往前推：Agent 生产化的关键既不在 prompt，也不在模型，而在于把思考和执行拆到两个物理边界里。

上一代同容器架构不是傻，是当年最直觉的路径。只有当规模、延迟、安全同时压上来，那三笔隐性成本才浮出水面。

所以那句最狠的话我留到这里说——Agent 想上线，最难的不是让模型更聪明，是让模型别跟自己的凭证挤在一个容器里。

## Closing

如果你正在做 Agent，我建议你在动手之前先问自己一个问题：我现在在维护的这套 harness，是我产品的差异化，还是我被迫扛的技术债？如果是后者，认真看一下托管方案。如果是前者，那就继续自建，但要意识到——你订阅的是跟模型代际速度赛跑的义务。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
