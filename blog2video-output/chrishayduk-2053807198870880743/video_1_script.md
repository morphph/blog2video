# Agent 死循环？目标定错了

[SLIDE 1: cover] (0:00 - 1:03)

OpenAI 的 Chris Hayduk 写了一篇博客，讲 Codex 新出的 /goal 命令到底该怎么用。这个命令的意思是：你给它一个目标，它自己循环干活，直到达成为止。听起来很美对吧？但他在 OpenAI 内部和自己的副业项目里都踩过坑——发现大多数人用错了。今天不聊怎么敲命令，只聊一件事：为什么你之前那套提示词风格，到了 /goal 里会让 Agent 当场崩掉。

[SLIDE 2: principle] (1:03 - 2:45)

过去半年模型变强得太快，我们这些用模型的人都被惯坏了。你随便比划两下，GPT 大概也能猜出你想要什么。这种"差不多就行"的提示风格，在对话里没问题。但放到 /goal 里，是灾难。

为什么？因为 /goal 的本质是一个循环。Agent 执行一个动作，给这个动作打分，检查分数是不是达到了目标。没达到就继续，达到就停下。整个机制的核心，就是第三步——检查分数是否达标。

那现在问题来了：如果你给的目标是"把代码改好"，Agent 怎么打分？什么状态算"改好了"？什么时候算"足够好"可以停了？目标本身没有刻度，循环就没有出口。

[SLIDE 3: principle] (2:45 - 4:12)

这才是 Chris 这篇博客里我觉得最反直觉的一点。

在对话式模型时代，提示模糊的代价是"输出质量打个折"——是一个连续的劣化。但到了 Agent 循环里，模糊不再是"差一点"，它会把同一个模糊，分裂成两个对立的极端。

一种极端是早退。模型干了几分钟，觉得"差不多了吧"，就停了。还有一种极端是死循环。模型永远不停，疯狂改代码，瞎转，因为它在追一个本来就追不到的目标。

同一种模糊，两种相反的死法。普通用户根本预期不到——你以为最坏的结果是"做得不够好"，结果它要么直接撂挑子，要么把你的代码改得面目全非还不肯停。

[SLIDE 4: image] (4:12 - 5:54)

那 Chris 给的解药是什么？非常简单。把"把代码改好"改成这样——"把某个具体文件里的代码运行时间减少百分之20，同时不能让现有的单元测试和集成测试出现任何回归。"

你看，一个数字，百分之20。一个硬约束，测试不能挂。Agent 立刻就知道：我跑个 benchmark 就能算出有没有到百分之20，我跑一遍测试就能知道有没有回归。停止条件清清楚楚。

这个例子看起来普通，但它背后是一个标准：可量化的目标，加上可验证的边界。少一个都不行。光有数字没有边界，Agent 可能为了砍运行时间把测试全删了。光有边界没有数字，Agent 又不知道该停在哪。

[SLIDE 5: image] (5:54 - 8:33)

但你可能马上会问：不是所有任务都能压成一个数字啊。比如要把一篇 NeurIPS 的论文改成 ICML 会议要求的格式，怎么量化？

Chris 在这里做了一个很妙的动作。ICML 的格式规则全部写在一个 LaTeX 文件里，又长又琐碎，模型直接对着这个文件评分根本不现实。所以他先让 Codex 把这个 LaTeX 文件里的规则全部抽出来，整理成一个 markdown 的 checklist，一共两百多条。

然后他给 Codex 的目标就变成了：基于这个 checklist 把论文改成 ICML 格式，技术内容不许动。

这一步的精髓在哪？Agent 不擅长判断"这篇论文是不是 ICML 风格"——这是一个抽象的整体感觉。但它非常擅长判断"checklist 第73条勾上没有"——这是一个具体的局部事实。把一个抽象目标，拆成两百多个具体小判断，模型就能当自己的裁判了。

而且他还让 Codex 边做边在 checklist 上打勾，状态写回文件系统。这样 Agent 自己能看到进度，他也能在旁边看着这个清单一行一行被勾掉。

这绕开了一个传统假设——"自我评分不可靠，必须有外部 evaluator"。其实不是，关键在于评分标准的颗粒度。粗粒度的标准模型评不准，细粒度的勾选清单它评得很准。

[SLIDE 6: image] (8:33 - 10:36)

讲完目标，第二件事是反馈循环。Agent 要评估自己干得怎么样，得有个测试机制。这个测试跑得越快、越容易触发，Agent 拿到反馈的频率就越高，迭代就越快。

Chris 自己在做蛋白质结构模型的架构搜索。如果他让 Agent 每次跑完整的训练集来打分，那一次评分就要好几天。/goal 还没等到第二轮就废了。

他的解法是用一个叫 NanoFold 的数据集——小，但采样质量好。同样的评分逻辑，跑完一遍从"天"压到"分钟"。这一刀下去，Agent 才真的能在 /goal 里连续运行几天，一轮一轮逼近目标。

但这里有个代价不能不讲。NanoFold 不是 /goal 命令自带的，是他自己事先准备好的一个轻量评估管道。换句话说，紧凑的反馈循环不是开 /goal 就有的——它是你必须先投资搭建的前置工程。你想用 goal mode 解决一个大问题，得先花时间把"小问题版本"搭出来。这一步省不掉。

[SLIDE 7: image] (10:36 - 12:15)

最后一件事，markdown 文件。Chris 说在 /goal 里他能让 GPT 一口气跑好几天。Codex 自己有上下文压缩能力，但跑这么久，让模型靠记忆维持一条连贯的思路，太难了。

他的做法是给 Agent 开三个 markdown 文件，让它边干活边往里写。三个文件名要记一下：PLAN.md、EXPERIMENTS.md、EXPERIMENT_NOTES.md。

PLAN.md 是高层计划，相当于路线图。EXPERIMENT_NOTES.md 是 scratchpad，按时间顺序记录 Agent 当下在想什么。这俩你大概能猜到用途。

真正有意思的是 EXPERIMENTS.md。它是一个结构化的实验档案——每个尝试都有假设、机制、判断规则、结果。一条一条整整齐齐排下来。

而且 Chris 明确说：这三个文件里，EXPERIMENTS.md 是最重要的那个。

[SLIDE 8: principle] (12:15 - 14:27)

这点也反直觉。人的直觉会觉得 PLAN.md 最重要——它指明方向嘛。

但 Chris 的判断是：长程 Agent 跑几天下来，真正会丢失的，不是"我要去哪"，而是"我已经试过哪些路、为什么不通"。一个失去失败记忆的 Agent，会反反复复撞同一堵墙。

PLAN.md 解决的是规划，EXPERIMENTS.md 解决的是失败记忆。当你和 Agent 一起回头看，你想看的不是它原计划怎么写的，而是它已经踩过哪些坑。哪条路证伪了，为什么证伪了，下一条路该往哪走，全部从这个文件里出。

这也是为什么他还要保留 EXPERIMENT_NOTES.md 那个实时 scratchpad——他自己说原话就是，方便他周期性地审计 Agent 在想什么，需要的时候把它推回正确方向。

注意这个细节。三个文件全开，模型还是会跑偏。/goal 不是完全自动驾驶，长程 Agent 仍然需要人类周期性介入校正。不要被"连续跑几天"这个说法误导成完全放手不管。

[SLIDE 9: summary] (14:27 - 16:36)

把这三件事连起来看，Chris 真正在讲的是同一件事：当你把模型从"对话伙伴"变成"循环执行体"，提示词的角色就变了。

在对话里，提示是一段邀请——告诉模型大概想聊什么。在 /goal 里，提示是一个合同——必须写清楚停止条件、验证机制、外置记忆。

很多人以为模型变强了就该用得更省力。Chris 的发现刚好相反：模型能跑得更久、更复杂，反而要求你把目标定义得更严格、把反馈循环搭得更紧、把记忆系统设计得更外置。

模型现在能跑几天不停了，但循环需要一个停下来的理由——你给它的是清单，还是雾。

下次你打开 /goal，先停一下，问自己三件事。第一，我的目标里有没有一个数字和一个硬约束？没有就先补上。第二，评估这个目标的反馈循环要多久才能跑一遍？如果是小时级以上，先去搭一个小数据集或小模型的轻量版。第三，Agent 跑一天之后，它能从哪里读到自己已经试过哪些路？如果没有 EXPERIMENTS.md 这种文件，它一定会原地打转。

清单不是模板，是 Agent 的呼吸方式。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
