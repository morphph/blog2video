# Insight Memo: Claude Code Agent Loop 深度拆解

## title_zh
Agent Loop凭什么只用14种状态？

## one_sentence_thesis
Claude Code 的 Agent Loop 之所以强大，不是因为循环本身复杂，而是因为它把所有复杂性——五级预处理、流式并行执行、分层错误恢复、双阈值预算刹车——全部推到了循环的外围，让 while(true) 本身保持极致简单。

## why_this_video_exists
大多数开发者对 Agent Loop 的认知停留在"调模型、执行工具、循环"的粗粒度理解。这篇博客从源码级别拆开了 Claude Code 的 QueryEngine，揭示了循环内部 14 种显式状态转换、五级预处理管道的具体触发阈值（93.5%上下文利用率）、流式工具并行执行的批次机制、以及预算跨压缩边界不重置等工程细节——这些是读源码才能获得的认知，看产品演示永远看不到。

## judgment_lines
- "循环的力量不在循环本身，在于每次迭代都必须回答'我为什么还在跑'" — 来源：transition 字段不是调试日志，而是整个循环的决策依据，7种续行+7种终止=14种显式状态转换，没有任何模糊地带
- "预处理比后处理更重要——'模型看到什么'比'模型说了什么'价值更高" — 来源：调用模型前有五级预处理管道（从零成本规则裁剪到消耗一次模型调用的完整压缩），模型返回后的处理相对简单
- "最危险的 Agent 状态不是报错，而是空转" — 来源：双阈值停止机制——90%预算消耗+连续3次每轮产出<500 token，组合判断才停止；预算跨压缩边界不重置，防止压缩成为无限续命手段
- "乐观策略是一种成本设计哲学：先假设简单情况，只有真需要时才升级" — 来源：输出限制默认8K而非64K，命中后才升级；五级预处理从轻到重排列，能用规则解决的不调模型

## evidence_map
- [具体数字] 五级预处理管道的 Autocompact 触发阈值：200K token 模型在 187K tokens（93.5%利用率）时触发，预留 13,000 tokens 缓冲区，生成最多 20,000 tokens 摘要，压缩后重置为 50,000 tokens 工作预算
- [具体数字] 14种显式循环状态转换：7种续行原因 + 7种终止原因，每次迭代系统都能精确说出"我为什么在这里"
- [具体数字] 输出限制三阶段恢复：第1次 8K→64K 升级，第2次 64K 重试，第3次报错；流式工具执行每批最多10个工具并行
- [具体事实] QueryEngine 分两层：Session Layer 管跨轮次状态（token总量、权限记录），Turn Layer 是约1,730行代码的 while(true) 执行引擎
- [具体机制] 流式传输直接消费原始 SSE 事件流而非 SDK 封装，实现逐事件级别控制；usage 和 stop_reason 只在最后的 message_delta 事件中才是确定值
- [具体机制] Tombstone Messages：流式传输中途失败时标记为"墓碑"消息，UI 层在重试前先移除，确保对话历史干净
- [具体机制] 智能退避重试 withRetry()：指数退避 + 最多10次重试 + 尊重 Retry-After 头 + 529过载用更长等待 + 401触发OAuth刷新 + 400解析token溢出信息
- [具体机制] 回退模型：Opus 连续3次529过载错误后静默切换到 Sonnet，可用性优先于能力
- [具体机制] Transcript-First 模式：调用模型 API 前先把用户消息持久化到本地磁盘，崩溃可恢复
- [具体机制] Token 预算跨压缩不重置：通过 task_budget.remaining 字段把压缩前消耗的预算带到压缩后
- [具体机制] 循环结束后三个静默后台任务：executePromptSuggestion()（生成建议）、executeExtractMemories()（提取记忆写入MEMORY.md）、executeAutoDream()（KAIROS相关自主探索），bare mode下跳过

## non_obvious_points
- 压缩不是续命——预算跨压缩边界不重置，防止 Agent 通过不断压缩来无限运行。这意味着压缩是为了释放上下文空间，不是为了重置工作预算。大多数人直觉上会认为"压缩了就等于开了新对话"，但 Claude Code 明确拒绝了这个设计。 — 为什么这不显而易见：压缩通常被理解为"给对话续命"，但预算管理和上下文管理是两个独立系统，压缩只影响后者
- transition 字段是循环的"自我审计"机制——每次续行都必须给出理由，不是调试用的，而是决策依据。这让整个循环的行为变成了可追踪、可审计的状态机，而不是一个黑盒 while(true)。 — 为什么这不显而易见：大多数 while(true) 循环用 break 退出就完事了，很少有人会要求循环每次迭代都"解释自己"
- 流式传输在 Agent 场景下不是 UI 优化，而是并行执行的基础设施——边生成边执行让每轮迭代节省秒级延迟，多轮循环累计到分钟级体验差异 — 为什么这不显而易见：大多数人把流式传输等同于"打字机效果"的用户体验优化，而非架构级的性能设计

## tradeoffs_and_limits
- 回退模型的能力降级 — 具体表现：Opus 连续3次过载后静默切换 Sonnet，用户可能不知道正在使用较弱的模型，在复杂任务上可能产出质量下降。可用性和能力之间的权衡是显式的设计决策，但对用户透明度不足
- 乐观策略的重试成本 — 具体表现：默认8K输出限制意味着需要长输出的任务必须先触发一次失败再升级，浪费一次API调用；五级预处理逐级尝试在极端情况下可能造成延迟叠加
- Agent Loop 的所有精密控制都依赖 Anthropic 自家 API 的特性 — 具体表现：SSE 原始事件流消费、服务端 prompt 缓存感知、cache editing API——这些和 Anthropic 基础设施深度耦合，第三方开发者用其他模型供应商无法复制同等精密度
