# Agent Loop凭什么只用14种状态？

## Hook
上一期我们拆了 Claude Code 的全景架构，得出了一个结论：核心循环只有不到两千行代码，但周围的 Harness 系统超过四十七万行。

那这个核心循环到底长什么样？今天我把它逐步拆开，从 while(true) 的每一步到五级预处理管道。不讲对比，不讲竞品，只聊这个循环本身。

## Agent Loop 的基本直觉
如果你用过 Claude Code，或者任何 AI 编码 Agent，你会感觉它在"思考"。它读代码、跑测试、改文件、再跑测试、再改文件，直到任务完成。

这种感觉的背后，就是 Agent Loop。

用最通俗的话讲，它就是一个不断重复的决策循环。看当前状态，调用模型让它决定下一步做什么，如果模型说要用工具就执行工具，把结果喂回去，让模型再决定。直到模型说"我完成了"，或者资源耗尽。

这个模式不只是 Claude Code 在用。Cursor 的 Agent Mode，GitHub Copilot 的 Workspace，Devin——它们的核心都是某种形式的 Agent Loop。

差别在哪？在于循环本身有多简单，循环周围的系统有多精密。Claude Code 的设计哲学很极端：把循环做到极致简单，把所有复杂性推到外围。

## QueryEngine：两层分离的设计
在源码里，Agent Loop 的实现叫 QueryEngine。它分成两层。

上层叫 Session Layer，负责跨轮次的状态管理。你和 Claude Code 进行一场持续对话的时候，Session Layer 在维护整场对话的累计 token 使用量，追踪哪些权限请求被你拒绝过，下次就不再重复请求。

下层叫 Turn Layer，这是真正的执行引擎。大约一千七百三十行代码的核心 while(true) 循环。每次你输入一条消息，Turn Layer 就启动一轮循环：预处理你的输入，组装上下文，调用模型，模型要用工具就执行，把结果送回去，继续循环，直到模型说完成了或者触发终止条件。

两层分离的好处很直接。Session Layer 只关心对话级别的状态，Turn Layer 只关心当前这一轮怎么把事情做完。各管各的，互不干涉。

## 14种状态转换：循环的自我审计
这个 while(true) 看起来简单，但实际上每一次迭代，循环都携带一个类型化的 State 对象。里面有当前的消息历史、自动压缩的追踪状态、输出限制恢复的计数器。

但最精妙的是一个叫 transition 的字段。它记录的是"为什么这次循环要继续"。

这不是一个调试用的日志。它是整个循环的决策依据。每次循环继续时，系统必须明确说出理由。这让循环的行为完全可追踪、可审计。

Claude Code 定义了七种续行原因。我挑几个最有代表性的讲。

第一个叫输出限制升级。模型第一次命中八千 token 的输出上限时触发。系统不报错，而是把限制升级到六万四千，然后重试。为什么默认是八千而不是一上来就给六万四？因为大部分回答不需要那么多。用低限制开始可以节省成本，只有真正需要时才放开。这是一种乐观策略——先假设简单情况，再逐步升级。

第二个叫被动压缩重试。API 返回 413 错误，说明对话历史超过了模型的上下文窗口。系统执行一次紧急压缩，然后重试。不是报错退出，而是自己想办法腾出空间。

第三个是最常见的：模型的响应里包含工具调用请求。执行工具，送回结果，继续循环。

同样，终止也有七种明确的原因。正常完成、达到硬性限制、模型调用出错、压缩后仍然超限、流式传输中断、Hook 阻止继续、图像处理出错。

七种续行加七种终止，总共十四种显式的状态转换。没有任何模糊的"可能继续也可能停止"。每一次迭代，系统都能精确说出"我为什么在这里"。

这就是"简单循环加精密控制"的具体体现。

## 五级预处理管道：模型看到什么比模型说了什么更重要
大部分人在思考 Agent Loop 的时候，注意力都在"调用模型、执行工具"这个主循环上。但 Claude Code 在每次调用模型之前，有一个精密的五级预处理管道在默默工作。

这五级从轻到重排列。能用规则解决的不调模型，能局部清理的不全局压缩。

第一级叫工具结果预算。如果上一轮的工具执行产生了大量输出，比如读了一个很大的文件，这一步会预算控制总量。不调模型，纯规则。

第二级叫片段裁剪。移除对话中已经过时的片段。通过 feature flag 控制开关。同样不调模型。

第三级叫微压缩。这就是我们第一期提到的"不调用模型的压缩"。它能感知 Anthropic 服务端的 prompt 缓存状态，选择最优的清理路径。零 API 调用成本。

第四级叫上下文坍缩。把旧的对话轮次"归档"成投影视图。对话的细节被压缩，但结构性信息被保留。

第五级才是自动压缩。只有当对话接近上下文窗口的天花板时才触发。触发阈值很精确：对于两百K token 的模型，压缩在大约十八万七千 tokens 时触发，也就是百分之九十三点五的利用率。预留一万三千 tokens 的缓冲区。生成最多两万 tokens 的结构化摘要。压缩后，工作预算重置为五万 tokens。

我认为这个设计里最值得学习的原则是：预处理比后处理更重要。"模型看到什么"比"模型说了什么"价值更高。把工程投入放在上下文组装上，回报比放在输出解析上更高。

## 流式传输：不是打字机效果，是并行执行的基础设施
大部分 AI 应用的工作模式是发请求，等模型生成完，拿到完整响应，再处理。但 Claude Code 不是这样。

Claude Code 直接消费原始的 SSE 事件流，而不是使用 SDK 封装好的高级流接口。为什么要这么麻烦？因为这样可以实现逐事件级别的控制。

一个关键细节：token 使用量和停止原因，在最后的 message delta 事件中才是确定的。它们在流的过程中会被就地修改。这意味着你不能在收到任何一个中间事件时就做最终决策。

但更有意思的是流式工具执行。当这个 feature gate 开启时，模型还在生成响应的同时，系统就已经开始执行工具了。工具调用被分成批次，每批最多十个工具并行执行。并行执行的工具之间上下文隔离，串行执行的工具立即传播上下文修改。

也就是说，Claude Code 不是"想完了再做"，而是边想边做。模型在生成后半段回答时，前半段提到的工具调用可能已经执行完毕了。

还有一个优雅的细节。如果流式传输在中途失败了怎么办？系统不会丢掉已经接收到的部分，而是把它标记为 tombstone 消息——一种"墓碑"标记。UI 层看到墓碑消息就知道"这条消息不完整，重试前先移除它"。对话历史始终干净，不会出现半截话或重复内容。

这里有一个不太直觉的认知。流式传输在 Agent 场景下不是 UI 优化，而是并行执行的基础设施。如果你能在模型生成响应的同时就开始执行工具，每个循环迭代都能节省几秒到十几秒的延迟。对于需要多轮循环的复杂任务，累计起来就是分钟级的体验差异。

## 错误恢复：先自动重试，最后才报错
一个在生产环境中运行的 Agent，必须能优雅地处理各种错误。Claude Code 的做法是分层恢复，每一层都有明确的上限。

网络错误、API 过载、认证失效，系统有一套完整的重试机制叫 withRetry。指数退避，每次重试的等待时间按指数增长加上随机抖动。最多十次重试。如果 API 返回了"多久后再试"的提示，按提示来。529 过载错误用更长的初始等待。401 认证过期时自动刷新 OAuth token。400 错误时从响应中提取 token 数量信息，用于下一次压缩决策。

这里有一个值得关注的设计。如果 Opus 模型连续出现三次 529 过载错误，Claude Code 会静默切换到 Sonnet 模型作为回退。系统在能力和可用性之间做了一个明确的权衡——宁可用一个稍弱的模型，也不让用户等待或报错。

但这也是一个 tradeoff。用户可能并不知道正在使用较弱的模型。在复杂任务上，Sonnet 的产出质量可能会下降。可用性优先的策略换来的代价是透明度不足。

还有一个模式叫 Transcript-First。在调用模型 API 之前，系统就先把用户消息持久化到本地磁盘。即使进程在 API 调用过程中崩溃，对话历史也不会丢失，下次启动可以从断点恢复。先写日记，再做事。简单但关键。

## Token 预算管理：知道什么时候该停
一个 Agent 可以无限循环，但 token 不是无限的。Claude Code 的预算管理系统解决了一个微妙的问题：怎么判断模型是"还在高效工作"还是"在空转浪费 token"？

系统用了一套双阈值的停止机制。

第一个叫完成阈值。当百分之九十的预算已经被消耗，系统认为工作基本完成。

第二个叫递减阈值。如果一轮循环只产生了不到五百个 token 的输出，系统认为没有实质进展。

两个条件的组合判断是：连续三次以上续行，每次产出低于五百 token，就停止。不是继续烧钱。

这个机制防止了一种常见的 Agent 陷阱——空转。模型不断循环，每次只做一点微小的修改，消耗大量 token 但实际上没有推进任务。

还有一个容易被忽略的细节。当对话被压缩时，token 预算不会重置。系统通过 task budget remaining 字段，把压缩前已经消耗的预算带到压缩后。

这个设计特别有意思。大多数人直觉上会认为"压缩了就等于开了新对话"，预算应该重置。但 Claude Code 明确拒绝了这个设计。压缩是为了释放上下文空间，不是为了重置工作预算。预算管理和上下文管理是两个独立的系统。

## 循环结束之后：静默的后台学习
模型说"我完成了"之后，故事并没有结束。

循环结束后还有三个静默的后台任务在运行。第一个生成"顺便说一句"类型的建议。你有时候会看到 Claude Code 在完成任务后主动提一个相关建议，就是这个在工作。

第二个从刚才的对话中提取结构化事实，写入记忆文件。项目结构、用户偏好、任务进度，这些被持久化下来，下次对话可以用。

第三个和 KAIROS 功能相关，做自主的后台探索。

这些后台任务在精简模式下会被跳过。也就是说，Claude Code 在每次正式对话结束后，都在悄悄地学习和积累。只是你看不到。

## Synthesis
回过头来看，上一期全景篇我们说核心循环简单、Harness 复杂。今天拆开这个循环之后，发现"简单"本身就是一种精密的设计。

while(true) 里面只做三件事：组装上下文、调用模型、执行动作。但这个循环外面，五级预处理管道控制模型能看到什么，十四种显式状态转换确保每次迭代都有据可查，流式传输让工具执行和模型推理并行进行，分层错误恢复让系统在出错时自己想办法而不是直接报错，双阈值预算机制让系统知道什么时候该停。

Agent Loop 的力量不在 while(true) 里面写了什么，而在 while(true) 外面挡住了什么。

## Closing
如果你在做自己的 Agent 产品，这期里有几个可以直接借用的设计：给你的循环加一个 transition 字段让每次迭代自我解释，建立分级预处理管道而不是无脑把所有信息塞进上下文，设计双阈值的停止机制防止空转。

这些不是理论，是 Claude Code 源码里正在运行的工程实践。
