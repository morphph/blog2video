# AI 看大代码库, 不是用 RAG

[SLIDE 1: cover] (0:00 - 0:51)

Anthropic 自己发了一篇博客，标题叫"Claude Code 在大型代码库里的工作机制"。里面有一句话我反复看了好几遍。他们说，在百万行代码、几千个工程师的活跃项目里，embedding 那一套行不通。所以 Claude Code 干脆，不建索引。今天不聊宏观的 harness 概念——只聊这个反直觉的判断，以及它在工程实操上逼出来的三个具体动作。

[SLIDE 2: principle] (0:51 - 2:18)

先把这件事讲清楚。市面上几乎所有"理解整个代码库"的 AI 工具，走的都是 RAG 这条路：把整个仓库切片、嵌入、塞进向量数据库，查的时候按相似度捞回来。听起来很合理。

但 Anthropic 在真实客户那里看到了什么呢？百万行的 monorepo，几十年的遗留系统，几千个工程师同时往里提交。Embedding pipeline 重建索引是要时间的。当一个开发者发起查询，那个索引反映的代码状态，已经是几周前、几天前，甚至几小时前的了。

注意这个时间尺度。不是几分钟的延迟可以忽略，是小时级、天级、周级的脱节。在一个每分钟都有人合并 PR 的代码库里，这意味着 AI 看到的"代码库"，已经是一个不存在的过去。

[SLIDE 3: image] (2:18 - 4:04)

Anthropic 的选择很硬：既然索引追不上提交，那就不建索引。

Claude Code 在大代码库里怎么找东西？跟一个工程师一模一样。直接遍历文件系统，打开目录，用 grep 搜，跟着引用跳过去。没有向量库，没有 chunking，没有云端索引。每一个开发者机器上跑的，都是活的代码库本身。

那符号级的精度怎么办？常见函数名 grep 一下能搜出几千条匹配，模型把 context 烧光也看不完。所以再叠一层 LSP——就是你 IDE 里那个"跳到定义""查找所有引用"背后的协议。Claude 直接复用工程师天天用的那套基础设施，go-to-definition 跟跳、find-references 跟着追，全部基于实时的代码状态。

这是一种很朴素的胜利。当索引模式被规模击穿的时候，最古老的工具——grep 和目录遍历——反而活了下来。

[SLIDE 4: principle] (4:04 - 5:54)

但 agentic 搜索有一个前提：Claude 得知道从哪里开始找。所以怎么布置上下文文件，就成了决定性的工程动作。这里有一个很反常识的判断。

直觉是什么？monorepo 的所有工具——IDE、build system、CI——都假设你从根目录入手。一份配置写在 repo 最上面，看起来才合理。

但 Anthropic 的建议正好相反。CLAUDE.md 应该初始化在子目录里，不是仓库根。原因是 Claude 在打开一个文件的时候，会自动沿目录树一路往上走，把路径上每一个 CLAUDE.md 都加载进来。你在子目录写局部规范，根目录的全局上下文一点不丢。但反过来，把所有东西堆在根目录，每个 session 都被无关信息淹没。

这个判断不只是布局技巧。它的本质是承认大代码库根本没有"全局视角"——每个工程师每次工作的，永远是其中一小块。Claude 也一样。

[SLIDE 5: principle] (5:54 - 7:45)

第二个推论更扎心。配置不是写完就放着的资产。它是会主动衰减的负债。

什么意思？你今天为了绕过模型某个短板，在 CLAUDE.md 里写了一条指令——"遇到这种情况要先做 X 再做 Y"。三个月后新模型发布，那个短板补上了。但你的指令不会自动消失。它还在那里，强迫一个本来可以一步到位的模型，走那条为旧模型设计的弯路。你以为帮它记性的笔记，反而成了脚镣。

Skill 也好，hook 也好，所有为补丁而生的配置，到了能力更强的模型上，全都变成 overhead。原文里有一句话我记得很清楚：为当前模型写的指令，可能会反过来跟未来的模型作对。

所以 Anthropic 给出的节奏是：每 3 到 6 个月一次完整的配置 review，主要模型发布之后再做一次。这不是建议，这是把"配置维护"变成一项常态化的工程职责。

写完就忘的 CLAUDE.md，三个月后就是你这套系统里最大的债。

[SLIDE 6: principle] (7:45 - 9:38)

第三个推论是关于 hooks 的，我觉得最有意思。

业界对 hook 的主流理解是什么？防呆。在 Claude 要执行命令之前拦一下，别让它干坏事。这个理解没错，但格局小了。

Anthropic 直接点出来：hook 真正高价值的用法，是让整套配置自我进化。具体怎么做？挂一个 stop hook，session 结束的时候触发。让模型回头看刚才这一通操作，反思哪里走了弯路，然后主动提议——CLAUDE.md 里这一条是不是该改了，那一条是不是该加上。趁着上下文还热乎，让系统自己沉淀经验。

还可以反过来——start hook 在会话开始的时候动态加载团队相关的上下文。哪个工程师打开哪个模块，自动注入对应的规范，不用每个人手动配。

这个翻转的意义在哪？它把 hook 从"防 Claude 做错事"的安全层，升级成了一个元配置层。你不再是手动维护那份 CLAUDE.md——你是让系统帮你维护它。

[SLIDE 7: image] (9:38 - 10:48)

技术讲完了。原文里还有一个观察，我觉得对任何想推 AI 工具的公司都有用。

铺得最快的那些组织，有一个共同点：在向所有人开放之前，先有一两个人——有时候真的就是一个人——把 tooling 提前搭好。有一家公司，两个工程师做了一套 plugin 和 MCP server，新人入职第一天打开 Claude Code，所需的上下文和能力全都在那里。

听起来不奇特，但反过来想就知道分量。卡点从来不是缺人，是没有人愿意花那个时间去做"地基"。一个愿意提前做的人，撬动的是几千人后续的产出效率。

[SLIDE 8: image] (10:48 - 12:18)

诚实地讲代价。Agentic 搜索在小代码库上其实不如 embedding。Embedding 是常数级响应，agentic grep 每次都要花 token 实时去找。这套方案的优势只在"索引追不上提交"的规模下才显现。

子目录初始化也有协作成本——每个子目录都得有人写 CLAUDE.md 并维护本地命令，比一个人在根目录写一份要费力。配置每 3 到 6 个月 review 一次，意味着你要把这件事列入团队的常态工程预算。

还有，这套方法默认你的代码库是常规工程环境：Git 管控、标准目录结构、工程师是主要贡献者。如果你在做游戏引擎，大量二进制资源；如果你用非常规的版本控制；如果非工程师也在往代码库里提交，那都需要额外的适配。

[SLIDE 9: principle] (12:18 - 13:53)

把这一切拉回来看，大代码库里的 AI 协作，最反直觉的结论其实只有两条。

第一条，你的 AI 不是靠 embedding 看懂代码库的，它靠的是把代码库变得 grep-friendly。文件结构清晰、命名一致、子目录有局部规范——这些"老派"的工程纪律，反而是 AI 时代最有用的资产。

第二条，配置不是一次性投入，是活的。CLAUDE.md 会衰减，hook 应该自我进化，旧补丁会拖垮新模型。你以为帮模型记性的那份文档，三个月不动，就开始让新模型变笨。

所以与其问"我们要不要用 RAG"，不如问两个更接地气的问题：我的代码库本身够不够 grep-friendly？我的 CLAUDE.md 还活着吗？这两件事做对了，下一代模型一发布，你的团队几乎是零成本接得住的。

[SLIDE 10: summary] (13:53 - 14:30)

如果你的团队在用 Claude Code，今晚就可以做两件事。第一，看看你的 CLAUDE.md 是不是堆在根目录——挪到真正相关的子目录里去。第二，翻翻它的修改时间，如果超过半年，那就坐下来重写一遍。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
