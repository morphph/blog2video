# 51万行泄漏，AI Agent靠什么赢？

## Hook

今天聊一个刚刚发生的大事。Claude Code，51万行源代码，全部泄漏了。我花了大量时间全部读完。今天不聊怎么泄漏的。只聊最重要的结论。

## Brand Intro

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。今天我们精读的是 Claude Code 泄漏的完整源码。

## 事情是怎么发生的

简单交代一下背景。3 月 31 日凌晨，Anthropic 发布 Claude Code 的例行 npm 更新时，不小心把一个将近 60MB 的 source map 文件打包进了公开包里。安全研究员在凌晨发现了它，几个小时之内代码被镜像到了几十个 GitHub 仓库。泄漏规模超出预期。将近 48 万行 TypeScript 代码，42 个以上的内置工具，44 个未发布的 feature flag。

这是我们第一次能完整看到，一个全球使用率最高的 AI 编码 Agent，内部到底长什么样。

## 一个先亮出来的核心结论

我读完这份源码之后，有一个结论越来越清晰。Claude Code 的核心竞争力不在模型，在模型周围那套精密的控制系统。

这不是客气话，是可以用代码行数验证的事实。

Claude Code 最大的单一模块叫 Query Engine，46,000 行代码。但它的核心逻辑，就是那个让 Claude 真正"思考"的部分，实际上只有大约 1,296 行。剩下的 45,000 行全在处理流式传输、错误恢复、缓存管理、权限检查。

一句话：Claude Code 用了不到 2,000 行让模型"思考"，用了超过 47 万行让思考变得可靠、安全、可控。

如果把模型比作引擎，那这 47 万行代码就是整辆车。引擎一样的情况下，谁的车造得好，谁就跑得快。这套"车身"在 AI 工程领域有一个专业名称，叫 Harness。

## 核心骨架：一个 while 循环

先从整体架构说起。Claude Code 的核心逻辑简单到让人意外。用户输入一句话，QueryEngine 组装系统提示词，调用模型，模型说要用工具就执行工具，把结果喂回去，继续循环，直到模型给出最终回答。

没有复杂的状态图，没有条件路由，没有 DAG 编排器。就是一个 while 循环。

但这个"简单"的循环周围，包裹着一整套精密的 Harness 系统。这才是 Claude Code 真正的竞争力。我把这套 Harness 分成三层来讲。

## 第一层：上下文管理

第一层解决的是"模型该看什么"的问题。

如果你只能从 Claude Code 学一样东西，学这个。Context engineering，上下文工程，是这份源码里工程含量最高的部分。也是我认为 2026 年 Agent 产品最被低估的核心能力。

上下文窗口有限，大约 200K token。但用户的对话可以无限长。Claude Code 设计了三级压缩来应对。

第一级叫微压缩。不调用模型，纯规则驱动，成本几乎为零。它按工具类型白名单，保留最近 N 个工具结果，把更早的结果清掉。但怎么清，有讲究。

调用 API 的时候，Anthropic 会把你发过去的 prompt 前缀缓存在服务端。下次请求如果前缀一样，就不用重新处理，省钱省时间。所以微压缩在清理旧结果的时候，要考虑一个问题。我这一刀下去，会不会把服务端的缓存搞失效？

如果用户一直在连续对话，服务端缓存还在，微压缩就走一条精细路径。通过 cache editing API 告诉服务端把某些工具结果删了，但不动 prompt 前缀，缓存继续有效。如果用户离开了一段时间回来，服务端缓存早就过期了，那就没必要小心翼翼了，直接把旧的工具输出替换成一个占位符。

这里面藏着一个反直觉的经济学权衡。直觉上你会觉得"删旧内容省 token"总是对的。但如果删的方式破坏了缓存前缀的连续性，后续所有请求都会 miss cache，成本和延迟反而大幅上升。所以 Claude Code 宁可用更精细的 API 操作，也不简单粗暴地替换。光这一个微压缩，源码里就有三条执行路径和两种清理策略。

第二级叫会话记忆压缩。它不做对话摘要，而是从对话中提取结构化事实。项目结构、用户偏好、任务进度。这些事实被持久化到本地的记忆目录里。提取的是事实，不是叙事。

第三级才是完整压缩。用一次独立的模型调用，把整段对话历史总结成一条精简的上下文边界消息。之前的消息从模型视野中移除，但 UI 层保留完整的滚动历史。

三级流水线，三个不同粒度的问题，三种不同成本的解法。微压缩去噪声，记忆压缩提事实，完整压缩清历史。

## 工具的智能加载

上下文管理不止压缩。Claude Code 内置了 42 个以上的工具，加上 MCP 扩展超过 80 个。但不是一开始就全部塞进上下文。核心工具启动时加载，扩展工具按需加载。如果工具输出太大，系统不会直接截断，而是存到外部，给模型一个摘要加一个指针，让它按需取用。

所有这些设计都指向同一个原则。上下文窗口是稀缺资源。关键不是装不装得下，而是该不该装进去。

## 第二层：安全与约束

第二层解决的是"模型不能做什么"的问题。

Claude Code 可以直接在你的电脑上执行 bash 命令、读写文件、操作 git。这个能力极其强大，但也极其危险。它的安全不是靠 prompt 里写"请不要执行危险命令"来约束的。它有四种权限模式，从逐一确认到完全自动。每次工具调用都要过一个五步评估流水线。

这里面最聪明的设计是双层分类器。第一层叫 Bash Classifier，纯规则匹配，把只读命令自动放行，不调模型，速度极快。

第二层叫 YOLO Classifier。名字很随意，实现一点都不随意。它是一个完整的 LLM-as-Judge 系统，用独立的模型调用来审查主 Agent 的每一个操作。而且有两阶段架构。第一阶段快速判断，放行就直接过。只有判断要拦截时，才进入第二阶段完整推理。这大大减少了误杀率。

错误处理策略是宁可误杀不可放过。解析失败、API 错误，全部默认拦截。这个设计体现了一个核心原则。生成和评估必须分离。主 Agent 负责"想做什么"，分类器 Agent 负责"能不能做"。

但这里有一个结构性的张力。用户选择完全自动模式就是为了不被打断。但分类器的保守策略意味着仍会频繁拦截。自动化程度越高，每次误杀的体验伤害就越大。

## 硬编码的安全底线

除了分类器，源码里还有 23 条编号的 bash 安全检查规则，防御零宽空格注入、IFS 空字节注入等攻击。其中至少一条来自 HackerOne 安全审计中发现的真实漏洞。再加上大约 8,000 行的 Hooks 系统，在工具调用前后、HTTP 请求前后都可以挂载回调函数做拦截。

这一层的核心思想是什么？Prompt 里的规则是建议，代码里的规则是法律。

## 第三层：多 Agent 协作

第三层解决的是"一个模型不够用怎么办"的问题。

Claude Code 的多 Agent 系统叫 Swarm。一个 Leader 加多个 Teammate。Leader 拆解任务、分配、收集结果。Teammate 共享权限，但上下文严格隔离。Leader 只看到指令和最终结果，中间过程全部看不到。

但光隔离还不够。源码里有一个 Team Memory Sync 机制，关键发现会同步回 Leader 的记忆目录，其他 Teammate 也能看到。上下文隔离加关键信息同步，解决了 multi-agent 最常见的两个问题。信息爆炸和信息孤岛。

还有 Coordinator Mode。开启后 Claude Code 变成纯粹的编排器，自己不干活，只拆任务、派任务、收结果。它的系统提示词里有一句话值得记住。Do not say based on your findings. Read the actual findings and specify exactly what to do. 编排器不能偷懒委派，必须理解每个子任务的结果再给下一步指令。

## 隐藏在 feature flag 后面的未来

源码里还藏着几个尚未发布的系统，更有意思。44 个 feature flag，功能已经完整构建，但在公开版本中被关闭。

投机执行，源码里叫 Speculation。Claude 回答完你的问题后，在你还没按回车之前，系统就已经在后台执行它预测你会做的下一步了。所有写入重定向到沙箱，接受就合并，拒绝就丢弃。一轮完成后立即开始下一轮，试图始终领先你好几步。

不过要注意，这个沙箱方案只在文件系统内可撤销的操作中成立。发 HTTP 请求、写数据库这类不可逆操作，沙箱没办法保护。

再说 KAIROS。当前所有 AI 工具都是被动的，你问一句它答一句。KAIROS 要把 Claude Code 变成一个永远在线的后台 daemon。系统按固定间隔向 Agent 发送 tick 提示，Agent 自主决定要不要主动做点什么。还配了一个叫 Dream 的后台记忆整理引擎，空闲时自动整合和修剪记忆。这是从"工具"到"同事"的转变。

ULTRAPLAN 把复杂的规划任务卸载到云端容器，运行 Opus 4.6，最长跑 30 分钟。它和 Manus 的区别很精准。Manus 把整个执行都放云端，ULTRAPLAN 只把规划放云端，实现仍然在本地。规划需要深度思考但不需要本地文件系统，实现需要本地环境但不需要 30 分钟推理。拆开放到各自最合适的地方。

## 一些让人意外的内部数据

泄漏还暴露了一些意外的内部数据。

最新 Capybara v8 的虚假声明率是百分之 29 到百分之 30，而之前 v4 版本只有百分之 16.7。新版本反而退步了。这说明更强的模型可能更"自信"地产生虚假声明。这恰恰解释了为什么 Harness 不会随着模型进步而减轻。模型越强，越需要独立的约束系统来对冲新增的失败模式。

Anthropic 内部大约百分之 70 到百分之 90 的代码由 Claude 自己编写。47 万行 Harness 的维护成本极高，而且和特定模型版本深度耦合。每次模型升级都可能需要重新校准。人类已经很难独立维护这个规模了。

源码里还有反蒸馏防御。开启后会在 API 请求中注入虚假的工具定义，污染竞争对手的训练数据。AI 产品之间的竞争已经深入到协议层面了。

## Synthesis

回过头来看，Claude Code 的每一个子系统都在做同一件事。在概率性的模型周围，构建确定性的工程系统。

模型可能输出错误的参数，Zod schema 拦截它。模型可能执行危险的命令，权限分类器阻止它。模型可能在长对话中迷失，压缩流水线为它清理上下文。没有一行代码试图让模型更聪明。所有的工程投入，都在让模型周围的系统更可靠。

Claude Code 用 1,296 行让模型学会思考，用 47 万行让思考变得可靠。你的 Agent 产品的护城河不在引擎多强，在你围绕引擎造了一辆什么样的车。

## Closing

如果你正在做 Agent 产品，认真想想这个问题。你在模型周围构建了什么样的 Harness？上下文怎么管理？安全边界在哪？这些才是决定产品天花板的地方。
