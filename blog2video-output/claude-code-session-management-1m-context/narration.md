# 你的AI编程效率，输在上下文管理上？

## Hook

Claude Code 刚升级到 100 万 token 的上下文窗口。很多人觉得，窗口大了，终于不用操心上下文管理了。但 Claude Code 团队跟大量用户聊完之后发现，恰恰相反——窗口越大，用得差的人和用得好的人，差距反而越大。差距出在哪？不是提示词写得好不好，而是每次 Claude 回复完之后，你做的那个决定。

## Brand Intro

这里是精读AI。今天我们来详细解读一下，Claude Code 官方团队是怎么建议你做 Context Management 的。

## 上下文窗口不是越大越安全

先说一个基本概念。上下文窗口，就是模型在生成回复时能"看到"的全部内容。包括系统提示词、你们之间的对话历史、每一次工具调用和它的输出、每一个被读取的文件。Claude Code 的上下文窗口现在是 100 万 token。

听起来很大对吧？但这里有一个反直觉的事实。上下文不是免费的。有一个现象叫 context rot，上下文腐烂。意思是，随着上下文越来越长，模型的注意力被分散到更多 token 上，老旧的、不相关的内容开始干扰当前任务。模型的表现会下降。

100 万 token 的窗口，让你能做更长的任务，比如从零搭一个全栈应用。但它同时也让 context rot 更隐蔽。因为你不会撞到硬性的上下文限制，你感觉不到问题，但模型的判断力已经在悄悄变差了。

## 每个转折点都是一次选择

这篇文章里我觉得最有价值的一个认知是：每次 Claude 完成一个回合之后，你其实站在一个分叉路口。你有五种选择。

第一种，继续对话。最自然，但不一定最优。第二种，Rewind，双击 Esc 键，回退到之前某条消息重新来过。第三种，/clear，清空会话，自己写一段简报开始新对话。第四种，Compact，让模型总结当前对话然后继续。第五种，Subagent，把下一块工作委派给一个有独立上下文的子代理。

大多数人只用第一种。但高手会根据情况在这五种之间切换。这就是分水岭。

## Rewind 比纠错更聪明

如果只能推荐一个习惯，Thariq 说他会推荐 Rewind。

来看一个具体场景。Claude 读了五个文件，尝试了方案 A，失败了。你的直觉反应是什么？打一句"这个不行，试试 X 方案"。对吧？

但更好的做法是：Rewind 到 Claude 读完文件之后那个节点，重新提示。告诉它"方案 A 行不通，foo 模块没有暴露那个接口，直接用方案 B"。

区别在哪？纠错的方式，会把方案 A 的所有工具调用、所有输出都留在上下文里。这些内容已经被证明是无用的了，但模型还是要花注意力去处理它们。这不仅浪费 token，还在主动制造 context rot。

而 Rewind 直接把失败路径从上下文中删掉了。上下文更干净，模型更聪明。在日常对话里，"指出错误让对方改"是最自然的反应。但在有限的上下文窗口里，删除比修正更高效。

还有一个很巧妙的功能叫 summarize from here。让 Claude 把当前学到的经验总结成一段交接消息。相当于未来的自己给过去的自己写封信：我试过这条路走不通，原因是什么，建议直接走另一条。

## Compact 和 /clear 的真正区别

当会话变长了，你有两种减负方式。Compact 或者 /clear 重新开始。它们看起来差不多，但本质区别很大。

Compact 是让模型来决定什么重要。它会总结对话历史，用摘要替换掉原始内容。好处是你不用动手，模型可能比你更全面。坏处是它是有损的，你在信任模型的判断力。

你还可以给 Compact 加指令引导，比如 /compact focus on the auth refactor, drop the test debugging。这样模型就知道该保留什么、该扔掉什么。

/clear 则是你自己来决定什么重要。你手动写下"我们在重构 auth 中间件，约束是 X，相关文件是 A 和 B，方案 Y 已经排除了"，然后开一个全新的会话。更费力，但上下文完全是你控制的。

核心区别不是自动还是手动，而是谁来做判断。

## Bad Compact 的真正原因

如果你跑过很多长会话，你可能遇到过 Compact 效果特别差的时候。为什么？

原文给了一个特别好的例子。你花了很长时间在调试一个问题，autocompact 自动触发了。因为会话一直在聊调试，摘要自然也聚焦在调试内容上。然后你的下一条消息是"顺便把 bar.ts 里那个警告也修了"。

但那个警告只在对话里被提到过一次，已经被摘要丢掉了。

这里最扎心的地方在于：compaction 发生在模型最笨的时刻。上下文越长，context rot 越严重，模型的判断力越差。而 compaction 恰恰在上下文最长的时候触发。最关键的摘要决策，由最差状态的模型来完成。这是一个结构性的恶性循环。

那怎么办？100 万 token 的窗口给了你一个时间差。你不用等到 autocompact 被动触发。你可以在上下文还不太长、模型还聪明的时候，主动 /compact，告诉它接下来你要做什么。

## Subagent 是上下文隔离器

最后说 Subagent。很多人把它理解成"并行执行"或者"分工协作"，但更准确的理解是：它是一种上下文隔离机制。

当 Claude 启动一个 Subagent 的时候，那个子代理拿到的是一个全新的上下文窗口。它可以做大量的中间工作，读文件、调试、反复尝试，最后只把结论带回来。所有中间过程不会污染你的主上下文。

判断要不要用 Subagent，原文给了一个很实用的 mental test：我需要这些工具输出本身，还是只需要结论？

比如"启动一个子代理，按照这个规范文件验证刚才的实现结果"。你不需要看它读了哪些文件、做了哪些对比，你只需要知道通过还是没通过。再比如"启动一个子代理去读另一个代码库的 auth 实现，总结它的方案，然后你自己用同样的方式实现"。中间的阅读过程可以很长，但你的主上下文只需要那份总结。

## Synthesis

回过头来看，这篇文章表面上在讲 Claude Code 的五个操作。但它真正在讲的是一个更深的认知：当你使用一个 AI 编程工具时，你管理的不是代码，而是注意力。

模型的注意力是有限资源。你往上下文里塞的每一段无用信息，都在消耗这个资源。Rewind 是在删除噪音，Compact 是在压缩信号，/clear 是在重置频道，Subagent 是在隔离干扰。这些操作的共同本质，都是在替模型管理注意力。

100 万 token 的上下文窗口不是让你不用管理上下文。而是让你终于有时间，在模型还聪明的时候，主动管理它。

## Closing

下次用 Claude Code 的时候，每当它完成一个回合，停一秒钟。问自己：继续对话，还是 Rewind？Compact，还是 /clear？这个一秒钟的决定，可能比你写什么提示词更影响最终结果。
