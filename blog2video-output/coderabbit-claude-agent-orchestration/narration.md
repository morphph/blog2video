# 每周审 200 万 PR，他们在 Claude Code 前加了一层

## Hook

你让 AI 写一段代码。它写了。能跑，单元测试也过了。但你一看——它解的根本不是你想问的那道题。这不是个例。CodeRabbit 每周帮 1 万 5 千个客户审 200 万个 PR，他们说，AI 生成代码最常见的失败，长这个样子。今天只聊一件事——他们怎么在 Claude Code 之前，再加了一层。

## 真正写错的，从来不是模型

CodeRabbit 是做 AI 代码评审的。每周 200 万个 PR 经过他们的系统——这个量级，意味着他们扫过的 AI 生成代码，可能比这个世界上任何一家公司都多。所以他们看到的失败模式，特别有代表性。

最常见的不是语法错误，也不是逻辑 bug。是"功能上完全正确、但跟用户想要的根本不是一回事"。代码能编译、单测能过、跑起来不报错——但它解的就是另一道题。

这是一个很反直觉的诊断。我们日常聊 AI 编码，焦点全在模型——模型够不够聪明、上下文够不够长、prompt 够不够花哨。但 CodeRabbit 的 VP of AI，David Loker，给了一个完全不同的答案。

他原话是这么说的："我们做开发越久，知识就越是被内化进脑子里。所有这些东西全在我们脑子里，我们就默认其他开发者也知道。"

他举了一个自己踩的坑。他想让 Agent 帮他做一个记忆系统。需求列了一堆，但漏写了一件事——这个系统该用什么方式登录。Agent 没问，自己脑补了一套实现。几个小时之后，Loker 一看，全是白干的。

听懂这个意思了吗？不是 Agent 蠢。是开发者自己，跳过了那些对他而言"显而易见"的事。AI 看不到你脑子里的东西。它只能在你没说的地方，自己猜。

## Plan Mode 不够，因为还要再上一层 Plan Mode

那 CodeRabbit 的解法是什么？

他们在 Claude Code 之前，又加了一个东西。一个独立的、规划层。这个层不写代码。它的工作就是把你的需求，翻译成一份特别精确的执行计划。

关键来了。Claude Code 自己是有 Plan Mode 的。Loker 特意澄清："这个规划系统不是要替代 Claude Code 的 Plan Mode。它是更高一层的编排，跑在 Claude Code 之前，目的是给 Claude Code 指一个又窄又准的方向。"

这句话信息量很大。它在说：单一工具自带的"规划"已经不够了。你需要在工具之上，再做一层规划。两层是分工的。下游那一层管"怎么写"，上游这一层管"到底在写什么"。

上游产出的不是一段 prompt。是一份可以协作编辑的 PRD——产品需求文档。它把团队的决策、上下文、隐含假设全部显式化，沉淀成一个文档。新人来了，看这份 PRD 就能进入状态。

我读到这里特别有感触。我们过去几年在被反复教育——AI 时代要做好 prompt engineering、要做好 context engineering。但 CodeRabbit 给的是一个更激进的版本：在工具的 Plan Mode 之上，再独立做一层产品级的规划系统。规划本身，要被当成一个工程模块来建设。

## 三个模型干三件事

那这个规划层内部长什么样？

CodeRabbit 把 Claude 全家桶拆开用了，按任务复杂度分发。整套规划层不是一个模型在跑，是三个模型在分工。

Opus 跑顶层。它是这个规划循环的总指挥，做最高层的策略理解——你想做什么、整体方向往哪儿走、有哪些大块需要分头处理。Sonnet 跑中间。它把 Opus 给出的方向，拆成一系列结构化的步骤，串成可以执行的工作流。Haiku 跑最底层那些范围很窄的活——比如 context 蒸馏，把一大块上下文压缩成精炼的几句话；比如某个具体字段的归类。

为什么要这么分？因为这三类活，对模型的要求完全不同。顶层策略需要的是判断力和宏观理解，必须用最强的模型。中层工作流编排需要的是结构化和稳定性，Sonnet 性价比最优。底层窄范围操作不需要太多推理，但被调用的次数特别多，成本敏感，Haiku 又快又便宜。

Loker 给了一个特别朴素的判据。原话是："如果 Haiku 在某个任务上能做得跟 Sonnet 一样好，我们就用 Haiku。"

听上去像废话，但这背后是一套真实的工程纪律。在生产环境里，每一次模型调用都是钱和延迟。你做一个规划系统，里面有几十次模型调用，你能不能把每一次都问一句："这一步真的需要 Opus 吗？还是 Sonnet 行？Sonnet 真的需要吗？Haiku 行不行？"

这个事知道是一回事，每个节点都真的去测、真的去切，是另一回事。CodeRabbit 是真的做了。

## 规划的抽象层级，是个超参数

接下来是这套系统里我觉得最有意思的一段。

CodeRabbit 单独搭了一套评估基础设施，专门评估"规划本身"的质量。手工调过的样本、人工巡检、加上一组 LLM judge——这些 judge 会从不同维度给一份 plan 打分。

打哪几个分？三个维度。一是生成代码的功能完备度。二是 scope creep——也就是范围有没有蔓延。三是 token 用量。

我想停一下，单独说一下第二个。scope creep。这本来是项目管理领域的词——一个项目原本要做 A，做着做着把 B、C、D 也吞进来了。CodeRabbit 把这个概念，搬进了对 AI 规划质量的自动评估里。

这意味着他们在 200 万个 PR 的数据里，看到 AI 规划有一个非常稳定的失败模式——它会偷偷扩张范围。你让它做登录，它顺手把注册也规划上了。这个倾向稳定到，他们觉得需要持续用一个独立的 judge 去监控。

然后是 plan 本身的抽象层级问题。Loker 说他们花了很多次迭代才找对地方。

太细的 plan，很快就 stale 了——一旦项目稍微变一点，整份 plan 就废了。但反过来，太粗的 plan 又给隐含假设留出了大量缝隙——AI 又开始脑补，又把开头那个"代码对了但解错题"的问题，搬了回来。

所以"plan 该写多细"，本身就是一个需要调的超参数。没有银弹。每个团队、每类任务，可能都得自己迭代。

## 把质量关，从代码搬到 plan

最后是 Loker 那句我特别想留下来的话。他说："plan 本身就变成了一道质量门槛。如果我们能保证这份 plan 在最一开始就质量过硬，下游的传导效应会非常显著。"

我读完整篇我的体会是这样——code review 的下半场，是 plan review。

过去十几年，软件工程的质量门槛在哪？在 PR、在 code review、在 CI。一段代码写出来，靠几道审查关把它过滤干净。

但在 AI 写代码的时代，等到代码已经写出来，再去做 review，已经太晚了。因为这时候的"错"，不是几行代码的事，是整个方向都跑偏了。审查再仔细，也只能告诉你"这段写得不对"，没法帮你把方向掰回来。

所以质量关必须前移。从评审已经写出来的代码，前移到评审还没开始写的那份 plan。CodeRabbit 整套架构，本质上是在做这件事。

这套打法当然不是免费的。多一层规划等于多一层延迟、多消耗多个模型的 token、还要团队搭配套的 eval 基础设施。规划层抽象层级这件事，得自己慢慢试。而且你得说服团队——在写代码之前，先经过一道 plan review。对很多习惯了"AI 直接出代码、人审 diff"的团队来说，这是一个流程上的改变。

但如果你正在生产环境里被那种"代码对了但解错题"的失败反复折磨——这套思路值得认真看一遍。

## Synthesis

我读完整篇，记住三件事就够了。

第一，AI 写代码最大的失败不是写错，是写对了别人没问的题。原因不在模型，在你脑子里那些没说出口的"显而易见"。

第二，Plan Mode 不够。你需要在工具的 Plan Mode 之上，再做一层独立的、产品级的规划编排。

第三，规划是可以被评估的。eval harness 不是只能给代码用的，给 plan 用，效果可能更明显——因为质量关一旦前移，整条下游都会跟着变好。

代码评审的下半场，是 plan 评审。AI 写错的那行代码，错从你没说出口的那一句开始。

## Closing

如果你也在用 AI 写代码、并且踩过那种"明明跑得通就是不对劲"的坑，今天可以做一件事——把你最近一次给 AI 的需求重新拎出来，问它一句："你觉得我哪几个地方没说清？这份需求里有哪些是隐含假设？"

把这一步做扎实，再让它动手。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
