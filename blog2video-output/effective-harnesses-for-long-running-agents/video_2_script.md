# 200个功能点？Agent这样一个个啃下来

[SLIDE 1: cover]

如果让你管理一个200多个功能需求的项目，但你的每个开发者只能工作几小时就永久失忆，你会怎么安排工作流？

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。

上期我们发现，即使是最强的Opus 4.5，连续工作也会失忆翻车——要么一次做太多爆Context，要么看到有代码就宣布完工。那怎么办？Anthropic给出了四个工程实践，让Agent真的能一个功能一个功能地啃下来。

[SLIDE 2: principle]

先说第一招：功能清单。

想象你开了一家餐厅，菜单上200道菜，每道都写清了怎么验收——摆盘对不对，味道够不够。新来的厨师不用猜该做什么，看单子就行。

Anthropic做的事一模一样。初始化Agent分析完需求后，生成了一个feature_list.json文件，里面列了超过200个具体功能，比如"用户点击新对话按钮，输入问题，按回车，能看到AI回复"。每个功能都带测试步骤，状态全标记为失败。

这里有个有趣的工程发现：他们一开始用Markdown格式写清单，结果Agent会偷偷删改里面的条目。换成JSON格式后，这个问题消失了——模型对JSON文件天然更"守规矩"。

同时，提示词里写了一句狠话："删除或修改测试是不可接受的。"Agent只被允许把状态从失败改成通过，不许动其他任何内容。

[SLIDE 3: comparison_cards]

清单有了，怎么执行？这就涉及到第二和第三招：增量开发加端到端测试。

过去的做法是让Agent一口气写完所有代码，然后跑单元测试看看对不对。问题是什么？单元测试只检查零件，不检查成品。Agent觉得函数能跑通，就标记完工，但用户打开页面一看，功能根本不能用。

Anthropic的做法是，每个Agent只做一个功能。做完之后，必须用Puppeteer MCP启动浏览器，像真人用户一样去点击、输入、翻页，确认功能真的能用，才能把状态改成通过。然后立刻git commit，写好提交信息，更新claude-progress.txt。

这样下一个Agent接手的时候，代码库永远是干净的，不会遇到上一个Agent留下的烂摊子。

不过也有局限。比如Claude无法看到浏览器原生alert弹窗，导致依赖弹窗的功能更容易出bug。这说明工具链的盲区，仍然需要人来兜底。

[SLIDE 4: checklist]

第四招是标准化启动流程。每个新Agent上线后，不是直接开始写代码，而是先跑一套固定步骤。

第一步，运行pwd，确认自己在哪个目录。第二步，读git log和claude-progress.txt，搞清前面做了什么。第三步，读feature_list.json，选一个最高优先级的未完成功能。第四步，运行init.sh启动开发服务器。第五步，用Puppeteer跑一遍基础功能，确认应用没有被上一个Agent搞坏。

这五步看起来简单，但省掉了大量Token。Agent不用花时间猜"我该做什么"和"代码怎么跑起来"，直接进入生产状态。

如果基础功能测试没通过呢？Agent会先修bug，而不是在破损的代码上叠加新功能。这个设计避免了问题像滚雪球一样越滚越严重。

[SLIDE 5: summary]

回顾一下这套方案的核心思路。让Agent高效工作，靠的不是更大的模型，而是更好的工程脚手架。JSON功能清单给Agent明确目标，增量开发避免贪多嚼不烂，端到端测试确保功能真的能用，标准化启动让每个Agent秒进状态。

你现在就可以在自己的Agent项目里试一试：建一个JSON格式的功能清单，规定每次只做一个功能，做完必须跑浏览器测试，做完必须提交代码和进度记录。
