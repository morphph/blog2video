# 18万年薪的三个员工，被一份订阅替代了？

## Hook

市面上"AI agent 替代员工"的教程一搜一百条。但几乎没有一条讲清楚那个最关键的机制——为什么三个 agent 各跑各的只是工具集合，加上哪一条线，它们才真正变成一个团队。我读到 Khairallah 这篇 solo founder 实战手册时，最有意思的不是"省了 18 万美金"那个煽情对比，是他把"agent 团队"这件事的拐点机制，难得讲透了一次。今天不聊每个 agent 要装哪些 MCP server——只聊三件事：为什么是 2026 年，关键机制在哪两条线上，边界在什么位置。

## 为什么是 2026 年这件事突然能跑了

先说一个反直觉的判断。这件事这一年突然能跑起来，跟模型变聪明关系不大。

过去两三年，大家也在喊"AI 替代员工"。但你打开看一眼，所谓的 agent 大多还是 GPT wrapper——一个聊天框，加几个 prompt 模板。它能帮你写邮件，但它读不到你的邮箱。它能帮你分析竞品，但它打不开竞品的网站。它能帮你拟周报，但它进不去你的项目管理工具。

它聪明，但它够不到你的东西。

2026 年真正的拐点是 MCP——Model Context Protocol。这套协议让 agent 第一次能稳定地"接触"你的工具栈。它能直接读你的 Gmail，能写进你的 Google Calendar，能查竞品公司的最新页面，能调用你的 CMS 发布内容。

注意博客里描述每个 agent 的能力时，作者不是在说"它的 prompt 写得多牛"。他在说"它通过 MCP 连了什么"。这才是关键。模型本身能力没翻天，但它从一个会聊天的盒子，变成了一个能动手的同事。

## 三个 agent，三种解放

在这个前提下，作者画了一张非常具体的三人小团队图。我用一段话带过，因为这不是这条视频的重点。

第一个是研究员 agent，盯竞品、盯趋势、盯机会，每周一早晨给你一份 brief，告诉你这周市场上发生了什么、你该做什么。第二个是内容 agent，从选题、初稿、编辑到全平台分发都包了，一个月帮你产出三十个内容点子和三十篇初稿。第三个是运营 agent，相当于你的 chief of staff，处理邮件分类、会议准备、周报输出。把每天本来要花一两个小时的杂活，压缩到十五分钟的快速 review。

听起来很美对吧。但这个分工本身，市面上一百条教程都讲过。真正的问题是——三个 agent 各自跑得再好，凭什么它们就是一个"团队"？

## 让 agent 变成团队的那条线

这是我读完这篇博客最想跟你聊的一段。

作者讲了一个具体的协作场景。研究员 agent 周一扫到一条情报：你的主要竞品发了一个新功能。这条情报立刻进入一个共享的 knowledge base。内容 agent 第二天开工前先读这个 base，发现了这条新情报，自动产出三篇回应内容——一篇分析、一条短视频脚本、一封邮件 newsletter。同一时间，运营 agent 也读到了，开始起草一封发给可能受影响客户的沟通邮件，等你早上来 review。

这条链上没有任何一个 agent 做了它原本职责之外的事。但你看，这就不是三把瑞士军刀了，这是一个会传话的小团队。

关键差别在哪里？在于它们共享同一份记忆。

很多人讲 agent 协作，默认的方式是"我把 A 的输出粘到 B 的输入里"。这是串联，不是协作。串联是脆弱的——任何一环手动断了，链路就死了。共享 knowledge base 不一样。它是一个所有 agent 都能读、都能写的中央备忘录。研究员发现的事实，不需要主动"传给"内容 agent，而是写进共享区，所有人下一次开工时自然读到。

我读完最深的判断是这个：决定一组 agent 能不能从工具集合升级成团队的，不是 agent 数量，不是模型聪不聪明，是 memory 拓扑。三个 agent 共享一份记忆，远比五个 agent 各自独立有用。所以如果你真要搭这套东西，最先该想清楚的不是 agent 怎么写，是这个共享记忆的 schema 长什么样——什么字段、谁写、怎么版本化、怎么避免污染。这才是工程的真正起点。

## 让 AI 内容不像 AI 的那个内循环

第二条关键机制，藏在内容 agent 里。

你一定见过那种一眼就能看出来是 AI 写的内容。空泛、套话、没有立场。大家通常把锅甩给模型——"AI 就是写不好"。但作者给了一个更精准的诊断：AI 内容之所以读起来像 AI，不是模型差，是人发了第一稿。

这句话我读到的时候停了一下。

什么意思？意思是，第一稿在哪个模型出来都差不多。差别在于发布之前，有没有一个评判机制把它再筛一遍。人类写手写完初稿会自己读两遍、改三遍、给同事看一眼。但大多数人用 AI 写内容时，第一稿出来直接就发了——根本没有评判这一步。

所以作者把内容 agent 设计成两个角色，硬是分开。

一个 agent 负责"写"，另一个 agent 负责"判断写得好不好"。后者按四个维度打分：voice match，语气是不是像你；hook strength，开头抓不抓人；value density，信息密度够不够；originality，有没有原创视角。任何一个维度低于阈值，自动打回去重写。这个内循环跑到所有维度都达标为止。

这才是内容 agent 真正的核心。它不是"会写"，是"会判断写得好不好"，并且会逼自己不达标就重来。

但故事还没完。作者强调了一句话我觉得非常成熟。AI 跑完所有质量门之后，你还要做最后一遍人工 pass。加进去的是什么？是个人故事、是行业内幕视角、是有立场的判断、是那种只有你能讲的话。

他用了一个非常准的比例——agent 处理 80% 的 production，你处理 20% 的 soul。注意这不是产能比例，是分工边界。production 是格式、变体、调度、跑量，可以完全交出去。soul 是个人立场、独家视角，不能交。一个 agent 设计得好不好，看它有没有把这条线画清楚——能不能识别"哪一步必须停下来等人"。

## 70-80% 这条诚实边界

讲到这里，整条 pitch 听起来都很美好。但博客里有一段我特别看重，因为它没有继续往上吹。

作者直接写了一句：这套方案大概能覆盖三个全职员工 70 到 80 的工作量，适用窗口大约是创业的前 12 到 18 个月。超过这个窗口，你需要的不是 agent 干更多，是真人。

他甚至列出了 agent 做不到的事——定价时的市场感觉、和受伤客户的情绪沟通、产品方向上的反直觉转向。这些事情共同点是什么？是判断、是共情、是创造性突破。这三样都是 agent 的硬边界。

我特别想强调一下，这个 70-80% 的数字不是谦虚，是边界。

很多人把 AI 的"替代率"理解成一个连续光谱，从 0% 慢慢往 100% 走。但我读完这篇之后觉得，更准的描述是两个不同性质区域的拼接——执行域里 agent 能做到 100% 替代，判断域里 agent 是 0% 替代。把这两块加权一平均，就是 70 到 80。

而 solo founder 阶段最妙的一点是什么？是这个阶段的工作里，本来就有相当大一块是纯执行——格式化邮件、整理周报、扫竞品页面、跑内容变体。这些事不需要判断力，agent 在这里是真正的 100% 替代。所以 70-80% 这个数字，恰恰是这套方案能成立的核心论点，而不是它的局限。

## 几个被忽略的代价

但既然讲到边界，还有几个代价要诚实地说。

第一，共享 knowledge base 是协作的力量来源，也是单点故障。任何一个 agent 写脏数据，三个 agent 一起喝毒。所以作者的隐含建议是，每个 agent 先单独跑两到三周校准，再连成一片，而不是三个一起上。

第二，"三周搭完三个 agent"听起来很爽，但它有一个隐藏前提——你得已经有清晰的品牌 voice 文档、ICP 画像、style guide、关键指标定义。这些前置文档本身的质量决定了 agent 输出的天花板。prompt 工程救不了一个想不清楚自己是谁的创始人。

第三，超过 12 到 18 个月之后，业务复杂度、人际关系深度、品牌叙事一致性这些维度上，70-80% 的覆盖率会持续往下掉。到某个点，必须开始招真人。这不是 agent 的失败，是 agent 设计上的硬边界。早点画清楚这条线，对所有人都好。

## Synthesis

回过头来看整件事。

solo founder 第一次有了"不雇人也能扩张"的真实选项，这一点是对的。但能让这件事真正跑起来的不是某个 agent 多聪明，而是两个机制——一个是共享 knowledge base，把三把瑞士军刀变成一个会传话的团队；另一个是内容 agent 里那个"写"和"判断写得好不好"分开的内循环，把 AI 内容从平庸第一稿拉到能直接发布的水准。

这两条线，是这篇博客真正值钱的部分，也是大多数 agent 教程根本不会讲到的地方。

2026 年最聪明的 solo founder 不是雇人，是建人。但能建成"团队"而不是"工具集"的，是那条让三个 agent 互相读到对方备忘的共享记忆线。

## Closing

如果你打算真的动手搭这套东西，给你三条带回家的判断。

一，先想清楚共享记忆的 schema，再写第一个 agent 的 prompt——拓扑决定上限。二，内容 agent 必须有自动质量门，把"写"和"评"拆成两个角色，否则你就是又生产了一台第一稿发布机。三，把 70-80% 这个数字记在心里——它告诉你哪些事可以完全交出去，哪些事必须自己做。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
