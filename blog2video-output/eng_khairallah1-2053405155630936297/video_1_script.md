# AI 输出像 AI 写的？你的 context 是空的

[SLIDE 1: cover] (0:00 - 0:57)

X 上有一篇 74 万阅读的长帖，作者叫 Khairallah AL-Awady。他讲了一件让我读完就想拍桌子的事：你 AI 输出之所以"听起来像 AI 写的"，根本不是模型的问题，也不是你 prompt 不够花哨。是因为模型对你一无所知，它在裸跑。今天不聊怎么写更好的 prompt，只聊一件事：prompt 周围那套被绝大多数人完全忽略的基础设施。

[SLIDE 2: principle] (0:57 - 2:30)

先说一个我读完最受冲击的判断。Prompt engineering 已经过时了。不是说写 prompt 不重要，是说光靠 prompt 这一层，你做得再精细，天花板已经到顶了。

为什么？想象一下。同一个厨师，同一个食材，他在自家厨房做出来的菜，和在一个空荡荡只有一口锅的房间里做出来的菜，能一样吗？Prompt 就是那个食材，是配料。Context 是整个厨房，是火候，是刀具，是冰箱里别的食材，是你贴在墙上的菜谱标准。

绝大多数人花一个小时去琢磨那一句 prompt 怎么写得更巧。"扮演一个资深专家"，"一步步思考"，换个词再跑一遍。结果几乎没差别。然后他们开始怀疑模型不行。

[SLIDE 3: image] (2:30 - 3:32)

但真正的问题是：你把一个不认识你的人，扔进一个空房间，让他凭空给你写东西。他当然只能给你一个"对所有人都说得通"的标准答案。模型不知道你是谁，不知道你写给谁看，不知道你眼里"好东西"长什么样，也不记得你上次跟它聊过什么。它没有眼睛。

所以输出"AI 味"特别重，不是审美问题，是信息缺失。一个失明的模型，默认会退回到最平均、最安全、最通用的那一档。这是它能选的最不会出错的策略。

[SLIDE 4: principle] (3:32 - 5:44)

那 context 到底是什么？这里有一个分层结构，是这篇文章里我觉得最值得记住的一张图。

每一次你跟 AI 对话，其实有三层 context 在同时起作用。

第一层叫即时 context，就是你刚刚敲下去的那句话，你给的指令，你要求的格式。99% 的人，所有的精力都花在这一层。

第二层叫会话 context。是这一轮对话里模型能看到的所有东西——你上传的文件、之前几轮的聊天记录、系统提示词。大部分人会用一点，但很少有人去刻意设计它。

第三层叫持久 context。是跨会话留下来的东西——记忆系统、context 文件、知识库、保存的偏好。原文里有一句话我反复读了三遍："almost nobody uses this properly, and it is where the biggest leverage lives."几乎没人用对，但最大的杠杆就在这里。

这就是 prompt-only 思维的死穴。你以为自己在调 prompt，其实你在反复抛光一个失明者手里那把唯一的刀。真正能让 AI 帮你做事的能力，全在你没碰过的第二层和第三层。

[SLIDE 5: image] (5:44 - 8:14)

讲到这里，最容易掉到"道理我都懂但不知道怎么动手"的坑里。所以这篇文章给了一个我觉得是全文最具体、最可上手的东西——四文件架构。

你只要维护四个文件，模型就从一个不认识你的助手，变成一个被入职过的同事。

第一个，identity 文件。你是谁，做什么，专业背景，沟通风格。相当于给 AI 的入职文档。

第二个，audience 文件。你为谁写。受众是谁，他们的知识水平，他们的痛点，他们日常用什么样的语言说话。这一个文件，决定了输出不再"对所有人都成立"。

第三个，standards 文件。在你眼里"好"长什么样。质量标准，格式偏好，反例，正例。这是质控系统。

第四个，project 文件。当前在做什么。这个月的目标，活跃的项目，最近做过的决定，还悬着的问题。

前三个文件相对稳定，做一次能用半年。第四个是动态层，需要周或者月级别地更新。这听起来像维护成本，但只要你一旦建好，每次新开会话不用再重新自我介绍，那两分钟的浪费乘以你一年用 AI 的次数，算笔账你会发现这是稳赚的。

每次会话开头，把这四个文件加载进去。AI 就从一个泛泛的助手，变成一个理解你世界的合作者。

[SLIDE 6: principle] (8:14 - 9:25)

讲到这里你可能会想：那我把所有能写的都写进去，所有知识库全塞进 context 窗口，是不是效果最好？

这是这篇文章里最反直觉的一句话。**不是。装得越多，反而越笨。**

把整个知识库塞进每一次对话，不光是 token 浪费，模型的注意力会被稀释。它什么都想用，结果什么都没用好。

[SLIDE 7: image] (9:25 - 11:20)

原文用了一个我觉得特别贴切的对比。一个外科医生上手术台之前，不会把所有医学教科书重新翻一遍。他翻的是这个病人的病历、这次手术的流程笔记、最新的影像。他加载的是相关 context，不是全部 context。

所以正确的做法叫动态 context loading。给每一类任务预先定义好"加载哪些文件"。写作任务加载 identity、audience、standards，再加上几篇你过去写得最好的样本。分析任务加载 identity 和 project，加上原始数据和历史分析。研究任务、策略任务，各自的加载规则不同。

这是一个特别容易被忽略的判断：context 工程不是"塞得越满越好"的工程，是"该塞什么不该塞什么"的工程。塞错了，它就反过来变成噪声工程。

[SLIDE 8: principle] (11:20 - 12:46)

最后还有一层，决定了 AI 到底是个"咨询师"还是个"员工"。这一层叫 MCP，Model Context Protocol。

Context 让模型知道一切关于你的事——你的受众、你的标准、你做过的决定。但如果它不能访问你的数据，不能查你的数据库，不能搜索网络，不能读你的邮件，它就只是一个非常了解你的文本生成器。一个会说话的顾问。

把 context 和 MCP 工具组合起来，模型就完成了一次类别跳跃——从顾问，变成操作员。它不再只是告诉你"你的周报应该包含哪些内容"，它直接拉数据、跑计算、生成报表、存到你的云盘里。

[SLIDE 9: image] (12:46 - 14:14)

这里有一个组合的顺序很重要。先 context，再 tools。System prompt 立角色——你是谁，知道什么，遵循什么标准。MCP servers 提供能力——搜索、文件、数据库、邮件、日历。Task prompt 把两者粘起来：基于你已经知道的本季度目标和竞品图景，去拉最新的市场数据，对比内部指标，生成一份策略简报。

Context 告诉模型"为什么"和"做什么"。Tools 告诉模型"怎么做"。这两层接上的瞬间，AI 才真正开始替你做事，而不是替你说话。

[SLIDE 10: summary] (14:14 - 16:30)

读完整篇我最大的一个感受是：差距从来不在模型本身。同一个 Claude，同一个 GPT，有人用出"通用废话"，有人用出"专属操作员"。差的不是 prompt 写得花不花，差的是 prompt 周围有没有一套被设计过的 context 架构。

Prompt 工程是语法，context 工程是基础设施。你以为 AI 输出平庸是因为 prompt 不够好，其实是因为模型对你一无所知。模型能力是常数，差距全在它周围的装配。

顺带说一句，现在能为企业做完整 context 架构审计加落地的人，单个项目报价已经到了五千到两万五千美金。市场已经开始为"基础设施"这件事买单。

如果你今天只想做一件事，不要再去翻"100 个 prompt 模板"的合集了。打开一个空文件，先把你自己的 identity 文件写出来——你是谁，做什么，你的语气和标准是什么。这一份文件，比你接下来一个月所有的 prompt 调试加起来都值钱。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
