# 模型越强，卡住你的反而是你自己

今天我带你精读一篇文章，标题叫《A Field Guide to Fable: Finding Your Unknowns》，作者是 Thariq，推特叫 @trq212，他是 Anthropic Claude Code 团队的人，也直接参与了 Claude Fable 5 这一代模型的发布——所以他讲的是内部人的第一手经验。这篇文章解决一个很扎心的问题：当模型强到某个程度，你会发现，活儿干得好不好，瓶颈已经不在模型了，而在你——在你能不能把你自己都没想清楚的东西讲清楚。听完这一讲，不管你是写代码的工程师，还是用 AI 做原型的产品、设计、运营，你都能拿到一套直接上手的方法：怎么在事情变贵之前，就把你不知道的东西挖出来。我们开始。

作者说，跟 Claude Fable 5 一起干活，反复在教他一个老道理，就是这句话：**地图不是疆域，the map is not the territory**。你看我身后这张图，最上面这一行就是它。

## 地图不是疆域，中间那道缝就是未知

什么叫地图，什么叫疆域？我给你翻成人话。**地图**，是你对「要做的这件事」的一种表示——就是你写的 prompt、你给的 skills、你塞进去的 context，是你**交给 Claude** 的那一堆东西。**疆域**呢，是这件事**真正要发生的地方**——是那个 codebase、是真实世界、是它们实际的约束和坑。

你看图上左边是地图，右边是疆域。问题在于，这两个东西**永远对不齐**。地图跟疆域之间那道缝、那个差，作者给它起了个名字，叫 **unknowns，未知**。这是整篇文章的核心词，你把它记住，后面全都围着它转。

为什么这道缝这么要命？因为当 Claude 干着干着，撞上一个 unknown、撞上地图上没画的地方，它没办法停下来问你，它只能基于「对你到底想要什么的最佳猜测」自己做个决定。**而活儿越大，Claude 要走的路越长，它可能撞上的未知就越多。**猜错一步，后面可能全歪。

作者有一句很重的话，这是全文的核心命题：

> "Fable is the first model where I find the quality of the work is bottlenecked by my ability to clarify its unknowns."

翻过来就是：Fable 是第一个让他觉得——工作质量是被「我澄清它的未知的能力」卡住的模型。你品品这句话。以前我们抱怨活儿干不好，都怪模型笨。现在他说，不是了，是我这个人讲不清楚，卡住了它。

还有一点：**光提前规划，并不总是够**。你可能是在代码写到一半，才突然发现一个未知；甚至这个未知反过来会告诉你——你其实压根该换一种完全不同的思路来解这个问题。所以跟 Fable 协作，是一个在实现**之前、之中、之后**反复发现未知的迭代过程。这个「之前、之中、之后」，等会儿就是这张图的主时间轴，你先记着。

## 用四个象限，把未知拆开看

既然未知这么关键，那就得先问一句：你的未知，到底长什么样？你总得先看得见它，才能去挖它。

作者说，他带着问题来找 Claude 的时候，习惯把未知拆成四类。你看图上这里，冒出来一个 2×2 的四象限——这个框架很有名，是 Rumsfeld 当年讲的 known 和 unknown 矩阵。我一个一个过。

第一格，**Known Knowns，已知的已知**。最简单，基本就是你 prompt 里写的东西——你明确知道、也明确告诉了 agent 你要什么。

第二格，**Known Unknowns，已知的未知**。就是你还没想清楚，但你**知道**自己没想清楚的。比如「这个接口怎么设计我还没定」——你至少知道你缺这块。

第三格开始有意思了，**Unknown Knowns，未知的已知**。是那种太显然、你根本不会专门写下来，但是你**一看到就认得**的东西。作者的例子特别贴切：视觉设计。你说不清你要什么风格，但设计稿摆你面前，你一眼就知道「这个对、那个不对」。这就是隐性知识——它在你脑子里，但你调不出来。

第四格，最麻烦，**Unknown Unknowns，未知的未知**。这是你**压根没考虑过**的东西，你根本没意识到自己缺这块知识。作者有个精准的问法：「我知道一件事能做到多好吗？」你连「好」的上限在哪都不知道，你怎么可能要求到那个高度。

那高手什么样？作者说，顶尖的 agentic coder，未知其实相对很少。他说看着像 Boris、像 Jarred 这样的人写 prompt，一眼就能看出来——他们**非常细节地知道自己要什么**，跟 codebase、跟模型行为都深度同步。但关键在这——**他们也会假设未知一定存在**，他们不装全知。

所以作者下了这么一个定义，这是全文第二重要的一句：

> "reducing and planning for your unknowns is the skill of agentic coding."

减少你的未知、并为你的未知做规划，这件事**本身**就是 agentic coding 那门核心技能。他把这门手艺重新定义了——不是你多会写 prompt，而是你多会管理未知。好消息是，这是一门**可以练的**技能，你跟 Claude 一起练就能变强。

## 太具体和太模糊，你会两头都输

那怎么练？在讲具体招式之前，作者先给你看一个陷阱。你看图上这里，左右两个红框，两支红箭头都往下汇到底下那个绿框——上面的小标题写着「指令的平衡」。

指挥 Claude，是一个很微妙的平衡。往左，**太具体**——你把话说得死死的，Claude 就严格照你的指令走，哪怕它发现换个方向更合适，它也不给你转，因为你没留转的空间。往右，**太模糊**——你说得太笼统，Claude 就自己拿主意，基于所谓的「行业最佳实践」做一堆假设，而那些未必适合你这个具体任务。

作者点破了本质：当你不为未知做准备，你会**两头都输**。你既不知道哪一段路会布满障碍、需要提前扫雷；也不知道哪一段路本是坦途、但你其实还想让 Claude 拐个弯、veer 一下。两种信息你都没有，只能瞎指挥。

好在，Claude 恰恰能帮你**更快**发现未知：它搜 codebase、搜互联网快得离谱，一般话题懂得比你多，从失败里迭代也比你快。

但这里有整段最重要的一步，你一定要划下来：**最关键的，是给 Claude 关于你「起点」的 context**。就是告诉它——你现在站在思考流程的哪个位置，你对这个问题、这个 codebase 到底有多少经验，你哪懂哪不懂，坦白交代。然后让它像一个 **thought partner、思想伙伴**那样跟你一起想。它不是你的工具，是你的搭子。

还有一句作者反复强调：几乎所有这些场景里，**HTML artifact 都是最好的载体**——用一个 HTML 页面，把想法可视化、摆出来给你反应。接下来这套工具箱，几乎每一招都落在一个 HTML 上。而且他特别说：**不是每次全用**，这是一个值得备着、按需取用的技巧集合。这套工具箱，就沿着刚才那条「实现前、中、后」的时间轴排开。我们跟着走。

## 实现前：五个便宜的探测

先看时间轴最左边，**实现之前**。这一段五招。每一招，你都要留意它是**冲着哪一格未知去的**——这是这篇文章的心法，别听成一堆零散 tips。

第一招，**Blind Spot Pass，盲点扫描**。冲着最难缠的那一格——**未知的未知**。什么时候用？比如你要在 codebase 一个从没碰过的新区域写功能，或者让 Claude 帮你做一件完全不熟的活儿，像调设计。这种时候你身上一定挂着一堆未知的未知——不知道该问什么、不知道「好」长什么样、不知道有哪些坑。做法很简单：直接让 Claude 帮你做一次盲点扫描，把这些未知的未知找出来、讲给你听。作者说他特别爱用字面那两个词——"blindspot pass" 和 "unknown unknowns"，直接这么说。而且再强调一遍：**一定要给它「你是谁、你懂什么」的 context**。比如：「我要加一个新的 auth provider，但我对这个 codebase 的 auth 模块一无所知，帮我做一次 blindspot pass，找出我相关的未知的未知。」

第二招，**Brainstorms and prototypes，头脑风暴和原型**。冲着第三格——**那种「看到才知道」的标准**，就是视觉设计那种，你说不清但一眼认得。作者说，在这种领域，**越早在原型阶段就把这些标准识别出来、说出来，就越值钱**。为什么？因为拖到实现阶段才发现，代价相对贵得多——spec 上一个小改动，可能导致代码里天差地别的实现，而且让 agent 回退它写过的东西更难。举个例子，你只是想看看「一个按钮加到这个框里长啥样」，那完全没必要先去接后端路由、在前端多维护一份 state——先拿 HTML 假数据 mock 出来，看一眼就行。作者说他几乎**每一个 coding session，都以探索和头脑风暴开场**，带着意图去圈定 scope。Claude 常能找到他会漏掉的高价值方向，有时也会「只见树木不见森林」——但头脑风暴能防止你把 scope 定得太窄或太宽。比如：「我想给这份数据做个 dashboard，但我没有视觉品味，给我一个 HTML 页面，放四个天差地别的设计方向，我来挑。」

第三招，**Interviews，访谈**。做完头脑风暴，你多半还有未知。这时候作者反过来，让 Claude **来访谈他**——就任何还含糊的地方，一个问题一个问题地问。请它访谈时，记得给它你问题的 context，好引导它问对方向。这一招有个特别精妙的 prompt：「一次问我一个问题，围绕任何含糊之处，**优先问那些「我的回答会改变架构」的问题**。」你听这个「优先改变架构」——是把有限的问答，花在最贵、最难反悔的决策上。

第四招，**References，参照物**。有时候你就是**描述不出来**你要什么——要么没有对应的词，要么复杂到描述清楚得花半天。这时候最好的答案是给它一个参照物。图、文档、图片都行，但作者甩出一句特别反直觉、又特别可操作的话：

> "the absolute best reference is source code."

绝对最好的参照物，是**源代码**。你想想，如果有个库已经用某种方式实现了你想要的行为，或者有个你特别喜欢的设计组件，那你别费劲描述了——直接把 Fable 指向那个文件夹，告诉它去找什么，**哪怕那是另一种编程语言**。作者说 Claude Design 就是这么工作的：你把它指向某个你喜欢的网站上的一个模块，它读的是**底层代码，不只是截图**——所以能拿到关于 markup、结构、这组件到底怎么搭出来的、丰富得多的细节。比如：「vendor/rate-limiter 里这个 Rust crate 实现了我想要的 backoff 行为，读它，然后在我们的 TypeScript client 里重实现同样的语义。」跨语言，照样能抄。

第五招，实现前最后一招，**Implementation Plans，实现计划**。觉得差不多可以动手了，作者倾向让 Claude 先出一份实现计划给他 review。但这里有个诀窍：**让计划重点放在最可能变的部分**——数据模型、type interface、面向用户的 UX flow。为什么？因为这样能逼 Claude 把「你其实可能需要改」的东西主动浮出来。那些机械性的、你不会去动的 refactor，埋到最底下就行。比如：「写一份 HTML 的实现计划，但把我最可能微调的决策放最前面：数据模型变更、新的 type interface、以及任何面向用户的部分；机械性的重构埋最底下，那部分我信你。」

## 实现中：让它一边干一边写笔记

五招讲完，时间轴往右推一格，进入**实现之中**。这一段只有一招，但它点破了一个特别重要的真相。

这一招叫 **Implementation notes，实现笔记**。作者说，对计划满意了，他会**开一个全新的 session**，把之前做的 artifact——比如 spec 文件加原型——一起塞进 prompt，让 agent 去实现。

但接下来这句话是灵魂：**无论你事前规划得多充分，总有未知的未知在暗处潜伏着**。agent 真干起来，可能因为在代码里撞见一个 edge case，就不得不换一种打法——你计划里根本没料到。

那怎么办？作者的办法是，让 Claude Code 维护一个临时文件，叫 **implementation-notes.md**，或者 .html 也行，让它把干活过程中做的每个决策都记下来——这样「下一次尝试」就能从这些笔记里学到东西。它承认了一件事：再好的地图也挡不住疆域里冒出新东西，那就让它一边走一边把新发现画进地图。有个好用的 prompt：「维护一个 implementation-notes.md。如果你撞上一个逼你偏离计划的 edge case，**选保守的那个选项**，把它记到 'Deviations' 下面，然后继续走。」选保守选项、记下偏离、别停——这就是让它在未知里稳稳地即兴发挥。

## 实现后：推介和一场你必须及格的测验

再往右推一格，时间轴到最后一段，**实现之后**。东西做出来了还没完，这一段两招。

第一招，**Pitches and explainers，推介和讲解**。作者说，交付一件东西，最重要的环节之一，是拿到别人的 buy-in、拿到批准。那在最终文档里搭一个 pitch 或 explainer，有两个作用：第一，当 reviewer 跟你当初一样、带着**同样的一堆未知**起步时，它能加速他们理解；第二，当专家想确认你**已经把他们会预见到的那些未知、那些常见失败点都考虑过了**时，它能加速批准。你看，未知这条线又回来了——推介的本质，是替对方消掉他们的未知。有个 prompt 很实用：「把原型、spec、实现笔记打包成一个我能直接丢进 Slack 拿 buy-in 的单一文档，**开头放一个 demo 的 GIF**。」

第二招，全套工具箱最后一招，**Quizzes，测验**。这一招我特别喜欢。作者说，一段很长的 session 之后，Claude 可能干了**比你意识到的多得多**的事。你光去读 code diff，只能得到很浅的理解——因为很多行为是依赖已有的 code path 的，diff 上根本看不出来。那怎么办？让 Claude 在给你补足一大堆 context 之后，**就这次改动来考你**，考一场 quiz，帮你真正搞懂到底发生了什么。作者放了一句很硬的话：

> "I only merge after I pass the quiz perfectly."

只有当我**满分**通过这场测验，我才会 merge。你想想这个标准——不是「看懂了大概」就合并，是「我能被考满分」才敢合并。prompt 可以这么写：「我想确保我完全理解这次改动里发生的一切，给我一份 HTML 报告，让我带着 context、直觉、做了什么去读懂，并在底部附一个我必须通过的 quiz。」

## 把这张图再走一遍：发布 Fable 那支视频

好，工具箱八招全讲完了。我们把镜头拉远一点，把这张图整个再走一遍，而且这次用一个**真实的例子**串起来——就是发布 Fable 时那支 launch video。

这支视频，是**完全由 Claude Code 剪辑的**。而剪视频对作者是全新领域，他自己说他绝不是专家。那他怎么下手？他**从他已知的东西出发**——也就是四象限里第一格，known knowns。你看这套方法怎么自然地跑起来：

他知道 Claude 能用代码剪视频、能转录，但不确定准不准。于是他让 Claude 讲讲——Whisper 这类转录到底怎么工作，他能不能用 ffmpeg 精准地把「呃」「嗯」和长停顿剪掉。你看，这就是一次**盲点扫描**。

接着，他想要一个「跟他说的每个字都逐字同步」的 UI，但不确定能不能做到。于是他让 Claude 用 Remotion 加转录，做一个**原型视频**来验证可行性。这就是**原型**那一招。

最后，视频做出来看着有点发闷、发灰。他知道这是 color grading、调色的问题，但并不真懂调色是什么。他第一反应是让 Claude 做几个变体来挑——但他很快意识到：**他根本不知道调色的「好」长什么样**。这不就是第四格、未知的未知吗？于是他改变策略，不让 Claude 直接做，而是让 Claude **教他**什么是 color grading，用这个方式先把自己的未知发现出来。你看，又绕回了盲点扫描。同一套方法，针对不同象限的未知，反复用。

## cheap now，永远小于 expensive later

我们走到这张图最后一块，也是作者收尾的地方。图的右下角，写着一句话：**cheap now，小于 expensive later**。这是整套方法底层的经济学，把前面所有招式一句话压干净。

作者说，模型越强，你用对方法能达成的事就越多。所以当一个 long-horizon、长周期的任务给你返回一个错的结果，别急着骂模型——很可能是，你需要**花更多时间去定义你的未知**，或者做一份能让 Claude「即兴穿过」这些未知的实现计划。

然后是全文的收束金句，你把它记一辈子：

> "Every explainer, brainstorm, interview, prototype, and reference is a cheap way to find out what you didn't know before it gets expensive to fix."

每一个 explainer、每一次 brainstorm、每一场 interview、每一个 prototype、每一份 reference——都是在事情**变贵之前**，用一个很便宜的方式，把你原本不知道的东西挖出来。

你回头看这一整张图就全通了：上面是地图对不齐疆域，缝隙就是未知；中间是四象限，教你把未知看清楚；然后是太具体和太模糊的双输陷阱；再往下是沿着实现前、中、后铺开的八件探测工具——盲点扫描、头脑风暴加原型、访谈、参照源码、实现计划、实现笔记、推介、测验；而这一切，最后都收在右下角这句话上：**现在便宜地问一句，好过将来昂贵地返一次工**。你花在挖未知上的每一分钟，都是在给未来的自己省下几十倍的返工。

所以作者留了一句特别干脆的行动指令，我也把它交给你：**你的下一个项目，就从「让 Claude 帮你找出你的 unknowns」开始。**

这一讲就到这儿。核心就一件事：模型已经很强了，现在真正决定活儿质量的，是你能不能把你自己都没想清的东西讲清楚——而这，是一门你今天就能开始练的手艺。我们下一讲见。
