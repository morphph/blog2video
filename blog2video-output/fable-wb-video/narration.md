# 模型越强，卡住你的反而是你自己

今天我带你精读一篇文章——《A Field Guide to Fable: Finding Your Unknowns》，作者 Thariq，推特叫 @trq212，Anthropic Claude Code 团队的人，也是 Claude Fable 5 这代模型的发布参与者，讲的是内部人的第一手经验。这篇解决一个特别扎心的问题：当模型强到某个程度，活儿干得好不好，瓶颈已经不在模型，而在你——在你能不能把你自己都没想清的东西讲清楚。听完这一讲，不管你写不写代码，你都能拿到一套方法：在事情变贵之前，把你不知道的东西挖出来。我们开始。

## 地图不是疆域，中间那道缝就是未知

作者说，跟 Fable 5 一起干活，反复在教他一个老道理：地图不是疆域，the map is not the territory。你看我身后这张图最上面，左边是地图，右边是疆域。地图，是你对「要做的事」的一种表示——你写的 prompt、你给的 skills、你塞进去的 context，是你交给 Claude 的东西。疆域，是这件事真正发生的地方——那个 codebase、真实世界、它们实际的约束和坑。

关键判断在这：地图和疆域永远对不齐。两者之间那道缝，作者给它起名叫 unknowns、未知——这是整篇文章的核心词，后面全围着它转。为什么这道缝要命？因为 Claude 干着干着撞上一个未知，它没法停下来问你，只能基于「对你到底想要什么的最佳猜测」自己做个决定。活儿越大，路越长，撞上的未知就越多，猜错一步，后面可能全歪。

作者有一句很重的核心命题：

> "Fable is the first model where I find the quality of the work is bottlenecked by my ability to clarify its unknowns."

Fable 是第一个让他觉得「工作质量被我澄清未知的能力卡住」的模型。你品品这句——以前活儿干不好，我们都怪模型笨；现在他说，不是了，是我这个人讲不清，卡住了它。

还有一层：光提前规划并不够。你可能写到一半才突然发现一个未知，甚至这个未知会反过来告诉你，你压根该换一种完全不同的思路。所以跟 Fable 协作，是一个在实现之前、之中、之后反复发现未知的迭代过程。这个「前、中、后」，等会就是这张图的主时间轴，你先记着。

## 用四个象限，把未知拆开看

未知这么关键，那得先问一句：你的未知到底长什么样？你总得先看见它，才能去挖它。作者带着问题找 Claude 时，习惯把未知拆成四类。你看图上这里冒出一个 2×2 的四象限——这是 Rumsfeld 那个很有名的 known 和 unknown 矩阵。

第一格，已知的已知，基本就是你 prompt 里写的——你明确知道、也明确说了的。第二格，已知的未知，是你还没想清、但你知道自己没想清的，比如「这个接口怎么设计我还没定」。第三格开始有意思了，未知的已知——那种太显然、你根本不会专门写下来、但一看到就认得的东西。作者的例子很准：视觉设计。你说不清你要什么风格，但设计稿摆你面前，你一眼就知道对不对。这就是隐性知识，在你脑子里，但你调不出来。第四格最麻烦，未知的未知——你压根没考虑过、根本没意识到自己缺的那块。作者有个精准的问法：「我知道一件事能做到多好吗？」你连「好」的上限在哪都不知道。

那高手什么样？作者说，顶尖的 agentic coder，未知其实相对很少。像 Boris、Jarred 这种人写 prompt，一眼能看出他们非常细节地知道自己要什么，跟 codebase、跟模型行为都深度同步。但关键判断在这——他们也假设未知一定存在，绝不装全知。

于是作者下了全文第二重要的一句定义：

> "reducing and planning for your unknowns is the skill of agentic coding."

减少你的未知、为你的未知做规划，这件事本身就是 agentic coding 那门核心技能。他把这门手艺重新定义了——不是你多会写 prompt，而是你多会管理未知。好消息是，这是一门可以练的技能，你跟 Claude 一起练就能变强。

## 太具体和太模糊，你会两头都输

那怎么练？在讲招式之前，作者先给你看一个陷阱。你看图上这里，左右两个红框——左边写着「太具体」，右边写着「太模糊」，两支红箭头都往下汇到底下那个绿框，上面小标题写着「指令的平衡」。

太具体，你把话说死，Claude 就严格照你的指令走，哪怕它发现换个方向更合适也不给你转，因为你没留转的空间。太模糊，你说得笼统，Claude 就自己拿主意，基于所谓「行业最佳实践」做一堆假设，而那些未必适合你这个任务。作者点破本质：当你不为未知做准备，你会两头都输——既不知道哪段路布满障碍、要提前扫雷，也不知道哪段路本是坦途、但你其实还想让 Claude 拐个弯。这是一个对称的陷阱：两个方向都输，输的方式还正好相反。

好在，Claude 恰恰能帮你更快发现未知：它搜 codebase、搜互联网快得离谱，从失败里迭代也比你快。但整段最重要的一步，就是图上那两支箭头最后汇到的那个绿框——给 Claude 关于你「起点」的 context。就是告诉它，你现在站在思考流程的哪个位置、你对这个问题和这个 codebase 到底有多少经验、你哪懂哪不懂，然后让它像一个 thought partner、思想伙伴那样跟你一起想。它不是你的工具，是你的搭子。作者还反复强调，几乎所有这些场景里，一个 HTML 页面都是最好的载体——把想法可视化、摆出来给你反应。接下来这套工具箱，就沿着「前、中、后」这条时间轴排开，而且不是每次全用，是一个按需取用的技巧集合。

## 实现前：五个便宜的探测

先看时间轴最左边，实现之前，五招。每一招你都要留意它冲着哪一格未知去——这是心法，别听成一堆零散 tips。

第一招，盲点扫描，Blind Spot Pass，冲着最难缠的那一格、未知的未知。什么时候用？你要在 codebase 一个从没碰过的新区域写功能，或者干一件完全不熟的活，身上一定挂着一堆未知的未知——不知道该问什么、不知道「好」长什么样、不知道有哪些坑。做法很简单：让 Claude 帮你做一次盲点扫描，把这些未知找出来、讲给你听。这里有个反复出现的要点：一定要给它「你是谁、你懂什么」的 context，它才知道你的盲点在哪。

第二招，头脑风暴和原型，冲着第三格那种「看到才知道」的标准。作者的判断很硬：越早在原型阶段就把这些标准识别、说出来，就越值钱。因为拖到实现阶段才发现，代价贵得多——spec 上一个小改动，可能导致代码里天差地别的实现，让 agent 回退也更难。所以你只是想看「一个按钮加进这个框长啥样」，就别先去接后端路由、在前端多维护一份 state，拿 HTML 假数据 mock 出来看一眼就够。作者说他几乎每个 session 都以探索和头脑风暴开场，带着意图去圈定 scope，防止把范围定得太窄或太宽。

第三招，访谈，Interviews。做完头脑风暴你多半还有未知，这时候反过来，让 Claude 来访谈你——就任何还含糊的地方，一个问题一个问题地问。这招精妙的地方在一个要求：优先问那些「我的回答会改变架构」的问题。你听这个——是把有限的问答，花在最贵、最难反悔的决策上。

第四招，参照物，References。有时你就是描述不出你要什么，要么没有对应的词，要么复杂到说清楚得花半天。这时候最好的答案，是给它一个参照物。作者甩出一句特别反直觉、又特别可操作的判断：绝对最好的参照物，是源代码。你想想，有个库已经用某种方式实现了你想要的行为，那你别费劲描述了，直接把 Fable 指向那个文件夹，告诉它去找什么，哪怕那是另一种编程语言。Claude Design 就是这么工作的：你把它指向某个网站上一个你喜欢的模块，它读的是底层代码、不只是截图，所以拿到的是关于结构、组件到底怎么搭出来的丰富细节。跨语言，照样能抄。

第五招，实现计划，Implementation Plans。差不多可以动手了，作者倾向让 Claude 先出一份计划给他 review。诀窍是：让计划把最可能变的部分放最前面——数据模型、type interface、面向用户的 UX flow。为什么？因为这样能逼 Claude 把「你其实可能需要改」的东西主动浮出来；那些机械性、你根本不会去动的 refactor，埋到最底下就行。

## 实现中：让它一边干一边写笔记

五招讲完，时间轴往右推一格，进入实现之中。这一段只有一招，但它点破了一个特别重要的真相。这招叫实现笔记，implementation notes。对计划满意了，作者会开一个全新的 session，把 spec、原型这些 artifact 塞进 prompt，让 agent 去实现。

但接下来这句话是灵魂：无论你事前规划得多充分，总有未知的未知在暗处潜伏。agent 真干起来，可能因为在代码里撞见一个 edge case，就不得不换一种打法——你计划里根本没料到。作者的办法是，让 Claude Code 维护一个临时文件，叫 implementation-notes.md，把干活过程中做的每个决策都记下来，好让「下一次尝试」从这些笔记里学到东西。而且交代它：撞上一个逼你偏离计划的 edge case，就选保守的那个选项，把它记到「Deviations」下面，然后继续走。这一招承认了一件事——再好的地图，也挡不住疆域里冒出新东西；那就让它一边走，一边把新发现画进地图。

## 实现后：推介，和一场你必须及格的测验

再往右推一格，时间轴到最后一段，实现之后，两招。第一招，推介和讲解，Pitches and explainers。作者说，交付一件东西最重要的环节之一，是拿到别人的 buy-in、拿到批准。在最终文档里搭一个 pitch，有两个作用：当 reviewer 跟你当初一样、带着同样一堆未知起步时，它加速对方理解；当专家想确认你已经把他们会预见的那些未知、那些常见失败点都考虑过时，它加速批准。你看，未知这条线又回来了——推介的本质，是替对方消掉他们的未知。

第二招，全套工具箱最后一招，测验，Quizzes。这招我特别喜欢。作者说，一段很长的 session 之后，Claude 可能干了比你意识到的多得多的事。你光读 code diff，只能得到很浅的理解，因为很多行为依赖已有的 code path，diff 上根本看不出来。那就让 Claude 在给你补足一大堆 context 之后，就这次改动考你一场 quiz，帮你真正搞懂发生了什么。作者的标准很硬：只有满分通过这场测验，他才会 merge。你想想这个标准——不是「大概看懂了」就合并，是「我能被考满分」才敢合并。

## 把这张图再走一遍：发布 Fable 那支视频

工具箱八招全讲完。我们把镜头拉远，用一个真实的例子把整套方法串一遍——发布 Fable 时那支 launch video，完全由 Claude Code 剪辑。剪视频对作者是全新领域，他绝不是专家，那他怎么下手？从他已知的东西出发，也就是四象限第一格、known knowns。

他知道 Claude 能用代码剪视频、能转录，但不确定准不准，于是让 Claude 讲讲 Whisper 这类转录怎么工作、能不能用 ffmpeg 精准剪掉「呃」「嗯」和长停顿——这就是一次盲点扫描。他想要一个跟他说的每个字都逐字同步的 UI，不确定能不能做到，于是让 Claude 用 Remotion 加转录做一个原型视频来验证可行性——这就是原型那一招。最后视频看着有点发闷发灰，他知道是 color grading、调色的问题，但并不真懂调色。他第一反应是让 Claude 做几个变体来挑，可很快意识到：自己根本不知道调色的「好」长什么样——这不就是第四格、未知的未知吗？于是他改让 Claude 教他什么是 color grading，先把自己的未知发现出来——又绕回了盲点扫描。同一套方法，针对不同象限的未知，反复用。

## cheap now，永远小于 expensive later

我们走到这张图最后一块，也是作者收尾的地方——右下角写着一句话：cheap now，小于 expensive later。这是整套方法底层的经济学，把前面所有招式一句话压干净。作者说，模型越强，你用对方法能达成的事就越多；所以当一个长周期任务返回一个错结果，别急着骂模型，很可能是你需要花更多时间去定义你的未知。

然后是全文的收束金句：

> "Every explainer, brainstorm, interview, prototype, and reference is a cheap way to find out what you didn't know before it gets expensive to fix."

每一个 explainer、每一次 brainstorm、每一场 interview、每一个 prototype、每一份 reference——都是在事情变贵之前，用一个很便宜的方式，把你原本不知道的东西挖出来。

你回头看这一整张图就全通了：最上面是地图对不齐疆域，缝就是未知；中间是四象限，教你把未知看清；然后是太具体和太模糊那两个红框、两支箭头汇向的双输陷阱；再往下是沿着前、中、后铺开的八件工具——盲点扫描、头脑风暴加原型、访谈、参照源码、实现计划、实现笔记、推介、测验；最后全收在右下角这句话上：现在便宜地问一句，好过将来昂贵地返一次工。你花在挖未知上的每一分钟，都是在给未来的自己省下几十倍的返工。所以作者留了一句特别干脆的行动指令，我也交给你：你的下一个项目，就从「让 Claude 帮你找出你的 unknowns」开始。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
