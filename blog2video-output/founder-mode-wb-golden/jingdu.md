# 精读：Founder Mode

## 精读

**作者**：Paul Graham（Y Combinator 联合创始人；写作 stake 是把一个刚被观察到、还没名字的现象命名并立此存照——他坦言 YC 至今没有一套关于它的成文方法论）
**来源**：paulgraham.com · 2024-09（原文标注月份）· 2026-07-05（vault raw 抓取日）· [原文](https://www.paulgraham.com/foundermode.html)
**原文字数**：约 1,100 words · **精读预读时长**：约 6 分钟
**一句话主旨**：运营公司有两种模式——**manager mode**（把组织子树当黑箱、只通过直接下属指挥、信奉「雇好人给空间」）与 **founder mode**（创始人跨层深入、skip-level 成常态、保留只有创始人能做的事）；硅谷的默认假设是「公司做大就得切到 manager mode」，但对创始人这套是**坏掉的**，founder mode 虽更复杂却更有效——只是我们对它几乎一无所知。

---

### 1. 缘起：一场所有人都会记住的演讲（原文无小标题，此为段落主题）

上周的一次 YC 活动上，**Brian Chesky（Airbnb 创始人）**做了一场演讲——在场每个人都会记住它。事后 Paul Graham 聊过的多数创始人都说，这是他们听过最好的一场；连 **Ron Conway** 这辈子头一回忘了做笔记。Graham 说他不打算复述那场演讲，而是想谈它引出的一个问题。

Chesky 演讲的主题是：**关于「如何运营更大的公司」的传统智慧是错的**。随着 Airbnb 长大，善意的人不断建议他，公司要想 scale 就必须用某种特定方式来运营。这些建议可以乐观地概括为一句话——**"hire good people and give them room to do their jobs"（雇好人，给他们空间把活干好）**。Chesky 照做了，结果却是灾难性的（disastrous）。于是他只能自己摸索出一条更好的路，其中一部分方法来自研究 **Steve Jobs 如何运营 Apple**。目前看来奏效了：Airbnb 现在的**自由现金流利润率（free cash flow margin）已跻身硅谷最好之列**。

而在场的、YC 投过的那批最成功的创始人，一个接一个地说：**同样的事也发生在他们身上**。他们在公司长大时被喂了同样的建议，但这套建议非但没帮到公司，反而**损害了公司**。

### 2. 谜底：那是「怎么管一家你没创立的公司」（原文无小标题，此为段落主题）

为什么所有人都在给这些创始人喂错的东西？这是 Graham 最大的困惑。琢磨一阵后他得出答案：**那些人教的，是「如何运营一家你没有创立的公司」——是「如果你只是一个职业经理人（professional manager）该怎么管」的方法**。

> **"There are things founders can do that managers can't, and not doing them feels wrong to founders, because it is."**
> —— 有些事是创始人能做而经理人做不了的；不去做这些事，创始人会觉得不对劲——**因为确实不对**。

这套 m.o.（modus operandi，做法）对创始人来说效果差到「感觉像是坏的」。

### 3. 两种模式：founder mode 与 manager mode（原文无小标题，此为段落主题）

于是本质上有**两种运营公司的方式：founder mode 与 manager mode**。到目前为止，连硅谷的多数人都**默认「把一家 startup scale 起来 = 切换到 manager mode」**。但我们能从两处反推出另一种模式的存在：一是**试过 manager mode 的创始人的沮丧**，二是他们**逃离它的尝试所取得的成功**。

据 Graham 所知，**没有任何一本书专门讲 founder mode，商学院也不知道它的存在**。目前手上有的，只是一个个创始人各自摸索出来的实验。但既然现在知道要找的是什么，就能开始搜寻它了。他希望几年后，founder mode 能像 manager mode 一样被充分理解——而现在已经能猜到它将在哪些方面不同。

### 4. 经理模式 = 把组织子树当黑箱（原文无小标题，此为段落主题）

经理被教的运营方式，很像**模块化设计（modular design）**：你把组织架构图上的**子树（subtrees of the org chart）当作黑箱（black boxes）**——你告诉直接下属做什么，至于「怎么做」是他们的事，你不介入细节。介入细节就是**微观管理（micromanaging）**，而那是坏事。

"Hire good people and give them room to do their jobs."（雇好人，给他们空间。）——这样描述听起来很棒，对吧？但根据一个又一个创始人的报告，这句话在实践中往往变成：

> **"hire professional fakers and let them drive the company into the ground."**
> —— 雇一群**专业的演员/装模作样者（professional fakers）**，然后任由他们把公司**开进沟里**。

### 5. 双向的 gaslighting（原文无小标题，此为段落主题）

Graham 在 Chesky 的演讲和事后交谈里都注意到一个主题：**被 gaslight（精神操控/让你怀疑自己判断）的感觉**。创始人感到自己**被两边同时 gaslight**——一边是那些告诉他「你必须像经理一样运营公司」的人，另一边是当他真照做后、那些为他工作的人。

通常，当你周围所有人都不同意你时，你的默认假设应该是**自己错了**。但这是极少数的例外之一：**没当过创始人的 VC 并不知道创始人该怎么运营公司；而 C-level 高管作为一个群体，包含了世界上一些最擅长撒谎的人。**（注 [1]：更外交辞令的说法是——资深 C-level 高管往往非常擅长 **"managing up"（向上管理）**；懂这个圈子的人不会否认这点。）

### 6. Founder mode 打破「只通过直接下属」的原则（原文无小标题，此为段落主题）

无论 founder mode 具体包含什么，有一点很清楚：它将**打破「CEO 只应通过其直接下属与公司互动」这条原则**。**"Skip-level" 会议**（越过一层、直接和下下级开会）将从一个「罕见到需要专门起个名字」的做法，变成**常态**。而一旦放弃了那条约束，可选的排列组合数量就极其庞大。

### 7. Steve Jobs 的 100 人务虚会（原文无小标题，此为段落主题）

举个例子：**Steve Jobs 每年会为他心目中「Apple 最重要的 100 个人」办一次务虚会（annual retreat）——而这 100 人并不是组织架构图上职位最高的 100 人。** 你能想象在一家普通公司做这件事，需要多大的意志力吗？可又想象一下它能多有用——它能**让一家大公司感觉像一家 startup**。Steve 想必不会一直办下去，如果它没用的话。但 Graham 说他从没听过第二家公司这么干。所以这到底是好主意还是坏主意？**我们仍然不知道**——这正说明我们对 founder mode 知道得有多少。（注 [2]：如果这种务虚会普及到连被政治主导的成熟公司也开始办，我们就能用「被邀请者在组织架构图上的平均深度」来**量化一家公司的衰老程度（senescence）**。）

### 8. 仍需授权，但它更好用（原文无小标题，此为段落主题）

显然，创始人不可能用「20 人时的方式」去运营一家 **2000 人的公司**——总得有**一定程度的授权（delegation）**。**自治的边界落在哪、有多清晰，大概会因公司而异；甚至在同一家公司里也会随时间变化，随着经理们赢得信任（as managers earn trust）**而移动。所以 founder mode 会比 manager mode **更复杂**。但它也会**更好用**——从个别创始人一路摸索的例子里，我们已经知道这一点。

### 9. 预测与误用风险（原文无小标题，此为段落主题）

Graham 的另一个预测：一旦我们搞清楚 founder mode 是什么，就会发现**已经有一批创始人早就基本走到了那一步**——只不过他们当时的做法，被许多人视为**古怪甚至更糟（eccentric or worse）**。（注 [3]：他还有一个不那么乐观的预测——**一旦 founder mode 这个概念被确立，人们就会开始滥用它**。那些连该授权的事都授权不了的创始人，会拿 founder mode 当借口；不是创始人的经理也会决定「我要像创始人一样行动」。这或许在某种程度上也管用，但**当它失灵时会一团糟**——而模块化做法至少能**限制一个坏 CEO 造成的破坏**。）

### 10. 收束：像 Steve Jobs 而非 John Sculley 那样（原文无小标题，此为段落主题）

奇妙的是，「我们对 founder mode 仍知之甚少」这件事本身反而**令人鼓舞**：看看创始人们已经取得的成就吧——而这一切还是**顶着一股「坏建议的逆风（headwind of bad advice）」**做出来的。

> **"Imagine what they'll do once we can tell them how to run their companies like Steve Jobs instead of John Sculley."**
> —— 想象一下，一旦我们能教他们**像 Steve Jobs 而不是 John Sculley 那样**运营公司，他们会做出什么。（Sculley 是 Jobs 之后接掌 Apple 的职业经理人 CEO——manager mode 的化身。）

## 精读收尾

- **一句话总结**：运营公司有两种模式——manager mode 把组织子树当黑箱、信奉「雇好人给空间」、结果常是「专业骗子把公司开进沟里」；founder mode 让创始人跨层深入、skip-level 成常态（如 Jobs 的 100 人务虚会），虽更复杂却更有效。硅谷默认「做大就切 manager mode」，但对创始人这套是坏掉的——而我们对 founder mode 几乎一无所知。

- **关键引语**：
  1. **"There are things founders can do that managers can't, and not doing them feels wrong to founders, because it is."** —— founder mode 存在性的情感证据：不对劲的感觉是真的。
  2. **"Hire good people and give them room to do their jobs."** … **"hire professional fakers and let them drive the company into the ground."** —— 同一句建议的理想版与实践版的对撞。
  3. **"Skip-level meetings will become the norm instead of a practice so unusual that there's a name for it."** —— founder mode 最具体的一条机制预测。
  4. **"So founder mode will be more complicated than manager mode. But it will also work better."** —— 全文的核心权衡判断。
  5. **"Imagine what they'll do once we can tell them how to run their companies like Steve Jobs instead of John Sculley."** —— 收束金句，把整篇的赌注押在一个人名对照上。

- **与 vault 的连接**：
  - [[latent-vs-deterministic]] —— manager mode 的失败是**信任维度**而非能力维度的（「专业骗子」「向上管理」「双向 gaslighting」都是 trust failure）；这与 Garry Tan「capability vs trust 两类失败模式」的划分同构。
  - [[garry-tan]] —— 本文缘起于 YC 活动，而 Garry 作为 YC 掌门人的整套「开放 harness / 创始人保留架构控制权」主张，正是 founder mode 在 AI-builder 语境里的回声：不把系统的关键层黑箱化。
  - [[orchestration-loop]] —— manager mode 的「把 org 子树当黑箱、只通过直接下属指挥」与 agent orchestration 里「orchestrator 只经由预定义接口调 worker」拓扑同形；founder mode 的 skip-level 相当于打破这层封装、让顶层直接读到底层的 ground truth。

- **视频适配自评**：**适合**做白板讲解视频。理由：全文是一个干净的**二元对照 + 分岔结构**（manager mode vs founder mode），每一路都有具体机制（黑箱 vs skip-level）和具体案例（专业骗子 vs Jobs 的 100 人务虚会），天然可空间化成一张对照图；且有强烈的讲解张力——「所有人都在给你错的建议」这一反直觉钩子 + 「Steve Jobs 而非 John Sculley」的金句收尾。唯一弱点是 PG 反复强调「我们其实还不知道 founder mode 具体是什么」，视频要诚实保留这份不确定性，别把它讲成一套已成型的方法论。
