# 两万行 prompt 越塞越笨？

[SLIDE 1: cover] (0:00 - 0:25)

上次那期我讲过：两个人用同一个 Claude，差 50 倍。那期里我带过一个概念没展开。Garry Tan 最近写了一篇博客专门讲它。他说：这才是 50 倍里真正看不见的那一半。

[SLIDE 2: image] (0:25 - 1:50)

先铺一下背景。Garry Tan 是 YC 现任掌门，自己也在用 Claude Code 搭了一套个人 Agent 系统。他把所有他遇到过的 quirk、所有的 convention、所有被坑过的边缘 case，全都写进 CLAUDE.md 这个系统提示词文件。

塞到两万行时，模型明显变慢了，回答也开始飘。他形容说：我以为我在让模型变聪明，其实我在把它淹死。

直觉总是错的。你想让模型什么都懂，于是就拼命往上下文里塞。但你不能靠吼得更大声，让一个人变得更聪明。你只能在他需要的那一刻，把对的那本书递过去。

[SLIDE 3: principle] (1:50 - 3:00)

他的修法听起来不像什么魔法。就是把两万行砍掉，换成两百行的决策树。

这两百行里写的是什么？不是知识本身，而是一张地图。遇到"这是一个人"，去 people 目录找。"这是一家公司"，去 companies 目录。"这是一篇政策分析"，去 civic 目录。

他把这个两百行的文件叫 resolver，路由表。原来那两万行的知识并没有消失，只是从"全塞进脑子里"变成了"按需取用"。响应立刻变快，归档立刻变准，幻觉也少了。不是模型更聪明了，是他终于不再用噪音把模型蒙住眼睛了。

[SLIDE 4: image] (3:00 - 4:15)

光讲这个，你可能觉得这是一个关于"prompt 要写短"的故事。但真正让 resolver 这个概念立起来的，是他后来遇到的一个具体 bug。

他让 agent 去摄入一篇叫 No New Deal for OpenAI 的文章，作者是 Will Manidis，写的是 OpenAI 的产业政策分析，一篇非常锋利的政治评论。

结果呢？agent 把它归到了 sources 目录。

这个目录是干嘛的？是用来倒原始数据的——CSV 文件、API 导出、批量爬虫结果。你把一篇政治分析塞进 sources，相当于把一篇论文塞进杂物柜。

一篇文章归错了位，其实修一下就完了。但他没有就这么放过。他顺藤摸瓜，审了所有往 brain 仓库里写东西的技能——一共十三个。

查完吓一跳：十三个里，只有三个查过那个路由表。剩下十个，全都在 skill 内部硬写了默认路径。idea-ingest 默认写 sources。pdf-ingest 默认写 originals。meeting-ingest 默认写 meetings。每一个技能都有自己那一套偷懒逻辑，像一个实习生，什么都往"杂项"文件夹里扔。

[SLIDE 5: quote] (4:15 - 4:55)

这里有一个非常关键的判断。Agent 系统的崩溃，不是戏剧性的幻觉，不是输出一段胡话把你逗乐。它是一种缓慢的、安静的漂移。

文件慢慢被归到错的地方。该产生的连接没产生。一个本来应该是结构化智能层的知识库，慢慢变成一个装着一万四千七百个文件的杂物抽屉。

[SLIDE 6: principle] (4:55 - 5:50)

工程直觉是：十个 bug 就修十个 bug。但他说这是打地鼠，修一个，另一个又漂走。

真正的杠杆是把归档逻辑从技能内部搬出来，搬到一份共享的 filing rules 文档里。然后在每个写 brain 的技能顶端，加两行强制规则：创建任何页面前，先读 RESOLVER.md 和 filing rules，按主题归档，不要按来源或者技能名归档。

一条规则，十个技能全修好。从此零误归档。

[SLIDE 7: image] (5:50 - 7:20)

接着他讲了另一个更让我警觉的故事。

他在 executive assistant 技能里建了一个签名追踪子系统。DocuSign 的截止日、没签的文件、提醒草稿——做得漂漂亮亮，完全可以用。

但你去问系统"check my signatures"，它耸肩。你问"我还有什么要签"，它也耸肩。为什么？因为路由表里没有 signatures 这个触发词。技能在那里，能力在那里，但系统够不到它。

他打了个比方：医院里有一位外科医生，但不在科室名录里。病人到前台挂号，前台说我们没有这个科。

一个完全没有的能力，是诚实的——系统说"我做不到"，你就知道要去建它。

一个存在但不可达的能力，是在撒谎。你以为系统在处理签名，其实它根本没接到任务。你不会发现，直到某份合同过期的那一刻才发现。

这是 Agent 系统独有的失败模式。传统软件里没有对应物。

[SLIDE 8: image] (7:20 - 8:15)

建了一个月后，他一数：四十多个技能。有的是为某次事件临时建的，有的是子 agent 在凌晨三点跑 cron 自动生成的。没人在维护那张路由表。

于是他写了一个叫 check-resolvable 的元技能，一个专门检查"能不能被触达"的技能。第一次跑下来，发现六个技能完全不可达。一个 flight tracker，你问航班它不理你。一个 content-ideas 生成器，只在 cron 里跑，你想手动触发都触发不了。一个 citation fixer，在技能目录里躺着，路由表根本没列它。

四十多里有六个。百分之十五的能力，是黑的。

[SLIDE 9: principle] (8:15 - 10:00)

讲到这里，他抛出了一个我觉得最反直觉的判断：路由表是会腐烂的。

第一天，完美。每个技能都登记了，每个触发词都准，每条路径都通。你觉得自己是个天才。

第三十天，三个新技能被子 agent 在凌晨建出来了，没人登记。

第六十天，触发词和用户实际说法对不上。技能描述里写着"track this flight"，用户说的是"is my flight delayed"。描述是一回事，用户说的是另一回事，技能就是不触发。

第九十天，这张路由表已经变成一份历史文档。记录的是系统曾经能做什么，而不是它现在能做什么。

最有意思的是他发现自己在做什么。

他开始用"read skills/flight-tracker/SKILL.md"这种直接路径来调用技能，绕开路由表。为什么？因为路由表上的触发词已经不准了，他知道哪个技能能做这件事，就干脆手动指路。

他说：这不是系统，这是一个有文件柜的人。

系统之所以能运转，是因为有一个懂它的人类在当中介。那一刻中介消失，一切就停摆。

[SLIDE 10: checklist] (10:00 - 11:45)

所以他给自己立了四道防线。

第一道：每一个写 brain 的技能，强制先查路由表和 filing rules，这条是合约，不是建议。

第二道：trigger evals。他建了五十条样例输入配期望输出的测试集。区分两种失败——该触发没触发，叫 false negative；错的技能被触发，叫 false positive。两种都可以通过改 markdown 修复，不用改代码。

第三道：check-resolvable 每周跑一次，像 linter 一样扫出不可达的技能。

第四道还没完全建出来。有一个 YC 公司的 CTO 在办公时间问他：能不能用一个 RLM，也就是强化学习循环，让路由表自己从流量里学习？观察八百次任务调度，看哪个触发词从来没命中，哪个技能总是被错派，然后每周自动重写路由表。

这是终局。他说 Claude Code 的 AutoDream——空闲时做记忆整合的那个系统——算是一个原始版本。但把这个原理专门套在路由表上，你就得到一张会自我进化的路由表。

[SLIDE 11: principle] (11:45 - 13:30)

还有一个观察让整套东西合拢。路由表不只存在于最顶层，它在系统的每一层都重复出现。

技能路由表在 AGENTS.md，把任务映射到技能。归档路由表在 RESOLVER.md，把内容映射到目录。上下文路由表在每个技能内部，把子任务映射到具体动作。

同一套架构，在每一层重复。所以它能从五个技能扩展到五十个，从一千个文件扩展到两万五千个，从一个玩具 demo 扩展到每天处理两百条输入的生产系统。

讲到这里，他把整个框架重新拉高。

他说我以为我在做技术。但当你有四十多个技能、两万五千个文件的时候，你拥有的不是代码，是一个组织。

技能是员工，每个人有一项能力。路由表是组织架构图，定义了谁处理什么、怎么派活、派不出去怎么升级。Filing rules 是内部流程，规定信息住在哪、决策怎么记录。Check-resolvable 是合规审计，不关心代码漂不漂亮，只问一个问题：这家公司声称自己能做的事，它真的做得到吗？Trigger evals 是绩效考核，给一个真实输入，看组织里对的那个人有没有站出来。

一旦你这么看，很多关于 Agent 的困惑都消失了。

问题不是模型不够聪明。问题是我们一直在造没有管理层的公司。一堆有才华的员工，加上一份模糊的协作期望。然后纳闷为什么协作得这么烂。

[SLIDE 12: summary] (13:30 - 14:50)

塞两万行让模型变笨，两百行的路由表反而让它变聪明——Agent 缺的不是更大的大脑，而是一张组织架构图。

如果你也在搭一套 Agent，我给你三个能今天就动手做的事。

第一，去看看你的系统提示词有多少行。如果超过一千行，大概率里面有一半是可以被抽成一张路由表的。

第二，去审一下你的每个技能或每个工具。它们是不是各自带着一套默认行为？那些默认行为是不是其实该抽到一份共享的规则文档里？

第三，写几条 trigger eval。随便十条都行。你用日常的口语说一句话，看它有没有触发你以为会触发的那个技能。不能过的地方，就是你系统里正在漂的地方。

别等系统崩了才来修路由表。它不会崩，它只会慢慢失联。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
