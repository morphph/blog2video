# 1.6 亿美金没解决的 Agent 顽疾？

[SLIDE 1: cover] (0:00 - 0:35)

YC 总裁 Garry Tan 上周发了一篇博客，第一句话就把 LangChain 点名了。融了 1.6 亿美金，三年时间，独角兽估值，但他说这帮人卖给你的，是健身房的会员卡，没给训练计划。今天不聊 LangChain 错在哪——只聊 Garry 自己用什么方法，把同一个 Agent 的 bug 永远地按死了。

[SLIDE 2: image] (0:35 - 2:35)

先讲他这周亲身踩的一个坑。

Agent 跟他说，你下一个会议还有 28 分钟。他信了，准备工作。结果真实距离是 88 分钟。整整差了一个钟头。

bug 在哪？Agent 在脑子里算 UTC 转太平洋时间的时区，算错了。但更荒谬的是，他电脑里早就有一个叫 context-now 的脚本，跑 50 毫秒返回一段确定性 JSON，里面明明白白写着 minutesUntil 等于 88。Agent 就是没去跑它。

同一周，他还问 Agent 一次将近十年前的商务旅行。一个本来应该一秒搞定的查询，Agent 先去调实时日历 API，被拒；再去翻邮件，全是噪声；再调一次 API，又被拒。整整绕了 5 分钟，才想起来搜本地知识库，秒命中。

本地有 3,146 个日历文件，覆盖 2013 到 2026 年。早就索引过，就在硬盘上，一个 grep 的距离。

[SLIDE 3: principle] (2:35 - 4:15)

这两个 bug 表面上不一样，本质是一回事。Garry 给这个本质取了名字。

他把 Agent 的工作分成两类。一类叫 latent，靠判断力，写邮件、做总结、读语境，这是模型该做的事。另一类叫 deterministic，靠精确，同样输入永远同样输出，本地 grep、时间戳相减，这些事写三行脚本就完了，根本不用模型。

日历搜索是 deterministic。时区换算也是 deterministic。但这两次，Agent 都把它们扔进了 latent space，开始推理、调 API、心算。

我读到这里有一个停顿。我们平时说 Agent 答错了，潜意识里以为是模型不够聪明。Garry 这里换了一个说法：Agent 不是答错了，是答在了错的机器空间里。模型选择了耍小聪明，而不是去执行纪律。这个判断我觉得非常准。

[SLIDE 4: principle] (4:15 - 6:30)

那怎么修？Garry 的修法非常工程化，而且有一个很妙的回路。

他先写一个 skill，本质是一份 markdown 合约。比如那个日历 skill 里有一条硬规则：所有历史日历查询必须先走本地知识库，实时 API 只允许查未来或者过去 48 小时。

但关键不在合约本身。关键在下一步。

合约写完之后，Agent 自己读这份合约，自己用判断力写出那个三行的 calendar-recall 脚本。脚本跑起来不到 100 毫秒，大部分时间还是 Bun 启动，真正的 grep 在毫秒以下。零 LLM 调用，零网络。

然后，skill 反过来强制 Agent，以后碰到这类问题必须运行这个脚本，不许再思考。

你品一下这个回路。Agent 用自己的智能，造出了一个约束自己的脚手架。然后这个脚手架反过来锁死 Agent，不让它再耍聪明。Garry 原话：模型的智能创造了防止模型变蠢的约束。

这是我读这篇文章最被点中的一句。大部分人讲 skill 和 tool，只看到 Agent 调脚本这一个方向。其实决定性的一步是反向那一下——脚本写完之后，Agent 不许再绕过它。

[SLIDE 5: image] (6:30 - 8:35)

更狠的是，Garry 把这整套流程压缩成了一个动词。

他描述自己每天的工作流。他跟 Agent 在对话里一起搭一个 OAuth webhook，搞了一个小时，终于跑通。他不会去开 ticket，不会写 spec。他只打一句话：

skillify it.

就这一个词，触发完整的 10 步流程。skill 合约、脚本、单元测试、集成测试、LLM 评测、resolver 入口、resolver 评测、可达性审计、端到端冒烟、归档规则。一句话进去，永久基础设施出来。

他举了好几个例子，每个都是一句 skillify it 触发整套。webhook 那次。Headless 浏览器还是 headed 浏览器的决策那次。Agent 老发坏掉的 ngrok 链接没自检那次。差点 double-book 11 点会议那次。

我看了之后第一反应是——这不就是把"那一次成功的对话"变成"永远不会忘的肌肉记忆"吗？大部分人和 Agent 协作的痛点就是，今天教会了，明天它又忘了。skillify 解决的就是这个。

[SLIDE 6: image] (8:35 - 10:05)

10 步我不全展开，原文已经够细，全讲就变成枯燥教程了。我只挑两步——也是我读完最意外的两步。

第七步叫 resolver eval。前面写了 skill、写了脚本、写了单元测试，听起来挺完整。但 Garry 说，大部分人栽就栽在这一层。

什么是 resolver？就是一张路由表，告诉 Agent，用户说"找我 2016 年的那次出差"应该调 calendar-recall，说"我下一个会议什么时候"应该调 context-now。光写这张表不够，你还得测它真的会路由对。

他的 resolver 评测套件有 50 多个用例，捕捉两种失败。一种是该触发没触发，描述写得太模糊；另一种是触发到错的 skill，两个描述撞车了。

"明天日历上有什么"到底该走 calendar-check 还是 calendar-recall 还是 google-calendar？三个 skill 时间维度不同，但一句话都可能命中。不测，永远不知道。

[SLIDE 7: image] (10:05 - 11:30)

第八步更刺激，叫 check-resolvable。一个月之后他系统里攒了 40 多个 skill。第一次跑这个审计，发现 6 个 skill 是 unreachable 的。百分之十五的能力是"暗的"。

什么意思？skill 文件就在那儿，脚本也能跑，但 resolver 根本路由不到它。一个航班追踪器，没人能通过聊航班把它唤醒。一个引用修复器，文件夹里躺着，路由表里没登记。

他给这种 skill 起了个名字，dark skill。比没有这个能力更糟。因为它制造一种虚假安全感——你以为系统覆盖了，实际它永远不会被调用。

还有一个发现也很扎眼。13 个会往知识库写东西的 skill 里，10 个把文件归错了目录。各自硬编码路径，没人去查统一的归档规则。

直觉上你会觉得，写完 skill 就完事了。Garry 这两步在告诉你：写完只是一半，路由层才是真正的瓶颈。

[SLIDE 8: checklist] (11:30 - 13:45)

我得诚实地讲一下代价，不然就变爽文了。

他光一个 context-now skill，每天跑 35 个 LLM 评测。整个系统 179 个单元测试，跑完不到 2 秒。这是单 skill 的量。40 多个 skill 全部按这个节奏跑，每天的评测 token 和时间成本是非线性上去的。文章里没给总成本，但你心里要有数——这套方法论假设了一个前提：你愿意为可靠性持续付费。

第二个前提更重要。skillify 假设你有一个长期、跨会话、服役数月到数年的 Agent，类似他自己那个叫 OpenClaw 的个人 Jarvis。如果你只是偶尔让 LLM 写封邮件，这套结构对你纯属负担。同一个错误不重复出现，这条曲线就压不平 10 步的成本。

第三个，Garry 自己也承认，这套是踩了"日历加时区"两次坑之后才形成的。没踩过坑的人，很难提前接受"每修一个 bug 都要走 10 步"这种代价。早期阶段，造护栏会显著拖慢功能开发节奏。

所以这不是给所有人的银弹。是给"我要养一个长期 Agent，错误重复出现就是真痛"的人的方法论。

[SLIDE 9: comparison_cards] (13:45 - 16:00)

讲到这里要提一下 Hermes Agent，Nous Research 出的。

Hermes 做对了一件事：它让 Agent 自己创建、修改、删除 skill。任务跑完，Agent 自己提议一个 skill 写到磁盘上。渐进式加载、记忆上限 2200 字符、条件激活——设计都挺聪明。

但 Hermes 漏了另一半。Hermes 不测试它写出来的 skill。没有单元测试，没有 resolver 评测，没有 check-resolvable，没有 DRY 审计，没有每天的健康检查。

结果会怎么样？周一 Agent 创建一个叫 deploy-k8s 的 skill。周四在另一个对话里又创建一个叫 kubernetes-deploy 的。两个都在，触发条件重叠，路由错了没人察觉。

或者 skill 写的时候完美，六周后上游 API 变了，它静悄悄返回垃圾，直到人肉发现。或者一个自动创建的 skill 触发条件太弱，从来匹配不上，沦为孤儿，慢慢腐烂。

Garry 一句话总结：Hermes 处理创建很漂亮，GBrain 处理验证。你两个都要。

我觉得这个对比挺关键。它告诉你 skill 系统不是一个东西，是两层——生成层和验证层。两层都要在，缺一层就会从某个方向开始腐烂。

[SLIDE 10: quote] (16:00 - 18:15)

把全文拉到全局来看。

健康的软件团队里有一条铁律：每个 bug 都要有一个测试。这个测试永远在那里，bug 在结构上不可能再发生。Garry 的主张就是 Agent 应该一样工作。

每个失败变成一个 skill。每个 skill 配测试。测试每天跑。

Agent 的判断力是被永久改写的，不只是当前 session，不只是上下文窗口还在的时候。明年这个时候和我协作的 Agent，会被过去一年里它犯过的每个错误塑造。

LangChain 不是错在它没工具。trajectory 评测、trace pipeline、LLM-as-judge，这些 primitives 它都有。Garry 也明确说一句 credit where it's due。

它错在没给一个 opinionated workflow——一个明确的顺序：先做什么，再做什么，什么时候算完。所以这不是 hit piece，是 1.6 亿美金买到了零件，没买到方法论。

真正让 Agent 进化的不是更聪明的模型，而是一句 skillify it——把每一次踩坑，变成永远不会再踩的护栏。

[SLIDE 11: summary] (18:15 - 19:55)

如果你也在养一个长期 Agent，我建议你做一件小事。打开你和 Agent 的聊天记录，搜一下你骂过"卧槽"或者"什么鬼"的位置。Garry 说这是他找到过最诚实的评测启发式——那些就是你缺的测试用例。

然后挑一个，把它 skillify 掉。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
