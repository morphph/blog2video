# 72 小时 14 个 PR：百分之九十测试覆盖凭什么不再是奢侈

## Hook

YC 总裁 Garry Tan，七十二小时之内合并了十四个 PR，新增将近两万九千行代码。而且他说，每一个 release 的测试质量，都比上一个更高。这不是一个 demo，这是一个真正在跑的开源项目。今天我不打算教你百分之九十覆盖率怎么打——我只想聊一件事：为什么"百分之九十"这条线，突然不再昂贵了。

## 这个数字背后的反常识

先把背景交代清楚。Garry 过去一年在做两个开源项目，一个叫 GStack，一个叫 GBrain。两个加起来，将近九十七万行代码，六百六十五个测试文件。这些代码几乎全部是 Claude Code 和 Codex 写的，他平均同时开着十五个 Conductor session。

但今天真正值得停下来想的，不是九十七万行这个数字，是另一组对比。七十二小时，十四个 PR，将近两万九千行新代码。同时，测试质量每一版都在向上走。

按过去五十年的工程常识，这件事不应该发生。速度和质量是要二选一的。要么快，要么稳。Ship fast, break things，或者 move slow, ship right。但 Garry 说，今天你不用选了。而真正解锁这一切的，不是 AI 把代码写得多快，是另一件更深的事。

## 软件这五十年，一直是脆的

要看懂这个变化，先要看清楚它替代了什么。

过去五十年，整个软件工程这门学科，是围绕一个核心假设组织起来的：错误必须被防止，因为错误的代价是灾难性的。

第一次写代码就得写对。漏掉一个边界条件，线上就崩。一次数据库迁移写错，客户数据就丢了。某个函数有微妙的逻辑，写它的人离职了，整个团队就再没人懂它为什么能跑。整个体系，建立在"人要小心"这个前提上。可人就是不小心。

所以我们造了一整套精密的流程来对抗它：code review、staging、QA 团队、release train。这些流程其实是在做同一件事——在错误抵达用户之前拦住它。

它确实有用。但它很慢。而且它给软件系统的复杂度，划了一条硬天花板：你的系统最多复杂到，一个团队的脑子能同时装下的那个程度。再复杂就崩。

## 现在的软件，变"软"了

我用"软"这个词不是说草率。是说一种过去做不到的韧性。

AI 编码 Agent，Claude、Codex、还有围绕它们长出来的整个生态，现在已经可以读代码、理解上下文、诊断错误、写出修复。不是百分之百完美，但好到一个程度——软件的错误模型本身变了。

迁移脚本崩了？Agent 读完报错，把四十五个数据库版本的演化历史读懂，写修复，写测试。文件同步在一个带几百万 symlink 的仓库里卡死了？Agent 诊断出 parser 超时，加上三十秒兜底，连修复带测试一起 ship。抽取 pipeline 出现归属错误？跨模型的 evaluation 把它抓出来，prompt 迭代一版，强制约束直接落到数据库层。

对大多数代码级错误——逻辑 bug、解析失败、边界情况——Agent 现在能在下一个回合就诊断并修好。这是真的新东西。剩下还灾难性的错误，是那些会破坏状态的：错误的生产迁移、被利用的安全漏洞、收不回来的隐私泄漏。棘轮在这些地方也有帮助，好的测试能在它们抵达生产前拦下大部分。但真正的相位变化是：codebase 里绝大多数错误，从今天起，都属于"能修"那一类。

## 棘轮到底是什么

讲到这里，可以引出 Garry 给这件事取的名字了：复杂度棘轮。

棘轮你应该见过，就是套筒扳手里那个机构——只能往一个方向转，反方向被卡死。这是个绝妙的比喻，因为它讲清了"单向"这件事。

在 AI 写出来的代码里，每一次 Agent 工作，都会给 codebase 沉淀下三样东西。第一样是测试。它把"什么叫对"这件事编码下来，每次有人改代码就自动跑一遍，破了就大声报错。第二样是文档。它记录的不是代码做了什么，是当初为什么这么做、权衡是什么。第三样是 evaluation 结果。它给输出质量打了分，下一版好不好，对比一下就知道。

下一次 Agent 来碰这份 codebase 的时候，这三样东西全部进入它的 context window。它没法回退到测试套件以下——测试会失败。它没法绕开文档——文档就在它眼前。它没法 ship 低于 baseline 的质量——分数都记着。

质量楼底，每一轮都往上走，永远不回头。这就是棘轮。

## 一个具体的棘轮长什么样

抽象讲完了，我给你一个具体的。

GBrain 是 Garry 在做的一个知识系统——它给 AI Agent 一个长期记忆，把你写的笔记、开的会议、读的资料全部索引进去。你可以理解成给你的 AI 助手装了一颗第二大脑。

它有一个核心功能叫"信念抽取"：从你读过的东西里抽出"谁相信什么，置信度多少"。比如"Garry 觉得比特币会到三十万美元，置信度零点四五"。"Jared 觉得这家初创公司留存很好，置信度零点八"。在两万八千页材料里抽这种东西。

第一次跑下来，抽出了十万零七百二十条 claim。Garry 用了一个跨模型的 evaluation——GPT-5.5 和 Claude 同时独立打分。综合分数：六点八分，满分十分。

最大的问题，他给它起了个名字，叫"持有者混淆"。比如这条 claim："AI 会在二零二七年取代百分之八十的软件工程师。" 这是谁的信念？是写这段话的人？还是被他引用的某个人？还是系统自己从一段播客里推断出来的？V1 在百分之三十五的情况下搞错了持有者。这件事很要命——如果你做的就是一个追踪"谁相信什么"的系统，你必须知道是谁。

修复的流程是这样：evaluation 结果被记下来，六种失败模式被识别出来，V2 的 prompt 把这六种都堵住了。置信度数字的精度，被强制在数据库层做约束——不准再出现零点七四这种假精度，只能是零点七五这种诚实的颗粒度。然后，十七个测试，把这套契约锁死。

从这一刻开始，未来任何一版抽取，没有这十七个测试全绿，就不能 ship。没有人需要记得"持有者混淆"是什么、为什么 weight rounding 重要——测试自己记得。

质量楼底永久升高了一格。这就是棘轮的一次咔哒声。

## 测试不是覆盖率，是机构记忆

这件事还有一层更深的意思。

传统软件公司的"机构记忆"长在哪里？长在人身上。那个知道为什么缓存层是这样设计的资深工程师。那个还记得当年差点搞垮数据库的迁移事故的架构师。那个能解释 billing 系统里那个怪边界的技术负责人。

但人会走。退休、被挖、烧光、burn out。人一走，知识就走了。每个软件公司都有过这种经历——打开一个关键文件，看到一行注释写着"不要改这里，去问 Dave"，可是 Dave 三年前就离职了。

Agent 的 context window，它不会辞职，不会被竞争对手挖走，不会忘。当测试套件里写着"权重舍入必须以零点零五为单位"，文档里写着"因为跨模型 eval 显示假精度会侵蚀置信度的可信度"——这份知识就是持久的。任何 Agent、任何模型、任何时间，加载这个 context，都能理解这条约束。

测试，是能跨越员工流动的机构记忆。对一个一人项目来说，它甚至是你唯一的机构记忆。

## 百分之九十这条线，是数据说话

讲到这里，那个数字可以拿出来了：百分之九十。这条线为什么是百分之九十？不是九十五，也不是八十？

Capers Jones 研究过超过一万个软件项目，测量一个叫"缺陷清除效率"的指标——简单说就是 bug 在抵达用户之前被抓住的比例。他的数据曲线非常清楚：覆盖率低于百分之七十的时候，这个效率大概在百分之六十五到七十五之间徘徊。但一旦覆盖率到百分之八十五到九十五，效率会跳到百分之九十二到九十七。

注意这不是一条直线。是一个非线性的曲线，在百分之八十五附近有一个明显的膝盖。过了膝盖，bug 逃逸率断崖式下降。

航空电子行业几十年前就摸清了这件事。FAA 的 DO-178C 标准要求飞行关键软件——就是那种出 bug 飞机会掉下来的——必须达到一种叫 MC/DC 的覆盖标准，比简单的行覆盖严格得多。普通的分支覆盖会漏掉百分之十到二十的故障，MC/DC 能做到百分之九十九以上的缺陷清除率。他们不是因为官僚喜欢繁文缛节才这么要求，是因为数据告诉他们，低于某个阈值，关键缺陷的逃逸率，就是会高到死人。

工厂那边也是同样的曲线——Six Sigma。三西格玛大概每百万出六万七千个缺陷；四西格玛六千二百个；五西格玛只有两百三十三个。四到五不是改进，是相位跳跃。

测试覆盖率服从同一种曲线。从百分之七十到百分之九十，不是好了百分之三十，是逃逸 bug 数量降了一个量级。

## 但这条线，以前一直是奢侈品

讲完了百分之九十为什么有效，要诚实地讲它为什么以前没人能用。

Mockus、Nagappan 和 Dinh-Trong 三个人研究过 Windows Vista。他们的发现是：覆盖率和发布后 bug 数量确实是负相关，但要爬到百分之九十以上，人力成本急剧上升。最后那百分之二十的覆盖率，所需的工作量远远超过前面百分之七十。

这件事在软件工程里是几十年的常识。所以大多数团队，写到百分之七十、八十就停下，告诉自己 good enough。

最后那一段为什么这么贵？因为它是工程师最讨厌的工作。第十四个边界情况的测试。周五下午五点要不要补完的那个 integration test。看一眼就想推到下周的那种又脏又长的 setup。它不是技术难，是消耗意志力。人类工程师的意志力是有上限的，所以百分之九十就成了航电级、医疗级才舍得砸钱的天花板。

## 真正变的是这一件事：AI 不知道什么叫累

到这里，整篇博客最锋利的那句话可以出来了。

AI 让代码写得更快，这件事所有人都注意到了。但真正改变游戏的，不是这一条。

真正改变的是——AI 让"验证"这件事，第一次便宜到可以维持在百分之九十这条线上。

Agent 不会在写第十四个边界测试的时候厌烦。它不会在周五下午五点偷工减料。它不会看着一个又脏又长的 integration test 心想"我下周再来弄"。那条让人类卡在百分之七十的努力曲线，对 Agent 不适用。你让 Claude 把一个模块所有边界都补上测试，它会愉快地、彻底地、在凌晨两点写完，一句怨言都没有。

那段曾经让百分之九十变成奢侈品的、又脏又累的最后百分之二十——恰恰是 AI Agent 最擅长的部分。

这才是真正的解锁。不是写得快——是验证得起。

百分之九十这条数据上的魔法线，过去要靠人类意志力堆上去。现在它，是免费的。

## 测试面已经不只是函数返回值了

棘轮的边界还在扩张。

大多数人对"单元测试"的理解，还停留在"我这个函数返回的数字对不对"。但 Garry 论证：现代系统的每一层，都是可以测的。

操作系统给你进程树、文件系统状态、网络套接字、cron 调度。终端给你每一次按键、每一行输出、每一个交互式提示。浏览器给你渲染后的页面、按钮状态、跳转事件。API 给你结构化的响应，你可以解析、可以校验。AI Agent 给你可观察的行为——它说了什么、调了什么工具、按什么顺序做、在动手前有没有先问。

只要可以被 harness 包住，就可以被观察。可以被观察，就可以被断言。可以被断言，就可以被棘轮锁住。

举一个具体例子。GStack 里有一个核心功能叫交互式 plan review：你让它评审你的架构，它会一段一段过，提问、试探边界、挑战假设。像一个真的会读代码的工程经理。

问题是，Claude Code 偶尔会跳过整个互动环节。它读完 plan 文件，把所有发现一次性 dump 出来，结束，整个过程一个问题都没问用户。可整个 review 的意义就在那个一来一回的对话里。它一跳过，整个功能就废了。

这种东西怎么测？你没法写单元测试断言"AI 有没有真的跟我聊天"。传统测试框架完全覆盖不了这个层面。

所以 Garry 用 Bun 的 TTY 功能，做了一个测试 harness，PR 编号一三五四。这个 harness 真的在一个伪终端里 spawn 一个 Claude Code 进程，喂给它一个特定场景，触发 review 技能，然后实时盯着终端的输出。如果 Agent 在结束前真的发起了交互式提问，测试通过。如果它一个问题没问就把发现 dump 完结束了，测试失败。

这已经不是在测代码了。这是在 TTY 层测一个 AI Agent 有没有遵守行为契约。是真的看着它干活，然后给它打分。

可观察的，就是可测的。这一句话，把过去五十年"测试"的语义扩到了一个全新的面积。

## 必须讲的代价

讲到这里，得诚实地说几句这件事的代价。不讲代价的爽点都是耍流氓。

第一，覆盖率会给你虚假信心。百分之九十的行覆盖，不等于百分之九十的行为正确。覆盖率只衡量这行代码被执行过，不衡量它的语义对不对。一个测试可以把一行代码走一遍，但根本没断言它在做什么。这也是为什么 Garry 反复强调"行为契约"而不是行覆盖率本身。

第二，跨模型 evaluation 不是零成本。十万条 claim 跑一遍 GPT-5.5 加 Claude 双模型打分，token 账单不是零。Eval 的频率和深度，会成为新的工程经济学约束。

第三，行为契约比语义深度更容易测。TTY 测试能验证"Agent 有没有问问题"，但很难验证"它问的问题是不是真的有质量"。能 assert 的是协议层，能不能 assert 内容深度——目前还是另一个开放问题。

第四，棘轮也会锁死合理的重构。十七个测试把"持有者混淆"的契约钉死了。但如果未来有一天，整个抽取逻辑需要被推翻重写，这些测试可能从"机构记忆"变成"机构化石"。质量楼底永远向上，意味着推翻一个曾经做对过的决定，会变得更难。

最后，灾难性错误本身没被棘轮覆盖。错误的生产迁移、未被察觉的安全漏洞、不可撤销的隐私泄漏——棘轮帮一部分忙，但帮不到全部。

## 我的判断

读完整篇博客，我最想留给你的，是一句话上的认知翻转。

过去五十年，整个软件工程都在做同一件事——防止错误发生。我们造 code review，造 staging，造 QA，造 release train，全部都是为了让错误不要抵达用户。这套体系慢、贵、并且在系统复杂度超过一个团队的脑容量时，必然崩溃。

而现在的相位变化是这样的——我们第一次不需要"防止"错误，我们让错误一旦发生，就被永远钉在棘轮上。每一个 bug 都换来一条测试，每一条测试都把楼底抬高一格，每一格都是永久的。

所以这一切不是"AI 让你写得更快"——是 AI 让"百分之九十测试覆盖"，从一个航电级、医疗级才舍得砸钱的奢侈品，变成了一个普通工程师在周二早上的默认设置。

每一家不采用这个模型的软件公司——Agent 加品味加只升不降的测试套件——它今天交付的速度和质量，已经在被一个用对了棘轮的单人项目超过。
