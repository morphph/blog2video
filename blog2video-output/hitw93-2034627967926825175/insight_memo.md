# Insight Memo: 你不知道的 Agent（Tw93）

## title_zh
换更贵的模型，为什么没救？

## one_sentence_thesis
Agent 工程的真正天花板不在模型能力，而在围绕模型搭的那套 Harness、工具描述和上下文分层，绝大多数被归因为"模型不行"的失败，实际是工程约束没立住。

## why_this_video_exists
观众能从其它"Agent 入门"内容里学到 ReAct、tool calling 这些概念，但拿不到这篇文章里这种"调试视角下的因果重排"：当 Agent 出错时，多数人本能去换模型或改 prompt，而这篇明确告诉你应该先查工具描述、再查评测系统，最后才动 Agent；它还把 Pass@k 与 Pass^k 这两个长得像但用法完全不同的指标摆在台面上，把一个常见的隐性误用揭开。这些是大部分博文不讲、官方文档不讲、做过工程的人才会有的判断。

## judgment_lines
- "Agent 表现下降时，先查环境和评测，不是先改 Agent" — 来源：第 8 节图 22 显示把资源上限放开后，基础设施错误率从高位掉到接近 0，模型得分几乎不变，"失败"原来大部分是评测环境内存峰值崩溃，不是模型退化。
- "工具选错不是模型能力问题，而是工具描述的 bug" — 来源：第 4 节明确写"调试 Agent 时应先检查工具定义，大多数工具选择错误的原因出在描述不准确"；第 3 节 Skills 数据也支持——没有反例时准确率 73%，加反例后升到 85%。
- "Pass@k 和 Pass^k 不是精度区别，是问题种类的区别" — 来源：第 8 节，Pass@k 回答"理论上能不能做到"（开发期能力探测），Pass^k 回答"已有功能有没有被改坏"（上线前回归），混用会让回归测试漏问题、能力评测过度告警。
- "多 Agent 的工程价值不是并行，而是把人从持续参与里释放出来" — 来源：第 7 节指挥者模式 vs 统筹者模式对比，统筹者模式让人只出现在起点和终点，中间产出落成分支和 PR 这类持久化工件。
- "稳定的大系统提示，比频繁变动的小提示实际成本更低" — 来源：第 3 节 Prompt Caching 解释，缓存命中靠精确前缀匹配，写入成本只付一次，后续读取折扣可达 90%；这与"短就便宜"的直觉相反。

## evidence_map
- [具体数字] 3 个工程师 5 个月写百万行代码、近 1500 个 PR，是传统开发速度 10 倍——OpenAI Codex 内部数据，论证 Harness 的杠杆作用（第 2 节）。
- [具体数字] 5 个 MCP 服务器约带来 55,000 tokens 工具定义开销，相当于 200K 上下文里没开始对话就用掉近三成（第 4 节）。
- [具体数字 + 对比数据] Tool Search 让上下文保留率达 95%，Opus 4 准确率从 49% 提升到 74%（第 4 节 Advanced Tool Use）。
- [具体数字 + 对比数据] Programmatic Tool Calling 把 token 消耗从约 150,000 降到约 2,000（第 4 节）。
- [具体数字 + 对比数据] Tool Use Examples 让工具调用准确率从 72% 提升到 90%（第 4 节）。
- [具体数字 + 对比数据] Skills 没有反例时准确率 73%，加反例后 85%，响应时间还降 18.1%（第 3 节图 9）。
- [具体数字] Cursor 把 MCP 工具描述同步到文件夹后，A/B 测试调用 MCP 工具的任务总 token 消耗减少 46.9%（第 3 节）。
- [具体数字] ChatGPT 记忆结构：约 33 条 User Memory + 约 15 个最近对话摘要，没用向量库也没用 RAG（第 5 节）。
- [具体数字] OpenClaw 在 tokenUsage/maxTokens ≥ 0.5 时触发记忆整合（第 5 节图 13）。
- [具体数字] 在线评测对 10%-20% 的 Trace 采样，并按"负反馈 100% 进队列、高成本对话优先审查、模型/Prompt 变更后头 48 小时全量审查"路由（第 9 节）。
- [具体代码事实] Agent Loop 核心实现不到 20 行 TypeScript，主循环结构稳定，扩展靠工具集/系统提示/外化状态三种方式叠加（第 1 节）。
- [具体 bug 场景] 评测分数下降时常见误判：进程被内存峰值杀掉、评分器有 bug 把对的判错、测试用例脱离生产场景、只看聚合分数漏掉某类系统性退化——这些表面上和"模型退化"完全一样（第 8 节）。
- [具体 bug 场景] 压缩时改动 UUID/hash/IP/端口/URL/文件名等标识符的一位，会让后续工具调用直接失效（第 3 节）。
- [具体 bug 场景] 多 Agent 幻觉互相放大：A 带偏，B 跟着强化，C 继续叠加，最后所有 Agent 收敛到同一个高置信度错误结论（第 7 节图 18）。
- [具体 bug 场景] 机票预订 Agent 案例（Anthropic Demystifying evals）：Opus 4.5 发现航空公司政策漏洞给用户找到更便宜方案，只看 transcript 会被判失败，看 outcome 才知道实际更好（第 8 节）。
- [一手引用 / 反模式列表] 第 11 节 8 条反模式：系统提示当知识库、工具数量失控、验证闭环缺失、多 Agent 无边界、记忆不整合、没有评测、过早引入多 Agent、约束靠期望不靠机制。
- [对比数据] 工具描述字数对比："约 45 tokens 的长描述" vs "约 9 tokens 的 Use when 描述"，路由准确率差距不大但累积成本可观（第 3 节）。
- [具体事实] OpenClaw 五层架构：Gateway / Channel 适配器（23+ 渠道）/ Pi Agent / 工具集 / 上下文+记忆，50% token 阈值自动整合（第 10 节）。
- [具体事实] Memory 四层模型：上下文窗口（工作记忆）/ Skills（程序性）/ JSONL 会话历史（情景）/ MEMORY.md（语义），按问题分而不是按存储介质分（第 5 节）。

## non_obvious_points
- 评测系统本身的 bug 比 Agent 的 bug 更难发现 — 为什么这不显而易见：评测出问题时呈现的现象（分数下降、用例失败）和模型退化完全一样，团队的本能反应是改 Agent，但这一改方向就错了；只有看具体 Trace 而不是聚合分数，并且专门验证基础设施健康，才能区分这两种失败源。多数团队的工程肌肉记忆是反过来的——先动业务代码、最后才怀疑测试框架。
- "调试 Agent 行为时优先查工具描述"是个隐藏的因果重排 — 为什么这不显而易见：当 Agent 选错工具，从输出层面看像是模型推理失败，所以人会去调 prompt、换模型、加思维链；但作者明确指出大多数工具选择错误的根因是工具描述缺少"什么时候不该用"的边界条件，Skills 那个 73%→85% 的数据就在量化这个反直觉的结论。
- Pass@k 和 Pass^k 不只是统计指标，而是两类工程问题的分界线 — 为什么这不显而易见：它们看起来只是符号上的差别（一个尖头朝外一个尖头朝上），但 k 次取最好 vs k 次必须全对，对应的是"能力上限探测"与"可靠性回归"两件完全不同的事；混用的代价是回归测试漏 bug 或能力评测过度告警，而这种混用在团队里非常常见，多数人没意识到自己在用错指标。
- 稳定的长系统提示反而比频繁变动的短提示便宜 — 为什么这不显而易见：直觉是"token 越少越便宜"，但 Prompt Caching 的写入成本只付一次、读取折扣可达 90%，所以"稳定性"比"长度"更决定成本。Skills 延迟加载真正的设计目的也不只是省 token，而是保护前缀稳定性，让缓存命中率不被打断。

## tradeoffs_and_limits
- Harness 优于模型升级的判断有适用边界 — 具体表现：作者明确说"这个判断在代码编写这类高可验证任务上最成立，但在开放式研究、多轮协商这类弱验证任务里，模型上限本身仍然更关键"。也就是说，把 Harness 推上去的前提是任务"对错可以被机器执行的标准判断"，对很多业务场景这条前提并不成立。
- 多 Agent 的协调开销可能超过并行收益 — 具体表现：第 11 节明确列为反模式"过早引入多 Agent，协调开销超过并行收益"；多 Agent 还会带来幻觉互相放大的新失败模式（A 带偏 → B 强化 → C 叠加），需要额外引入任务图、隔离边界、交叉验证才能控制，整套基础设施成本远高于单 Agent。
- 上下文缓存对前缀稳定性的硬要求会反过来约束架构 — 具体表现：任何一个 token 不同都会破坏匹配，所以接很多 MCP 工具且工具集频繁变动的 Agent，缓存命中会不断失效；这意味着"工具数量自由扩展"和"上下文成本可控"是冲突的，必须在工具集设计阶段就考虑稳定性。
- 评测体系的建设成本被低估 — 具体表现：搭评测要从 20-50 个真实失败案例起步，环境隔离、正反例覆盖、评分器选型、定期看完整 Trace、套件饱和后还要补充更难任务，这些都是常规工作量；调查数据显示有近四分之一的团队还没开始做评测，传统 ML 指标使用率只有 16.9%，反映建评测的真实成本被普遍低估。

## what_to_leave_out

**不该进入的素材：**
- OpenClaw 的具体 TypeScript 实现细节（MessageBus 类、AgentLoop 类、CronTask interface 等）——这些是落地代码，视频展示会变成代码朗读，对观众无价值。
- 工作流五种控制模式的完整列举（提示链/路由/并行/编排器/评估器优化器）——属于"Agent 入门内容"，本视频不应做综述。
- ChatGPT 四层记忆 vs OpenClaw 混合检索的并列对比细节——选其一作为例子说明记忆设计思路即可，不必双轨展开。
- 渠道适配器和 23+ 渠道这类工程实现广度——这是 OpenClaw 的特征，不是 Agent 工程的普适洞察。
- Provider 故障切换、白名单授权、操作审计日志的代码细节——属于成熟工程实践，没有反直觉点。
- Cron 和 heartbeat 的具体实现——附属功能，主线讲不到。

**应避免的叙事方向：**
- 不要把整条视频框架建立在"教观众怎么做 Agent"上——这篇文章的价值是判断与因果重排，不是教程，写成 step-by-step 会立刻失去锋利。
- 不要试图把 12 个章节平均覆盖——一定会变成"百科式综述"，无重点；视频应只挑 3-5 个最反直觉的判断作为主线。
- 不要把"Harness 比模型重要"做成全片唯一论点——这一条在标题层吸睛，但它有适用边界（弱验证任务不成立），若不带这条边界单押会显得不够专业。
- 不要陷入"OpenClaw 介绍"——OpenClaw 是文章的收尾案例，不是文章主角；视频也不应让 OpenClaw 占据多于 1 张 slide。
- 不要用比喻替代证据（"Agent 就像 XXX"这类）——本文最强的素材是 Cursor 46.9%、Tool Search 49%→74%、OpenAI 1500 PR 10× 速度这些可被验证的具体数字，把这些数字让出来换比喻就浪费了原料。
- 不要试图同时讲完 ACI 工具设计、记忆四层、Pass@k vs Pass^k 三个体系——每一个都需要几十秒铺垫，硬塞会全部讲不清楚。Script Writer 应挑其中两到三个，让剩下的留作钩子。
