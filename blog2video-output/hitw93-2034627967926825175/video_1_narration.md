# 换更贵的模型，为什么没救？

## Hook

Tw93 写了一篇长文，叫《你不知道的 Agent》。三万字，把 Agent 工程能踩的坑几乎都梳理了一遍。我读完最反直觉的一点，特别想跟你聊。当你的 Agent 表现下降，你的本能反应是换更贵的模型，但这一刀大概率砍错了方向。今天不聊 Agent 入门——只聊这篇里最锋利的那几个判断重排。

## 直觉错在哪里：Agent 不行不等于模型不行

我们对 Agent 的直觉，几乎全是从模型的角度出发的。Agent 答错了，是不是模型不够聪明？Agent 用错工具了，是不是推理能力不行？Agent 在长对话里迷路了，是不是该换 Opus 试试？

这套直觉错在一个地方。它把所有"Agent 出问题"都默认归到模型头上。

但这篇文章的视角是完全不同的。它是一个调试视角——当 Agent 行为异常，应该按什么顺序去查。读完之后我才意识到，大部分被归因为"模型不行"的失败，根本不是模型的问题。Harness 没搭好、工具描述写歪了、评测系统自己有 bug——这三层每一层都比换模型重要。

下面三个反直觉点，每一个都对应一个"查错顺序"上的重排。

## 反直觉点一：Harness 比模型本身重要

先从那个最震撼我的数据说起。OpenAI Codex 团队，三个工程师，五个月时间，写出了接近一百万行代码，提交了将近一千五百个 PR。是传统开发速度的十倍。

注意这个数字的颠覆性。十倍生产力的杠杆，不在他们用了多强的模型，而在他们围绕模型搭的那套 Harness——也就是上下文管理、工具集、权限系统、外化状态——所有这些不是模型的工程组件。

模型就是那个引擎。但你能不能跑出十倍速度，看的是你给引擎配了什么底盘、什么传动、什么导航。

但我必须说一个边界。这个判断在代码任务上最成立，因为代码的对错可以被机器精确验证——编译过了、测试过了、就是过了。换到开放式研究、多轮协商这种弱验证场景，模型上限本身还是更关键的瓶颈。

所以这一条不是"模型不重要了"。是说在可验证任务里，提升 Harness 的回报比升级模型大得多。但前提是你的任务真的能被自动判对错。

## 反直觉点二：工具描述是 Agent bug 的第一嫌疑人

第二个反直觉点，我读完直接反思了自己之前几乎所有的 Agent 调试经验。

场景是这样的。Agent 选错了工具，或者该用工具的时候没用。你的第一反应是什么？我以前的反应是：调 prompt，加思维链，加 few-shot，再不行就换模型。

但这篇文章直接告诉你，先去查工具描述。大多数工具选择错误的根因，是工具描述没写清楚——尤其是没写清楚什么时候不该用这个工具。

有几个数字把这个反直觉量化得特别狠。

Anthropic 的 Skills 设计里，工具描述只写正例的时候准确率是百分之七十三。加上反例——也就是明确告诉模型"什么情况下不要用这个 Skill"——准确率直接跳到百分之八十五。响应时间还降了百分之十八。

Tool Search 这个机制，是按需把工具描述加载进上下文，而不是全部塞进来。Opus 4 上的工具调用准确率，从百分之四十九提升到百分之七十四。上下文保留率达到百分之九十五。

更夸张的是 Programmatic Tool Calling。让 Agent 把多个工具调用先写成代码组合，再一次执行。Token 消耗从十五万降到两千。差了七十多倍。

还有一个我觉得特别说明问题的案例。Cursor 把 MCP 工具的描述同步到一个文件夹里，让 Agent 自己去读。A B 测试结果是，调用 MCP 工具的任务，总 token 消耗减少了百分之四十六点九。

把这几个数字放在一起，结论就很硬了。Agent 选错工具，多数时候不是它"不会"，是你没把"什么时候用、什么时候不用"讲明白。先去改描述，比换模型便宜一万倍。

## 反直觉点三：评测系统自己的 bug 比 Agent bug 更难发现

第三个反直觉点是最隐蔽的，也是我觉得最值得记住的。

评测分数掉了。你的第一反应是什么？大部分团队的反应是，模型可能退化了，赶紧查最近的改动、回滚 prompt、看 trace。所有动作都指向同一个方向：怀疑 Agent。

但这篇文章里有一个图特别震撼。一个团队遇到评测分数下降，调查之后发现，根本不是模型的问题。是评测进程被内存峰值给杀掉了。把资源上限放开之后，基础设施错误率从高位掉到接近零，模型得分基本没变。所谓的"模型退化"，本质上是评测环境崩溃。

但你光看聚合分数，你看不到这一点。聚合分数告诉你的只有"分数掉了"——它不会告诉你是因为内存炸了、评分器写错了、还是测试用例脱离了生产场景。

更阴险的是 Pass@k 和 Pass^k 这两个指标。它们长得几乎一样，一个尖号朝外，一个尖号朝上。但讲的是完全不同的事。

Pass@k 是"k 次里有一次对就算对"——这是探测能力上限，回答"理论上能不能做到"。Pass^k 是"k 次必须全对才算对"——这是回归测试，回答"已经有的功能有没有被改坏"。

混用的代价我读完才想清楚。把 Pass@k 当回归用，你的回归测试会把偶尔成功也判成通过，bug 漏出去。把 Pass^k 当能力探测用，你会把刚刚有点苗头的能力给掐死。这种误用在团队里非常常见，多数人没意识到自己在用错指标。

还有一个机票预订 Agent 的案例特别有意思。Opus 4.5 在订机票的时候，发现了航空公司政策的一个漏洞，给用户找到了更便宜的方案。但你只看 trace——也就是只看它的执行过程——会觉得它没按标准流程走，判失败。只有看 outcome——最终结果对用户更好——你才知道它实际上干得更漂亮。

评分器自己的局限，比 Agent 的局限更难发现。

## 调试顺序应该这样重排

把这三个反直觉点连起来看，整篇文章其实在做一件事：重排 Agent 调试的因果顺序。

大多数人的本能顺序是：Agent 出问题 → 改 Agent → 换模型。

这篇文章告诉你的正确顺序是反过来的。先查环境和评测——不是 Agent 真的退化了，是不是你的测试框架自己崩了？再查工具描述——不是模型选错了，是不是你没告诉它什么时候不该选？再查 Harness——上下文是不是被无效内容污染了？最后，才是真的去动 Agent 本身的 prompt 或者换模型。

这套顺序反过来的代价非常具体。你会花一周改 prompt，发现没用；再花一周加思维链，发现还是没用；再花一周升级到更贵的模型，发现还是那样。三周之后才意识到，问题在评测环境的内存配置上。

为什么这种重排难做？因为它反工程肌肉记忆。我们写代码的本能是先动业务逻辑、最后才怀疑测试框架。但 Agent 不一样。Agent 的"业务逻辑"是模型，是黑盒，你动它的回报最低、成本最高。该先动的恰恰是周边那些确定性的工程系统——它们才是你真正能控制的地方。

## 一句话带走

这篇文章给我最大的收获，不是某个具体技术。是它把我对 Agent 失败的归因方式整个翻过来了。

换更贵的模型救不了一个工具描述写错的 Agent。Agent 工程的天花板，不在模型能做什么，而在你给模型周围搭了什么。

下次你的 Agent 出问题，记住这个顺序。先看评测有没有自己崩，再看工具描述有没有讲清边界，最后才动模型。多数情况下，问题在前两步就解决了。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
