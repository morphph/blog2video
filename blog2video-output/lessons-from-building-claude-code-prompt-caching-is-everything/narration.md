# Claude Code 的省钱命门：缓存

## Hook

Anthropic 团队刚刚公开了 Claude Code 的一篇内部工程总结。一句话讲完核心：让一个 Agent 能跑得起来的，不是模型多强，是缓存命中率多高。今天不聊 prompt 怎么写得更花哨，只聊 Claude Code 团队踩过的那几条反直觉的工程红线。

## 缓存不是优化项，是基础设施

我读完之后最震撼的一点，是 Claude Code 团队对 prompt cache 的态度。

在很多团队里，缓存是个性能优化项，做了更好，没做也能上线。但在 Claude Code 这边，他们把整套 harness，就是包在模型外面的那层工程系统，从第一天就围绕 prompt cache 来设计。

更狠的是运维层面。他们对 prompt cache 的命中率设了告警，命中率掉了几个百分点，直接定为 SEV，也就是事故级别的告警。一个工程指标被当成线上事故来对待，这意味着什么？

意味着对一个长会话的 Agent 来说，缓存击穿不是慢一点，是直接让产品的成本结构崩掉。订阅制的合理额度、可接受的延迟，都是建立在高命中率之上的。命中率一旦掉下来，这些都跟着塌。

## 前缀匹配这一条规则，重写了所有架构决策

为什么缓存对 Agent 这么敏感？因为 Anthropic 的 prompt cache 是按前缀匹配工作的。

什么意思？你发给 API 的请求，从最开始的第一个字节，一直到你设的某个缓存断点，这一整段如果跟上次一模一样，就直接命中缓存，不用重新处理。但只要这一段里任何一个位置变了，从那个位置往后所有的内容都要重新算，缓存全部作废。

这条规则听起来很简单，但带来的设计约束非常强。它意味着你必须把稳定的内容放最前面，把变化的内容放最后面。

Claude Code 的 prompt 是这样分层的。最前面是静态 system prompt 和工具定义，这一层是全局共享的缓存。第二层是 CLAUDE.md，项目级别的配置，缓存到一个项目内复用。第三层是 session context，这一次会话内复用。最后才是对话消息本身，每一轮都在变。

这样安排的好处是，越前面的层覆盖的请求越多，缓存的杠杆越大。但代价也很真实。你失去了"动态调整 prompt"的自由度。任何想往前面塞动态内容的诱惑，都得抵抗。

## 在 system prompt 里塞一个时间戳，会让全公司变贵

这条原则的脆弱性，藏在很多看不见的细节里。

Claude Code 团队自己踩过几个真实的坑。第一个最简单：他们曾经在 static system prompt 里塞了一个精确的时间戳。每次请求时间都不一样，等于每个请求的 prefix 从一开始就不一样了。所有静态部分的缓存全部失效。

第二个坑更隐蔽。工具定义在序列化的时候顺序非确定，今天工具 A 在前，明天工具 B 在前。对模型来说功能完全等价，但对缓存来说，这是两个不同的 prefix。

第三个是 Agent 工具的子 agent 列表参数被改动了。这种修改在功能上看起来无害，但它落在 cached prefix 里，整段缓存就被无声击穿。

这就是这套约束最难处理的地方。它没有报错、没有崩溃、产品照常运行，只是变贵了、变慢了。如果你没有缓存命中率的监控，你根本看不见这件事正在发生。

## 信息更新走 message，不要改 prompt

那如果信息确实需要更新呢？比如时间变了，比如用户改了一个文件，模型确实需要知道这件事。

直觉做法是改 prompt：把新的时间写进去，把新的文件状态写进去。但这就回到上一段那个坑了——任何对 prompt 的修改都是缓存击穿。

Claude Code 的做法是另一条路：信息更新走对话消息，不走 prompt。

具体怎么做？他们在下一条 user message 或者 tool 返回结果里，插入一个 system-reminder 标签，把更新的信息放在里面。模型读到这个标签，知道这是系统给它的提醒，行为上跟改 prompt 是等价的。但因为修改发生在 message 层、不在 prefix 里，缓存继续有效。

这是一个很小但很有教育意义的设计。它告诉你，prompt 和 message 的边界，从来不只是"约定俗成放哪里"，是缓存这条规则把它们划成了两个完全不同的东西。

## 切到便宜模型反而更贵

这一条最反直觉。我读到的时候愣了一下。

设想一个场景。你跟 Opus 已经聊了 10 万 token，对话很长。现在你想问一个简单的问题，就一句话能答完那种。

你的第一反应大概是：这种简单问题用 Haiku 答就行了，便宜很多。这是教科书级别的省钱思路，对吧？

但 Claude Code 团队的发现是：在这个场景里，切到 Haiku 反而更贵。为什么？因为 prompt cache 是按模型隔离的。Opus 那边缓存好的 10 万 token，Haiku 一个字节都用不上。要让 Haiku 回答，整段历史得在 Haiku 这边重新建一次缓存，从头算一遍。

这一笔重建的成本，比让 Opus 直接答这一个简单问题还高。模型差价省下的钱，远远赶不上 prefix 重建的钱。

这就翻转了一个很基础的认知：模型选择的成本计算单位，不是单次调用，是整段缓存的生命周期。

那真要切模型怎么办？Claude Code 的做法是用子 agent。让 Opus 在自己的会话里准备一段交接消息，然后让 Haiku 作为一个独立的子 agent，从一段干净的、专门给它写的 prompt 开始，单独完成那个任务。这样两边的缓存各自独立，没有互相污染。

## Plan Mode：不要换工具集，要把状态变成工具

第二个反直觉的设计，关于工具的增删。

很多人对工具系统有一个直觉：模型当下需要哪些工具，就给它哪些工具，看起来更优雅、更省 token。Plan Mode 就是一个典型场景——用户进入规划模式，理论上模型只需要只读工具，写工具应该被关掉。

直觉做法是切换工具集：进入 Plan Mode，把工具集换成只读子集。退出再换回来。

但这套设计在 cache 视角下是灾难。工具定义就在 cached prefix 里，你改一个工具，从那一刻往后所有的会话历史的缓存全部失效。

Claude Code 的解法很巧妙。所有工具一直留着，一个都不删。Plan Mode 本身被实现成两个工具：EnterPlanMode 和 ExitPlanMode。

模型调一下 EnterPlanMode，系统就给它发一条状态消息，告诉它"你现在在 Plan Mode 里，只能探索代码，不要写文件，规划完了调 ExitPlanMode"。工具集没动一根毫毛，缓存完整保留。

而且因为 EnterPlanMode 本身就是一个工具，模型遇到难题时可以自己决定进入 Plan Mode，不需要等用户切。这是一个意料之外的好处。

同样的思路也适用于 MCP 工具。Claude Code 可以加载几十个 MCP 工具，全部塞进每次请求成本太高，但中途删除又会击穿缓存。

他们的解法叫 defer loading。那些不常用的工具发轻量级的占位 stub，只有工具名加一个标记，告诉模型"这工具存在，但完整定义先不加载"。模型通过 tool search 主动发现，需要才加载完整 schema。占位 stub 在 prefix 里位置和顺序一直稳定，缓存就稳。

这两个设计有同一个底层逻辑：模型的状态切换不应该靠改工具集表达，要靠工具调用本身来表达。

## 压缩对话最直觉的做法，正是最贵的

第三个反直觉的点，可能也是这篇博客最精华的一段。

什么是压缩？长会话的上下文窗口快满了，要把前面的历史总结成一段摘要，把摘要塞回去当新的起点继续聊。这是所有长 Agent 都要面对的问题。

直觉做法是怎么压？另起一个独立的 API call。给它一个新的 system prompt，比如"请总结下面的对话"，不挂任何工具，把整段历史发过去，让模型吐摘要。

这个做法干净、模块化、单一职责，工程师看了第一眼会说"就该这么写"。

但这恰恰是最贵的做法。因为前缀匹配是按字节算的。你换了 system prompt，从第一个 token 开始 prefix 就不一样了。原来父对话那么长的缓存，一字节都用不上。整段对话历史，按未缓存的全价计费一遍。

而且越长的对话越需要压缩，越需要压缩这一刀就越贵。这是一个反向放大的成本陷阱。

Claude Code 的解法叫 cache-safe forking。压缩这个操作不是另起一个独立任务，是从父对话叉出来的一个分支。

具体做法是：用跟父对话完全一样的 system prompt、user context、工具定义，把父对话的全部历史 prepend 在前面，再把压缩指令作为一条新的 user message append 在最后。

从 API 看过去，这个请求跟父对话最后一次调用几乎一模一样——同样的 prefix、同样的工具、同样的历史。整段 prefix 命中缓存，新付费的就只有最后那条压缩指令本身。

这里有一个让人很容易拐错弯的认知：压缩在心智模型里是"独立的总结任务"，但在缓存视角下，它是"父对话的一次延伸"。叉出去的操作必须和父对话共享前缀，才能省钱。

代价当然也存在。这套设计会让上下文窗口变紧——压缩时要带上"用不到"的完整工具定义，还要预留一段 compaction buffer 给压缩指令和摘要输出。有效容量被吃掉一部分。但相比缓存击穿带来的成本爆炸，这个代价是划算的。

Anthropic 后来把这套压缩 pattern 直接做进了 API 里。开发者要做长会话 Agent，可以直接调用，不用再自己重新踩一遍坑。

## 这篇博客真正想说的事

回过头来看这五条原则——前缀匹配、message 不改 prompt、不切模型、不动工具集、压缩共享父 prefix——它们表面上是五条不相关的工程实践。但底层是同一件事。

Agent 工程师过去关注的是 prompt 写得多漂亮、工具设计多巧、模型选得多准。这些当然重要。但 Claude Code 这篇博客在告诉你：在长会话场景里，真正决定一个产品能不能跑得起的，是更底层的一条约束——你能不能让一段对话从头到尾共享同一个前缀。

这条约束改写了所有上层设计。它告诉你：动态调整工具是反模式，切便宜模型可能更贵，独立的总结任务比延伸任务更贵，prompt 里随便塞一个时间戳会让全公司账单变贵。

这是只有真正在生产规模上跑过 Agent 的团队才会发现的工程现实。它不是某种花哨的优化技巧，是 Agent 这种产品形态在生产环境里的硬性约束。

## 收尾

如果你也在做长会话的 Agent 产品，这一篇值得收藏反复读。我自己读完之后做了一件事——把缓存命中率加进了我们项目的监控面板，跟可用性放在同一个页面上看。Claude Code 团队把它当 SLI，那它就是 SLI。

一句话总结今天这篇：Agent 不是给模型加工具，是给缓存让路。你能不能让一段对话从头到尾共享同一个前缀，决定了它能不能跑得起。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
