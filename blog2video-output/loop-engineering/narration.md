# Claude Code 之父：我不再写提示词了

Loop Engineering 全网最全指南，来了。我连搞几个通宵，把全网关于 Loop Engineering 的一手材料全部读完，浓缩成今天这一期，一次讲透。

## Hook

先说你大概率正处在的状态。你现在用 AI 写代码，节奏是这样的：想清楚要做什么，写一段提示词，看它输出。不满意，再改提示词。但有一群人，已经不这么做了。

Claude Code 的负责人 Boris Cherny，直接说过这么一句话：我已经不给 Claude 写提示词了。我的工作，是写循环。My job is to write loops.

这个循环系统，具体长什么样？与其给你念模块清单，不如带你看一个真实循环的一天。

## 一个循环的一天

每天早上，一个定时任务自动醒来，在你的仓库上运行。这是循环的心跳，叫 Automation。

它做的第一件事，是调用一个 triage skill。Skill 是一份打包好的项目知识，告诉它这个项目里，问题该怎么分流。它读昨天的 CI 失败、新开的 issue、最近的提交。

发现的问题，写进一个 markdown 状态文件。这一步很关键，等会儿你就知道为什么。

接下来，对每个值得处理的问题，它开一个隔离的 worktree，一份独立的代码副本。为什么必须隔离？因为多个智能体同时改一份代码，互相踩脚就是灾难。一旦开始并行，隔离不是优化，是底线。

然后，一个子智能体在 worktree 里起草修复。另一个子智能体，按项目规范和现有测试，审查这份修复。注意这个细节：写的和查的，不是同一个。这是全片最重要的伏笔，马上展开。

审查通过，循环通过 MCP 连接器自动开 PR、更新工单。MCP 是智能体跟真实世界对接的协议。Claude Code 和 Codex 都用它，两边概念一一对应，连接器基本互通。

它处理不了的问题呢？落进一个收件箱，等人来看。

一天结束，状态文件记下今天试了什么、过了什么、剩下什么。明天早上，循环从今天停下的地方继续。这就是状态文件的意义：智能体每次运行结束都会失忆，状态文件是循环唯一的记忆。没有它，每天都从零开始。

这一整天里，你出现了几次？一次。看收件箱那一次。这就是「我的工作是写循环」的具体含义。

## 裁判和选手，不能是同一个

现在展开那个伏笔：为什么写代码的和验证代码的，必须是两个智能体？

因为让模型评判自己的工作，它会自信地称赞自己，哪怕质量明显平庸。这不是猜测，是 Claude 背后的团队拿真实系统验证过的结论。

他们用 GAN 的思路，设计了一个三角色的修复循环。

Planner，规划者。接到一段一到四句话的问题描述，扩写成完整的修复方案。它被故意限制：只管做什么，不碰实现细节。听起来反直觉，规划不是越细越好吗？不是。上游规划里的技术错误，会向下游级联传播。让它少说，是结构性防御，不是偷懒。

Generator，执行者。按方案逐步实现，做完给自己打分。分数趋势向好，就继续优化。方向本身错了，就果断推翻，从头来过。

真正的主角是 Evaluator，评审者。它通过 Playwright MCP，像真实用户一样操作应用：点 UI，调 API，查数据库状态。任何一个维度低于阈值，整轮作废，打回去再来。

它抓到的 bug，具体到什么程度？举两个真实例子。矩形填充工具，只在拖拽的起点和终点放了图块，没有填充整个区域——fillRectangle 函数存在，但 mouseUp 的时候没被正确触发。再比如，一个 PUT 路由 /frames/reorder，定义在 /{frame_id} 之后，框架把 reorder 当成整数 ID 去解析，直接返回 422。

这种级别的反馈，靠模型自我批评，永远拿不到。

代价呢？他们内部的数据是：标准对话消耗 1 倍 token，单智能体循环约 4 倍，多智能体系统约 15 倍。但多智能体在内部评估里，比单智能体好了百分之 90.2。

我的看法是，这 15 倍不是浪费。你是在用钱，买一个单智能体在结构上给不了你的东西：一个不会给自己放水的裁判。

这个原则，甚至已经做进了产品的默认行为。Claude Code 的 `/goal` 命令，你给它一个目标条件，它持续迭代直到满足。而判断目标有没有达成的，是一个独立的小模型，不是写代码的那个。你只看到「设个目标就能走开」，没看到它可信的原因恰恰是：裁判和选手，从来不是同一个。

## 智能体会作弊，所以评分标准才是真功夫

但 Maker 和 Checker 分开，只解决了一半问题。另一半是：你拿什么标准去检查？

这里有个反直觉的事实：智能体会作弊，而且是合法作弊。为了让测试通过，它可能直接删掉失败的测试。为了让 lint 通过，它可能用 eslint-disable 把代码淹没。检查全绿，工作稀烂。

所以评分标准必须检查正确性本身，不只是指标。圈子里现在流行一句话：设计评分标准才是真本事，模型反而是简单的部分。Rubric design is the skill now.

评分之外，循环必须有熔断。每个循环都要有明确的停止条件。生产环境的参考参数：最多迭代 15 到 25 步，超时三百秒左右，单次成本预算 2 美元上下。一个实用技巧：给每次迭代取哈希指纹，连续三次一模一样，立刻停。不设熔断的循环，就是不设上限的账单。

另外有两个习惯，方向跟传统工程完全相反。工具出错的时候，返回错误字符串，不要抛异常。传统工程里异常是规范，但在循环里，异常会杀死循环本身，错误字符串才让模型有机会自己纠错。同样反直觉的是失败记录：保留失败的痕迹，不要清理现场。失败记录是模型避免重复同样尝试的唯一证据。擦掉失败，等于擦掉证据。

## 从开车，到运营整个车队

防住了作弊，设好了熔断，一个循环就能自己转了。这时候退一步看，你会发现这套玩法不是凭空冒出来的。过去三年，用 AI 写代码的姿势，换了好几代。每一代都是被上一代的瓶颈逼出来的。

最早是 Prompt Engineering，提示工程。研究怎么措辞，怎么哄模型。但模型越来越聪明，措辞的边际收益一直在递减。你精心调一晚上的提示词，换个新模型，随便写写，效果也差不多。

于是重心移到了 Context Engineering，上下文工程。不纠结措辞了，转去策划模型能看到什么：写好 CLAUDE.md，备好文档，理顺项目结构。这一层到今天依然重要。但它只解决一件事：单次调用的质量。

单次调用再好，也有个绕不过去的问题：每一步都得你守在旁边。它写完了，谁来确认写对了？依然是你。

所以下一层是反馈循环：让智能体自己验证自己的工作。跑测试，查日志，打开浏览器看渲染结果。我自己的判断是，这一层是目前大多数人回报最大的投资点。不需要任何复杂系统，只要让 AI 能看见自己的代码跑起来是什么样，输出质量就有质的飞跃。

再往上，是 Harness，驾驭系统。一句话定义：Agent 等于 Model 加 Harness。模型负责聪明，Harness 负责在它跑偏之前给方向、跑完之后给反馈。

而 Loop Engineering，循环工程，是这条路的收敛点。不是把一次智能体运行做好，而是设计一个系统，持续地调度、生成、编排这些运行。

打个比方。提示工程，是你手动开车。上下文工程，是设好了 GPS。反馈循环，是装上了车道偏离警告。Harness，是整套驾驶辅助系统。而循环工程——你设计的是自动驾驶的运营平台，决定什么车、什么时间、跑什么路线。

Boris Cherny 把这条路压缩成一条时间线。2023 年，你写代码。2024 年，你提示 Claude 写代码。2025 年，你写循环，让循环去提示 Claude。2026 年，你构建系统，来运行这些循环。听到这里你应该明白了，这不是预言，是已经发生的演进。

你的角色变了。从操作者，变成系统设计者。你定义目标和验证标准，让系统替你，成为那个提示智能体的人。

## 你的第一个循环，今晚就能跑起来

听到这里你可能觉得，这套系统离我太远。其实入口很近，而且完全不需要一步到位。

如果你今天每次打开 Claude Code 都从头写提示词，第一步只需要 `/goal`。比如你在修一个前端适配问题，不要说「帮我修这个 bug」，而是：`/goal`，所有 Playwright 截图和设计稿的像素差异小于百分之一，且 npm test 全部通过。设好，去喝杯咖啡。它会自己改代码、跑测试、看结果、再调整。

你身份的转变，就从这一句开始：从逐步指挥它做什么，变成定义终态，让它自己找路。

等单个 `/goal` 兜不住任务复杂度了，再上 Dynamic Workflows，动态工作流。它会根据你的任务，动态生成一段编排脚本，调度最多上千个并行子智能体。最猛的真实案例来自 Bun 的作者：他用这套东西，把 Bun 从 Zig 移植到 Rust。75 万行代码，数百个智能体并行，百分之 99.8 的测试通过，11 天完成。

但要提醒两句。这个功能目前处于研究预览阶段，不算成熟稳定。它的 token 消耗也显著高于普通会话，先小范围试，确认有效再铺开。

这三个工具是互补的：`/goal` 解决深度，Dynamic Workflows 解决广度，`/loop` 解决持续性。

再往后的路径就清晰了。用 worktree 把并行任务隔离开。在 agents 目录里定义一个 reviewer 子智能体，把写和查分离落地。再建一个 PROGRESS.md，让每次运行把经验和坑写进去，下一次从进度继续，而不是从零开始。做到这一步，你就有了一个会过夜的循环。

成本上有一个杠杆值得知道：prompt caching。用好它，token 单价能从每百万 3 美元，降到每百万 0.3 美元，十倍差距。前提是 prompt 保持追加式增长，中途别换 tools 列表、别换模型——一换，缓存就碎了。给个参照系：三智能体系统生成一个完整应用，单次成本在 125 到 200 美元之间。而日常的 bug 修复循环，应该控制在 2 美元以内。

## 循环替你写代码，替不了你当工程师

把整台机器合上之前，有三个警告。我认为它们比前面所有技巧都值钱。

最直接的一条：验证永远是你的责任。智能体说 done，只是一个声明，不是一个证明。循环跑完了，CI 全绿了，PR 自动开了——这些只代表你设定的检查通过了。而你的检查，可能不够好。

比它更隐蔽的，是理解力债务。循环交付得越快，你的代码库里「存在但你不理解」的部分就越大。这不是可以优化掉的 bug，它是交付速度的直接副产品。你只能持续偿还：抽查、读 PR、问为什么。

而我觉得最锋利的，是认知投降这个陷阱。同样是搭循环，出发点不同，结局完全不同。出于工程判断去设计循环，是进步。为了回避思考去设计循环，是灾难的序曲。

现在合上看全貌。从提示词，到上下文，到反馈循环，到 Harness，到循环。每一步的本质都一样：把重复性的判断交给机器，把系统性的设计留给人。

循环替你写代码，但替不了你当工程师。建造循环，但要以一个打算继续当工程师的人的姿态，去建造它。

## Closing

今晚就能做的最小动作：打开 Claude Code，把你本来要一路盯着的那件事，写成一个 `/goal`，给它一个机器能检查的完成条件。你的第一个循环，就这么开始。
