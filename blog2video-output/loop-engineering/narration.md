# Claude Code 之父：我不再写提示词了

Loop Engineering 全网最全指南，来了。我连搞几个通宵，把全网关于 Loop Engineering 的一手材料全部读完，浓缩成今天这一期，一次讲透。

## Hook

先说你大概率正处在的状态。你现在用 AI 写代码，节奏是这样的：想清楚要做什么，写一段提示词，看它输出。不满意，再改提示词。但有一群人，已经不这么做了。

Claude Code 的负责人 Boris Cherny，直接说过这么一句话：我已经不给 Claude 写提示词了。我的工作，是写循环。My job is to write loops.

这个循环系统，具体长什么样？与其给你念模块清单，不如带你看一个真实循环的一天。

## 一个循环的一天

每天早上，一个定时任务自动醒来，在你的仓库上运行。这是循环的心跳，叫 Automation。

它做的第一件事，是调用一个 triage skill。Skill 是一份打包好的项目知识，告诉它这个项目里，问题该怎么分流。它读昨天的 CI 失败、新开的 issue、最近的提交。

发现的问题，写进一个 markdown 状态文件。这一步很关键，等会儿你就知道为什么。

接下来，对每个值得处理的问题，它开一个隔离的 worktree，一份独立的代码副本。为什么必须隔离？因为多个智能体同时改一份代码，互相踩脚就是灾难。一旦开始并行，隔离不是优化，是底线。

然后，一个子智能体在 worktree 里起草修复。另一个子智能体，按项目规范和现有测试，审查这份修复。注意这个细节：写的和查的，不是同一个。这是全片最重要的伏笔，马上展开。

审查通过，循环通过 MCP 连接器自动开 PR、更新工单。MCP 是智能体跟真实世界对接的协议。Claude Code 和 Codex 都用它，两边概念一一对应，连接器基本互通。

它处理不了的问题呢？落进一个收件箱，等人来看。

一天结束，状态文件记下今天试了什么、过了什么、剩下什么。明天早上，循环从今天停下的地方继续。这就是状态文件的意义：智能体每次运行结束都会失忆，状态文件是循环唯一的记忆。没有它，每天都从零开始。

这一整天里，你出现了几次？一次。看收件箱那一次。这就是「我的工作是写循环」的具体含义。

## 从提示词到循环：先快进这三年

「写循环」这个姿势，不是凭空冒出来的。过去三年，用 AI 写代码的方式换了好几代，每一代都是被上一代的瓶颈逼出来的。先花一分钟，把这条路快进一遍。

最早是 Prompt Engineering，研究怎么措辞。但模型越来越聪明，措辞的边际收益一直在递减。于是重心移到 Context Engineering：不纠结说法，转去策划模型能看到什么。这一层到今天依然重要，但它只管单次调用的质量——写完了谁来确认写对了？依然是你。

所以下一层是反馈循环：让智能体自己验证自己，跑测试，查日志，打开浏览器看渲染结果。我的判断是，这一层是目前大多数人回报最大的投资点。再往上是 Harness，驾驭系统，一句话定义：Agent 等于 Model 加 Harness。

而 Loop Engineering 是这条路的收敛点：不是把一次运行做好，而是设计一个系统，持续调度这些运行。用开车打比方，就是从手动开车，一路升级到运营整个自动驾驶车队。

Boris Cherny 把这条路压成一条时间线。2023 年，你写代码。2024 年，你提示 Claude 写代码。2025 年，你写循环，让循环提示 Claude。2026 年，你构建系统，运行这些循环。你刚看完的那一天，就停在这条时间线的最后一格。

## 回放那一天：五大模块，一一命名

这套循环的解剖图，最早是 Addy Osmani 画出来的：五个构建模块，加一个贯穿全程的状态层。这个拆法已经成了社区共识。听起来像清单？其实你全都见过——就在早上那一天里。我带你回去，一个一个认。

还记得早上那个自动醒来的定时任务吗？那是第一个模块，Automation，自动化。它解决的失败模式最朴素：没有触发器，循环就得靠你记得去启动——那就不叫循环了。

Codex 那边有个 Automations 面板，配好项目、提示词和频率就行。没发现问题的运行，还会自动归档，不来烦你。Claude Code 这边是另一套：/loop 让任务按节奏反复跑，Hooks 在生命周期的关键节点挂上命令。另外有个 /goal，是我最喜欢的设计，先按下不表，案例里讲。

想让循环在你合上笔记本之后继续转？接上 GitHub Actions 这类 CI 设施就行。

接着，循环给每个问题开了一份独立的代码副本——第二个模块，Worktree。为什么必须隔离，早上说透了，不重复。值得补的是两边的实现：Codex 是内建的，每个线程自动一份。Claude Code 用 git 原生能力：开会话时加 --worktree 参数；或者给子智能体配置写一句 isolation: worktree，干完活还会自动清理。

那个 triage skill 呢？Skill 是第三个模块，打包好的项目知识。一个文件夹，一个 SKILL.md 写清指令，配上脚本和参考资料。它解决的失败模式你肯定遇过：项目里的门道，每开一次新会话，都得重新教一遍。

两边格式完全一样，可以手动调用，也能在任务匹配描述时自动触发。这里有个反直觉的实战经验：技能描述要写得越无聊越好。精确、朴素，自动匹配才准。写得花哨，反而触发不准。

然后是自动开 PR、更新工单那一步——第四个模块，Plugins 和 Connectors，靠 MCP 跟真实世界对接。读 issue tracker、查数据库、往 Slack 发消息，都走这条路。两边协议相同、连接器互通，早上说过，不展开。

第五个模块，就是早上埋的那个伏笔：写修复的和审修复的，是两个子智能体。Sub-agents，Maker/Checker 分离。Claude Code 这边，子智能体定义在 .claude/agents/ 目录下，还能组成 agent team，互相传活。Codex 那边对应 .codex/agents/，用 TOML 文件写。至于为什么必须分开——下一节，用一个真实系统给你看证据。

最后是 State，状态层。它不算第六个模块，更像贯穿前五个的底座。早上你已经看过它救场：智能体会失忆，仓库不会。形式随你挑：一个进度文件，一份 AGENTS.md，甚至一个 Linear 看板，靠 MCP 读写。

五个模块加一个状态层，拼回去就是早上那一天。这个框架一点都不神秘——你只是刚刚才知道，每个零件叫什么名字。

## 真实案例：裁判和选手，不能是同一个

第一个案例，自动 PR 工作流。流程你已经看过全程，就是早上那一天：从 triage 扫描，到自动开 PR。这里只补一个增量——那个我按下不表的 /goal。

它的用法，跟你习惯的指挥方式相反。你不说「修复这个 bug」，你说：跑到 test/auth 下所有测试通过、lint 干净为止。你定义的是终态，路径它自己找，失败了自己换思路。

更关键的是裁判。判断终态有没有达成的，是一个独立的小模型，不是写代码的那个智能体自己。你看到的是「设个目标就能走开」，它可信的原因是：裁判和选手，从来不是同一个。为什么必须这样？第二个案例，就是证据。

第二个案例来自 Claude 背后的团队，一个三智能体 bug 修复循环。他们用的是 GAN 的思路，生成对抗：一边拼命做，一边拼命挑刺。

三个角色。Planner，规划者，接到一到四句话的问题描述，扩写成完整的修复方案。它被故意限制：只管做什么，不碰实现细节。反直觉吧？规划不是越细越好吗？不是。规划层一旦在技术细节上犯错，错误会向下游级联传播。让它少说，是结构性防御，不是偷懒。

Generator，执行者，按方案逐步实现，做完给自己打分。分数趋势向好，就继续优化。方向本身错了，就果断推翻，从头来过。

真正的主角是 Evaluator，评审者。它通过 Playwright，像真实用户一样操作应用：点 UI，调 API，查数据库状态。任何一个维度低于阈值，整轮作废，打回重做。

它能抓到多具体的 bug？两个真实例子。矩形填充工具，只在拖拽的起点和终点放了图块，中间全空——fillRectangle 函数存在，但 mouseUp 的时候没被正确触发。另一个，PUT /frames/reorder 这个路由，定义在 /{frame_id} 之后，框架把 reorder 当成整数 ID 去解析，直接返回 422。

这种级别的反馈，靠模型自我批评，永远拿不到。团队的原话是：让模型评判自己的工作，它会自信地称赞自己，哪怕质量明显平庸。

代价当然有。内部数据：标准对话消耗 1 倍 token，单智能体循环约 4 倍，多智能体系统约 15 倍。但多智能体在内部评估里，比单智能体好了百分之 90.2。我的看法是，这 15 倍不是浪费。你是在花钱买一个结构上才给得了的东西：一个不会给自己放水的裁判。

## 四条设计原则

把这两个案例拧干，剩下四条原则。

第一条，自验证。智能体必须能端到端验证自己的工作：跑测试，跑 lint，跑类型检查。「我觉得改好了」不算验证，机器可检查的通过或失败，才算。

第二条，Maker/Checker 分离。这条你刚看完一整节的证据，不重复。只补一句定位：它是整个循环工程里，最重要的结构性决策。

第三条，成功标准必须可检查，而且检查的是正确性本身，不只是指标。因为智能体会作弊，还是合法作弊。为了让测试通过，它可能直接删掉失败的测试。为了让 lint 通过，它可能用 eslint-disable 把代码淹没。检查全绿，工作稀烂。所以圈子里现在流行一句话：设计评分标准才是真本事，模型反而是简单的部分。Rubric design is the skill now.

第四条，熔断。每个循环必须有明确的停止条件。生产环境的参考参数：最多迭代 15 到 25 步，超时三百秒左右，单次成本预算 2 美元上下。再加一个实用技巧：给每次迭代取哈希指纹，连续三次一模一样，立刻停。不设熔断的循环，就是不设上限的账单。

## 你的第一个循环，今晚就能跑起来

原则都在了。最后讲怎么从零开始，今晚就动手。入口比你想的近，完全不用一步到位。

第一步还是 /goal。比如你在修一个前端适配问题，别说「帮我修这个 bug」，写成：所有 Playwright 截图和设计稿的像素差异小于百分之一，且 npm test 全部通过。设好，去喝杯咖啡。它自己改代码、跑测试、看结果、再调整。还是案例里那个原则：定义终态，让它自己找路。你身份的转变，就从这一句开始。

等单个 /goal 兜不住任务复杂度了，再上 Dynamic Workflows，动态工作流。它根据你的任务，动态生成一段编排脚本，调度最多上千个并行子智能体。最猛的真实案例来自 Bun 的作者：他用这套东西，把 Bun 从 Zig 移植到 Rust。75 万行代码，数百个智能体并行，百分之 99.8 的测试通过，11 天完成。

但要提醒两句。这个功能目前处于研究预览阶段，不算成熟稳定。它的 token 消耗也显著高于普通会话，先小范围试，确认有效再铺开。

这三个工具是互补的：/goal 管深度，Dynamic Workflows 管广度，/loop 管持续性。

再往后的路径就清晰了。用 worktree 把并行任务隔离开。在 .claude/agents/ 里定义一个 reviewer 子智能体，把写和查的分离落地：安全审查的盯漏洞，性能审查的盯瓶颈。再建一个 PROGRESS.md，每次运行把经验和坑写进去，下次从进度继续。做到这一步，你就有了一个会过夜的循环。

成本上有一个十倍杠杆：prompt caching。前面说过多智能体烧 15 倍 token，而用好缓存，token 单价能从每百万 3 美元，降到每百万 0.3 美元。前提是 prompt 保持追加式增长，中途别换 tools 列表、别换模型——一换，缓存就碎了。给个参照系：三智能体系统生成一个完整应用，单次成本 125 到 200 美元。日常的 bug 修复循环，应该控制在 2 美元以内。

最后是三个新手最容易踩的坑。第一，工具给太多、描述写太模糊。一个场景，连人类工程师都说不清该用哪个工具，智能体也不可能选对。少而精的工具集，远好过大而全的工具库。

第二，工具出错的时候，返回错误字符串，不要抛异常。传统工程里异常是规范，但在循环里，异常会杀死循环本身，错误字符串才给模型自己纠错的机会。

第三，保留失败的痕迹，不要清理现场。失败记录是模型避免重复同样尝试的唯一证据。擦掉失败，等于擦掉证据。

## 循环替你写代码，替不了你当工程师

到这里，整台机器你都会搭了。合上之前，三个警告。我认为它们比前面所有技巧都值钱。

最直接的一条：验证永远是你的责任。智能体说 done，只是一个声明，不是一个证明。循环跑完了，CI 全绿了，PR 自动开了——这些只代表你设定的检查通过了。而你的检查，可能不够好。

比它更隐蔽的，是理解力债务。循环交付得越快，你的代码库里「存在但你不理解」的部分就越大。这不是能优化掉的 bug，它是交付速度的直接副产品。你只能持续偿还：抽查，读 PR，问为什么。

而我觉得最锋利的，是认知投降这个陷阱。同样是搭循环，出发点不同，结局完全不同。出于工程判断去设计循环，是进步。为了回避思考去设计循环，是灾难的序曲。

现在合上全貌。从提示词到循环，每一步的本质都一样：把重复性的判断交给机器，把系统性的设计留给人。

循环替你写代码，替不了你当工程师。建造循环，但要以一个打算继续当工程师的人的姿态，去建造它。
