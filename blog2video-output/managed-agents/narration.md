# Anthropic把Agent拆成"脑"和"手"，性能暴涨90%？

## Hook

你花三个月精心打磨的 Agent 系统，模型一升级，里面的补丁就变成了废代码。这不是假设，是 Anthropic 自己踩过的坑。他们刚公开了 Managed Agents 的内部架构演进，核心结论只有一句话：别再优化 harness 了，设计一个能不断替换 harness 的系统。

## Brand Intro

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。今天我们精读的是 Anthropic 工程博客最新发布的 Managed Agents 架构设计。

## Harness 是一组会过期的假设

先说一个关键认知。我们平时说的 Agent harness，就是模型外面包的那层控制系统。循环调用模型、路由工具、管理上下文，这些都算 harness 的活儿。

但 harness 有一个本质问题：它编码的是"模型做不到什么"的假设。模型不会自己管理上下文？harness 来管。模型会执行危险命令？harness 来拦。

问题在于，模型在进步。假设会过期。

Anthropic 举了一个真实案例。Claude Sonnet 4.5 有一个毛病，叫 context anxiety。当它感觉自己的上下文窗口快用完了，它就会提前草草收场，不管任务做没做完。

团队的应对方案是在 harness 里加了 context reset，主动帮它重置上下文。问题解决了。

但是，当他们把同一套 harness 用在 Claude Opus 4.5 上的时候，发现 context anxiety 这个行为已经消失了。模型自己学会了处理这个问题。那个 reset 补丁变成了 dead weight，纯粹的死重量。

这不是个例。Anthropic 的判断是，随着模型不断升级，harness 里的补丁会越来越多地变成废代码。你越是精心优化 harness，它过期得越快。

## 一开始：所有东西塞进一个容器

Managed Agents 是 Anthropic 的托管 Agent 服务，帮客户跑长时间的 Agent 任务。最初的架构很直觉：把所有东西放进一个容器。Session 日志、Agent harness、执行沙箱，全在一起。

好处显而易见。文件操作就是本地系统调用，不需要设计任何服务边界。简单粗暴，能跑。

但问题来了。他们养了一只"宠物"。

在基础设施领域有个经典比喻：宠物 vs 牲畜。宠物是有名字的、精心照顾的、坏了就心疼的。牲畜是可替换的、挂了就换一个的。

他们的容器变成了宠物。容器一挂，session 就丢了。容器卡住了，就得想办法把它救回来。

## 救容器有多痛苦

救容器这件事本身就是噩梦。当 session 卡住的时候，团队唯一能看到的窗口就是 WebSocket 事件流。但事件流只能告诉你"出问题了"，不能告诉你问题出在哪一层。

Harness 的 bug、网络丢包、容器离线，这三种完全不同的故障，在事件流里看起来长得一模一样。

要搞清楚到底怎么了，工程师得打开一个 shell 进到容器里面去调试。但这个容器里还有用户数据。于是就陷入了一个两难：要调试就得进容器，进容器就碰到了用户数据。实际上等于丧失了调试能力。

还有第二个问题。harness 默认假设所有资源都在容器里。当客户说，我想让 Claude 连我自己的私有云，行不行？

行，但得把客户的网络和 Anthropic 的网络做对等互联。或者让客户在自己环境里跑 Anthropic 的 harness。两个选项都很重。一个写死在 harness 里的假设，变成了架构级的限制。

## 把脑和手拆开

解决方案是三个字：解耦。

把"脑"和"手"拆开。脑就是 Claude 和它的 harness，负责推理和决策。手就是沙箱和工具，负责执行操作。再加上一个独立的 session 日志，记录所有发生过的事情。

三者之间通过接口通信，互不依赖。任何一个挂了，不影响其他两个。

具体来说，harness 离开了容器。它调用容器的方式，跟调用任何其他工具一样。一个统一的接口：execute，传入名称和输入，返回一个字符串。

容器从宠物变成了牲畜。挂了？harness 把错误当成普通的工具调用失败，传回给 Claude。Claude 觉得应该重试？那就用 provision 接口拉起一个新容器。不用救，直接换。

## Harness 自己也可以挂

更有意思的是，harness 本身也变成了牲畜。

因为 session 日志存在 harness 外面。harness 里面没有任何需要在崩溃后幸存的状态。挂了就挂了。

新的 harness 启动后，调用 wake 拿到 session ID，调用 getSession 拿回事件日志，从最后一条事件继续跑。在运行过程中，harness 用 emitEvent 不断往 session 写入事件，保证记录是持久的。

这意味着系统里没有任何一个组件是不可替换的。脑可以换，手可以换，两者之间的连接也可以换。所有状态都在 session 日志里，而 session 日志是独立的、持久的。

## 安全边界：凭证不可达

解耦还顺手解决了一个安全问题。

在之前的单容器架构里，Claude 生成的代码和凭证跑在同一个环境中。这意味着什么？如果一个 prompt injection 攻击成功说服了 Claude 去读自己的环境变量，攻击者就拿到了凭证。

拿到凭证之后能干什么？可以用这些 token 生成新的、不受限制的 session，然后把工作委派给它们。游戏结束。

你可能会说，那就限制 token 的权限范围。但这里有一个反直觉的点：这种限制本质上是在假设"模型用受限 token 做不了太多事"。而模型在变聪明。今天做不到的事，明天也许就能做到。

所以 Anthropic 的结论是：不要靠限制权限来防御，要让凭证在物理上不可达。

他们用了两种模式。第一种是 Git 场景。用仓库的 access token 在沙箱初始化时克隆代码，把 token 写进本地 git remote 配置。之后 Claude 在沙箱里 push 和 pull 都正常工作，但它永远接触不到 token 本身。

第二种是 MCP 工具场景。OAuth token 存在沙箱外面的安全保险库里。Claude 通过一个专门的代理来调用 MCP 工具。代理用 session 关联的 token 去保险库取凭证，完成外部调用。Harness 自始至终不知道任何凭证的内容。

安全的核心不是"权限太大"，而是"凭证可达"。结构性修复就是让它不可达。

## Session 不是 Context Window

长任务经常超出 Claude 的上下文窗口。常见的应对方式是压缩、摘要、裁剪。但这些策略有一个共同问题：它们涉及不可逆的决策。

你决定扔掉某些 token 的时候，你不知道未来的对话轮次会不会需要它们。压缩后的消息如果没有额外存储，就真的丢了。

Anthropic 之前的工作探索过一种思路：把上下文当成一个独立对象，存在 context window 之外，让模型通过写代码来查询和切片。

Managed Agents 把这个思路工程化了。Session 日志就是这个独立的上下文对象。接口是 getEvents，允许 harness 按位置切片读取事件流。

可以从上次读到的位置继续往下读。可以倒回某个特定时刻之前几条事件，看看那个动作的前因。可以在执行某个关键操作之前重新读取相关上下文。

读出来的事件在传给 Claude 的 context window 之前，harness 还可以做任意变换。比如重新组织顺序来提高 prompt cache 命中率，或者做各种 context engineering。

这里有一个设计巧思。Anthropic 把"可恢复的上下文存储"和"任意的上下文管理"拆成了两个独立的关注点。存储放在 session 里，保证持久和可查询。管理放在 harness 里，可以随意变换。

为什么要这样拆？因为他们不知道未来的模型需要什么样的 context engineering。Session 接口只保证一件事：数据在那里，你可以拿。怎么用，harness 说了算。harness 可以换，但数据不会丢。

## 性能：p95 延迟暴降超过90%

解耦带来了一个意外的性能红利。

在旧架构里，每个 session 启动的时候，都要先拉起一个容器。哪怕这个 session 可能根本不需要执行任何代码。容器要克隆代码仓库、启动进程、拉取事件日志。这些都是死时间。

用户感受到的延迟叫 TTFT，time to first token。从提交任务到看到第一个回复字符的等待时间。这是用户体感最强烈的延迟。

解耦之后，容器变成了按需分配。不需要容器的 session 就不等容器。推理可以在编排层拿到事件日志后立即开始。

结果是 p50 TTFT 下降了大约百分之60，p95 TTFT 下降超过百分之90。

百分之90。这个数字值得停下来想一想。

p95 代表的是最慢的那百分之5的请求。这些请求的延迟降低超过百分之90，意味着之前那些需要等很久的 session，等待时间变成了原来的十分之一都不到。

而且这个改善不是靠加速什么东西得来的。恰恰相反，是靠消除不必要的依赖得来的。不是让容器启动更快，是让不需要容器的 session 根本不碰容器。

## 多脑多手

解耦还打开了一个新的可能性：多脑多手。

先说多脑。扩展到多个 brain 只需要启动多个无状态的 harness。它们不需要各自独占一个容器。需要 sandbox 的时候再通过工具调用去分配。

这也解决了之前的 VPC 问题。harness 不在容器里了，也就不再假设所有资源都在本地。客户的私有云资源可以作为远程工具被调用，不需要网络对等互联。

再说多手。每个 brain 可以连接多个 hand。每个 hand 就是一个工具接口：execute，传入名称和输入，返回字符串。这个接口可以是一个容器，可以是一个 MCP server，甚至可以是一个手机或者一个游戏模拟器。Harness 不关心也不需要知道。

而且因为 hand 和 brain 不绑定，brain 之间可以互相传递 hand。一个 Agent 用完的沙箱，可以交给另一个 Agent 继续用。

但这里有一个 tradeoff 值得说。让模型同时管理多个执行环境，决定把工作发到哪里，这是一个更难的认知任务。Anthropic 最初把所有东西放进一个容器，其中一个原因就是早期模型做不到多环境决策。是模型能力的提升，才让这个架构成为可能。

这又回到了开头的主题：harness 编码的是模型能力的假设。模型变强了，单容器这个限制就反过来变成了瓶颈。

## Synthesis

回过头看，Managed Agents 的设计思路其实来自一个几十年前就解决过的问题：怎么为还没被发明的程序设计系统？

操作系统的答案是虚拟化。把硬件抽象成进程、文件这些接口。接口比硬件活得久。read 命令不关心底下是70年代的磁盘组还是现代的 SSD。上面的抽象稳定，下面的实现随便换。

Managed Agents 做的是同一件事。把 Agent 的组件虚拟化成三个接口：session、harness、sandbox。不对具体实现表态，只对接口的形状表态。

他们赌的是这三个接口能比任何一个具体的 harness 实现活得更久。这个赌注的依据是：模型在进步，harness 里的假设在不断失效，但"Agent 需要操作状态、需要执行计算、需要可靠地长时间运行"这些需求不会消失。

一句话总结。Harness 越好，过期越快。所以 Anthropic 不再优化某一个 harness，而是设计了一个能不断替换 harness 的元系统。这可能是目前对 Agent 架构最务实的工程回答。
