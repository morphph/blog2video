# Anthropic 让 Agent 关掉 500 个 bug，凭什么？

## Hook

Anthropic 发新产品 Claude Tag 那天放了一句话：他们正在把工作的未来分享给整个世界。配套博客里给了 4 条经验——Roster、north star、Doer-Verifier、信任曲线。听起来全是组织管理学的词，却是他们让自家 Agent 独立修完一大批 bug 的真实地基。

## 从单人模式到多人在线

我们过去用 AI 的方式，其实一直是单人模式。一个人，一个 chat 窗口，一个任务。从 ChatGPT 到 Cursor 到 Claude Code，工具越来越强，场景越来越多，但模型本质上还是你一个人的副驾驶。

这次 Anthropic 把这个范式直接掀了。Claude Tag 这个产品，把 Agent 放进 Slack 这种团队真正在干活的地方。它不再是你私人桌面上的助手，而是和你同事一样，挂在团队频道里，跟所有人一起共享一个工作空间。

这套新玩法，他们叫 multiplayer agent，多人在线模式的 Agent。人类负责定战略，Claude 负责跑执行。听起来像市场话术，但 Anthropic 这篇文章真正值钱的地方，是把跑这个模式的四条具体经验摆出来，并且明确告诉你：每一条都对应一个他们踩过的坑。

## Agent 不是 API，是同事

先搞清楚 multiplayer agent 到底是什么。它和你平时调用的那个 Agent 不一样，至少多了三样东西。

第一，它有持久记忆。它能记住团队的目标，知道你们要往哪里去。第二，它有自己的凭据，不绑定到任何一个具体的人。这意味着它能在一套安全可预测的规则下独立行动，而不是借你的账号去干活。第三，它能持续广泛地访问信息，从而长出对整个组织怎么运转的理解。

这三样东西加起来，才让 Agent 有资格做"团队成员"，而不是"工具人"。但 Anthropic 自己也说得很直白：这只是技术地基。要让人和 Agent 真的能一起把事做成，靠的不是这套能力栈，是接下来这四课组织活。

## 第一课：把工作搬到台面上

第一课，Work in public——所有信息默认公开，让 Agent 有广阔的上下文可看。

这话听起来像废话，但你想一下你自己团队的日常：多少决定是在私聊里拍板的？多少关键信息是在走廊里口头同步的？多少文档是"先发给你一个人，别外传"的？这些东西对人类来说是日常社交润滑剂，对 Agent 来说全部等于零。

Anthropic 在这里抛出了我读完最受震撼的一句话：对 Agent 而言，没写下来并且可被搜索到的东西，就等于不存在。Slack 私聊、走廊对话、被限定权限的文档，Agent 一样都拿不到。

他们的做法不是逐个文档去问"这个能不能给 Agent 看"，那种微决策疲劳会同时拖垮人和 Agent。他们的做法是在公司层面画几条粗的安全边界，整个 workspace 一刀切。在边界内，所有上下文对所有人和所有 Agent 都流动。在边界外，谁都看不到。

代价也讲得清楚。默认内部公开这件事，需要文化转变。对习惯了 need-to-know 那套安全直觉的组织，这是真门槛，不是改个配置项就能完成的事。但你要看回报：Agent 因为能读到会议纪要，就不会再去推已经被砍掉的项目。Agent 因为能跨团队读 product spec，就能把别人成功过的模式带过来。它读文档比人快得多，常常能挖出团队自己都漏掉的相关信息。

所以"默认私密"这种协作文化，在多 Agent 团队这里是一种隐形税。你不交，你的 Agent 永远活在上下文饥饿里。

## 第二课：人和 Agent 共用一张花名册

第二课，给每一个人和每一个 Agent 一个明确的角色，配上他们干活需要的工具。

这一课的关键词是 roster，花名册。在 Anthropic 的多 Agent 团队里，人和 Agent 共用同一张花名册、同一套产物、同一个工作空间。Agent 有自己的凭据、自己的 skill 文件、自己的工具权限。不同的 Agent 还分担不同的角色：一个负责数据分析，一个负责守住设计规范，一个负责跑研究综合。

项目启动的时候，人类直接和 Agent 聊：这个项目，谁干啥。一旦分工敲定，主 Agent 可能会再起几个子 Agent 来处理细分任务。但每一个 Agent 都必须配齐对应的工具。负责数据分析的那个，要能接 BigQuery。负责 QA 的那个，要能接 Playwright MCP。工具不齐的 Agent，就像没装电脑的新员工，挂个名而已。

为什么这么重要？因为没有 roster，会出现一个 Anthropic 点名的失败模式：每个人都偷偷养自己的私人 AI。同一份指标，三个人各让自己的 Claude 算一遍，三个数都不一样，团队 context 当场碎掉。而一个共用的多 Agent 团队成员，把这件事做一次，所有人看同一个数。

人和 Agent 在同一条 Slack 线程里干活，任何人都可以接住任何人放下的活。Anthropic 一个工程团队甚至专门加了一个 release manager Agent，项目一复杂，就往花名册里加新成员。花名册让"团队"这个心智模型，可以随着 Agent 数量的增长而平滑扩展。

## 第三课：北极星不是 KPI，是 Agent 的主动性开关

第三课让我读完特别想圈起来：set a north star to make agents more proactive，设一颗北极星，让 Agent 变得主动。

什么意思？大部分时候，Agent 是被动接活的——你派什么它干什么。但 Anthropic 团队里最重要的那些 Agent，会自己提出新项目、新方向。这件事不会凭空发生，得满足两个前提：第一，团队已经按第一课和第二课把上下文铺好、角色配齐；第二，团队得给 Agent 一个明确的 north star。

北极星是什么？是一个雄心很大、覆盖很广的目标，作为团队判断"这件事该不该做"的指南针。Anthropic 强调，north star 永远由人类来定，必须扎根在公司的使命和业务目标里。

举个原文里的具体例子。有一个内部工具团队，他们的 north star 写的是：让产品的 onboarding 更有用。这句话一旦写下来发给 Agent，他们团队里某个 Agent 就主动建议改 onboarding flow 里的错误提示文案。下一周，onboarding 成功率显著上升。

注意，这个 Agent 没有被派活，它是看了 north star 自己提的方案。

但这一课有个容易忽略的代价。Anthropic 明说：不太可能团队里每个 Agent 都有能力和信用度去主动出活。人类要再做一次挑选，决定哪些 Agent 可以拿到这个主动权。北极星不是发完就完事，是配套一份"主动性授权清单"。

我读到这里突然意识到，Agent 主动性的开关，根本不在模型参数里，就在这一句 north star 的措辞里。

## 第四课：信任不是一次性给的，是沿任务一档一档解锁的

第四课是这篇文章里证据最重、争议最少的一条：信任要慢慢建立。

Anthropic 工程师让 Agent 独立处理了一大批 bug 修复。但开篇就声明：things certainly didn't start off that way——一开始绝对不是这样。

他们把 Agent 当新同事看待。新同事入职，你要花时间评估他的能力，要走多轮反馈把团队里那些没写下来的隐性规则一条条外化给他。Agent 也是一样。你要不断给它派各种各样的任务，才能摸清它能做什么、目标该怎么描述、要给它哪些 skill 文件、什么样的 prompt 能引出你想要的行为。

还有一个反直觉的细节：模型升级之后，旧 prompt 反而可能要重写。原来对老模型有用的 guardrail，到了更聪明的新模型这里，可能反过来卡住它，让它做不出更有创造性的方案。直觉上你以为模型越强越省事，现实是更强的模型需要你松开旧脚手架。今天的护栏，明天可能就是瓶颈。

那怎么持续保证质量？Anthropic 给的答案是：让 Agent 在送到人面前就先自检。代码有测试。文档有 rubric 和风格指南。除此之外，他们大量用一种叫 Doer-Verifier 的搭档结构——一个 Agent 干活，另一个 Agent 专门检查前一个 Agent 的活。

这里有一个我读完才回过味的判断。Doer-Verifier 表面看起来是"两个 Agent 互查、容错冗余"，但 Anthropic 把它和另一句话挂在同一根逻辑线上：把人类注意力当成稀缺资源对待。让 Agent 互查的真正目的，不是省 Agent，是省人。每一次送到人面前的活，已经是过了内部质量门的活。

那个 500 bug 的故事，原文是这样讲的：一位工程负责人接手一个 backlog 很大的新团队。他派了两组 Agent：第一组读全部 backlog，看看每条有没有 owner，给没主的事打复杂度分；第二组从复杂度中低的事里挑出来直接产出代码改动。一开始，人类审查 Agent 的每一个决策，标出哪些必须人参与的。然后，他们把"遇到这种决策要上报人类"这条规则教给 Agent。再然后，每周让 Agent 自己写一份 lessons & missteps 周报，记录踩过的坑，下次别再踩。慢慢地，他能把越来越复杂的任务交给 Agent，越来越少时间盯日常。

最后一步特别关键。Agent 独立之后，他还专门教它们怎么和人沟通：把问题打包、一次性问完；重要 context 重复给人一遍，方便人快速接上；控制每次让人看的事数量。甚至他团队里有 Agent 的唯一职责，就是决定哪些事值得打扰人。

信任曲线就是这样跑出来的。不是一次性授权，是沿任务类型一档一档解锁。500 这个数字，是这条曲线跑到后期的结果，不是起点。

## 这四课不是新东西，是被 Agent 重新放大的旧东西

四课讲完，回到全局。

我读完最深的感慨是，这四件事单拎出来，每一条对人类团队都不是新鲜事。强北极星、清晰角色、扎实的文档、共识的质量门、给人犯错和学习的空间——这些是我们已经知道几十年的健康团队习惯。

Anthropic 自己在文章最后也承认了这一点：None of these patterns are new—at least not for humans. 这些 pattern 没有一个是新的，至少对人来说不是。

但他们紧接着说了一句更重的：Agent 让这些 pattern 变得更加不能跳过。

为什么？因为 Agent 把"组织松散"的代价直接放大了。人和人之间，私聊里说一句话，对方能心领神会，能脑补背景。Agent 不会。你团队里的隐性默契越多，Agent 越接不住活。你团队里的角色越模糊，Agent 越会被一群"个人版 AI"取代，每个人在桌子底下偷养自己的一只，team context 当场分裂。你团队里没有北极星，Agent 永远只能被动等活；你团队里没有逐步授权的耐心，Agent 永远跑不到独立修一大批 bug 那一步。

也就是说，Agent 协作的瓶颈，从来不在 Agent 这一侧。瓶颈在你团队那些一直没认真做的组织活——只不过 Agent 把账本翻出来，让你不能再装看不见。

## 总结

所以，回到开头那个数字。让 Agent 关掉那 500 个 bug 的，不是模型，是把"默认公开"写进团队文化的那条决定。

模型给你的是引擎，组织文化决定你能不能开得动。这四课的真正含义是：多 Agent 时代，最稀缺的能力，不是写 prompt，不是接 MCP，而是把人和 Agent 当作一支真正的团队来组织。

## 收尾

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
