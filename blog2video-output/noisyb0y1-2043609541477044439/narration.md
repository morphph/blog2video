# 一个文件让Claude代码违规率从40%降到3%？

## Hook

一个 Google 工程师，11年经验，现在每天只工作两三个小时。剩下的时间系统自己跑，活照干，钱照拿。他靠的不是什么黑科技，而是一个 markdown 文件加一套 agent 编排。今天我把他的整套方法拆开给你看。

## Brand Intro

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。今天我们精读的是一篇关于 Claude Code 自动化工程实践的深度分析。

## 一个 markdown 文件为什么能改变 Claude 的行为

故事要从 Andrej Karpathy 说起。他观察到 LLM 写代码时有几个高频犯的错：过度工程化、无视项目已有的风格、擅自加依赖、改了不该改的文件。这些不是随机 bug，是可预测的失败模式。

有人把这些观察浓缩成了一个 CLAUDE.md 文件，放在项目根目录。一周之内 GitHub 上拿了一万五千颗星。

这个文件的核心就四条原则。第一，写代码前先想清楚，防止假设错误和遗漏权衡。第二，简单优先，防止过度抽象。第三，手术刀式修改，只动该动的代码。第四，目标驱动执行，先写测试再写实现。

没有框架，没有复杂工具链。就一个文件，五分钟配好。

## 从百分之40到百分之3，到底发生了什么

我觉得这里最值得注意的不是"提示词优化"这个概念。而是它本质上在做的事情：把可预测的失败模式变成了编译期约束。

就像 linter 对人类代码的作用一样。你不需要每次 code review 都提醒同事"别用 var"，配一条规则就行了。CLAUDE.md 对 Claude 做的是同样的事。

实际效果是什么？没有这个文件的时候，Claude 大概百分之40的情况会违反项目规范。加上之后，违规率掉到百分之3左右。

不过我要说一句：这个数字来自社区经验，不是严格的 A/B 测试。但方向是明确的，配置成本几乎为零，收益肉眼可见。

## 一个仓库装下27个 agent

接下来聊一个更大的东西。GitHub 上有个仓库叫 Everything Claude Code，十五万颗星。它不是一个 prompt 合集，更像是一套标准化的 AI 工程系统。

里面有三十多个专门化的 agent。做规划的、做架构决策的、做测试驱动开发的、做代码审查的、做安全审计的。还有一百八十多个预写好的 skill。

我觉得这个仓库真正有意思的地方，不是省了你写 prompt 的时间。而是它证明了一件事：agent 系统可以被标准化为可复用的组件。就像 npm 包一样，拿来就用。

但这里有个很现实的坑。你不能贪心把所有 agent 和 skill 全部加载到上下文里。二十七个 agent 加六十四个 skill 同时塞进去，上下文窗口直接爆掉，质量反而下降。只拿你真正需要的，这是使用它的关键。

## 隐藏的 token 膨胀丑闻

接下来这个发现，是我觉得整篇内容里最值得警惕的部分。

有人架了一个 HTTP 代理，拦截了 Claude Code 不同版本的完整 API 请求。结果发现了一件诡异的事。

v2.1.98 版本，发送了169,514字节的请求，计费49,726个 token。升级到 v2.1.100 之后，发送的数据反而少了978字节，但计费却多了20,196个 token。

少发数据，多收 token。膨胀完全发生在服务端，你通过 /context 命令根本看不到。

这个问题不只是账单上多花了钱。那两万个 token 是实打实地占了你的上下文窗口。你精心配置的 CLAUDE.md 指令，被这些隐藏内容稀释了。长会话里 Claude 越来越不听话？可能不是你的 prompt 写得差，是你的指令权重被冲淡了。

临时的修复方案是回退到旧版。但我必须说清楚代价：旧版本不会持续获得更新和安全修复。这是一个你不得不做的权衡。

## 完整自动化长什么样

最后回到开头那位工程师的案例。他搭了一个三步闭环系统。

第一步，分类。一个 dotnet 应用每15分钟调用 GitLab API，Claude 读取新 issue，判断它是否具备开发条件。不具备的话，自动起草一个回复贴到 GitLab 上等人确认。

第二步，执行。如果 issue 准备好了，subagent 直接开工。写完代码推到新分支，创建 PR 等人 review。

第三步，PR 流程。系统检查是否有新的 review comment，如果有，自动实现修改。

整个循环每15分钟跑一次。这位工程师从每天写8小时代码，变成了每天花两三个小时做 review 和测试。代码质量没有下降，因为他审查每一行。

但这里我要指出一个关键前提：质量完全依赖人工 review 环节。如果哪天他偷懒跳过 review，或者只是走马观花地扫一眼，就没有任何兜底机制了。自动化解放了执行层，但审查层的责任反而更重了。

## Synthesis

回头看整个方案，核心逻辑其实很清晰。CLAUDE.md 解决的是"让 AI 不犯蠢"的问题。Agent 编排解决的是"让 AI 自己跑起来"的问题。而人，退到了审查者的位置。

一个 markdown 文件把 Claude 的犯错率从百分之40砍到百分之3。真正的自动化不是让 AI 更聪明，而是让它不犯蠢。

## Closing

如果你也在用 Claude Code 写代码，最值得立刻做的一件事就是给你的项目加一个 CLAUDE.md。五分钟的配置，换来的是每次交互质量的系统性提升。至于完整的自动化闭环，量力而行，先从约束文件开始，再逐步加 agent，最后才是全流程编排。
