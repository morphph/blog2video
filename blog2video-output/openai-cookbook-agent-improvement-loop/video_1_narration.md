# Agent 不是改 prompt，是改 5 个面

## Hook

Codex 跑出来效果不对，你的团队大概率在 Slack 里留几句"下次注意要引用真实数据"——下次它照样踩。OpenAI 官方 cookbook 把这件事点穿了：教训留成评论，是一次性消耗品。真正能让 Codex 越用越强的，是一条把每次失败变成永久 eval 的飞轮。

## 你在改 prompt，别人在搭一个改进飞轮

先说一个我特别熟悉的场景。Agent 跑出来效果不对，团队在 Slack 里讨论一通，留几句话："下次注意要引用真实数据"、"下次不要瞎推断指标"。这些话当时看挺像那么回事，但下一次跑，同样的坑还是踩。

原文里有一句话点得特别狠，说大多数团队的迭代方式，是把教训留成 disconnected comments——一条条断开的评论。听起来是经验，其实是一次性消耗品。说完就忘，下次重来。

而这篇 cookbook 提的方法，是另一种姿态。它不是优化某一次回答，它是建一条飞轮。每一次失败的 feedback，都会被沉淀成下一轮的 eval。学到的东西不靠人记，靠代码记。这才是"越用越强"四个字真正的含义。

## Harness 不是 prompt，是 5 个面

这条飞轮第一个反直觉的点，就在你以为要改的对象上。

你跑了一次 Agent，结果不行，你的第一反应大概率是回到 system prompt，加一句"请务必引用真实数据"。但原文一开始就把"harness"这个词钉死了。Harness 是一份完整的契约，包含五个面：instructions、tools、routing、output requirements、validation checks。指令、工具、路由、输出要求、校验。

你听到这里就明白了——prompt 只是其中一个面。当你只在改 prompt 的时候，你其实只动了五分之一。剩下的四个面，工具够不够、调用顺序对不对、要求模型输出什么、有没有人去校验，全都没动。Agent 表现没改善，不是因为模型笨，是因为你以为问题在 prompt，其实问题在另外四个面里。

这一刀切得很干脆。它把"调 Agent"从一个写作问题，变成了一个工程问题。

## 把 feedback 变成 eval，才是最高杠杆的一步

整条飞轮里有六个组件：Agents SDK、trace processor、feedback 收集、Promptfoo、HALO、Codex。看起来 trace 很性感，HALO 听起来很高级，Codex 自动出 PR 最像未来。但我读完之后认为，整条飞轮里杠杆最大的那一步，是看起来最不起眼的——把 feedback 转成 Promptfoo eval。

为什么？因为这一步是经验从"一次性"变成"可复用"的唯一接口。

你想一下，没有这一步会怎样。你跑 trace，你收 feedback，HALO 给你排序，Codex 帮你改完代码。挺好。但下一次跑，新的 Agent 怎么知道这次学到的东西？没法知道。除非你把这次学到的判准，固化成一条永远会被执行的 eval。

只有这一步做到了，下次回归的时候，老错误才会被自动拦下来。其他组件没有这一步，全是空转。

这也是为什么我说"你以为在改 prompt，其实要改的是一条飞轮"。飞轮的核心齿轮，不是哪个组件最炫，而是哪一步让经验能复利。

## 5 条 trace，必须打的是失败模式

第二个反直觉的设计，藏在它的样本选择里。

这套流水线里有 5 条 traced runs，覆盖 5 种场景。融资风险，要从烧钱速度和现金跑道推出来。营收质量，要把 ARR bridge 对账。客户集中度，要把母账户合并以后重新看。企业级安全准备度，要在 SOC 2 缺位的前提下评估。还有一类，是那种根本不该被模型推断的指标，模型却容易硬猜。

你注意到了吗？五条 trace，没有一条是"演示成功"。全部是失败模式。

这一点和我们大部分人的直觉完全相反。我们做 demo 的时候，总想先挑几个能跑通的场景，让别人看到效果。但这套流水线从一开始就把 eval 当成防回归工具来设计——既然是防回归，样本就必须覆盖"会出错的地方"，不是"已经能跑的地方"。

happy path 不用测，反正大概率能过。真正要测的，是 Agent 历来栽过跟头的那五个地方。

这是一种很工程师的思维。但很多团队做 Agent eval，做着做着就变成了在收集成功案例，自己感动自己。

## 输出契约 6 件套：什么叫"Agent 把任务做完了"

接着说第三个面，输出要求。这一段我觉得是整篇 cookbook 里最容易被低估的设计。

大多数团队心里"Agent 做完任务"的定义是什么？模型回完话就算完。一段漂亮的总结，结束。

但这套 harness 把"完成"重新定义成一组可机器校验的物理产物。Agent 跑完，必须落下六个文件：summary_answer.md，一句话答案；investment_memo.md，完整版分析；risk_register.json，结构化的风险清单；open_questions.md，还没回答的开放问题；citations.json，每条 claim 对应到了哪份文件；evidence_table.csv，一份审计追溯表。

六件产物，落在工作目录里。然后还不算完——还要过两道校验。一个脚本叫 check_evidence_coverage.py，专门检查每一条 claim 是不是真的引用了 dataroom 里存在的文件，防止模型瞎编引用。另一个叫 validate_output_contract.py，检查六个文件存不存在、JSON 结构对不对、引用的 source 合不合法。

这套设计的意义在哪里？只有当"完成"被定义成机器可校验的东西，Promptfoo 才能把它当成 pass 或 fail 来跑。换句话说，没有这份六件套，eval 根本无从下手。所谓的"Agent 改进飞轮"，前提是先有一条机器看得懂的及格线。

## Harness 不是写在 prompt 里，是写在代码里

再往里看一层，你会发现更狠的设计。这套 harness 不靠自然语言约束 Agent，它靠数据结构。

源码里有三个 Python dataclass：ModelSettings，AgentConfig，ToolPolicy。allowed data roots，Agent 能读哪些目录。writable output dirs，能往哪里写。required artifacts，必须落下哪些文件。evidence preferences，证据冲突时优先信谁。

这些约束不是在 system prompt 里写"请你只读这些目录"，而是直接写进 Python 类。

差别在哪？写在 prompt 里的，是请求，模型可以不听。写在数据结构里的，是代码对象——HALO 可以给它打分，Codex 可以直接改它。harness 一旦"数据结构化"，就变成了可以被自动优化的东西。

这也是为什么我说，agent 改进的本质是工程，不是写作。你在 prompt 里再怎么写"请引用真实数据"，都不如一个 check_evidence_coverage.py 跑一遍来得硬。

## 20 分钟跑完一轮，但代价是四套系统

讲到这里，我必须把代价也讲清楚。

这条飞轮的吸引力很大一部分来自一个数字。原文 prerequisites 里写着：默认配置下，跑完一整轮大约二十分钟。这意味着什么？意味着一次 trace、feedback、eval、HALO 排序、Codex PR 的完整 self-improvement 循环，理论上你午休时间就能跑完一轮。

但代价也很实在。这条飞轮要同时跑通四套系统：OpenAI Agents SDK、Promptfoo、HALO、Codex。任何一环挂了，整条飞轮就停摆。团队要承担四套工具的运维和升级成本。

更现实的一点是，HALO 是 OpenAI 专有组件。给 harness 改动排序这一步，目前在 OpenAI 生态外没有等价的替代品。如果你哪天想脱离 OpenAI 这套栈，这一块得自己实现一个优化器。

还有一个隐性成本。"feedback 转 eval"看起来是自动的，实际上仍然需要人判断——这条反馈值不值得变成一条永久的 eval。低质量的 feedback 直接入库，会污染整个评测集，让未来的迭代被噪声牵着走。

最后是规模问题。20 分钟一轮，前提是 eval 数量很小。当 eval 从 5 条涨到 100 条，HALO 排序和 Promptfoo 全量复跑都会线性甚至超线性变长。飞轮跑得越久，转速越慢。这是任何 eval 体系都绕不开的代价。

## Synthesis

回头看这整条飞轮，我想说的判断只有一句：Agent 改进是基础设施工作，不是 prompt 工作。

你不在调模型，你在搭一条流水线。流水线的入口是真实的失败 trace，出口是 Codex 提交的 PR。中间最关键的那一步，是把"这次的教训"变成"下次也会跑的 eval"，让经验从一次性评论变成永久资产。

这篇 cookbook 真正值钱的地方，不是它推荐了哪个工具栈，而是它把一件事讲透了：harness 是 5 个面，不是 1 个 prompt。当你只动 prompt 的时候，你只动了五分之一；剩下的四个面——工具、路由、输出契约、校验——才是 Agent 真正越来越靠谱的地方。

别人在改 prompt，他们在搭一条让每次失败都变成下次评测的飞轮。Agent 不是被调出来的，是被沉淀出来的。

## Closing

所以下一次你的 Agent 又跑挂了，先别急着回到 system prompt 加一句话。问自己三个问题：这次的失败，能不能变成一条 eval？这条 eval 下次还会被跑吗？要改的，是 prompt，还是工具、路由、输出契约、校验这四个面里的某一个？

想清楚这三个问题，再动手。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
