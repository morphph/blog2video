# Agent 不是改了，是差距变小

## Hook

你让 Codex 跑了一晚上的自动修复，早上起来看，几十次 commit、几百行改动。但代码真的更好了吗？OpenAI 自己出的 cookbook 给了一个判断标准，能让你不靠肉眼也能知道——Agent 是真在收敛，还是只是在烧账单。

## 真正的成功信号，不是 Agent 在动手

先把结论亮出来。原文里有一句话，我觉得是整篇的核心。它说：重要的信号，不是 Codex 又做了一次编辑。重要的信号，是每一轮跑完之后，剩下的验证差距在变小。

你品一下这句话。我们看 Agent 跑循环的时候，下意识盯着什么？盯着它有没有在动手。日志一直在刷，文件一直在改，看起来很努力，我们就觉得它在工作。但这种"在工作"的感觉，可能是假的。

真正的衡量标准只有一个。你把这一轮验证完，剩下多少问题；下一轮验证完，剩下多少问题。两个数字一比。变少，是在收敛。不变，是卡住了。变多，是跑偏了。Agent 到底有没有在朝目标走，看的是这个差距，叫 delta。不是看它有没有在敲键盘。

这个视角翻转，挺反直觉的。但你想想，一个人在解 bug，他改了一百行代码，bug 还在；他改了一行代码，bug 没了。哪个叫工作？我们对人很清楚，对 Agent 反而糊涂。因为 Agent 一直在动，我们就被动作骗了。

## 想测 delta，三个阶段就不能互相帮忙

那问题来了。要测 delta，前提是什么？前提是你得有一个干净的、可比较的差距快照。这就引出了原文里另一个非常硬核的规定。

它把整个循环拆成三个阶段。Review，Repair，Validation。Review 负责检查，找问题。Repair 负责修，根据问题改文件。Validation 负责验证，跑一遍看还剩多少问题。

听起来很普通对吧？但原文有一个特别严格的约束。Review 阶段不准改文件，只准输出发现的问题。Repair 阶段不准重新评估，只按照 Review 给的清单改。Validation 阶段不准修，只准报告。三个动作，被刻意隔离。

我一开始觉得这是工程洁癖。Review 发现了问题，顺手改一下不是更快？但想清楚之后，我觉得这个隔离不是为了分工，是为了测量。

你想，如果 Review 顺手改了一刀，Validation 这一轮跑出来的差距，就不是"上一轮 Repair 之后的真实差距"了，它混进了 Review 自己改的内容。下一轮再跑，delta 不可比较。收敛信号被污染。你看着数字在变，但你不知道是 Agent 在收敛，还是阶段之间在互相帮倒忙。

三相纯度的真正理由，是让每一轮的差距快照都干净。能比较，才能判断在不在收敛。

## 结构化 JSON 不是日志，是契约

三个阶段怎么交接？原文里也写得很清楚。每个阶段都输出机器可读的 JSON。

Review 输出一份 findings 清单，每个问题有类型、有严重程度。Repair 输出一份 change summary，列出改了什么、新的文件路径在哪。Validation 输出执行状态，还剩多少差距。

这看着像标准工程实践。但我觉得它背后有个更深的意思。

如果 Review 输出的是一篇自然语言报告，Repair 阶段自己去读，整条链就退化成小作文接龙。每一次"理解"都会有偏差，错误会累积。换成 schema 之后，Repair 不需要"读懂" Review。它消费的是一份字段固定的合同。下游不解释上游，只签合同。

这才是这个循环能稳定跑好几轮的底座。多轮协作不是靠 Agent 更聪明，是靠阶段之间不需要互相理解。

## 没有 stop 的 loop，不是 loop，是死循环

第三个我觉得特别值的点，是停止条件。

原文在 Production Considerations 里把它列在第一位。它给了三种合法的停止理由。第一种最干脆，全部通过验证，结束。第二种是兜底，达到最大尝试次数，停。第三种最有意思，叫 delta plateauing——差距不再缩小了，停。

第三种为什么有意思？因为它等于承认"打不下去了"也是一种结论。Agent 不一定要把所有问题都修完才能停。如果连续几轮 delta 不再变小，说明它已经收敛到瓶颈了，再跑下去只是烧 token。这个时候停下来交给人，比硬撑更诚实。

反过来说，我之前自己写过的 Agent 循环，几乎都没明确写过停止条件。它就一直跑。看着像在工作，其实早就 plateau 了，只是没人量。

没有 stop 的 loop，本质上就是死循环。它会让你以为 Agent 在勤奋工作，实际上只是在烧账单。

## 三个 notebook，三轮收敛

原文给了一个具体的 demo，验证这套循环到底跑成什么样。三个故意做旧的 notebook，跑了三轮。

第一轮，一个 notebook 通过，剩下两个继续。第二轮，第二个 notebook 通过，最难的那个范围在收窄。第三轮，全部通过。

我想强调的不是"三轮就收敛"这个数字。这是样本结果，不是论点。我想强调的是这条曲线的形状。它是单调的。每一轮剩下的问题都比上一轮少。不是前两轮卡住、第三轮突然全好，是稳稳地、可见地在缩小差距。

这就是 delta 这个信号的价值。你不需要等到 Agent 完全跑完，才知道它在不在工作。第二轮验证一出，你看 delta 比第一轮小，就知道这套循环在收敛。如果第二轮 delta 跟第一轮一样大，你就该考虑换方案了，不用等它跑到第十轮才发现白跑。

## 这套机制有一个根本盲点

讲到这我得说一个 tradeoff，不然就只讲爽点了。

这整套循环的成立，依赖一个假设——Validation 输出是可信的。如果验证规则本身写错了，比如把"应该用新 API"写成"应该用旧 API"，Agent 会朝着错误的方向收敛。而且因为 delta 一直在变小，看起来一切正常。

这是闭环模式的根本盲点。validator 没有 validator。

所以业务规则、验证标准这些东西，必须在循环开始之前显式定义清楚，preferred models 是什么、reader experience 长什么样、reproducibility 怎么算通过。validator 写错了，循环再漂亮也是错的。

## Synthesis

把这几条捏在一起，我自己的判断是这样。

判断一个 Agent 循环有没有在工作，别看它改了多少东西，看下一轮的差距有没有变小。而要能这么测量，前提是 Review、Repair、Validation 三个动作没有互相帮忙——每个阶段动词单一，输出 schema 化，阶段之间签合同而不是讲故事。最后还得给这个循环明确写出停止条件，pass、max attempts、或者 plateau，三选一。

这三件事缺一不可。差距是信号，三相纯度是测量前提，停止条件是出口。没有这三件，Agent 循环就只是一个看起来很努力、但你不知道它什么时候算完的黑盒。

## Closing

下次你再搭一个 Agent 自循环，别先去想怎么让模型修得更好。先回答三个问题：每一轮跑完，我用什么数字衡量"更接近完成"？这个数字怎么保证是干净的？什么时候我会让它停下来？

这三个问题答不出来，再聪明的模型也救不了你的循环。
