[SLIDE 1: cover] (0:00 - 0:30)

你让 AI Agent 帮你写代码，结果它一口气生成90个测试，再一口气写完所有实现——跑完一看，全是垃圾。有没有一种方法，能像遛狗一样拴住它？

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。今天我们精读的是一位开发者关于 Red Green Refactor 和 AI 编程的分享。

答案是一个已经存在了二三十年的老方法：TDD，测试驱动开发。

[SLIDE 2: principle] (0:30 - 2:00)

TDD 的核心循环叫 Red Green Refactor，你可以把它想象成交通信号灯。Red，先写一个注定会失败的测试，让 CI 变红——就像红灯亮了，所有人停下来确认方向。Green，写最小的实现代码让测试通过，CI 变绿——绿灯亮了，放行。Refactor，在测试保护下重构代码——相当于黄灯整理车道，优化通行效率。

Kent Beck 在《极限编程》里最早推广了这套方法。Simon Willison 后来说了一句很到位的话：test-first 开发天然适配编程 Agent。原因很简单——你先写好验收标准，再让 AI 去实现，AI 的每一步都有明确的对错反馈。

这位开发者亲身验证了这一点：当他看到 Agent 先写失败测试、再写实现通过后，他甚至不需要逐行阅读测试代码。只扫一眼标题就够了，因为红变绿的过程本身就是验证。

[SLIDE 3: comparison_cards] (2:00 - 3:30)

那为什么 AI 时代这件事变得更重要了？问题出在 LLM 的本能上。

LLM 喜欢水平铺开：一次性写出一大堆测试，然后试图一口气实现所有逻辑。这位开发者说得很直白——它会在一个文件里塞进90个测试，然后用一次巨大的编辑试图全部通过。结果呢？大量无意义的测试，代码质量稀烂。

正确的做法是单测试循环法：写一个测试，跑失败；写实现，跑通过；再写下一个测试，再写实现。一组一组来，每组做完检查姿势再继续。

这就像健身教练不会让你一口气做100个俯卧撑，而是一组10个，做完检查动作是否标准。每一轮红绿循环，都在保证 AI 写出的代码真正服务于功能，而不是凑数。

[SLIDE 4: checklist] (3:30 - 4:30)

具体怎么操作？你可以在 AI 编程工具里配置一个 TDD 技能指令，核心规则就三条。

第一，每次只写一个失败测试，禁止批量生成。第二，写最小实现让这个测试通过，不许多做。第三，所有测试通过后，再寻找重构机会。

仍然有一点很关键：代码库本身的质量决定了 AI 的上限。这位开发者的原话是——如果你的代码库是一团泥巴，LLM 会很乐意在泥巴里打滚。就像任何开发者一样，给它什么环境，它就产出什么质量。所以强类型语言比如 TypeScript、完善的单元测试，这些都是拴住 AI 的牵引绳。

[SLIDE 5: summary] (4:30 - 5:00)

一句话总结：AI 越能写代码，你越需要用测试来拴住它。一次一个红绿循环，就是最好的牵引绳。

今天就试试：在你的 Agent 配置里加上一条规则——每次只写一个失败测试，再写实现。
