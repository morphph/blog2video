# 1 个 prompt 当 6 个工程师，注定崩

## Hook

Claude Code 用了一个月，你比写代码之前更累——花在监督 AI 的时间，已经超过过去自己敲代码的时间。这就是 vibe coding 的天花板。一个 2.3M 阅读的 X 长帖给了一套出路：把这一个 session 拆成 7 个专职 agent。

## 为什么 vibe coding 会撞墙——不是模型不够强

我先把这个痛点说透一点。你刚用 Claude Code 的时候是觉得有魔法的。一句话过去，整段代码出来，调一下就能跑。

但是到了第三十天，你会发现一件事：你不是在写代码，你是在监督 AI 写代码。同一个逻辑在三个文件里出现。两周前定的命名规范，它早就忘了。新加的功能把旧的搞挂了。测试不是没写，就是写得稀薄到等于没写。

很多人把这归因到"模型还不够强"。我觉得这个判断是错的。问题不在模型，问题在结构。

你想想看，当你在 Claude Code 里敲下"帮我做这个功能"的时候，你实际上是在让同一个 session 同时扮演六个角色：产品分析师、架构师、后端工程师、前端工程师、测试工程师、还有代码审查员。六个工种，挤在同一个对话框里，共用一个上下文窗口。

更要命的是错误会级联放大。计划里一个错误假设，会变成错误的数据模型。错误的数据模型，会变成错误的 API。错误的 API，又会变成错误的 UI。等你察觉的时候，bug 已经从架构层一路扩散到了界面层，全栈都是错的。

这不是 AI 失效了，是你的工作流失效了。Vibe coding 不是技术问题，是组织结构问题——你把一个产品团队的活，硬塞给了一个永远开着六个会的人。

## 7 个 agent 的本质——是工具权限的硬隔离

那解法是什么？把这六个工种，拆成七个专职 agent，每个 agent 一个干净的上下文窗口。听起来像是套了个 SOP，但真正的关键不在这里。

关键在于工具权限的**硬隔离**。

我特意强调"硬"这个字。一般人想到约束 AI，第一反应是写 prompt——"请不要碰前端文件"、"请只修改后端目录"。这种叫软约束，它约束的是意图。但是 AI 一旦在长对话里漂移了，意图根本压不住。

这套系统不一样。Backend Builder 这个 agent，拿到的工具权限里，物理上就没有访问前端文件夹的能力。它不是"不被允许"，而是"做不到"。哪怕它脑子一抽想去改前端组件，工具层就给你拦住了。

每个 agent 的工具配置都是反复推敲过的。Researcher、Story Writer、Spec Writer、Validator，这四个只读。Backend Builder 有写权限，但被锁在后端目录里。Frontend Builder 同理，只能动前端。Test Verifier 只能写测试文件。

一个不能写代码的 agent，再"自信"也不会写出代码污染你的代码库。

这是从软约束到硬隔离的一次范式跳跃。Prompt 里的规则是建议，代码里的规则是法律。

## 真正的杠杆是 3 个人类闸口

讲到这里你可能以为重点是这七个 agent 的分工。其实不是。整套系统真正的杠杆，是三个人类闸口。

只有三个。Story 一次，brief 一次，PR 一次。其他全自动。

我重点讲第二个闸口，brief 这一关。Spec Writer 这个 agent 拿到批准过的用户故事和 Researcher 的发现之后，会产出一份技术蓝图：数据模型怎么改、API 怎么设计、前端要做哪些组件、需要补哪些测试，连每个会被动到的文件都列出来。

你必须在这一刻读完它，然后批准。

为什么这个时刻这么重要？举个原文给的例子。如果 brief 里出现"store IDs in memory"这种描述——把 ID 存在内存里——这就是一个红旗。它意味着这个功能可能不能跨服务器扩展，可能在重启后丢状态。

你在 brief 这一关看到，五秒钟拦截。但是如果你放过去，让 Backend Builder 直接动手，等十个文件改完，bug 才会从测试里冒出来。这时候你回头改架构，那十个文件全部要重写。

人类 review 不是这套系统的瓶颈，它是这套系统能成立的前提。自动化的常识告诉你"减少人类介入等于提效"，但这里完全反过来——它把人类锁定在三个**必须发生**的决策点上，反而保证了流程能跑下去，因为它把"我要不要 review 一下"这个犹豫本身去掉了。

## 一个 invoice 提醒功能的完整链路

光讲框架不够直观，我把原文里的演示场景过一遍，你就理解这条链子是怎么咬合的。

你打开 Claude Code，输入一句话："给超过七天没付款的发票做个提醒功能。"

然后你不再打字。Researcher 启动，把现有的发票、支付、邮件相关代码扫一遍，列出文件、模式和风险。Story Writer 接手，写出用户故事和验收标准。你读一遍——批准。

Spec Writer 把故事翻译成技术 brief。你再读一遍——批准。

Backend Builder 实现服务、API、后台任务、单元测试。所有测试绿。Frontend Builder 读了 Backend Builder 的总结，按照它产出的 API 契约，写出管理界面和触发按钮，自己的测试也绿。

Test Verifier 上场。这个 agent 不写单元测试，它写**验收测试**——从外部模拟真实用户的视角，验证用户故事里每一条标准是不是真的实现了。它跑完报告：七条通过，一条失败。失败原因是手动触发那个按钮没有检查租户归属。

如果换在 vibe coding 模式下，这个 bug 大概率要到上线之后某个客户碰到才会暴露。但在这里，Validator 立刻接力，定位到 Critical 级别，给出文件路径和行号。问题反弹回 Backend Builder，修一行。再跑一遍，八条全过。

你打开 PR，最后一次 review，合入。

## Validator 为什么必须独立——它的价值就是不修任何东西

我特别想把 Validator 这个角色单拎出来讲。因为它是整套系统里最反直觉的一个。

它什么都不修。它只看磁盘上的代码长什么样，对照原始 story 和 brief，告诉你哪里不一致。验收标准漏了哪条没实现、失败路径有没有测试覆盖、权限检查有没有遗漏、敏感日志有没有泄露、有没有重复逻辑应该复用现成的 helper。

输出按严重度分组，Critical、Important、Minor，每个 finding 都带文件路径和行号。如果没问题就直说没问题，不为了显得专业去捏造 issue。

为什么必须独立？原文有一句话我觉得是全文最锋利的：A self-graded paper is worthless. 自评的作业是没有价值的。

Backend Builder 自己跑测试说"全绿"，Frontend Builder 自己说"组件没问题"，这些都是自评。一个真正诚实的审稿人，必须看不到代码是怎么被写出来的，只看代码现在长什么样。Validator 的隔离不是冗余，是它整个存在的理由。

## 7 个角色不是重点，重点是把哪些决定还给人

讲到这里，你可能会觉得这套系统的核心是"agent 数量"或者"流程严密"。我觉得都不是。

它真正的核心在于回答一个问题：**哪些决定必须由人做？**

作者的回答是三个。这个问题对不对（story 那一关）、这个设计合不合理（brief 那一关）、这个东西能不能 ship（PR 那一关）。其他的，AI 都能做，而且做得比人快。

这套架构的价值不是把人赶出流程，而是把人从那些不需要人的部分里拿出来。原文有一句话我很喜欢：流水线不是把你从流程里赶出去，它只是把你从那些不需要你的部分里拿出来。

你还在环里，但你只待在判断力真正有价值的那几个节点上。

你不再是那个一边敲代码一边给 AI 收拾烂摊子的人。你变成了真正在做产品决策的那个人。

## Closing

最后给你一个本周可以做的具体动作。不用搭七个 agent，先做一件事：下次让 Claude Code 写功能之前，先要求它**只 research，不写代码**——让它把要动的文件列出来，把现有模式说清楚，把它的假设说出口。

你会立刻看到一件事：那些原本要在第十个文件里才暴露的错误假设，会在第一段输出里就冒出来。这就是 brief 闸口的最小可行版本。

把"先研究、后建造"变成肌肉记忆，你已经走出了 vibe coding 的天花板。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
