# Agent 100 倍生产力的秘密不是模型

## Hook

两个人用同一个 Claude。一个产出 2 倍生产力，一个产出 100 倍。差的不是模型，不是参数，不是 prompt——他们连订阅的套餐都一样。

2026 年 3 月 31 日，Anthropic 不小心把 Claude Code 的完整源码发到了 npm，51 万 2 千行。YC 总裁 Garry Tan 读完之后说：这 50 倍的差距，写在一张卡片上就讲完了。

## Brand Intro

这里是精读AI。今天我们来拆解一下 YC 总裁 Garry Tan 的最新架构心法——Thin Harness, Fat Skills。

## 100 倍差距不在模型脑子里

我们先把话说清楚。两个人用同一个 Claude，一个产出 2 倍生产力，一个产出 100 倍。差 50 倍。差的是什么？

不是模型。模型是同一个。不是参数。参数是一样的。差的是模型周围那一层东西——Garry Tan 管它叫 harness，翻译成中文就是"脚手架"，围着模型的那一圈结构。

Live repo context、prompt caching、专门打造的工具、压缩上下文、结构化的会话记忆、并行子 Agent。这些东西没有一样是让模型变聪明的。它们做的事只有一件：在正确的时间，把正确的上下文，送到模型面前，不让噪声淹死它。

所以每一个 AI 产品真正要问的问题只有一个——什么东西该进 harness，什么东西不该进。Garry Tan 给出的答案有一个非常具体的形状。Thin Harness, Fat Skills。

## Skill 不是 prompt，是带参数的方法调用

我们先讲 skill。这是五个概念里最反直觉的一个。

大多数人以为 skill 就是一个写好的 prompt 模板，像"帮我写一封邮件"那种。不是。Garry Tan 的说法是：skill 是一个带参数的方法调用。它用 markdown 做编程语言，用人类判断做 runtime。

他举了一个例子叫 /investigate。这个 skill 一共七步——圈定数据、建立时间线、对每份文档做 diarize、综合、正反两面辩论、引用来源。它接三个参数：目标、问题、数据集。

现在请你跟着我想一下。同一个 markdown 文件，同样七步。第一次调用，目标是一位安全科学家，数据集是 210 万封证据邮件，问题是"这位吹哨人是不是被噤声了"——它就变成了一个医学研究分析师。第二次调用，目标换成一家空壳公司，数据集换成 FEC 政治献金文件——同样七步，它就变成了一个法证调查员。

Skill 描述的是判断的过程，invocation 提供的是这次要看的世界。这不是 prompt engineering，这是软件工程。

## 不是模型不懂推理，是它不懂你的数据

为什么 skill 这么重要？因为模型真正卡壳的地方你可能猜错了。

模型已经会推理、会综合、会写代码。这些它自己就会。它失败的原因只有一个——它不懂你的数据。它不懂你的数据库 schema、不懂你们团队的命名惯例、不懂你这个问题的具体形状。

Skill 就是补上这一层。你把自己脑子里那些"遇到这种情况要先看日志再去查账单"的流程，写成 markdown。下一次模型遇到同类问题，它就按这个流程走。你的判断力，就这样被封存成了一个可以反复调用的文件。

## Harness 要薄，薄到只有 200 行

讲完 skill，再讲 harness。Harness 是跑 LLM 的那个程序本身。它只做四件事：循环调用模型，读写你的文件，管理上下文，执行安全策略。就这四件。

Garry Tan 推荐的架构里，harness 只有大约 200 行代码，JSON 进，文本出，默认只读。

你可能马上会问，那为什么市面上那么多 AI 产品的 harness 动不动就几千行、几十个工具？Garry Tan 的原话非常狠——那叫反模式。

40 多个工具定义吃掉半个 context window。每个所谓的 God-tool 做一次 MCP 调用要 2 到 5 秒。把每一个 REST API endpoint 都包成一个独立工具，结果就是 3 倍的 token、3 倍的延迟、3 倍的失败率。

他举了一个对比特别直接。一个好用的 Playwright CLI，浏览器每一个操作 100 毫秒搞定。而一个典型的 Chrome MCP，要走截图、找元素、点击、等待、读结果一整条链，一次要 15 秒。差了 75 倍。

同样的任务，薄的那一边是 100 毫秒。厚的那一边是 15 秒。你以为工具越多 Agent 越强，现实正好相反。

## 作者自己的 CLAUDE.md，从 2 万行砍到 200 行

Harness 的薄，不只是代码量。更难的是克制你把东西往里塞的冲动。

Garry Tan 自己举了一个糗事。他的 CLAUDE.md 文件——就是那个告诉 Claude Code 怎么干活的说明书——一度写到了 2 万行。他把遇到的每一个怪癖、每一个踩过的坑、每一条经验，全都堆进去了。

结果是什么？模型的注意力反而变差了。最讽刺的是，Claude Code 自己提醒他：你这个文件太厚了，我读不动了。

他最后怎么改的？砍到大约 200 行。100 倍的压缩。砍掉的那 19,800 行没删，转成了外部文档，靠一个叫 resolver 的路由机制按需加载——什么任务来了，resolver 知道该读哪份文档。

2 万行知识，随用随取，但是不再污染 context window。这个反转很关键。行业在卷更大的 context window，但真正的瓶颈从来不是窗口多大，是在正确时机加载正确的文档。

## 最致命的错误：把确定性问题塞进 latent space

讲到这里，我必须插一个最容易踩的坑。这是 Garry Tan 说 Agent 设计最常见的致命错误。

他把系统里的每一步分成两种。一种叫 latent，翻译过来就是"潜空间"——智能活在这里。模型读、理解、判断、综合、识别模式。这是它该干的事。

另一种叫 deterministic，确定性的——信任活在这里。同样的输入，永远同样的输出。SQL 查询、编译代码、算术运算，都是这种。

然后他举了一个例子我听完就记住了。你让一个 LLM 给 8 个人安排一张晚宴桌的座位，考虑每个人的性格和社交氛围——没问题，它能做得很好。

但你让它给 800 个人排座位呢？它会给你一张看起来完美合理、但是完全错误的座位表。因为这是一个组合优化问题，属于确定性那一侧，你把它扔进了潜空间。

最差的系统，就是把活儿放错了边。最好的系统，对这条线的态度是冷酷的——该 latent 的放 latent，该 deterministic 的坚决下沉到代码里。

## Santos 的 Datadog 伪装术

光讲概念太抽象。Garry Tan 在文章后半段拿 YC 自己在做的系统举了例子，我挑最有冲击力的一个讲给你听。

2026 年 7 月，YC Startup School 会在 Chase Center 召开，6 千个创始人要来。传统做法是 15 个人的运营团队一份份读申请、做直觉判断、更新表格。200 人还能扛，6 千人直接崩溃。

没有人能在脑子里同时装下 6 千份创始人档案，更别提从中发现"拉各斯、新加坡、布鲁克林这三个人其实在解同一个痛点，只是用词不一样"这种关联。

他们写了一个叫 /enrich-founder 的 skill。每个创始人的申请、问卷、一对一对话录音、X 上的发言、GitHub commit，全拉进来，跑一遍 diarize——就是让模型把所有材料读一遍，写成结构化档案。

然后就抓到了这样的东西。一个创始人叫 Maria Santos，公司叫 Contrail，她在申请里写的是"AI Agent 的 Datadog"——听起来是个观测性工具。但 diarization skill 读完她的 GitHub commit 发现，她 80% 的代码都在 billing 模块。

这个创始人不是在做 observability，她在做一个伪装成 observability 的 FinOps 工具。

这个判断，你用 embedding 相似度搜不到，用关键词过滤也抓不到。因为她说的话和她做的事根本不是同一个词。只有一个东西能同时抓到——模型把申请、commit、对话三份材料同时读完，在脑子里对照着做判断。

Garry Tan 在原文里打了一个感叹号，说这才是该放进 latent space 的完美任务。

## 会自己重写的 skill

故事还没完。活动办完之后，他们又跑了一个叫 /improve 的 skill。

这个 skill 最反常识的一点是——它不去读差评。它专门去读那些"还 OK"的中等评价。

为什么？因为差评噪声太大，有各种各样的原因。但"OK"这种评价最危险——系统差一点就成功了，只差一点，是最适合反推规则漏洞的样本。

/improve 读完之后，把新的规则直接写回 matching skill 文件里。比如它会加一条：如果某人自称"AI 基础设施"但代码 80% 在 billing，那就重新归类成 FinTech。

下一次活动跑的时候，skill 自动用上了这些新规则。7 月那场 OK 评级是 12%，下一场降到 4%。没有人改代码。是 skill 文件自己学会的。

这就是为什么 Garry Tan 说 skill 是永久升级。模型版本每升一次，所有 skill 的 judgment 步骤自动变强。而下沉到代码里的确定性那一层，一行都不用动，继续完美可靠。

## 代价：这不是银弹

讲到这儿我必须停下来说一句代价，不然你会以为这个东西是万能的。

不是。skill 路径是一种纪律，不是灵感。Garry Tan 自己给 Agent 定了一条硬规矩——如果一件事可能再发生，你不准一次性地做。你要手动做 3 到 10 次给我看，我批准了，你就把它固化成 skill 文件；如果要自动跑，就放到 cron 上。他的判定标准很刻薄："如果同一件事要我问你第二次，那就是你第一次失败了。"

听起来很爽。但现实是，如果你的团队做不到这种纪律，skill 层会迅速失控，变成另一个 2 万行的 CLAUDE.md，模型又读不动了。

还有 diarization 这个动作本身——既烧 token 又慢。6 千个创始人要每天跑一次，成本不是小数字。这不是 RAG，embedding 替代不了，只能让模型真的把材料读一遍。

Thin Harness, Fat Skills 是个方向，不是一个免费午餐。

## Synthesis

所以回到开头那个 100 倍。

同样的 Claude，10 倍用户和 100 倍用户的差距，不在模型脑子里。在模型周围那 200 行脚手架里。在你愿不愿意把判断力从对话里抽出来，写成一份可以被重复调用的 markdown。在你做每一步之前有没有先问一句——这是该模型干的，还是该 SQL 干的。

模型是公共资源。skill 是你自己的复利。
