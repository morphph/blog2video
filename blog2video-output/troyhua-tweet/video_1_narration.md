# Claude Code 的 6 层记忆管线：200K token 背后的经济学

## Hook

今天我们解读目前公开的最详细的 Claude Code 记忆架构拆解。作者是卡内基梅隆大学专攻 Agentic Memory 的博士 Troy Hua。他从源码里逆向出了一套 6 层记忆管线——最便宜的不到 1 毫秒，最贵的要等你睡着了才启动。

## Brand Intro

这里是精读AI。AI 世界很吵，每期帮你读透一篇最值得读的。今天我们精读的就是这篇 Claude Code 记忆系统的源码级拆解。

## 为什么上下文管理是经济学问题

先建立一个核心认知。Claude Code 的上下文窗口，200K tokens。听起来很大。但实际编码任务中，读几个文件、跑几次测试，上下文就快满了。

满了怎么办？最粗暴的方法是一刀切压缩。快满了就调一次 API 做摘要。但 API 调用要花钱、花时间。每次都调，成本会非常高。

Claude Code 的解法是分层拦截。把上下文管理拆成 6 层。从最便宜到最贵排列。便宜的层能解决问题，贵的层就不用启动。这不是技术架构问题。这是经济学问题。

## 前两层：几乎免费的防线

第一层叫工具结果存储。工具返回了几万字符的内容。系统不会全塞进上下文。它把大结果写到磁盘，只留一个预览。磁盘写入，不到 1 毫秒。

第二层叫微压缩。每轮对话结束后，自动清理过时的结果。超过 60 分钟没引用的会被移除。只保留最近 5 条。同样不到 1 毫秒，不调模型。

这两层做的是最基础的垃圾回收。大部分情况下，光靠它们就够了。

## 第三层 vs 第四层：成本分水岭

前两层不够用了，上下文逼近天花板。系统来到第三层：Session Memory。

这一层做了一件很聪明的事。Claude Code 在对话中会持续维护结构化笔记。记录任务进度、关键决策、文件变更。到了需要压缩的时候，直接复用这份笔记。不调 API，不让模型重新总结。5 秒完成。

第三层还不够呢？才触发第四层。Fork 出一个专门的摘要 Agent。对整段对话做完整的结构化总结。这是一次完整 API 调用，大约 10 秒。

第三层和第四层的差距是质变级的。一个零 API 调用，一个完整 API 调用。第三层存在的意义，就是让第四层尽量不被触发。

还有一个细节：自动压缩有三次熔断机制。连续失败三次就停止尝试。不会陷入死循环。策略反复失败，强行重试只是浪费资源。

## Dreaming：你睡觉时它在整理记忆

前四层都在对话过程中。第五层和第六层在对话之外。

第五层叫自动记忆提取。每轮对话结束后，后台提取值得记住的事实。项目结构、用户偏好、技术决策。写入持久化的记忆文件。下次对话直接可用。

但最精妙的是第六层：Dreaming。

Dreaming 是跨会话的记忆整合。它不是每次都跑。它有 5 道门控，全部通过才启动。功能开关是否打开。距上次整合是否超过 24 小时。扫描间隔是否超过 10 分钟。期间是否累计了 5 次会话。文件锁是否空闲。

5 道门控，每道成本就一次文件系统调用。全部放行后，Dreaming 才会启动。它回顾最近多场对话，提炼跨会话的模式。合并重复知识，清理过时信息。大约 30 秒完成。

为什么叫 Dreaming？因为人类睡眠也在做类似的事。白天的碎片记忆，在夜间被整合巩固。Dreaming，就是 AI 版的睡眠巩固。

第五层和第六层的成本标注都是 Free 加星号。星号的意思是：后台运行，不阻塞用户。实际消耗计算资源，但用户感知为零。这是产品思维。感知成本和实际成本是两码事。

## Fork Agent：边际成本接近零

6 层之上还有第七层：跨 Agent 通信。这里有一个设计细节值得注意。

Claude Code 的多 Agent 架构有 4 种模式。但用得最多的是 Fork Agent。Fork 不创建新上下文，直接继承父 Agent 的完整历史。

关键在于：继承是字节级完全一致的。这能命中 KV Cache 前缀匹配。已经计算过的上下文不需要重新计算。Fork 的前缀和父 Agent 一模一样。所以边际推理成本接近于零。

这就解释了为什么大量使用 Fork。不是偏好问题，是成本问题。Fork 几乎免费。Named Agent 要从零构建上下文。

## 记忆也有版本控制

最后提一个容易忽略的设计。Claude Code 的记忆有三个作用域。User 级别在用户主目录，是全局记忆。Project 级别在项目 .claude 目录里。Local 级别不进版本控制。

关键在 Project 级别——它通过 VCS 共享。一个人教会它的项目知识，会通过 Git 同步给全团队。这不只是记忆系统，这是隐性的团队知识管理。

## Synthesis

回过头来看，大多数 AI 产品的上下文管理是一刀切。快满了就压缩，压缩不了就截断。Claude Code 重新定义了这个问题。不是"怎么压缩"，而是"怎么让压缩尽量不发生"。

最便宜的层先上。磁盘写入挡住微压缩。微压缩挡住 Session Memory。Session Memory 挡住完整 API 调用。对话内的机制挡住对话外的机制。每一层都是前一层的保底。

而当你不在的时候，Dreaming 在后台默默工作。整合你最近几场对话的碎片记忆。你第二天打开 Claude Code，会发现它更懂你的项目了。但你不会察觉。因为感知成本是零。

上下文管理做成了经济学。这是这套系统最优雅的地方。
