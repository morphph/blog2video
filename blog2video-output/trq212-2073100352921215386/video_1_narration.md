# 模型太强，反而卡在你这一环？

## Hook

Anthropic 做 Claude Code 的工程师 Thariq，最近拿 Claude Fable 5 做了不少东西，得出一个反直觉的结论——作品好不好，头一回不再取决于模型，而取决于你能不能把自己"不知道的那部分"说清楚。

模型越强，你反而越容易卡在自己这一环。今天不聊怎么把 prompt 写得更花哨，只聊这条把瓶颈从模型搬回你身上的缝，到底该怎么补。

## 地图不是地形

先说一个特别老、但一到 AI 面前又变得格外灵验的道理：地图，不是地形。

你给 Claude 的东西——你的 prompt、你的 skill、你喂进去的上下文——那是一张地图，是你脑子里"这活儿该怎么做"的一份表示。而真正做事的地方，是代码库、是真实世界、是那些实打实的约束，那才是地形。

地图和地形之间的那条缝，就是你的"未知"。Claude 一旦撞上一个未知，它没法问你，只能按"我猜他大概想要这个"往下走。活儿越大，它会撞上的未知就越多。

到了 Fable 这一代，我第一次清楚地感到：决定成品质量的，不是模型的能力上限，而是我能不能把这些未知讲明白。

而且光靠提前规划救不了你。有些未知埋得很深，要到实现中途才冒出来。有时它甚至会告诉你——这问题压根该换一种解法。

所以这不是一锤子买卖。它是一个在动手前、动手中、动手后，反复挖未知的过程。

## 你的未知，分成四种

那"未知"到底是什么样子？把它拆成一个二乘二的方格，一下就清楚了。

第一种，已知的已知。就是你 prompt 里明明白白写下来的东西——你告诉 agent 你要什么。

第二种，已知的未知。你还没想清楚，但你清楚自己没想清楚的那些问题。

第三种，未知的已知。这种最微妙——显然到你根本不会写下来，可一旦看见，你立刻认得出"对，就是这个"。

第四种，未知的未知。你压根没考虑过的东西，你甚至不知道这条路上埋着这么一个坑。

这里有个反直觉的点。你看那些顶尖高手写 prompt，会以为他们赢在"什么都懂、几乎没有未知"。

但真相是，他们同样默认自己有未知，并且主动为未知留出余地。把未知减到最少、又替它做好准备——这件事本身，才是 agentic coding 真正的核心技能。

好消息是，这是一项能练的技能。而练它最好的搭档，恰恰就是 Claude。

## 太具体和太模糊，会用两种方式害你

给 Claude 下指令，是个很微妙的平衡。

你要是太具体，它会死死照着你的话做，哪怕这时候该转向、该变通，它也不转。你要是太模糊，它就退回到行业里的通用最佳实践，而那套东西，很可能根本不适合你这个活儿。

注意，这是一个对称的陷阱。大多数人只怕自己"说得不够细"，本能地往死里写详细。

可过度具体和过度模糊，是两个相反方向、同样能把你带沟里的坑。真正的病根不在"具体还是模糊"这根刻度上，而在于——你有没有替未知留出空间。

那 Claude 怎么帮你？它搜代码库、搜互联网都快得离谱，平均知识面比你广，撞了南墙以后迭代也比你快。所以它帮你挖未知的速度，远超你自己闷头想。

关键动作只有一个：把你的起点交给它。告诉它你现在想到哪一步、你对这个问题和这套代码有多少底、让它像一个真正的思考搭档那样跟你一起想。

而承载这一切最顺手的媒介，往往就是一个 HTML 页面——把想法直接摆出来给你看。

## 动手之前：先把盲区逼出来

真正的技法，是从动手之前就开始的。这里我挑最有用的两招讲。

第一招，盲区扫描。当你要在一块完全陌生的代码里加功能，或者做一件你根本不在行的事，你身上全是"未知的未知"——你连该问什么问题都不知道，不知道什么算好，不知道前人踩过哪些坑。

这时候，你就直接对 Claude 说这两个词：blindspot pass，加上 unknown unknowns。

比如："我要加一个新的 auth provider，可我对这个代码库的 auth 模块一无所知，你帮我做一次盲区扫描，把我相关的未知的未知找出来，好让我能更好地给你下指令。"

你把"我是谁、我懂多少"这个背景交清楚，它就能对着你的盲区照一遍光。

第二招，让它反过来面试你。头脑风暴做完，你手上通常仍有没理清的地方。那就让 Claude 来采访你：一次只问一个问题，而且优先问那些"我的回答会改变整个架构"的问题。

一句话就够——它会顺着你的答案，把你自己都没意识到的模糊地带，一个个抠出来。

这里藏着一个最容易被低估的点：最贵的未知，往往是第三种，那个"未知的已知"。就是你心里其实有杆秤、只是从没写下来的隐性标准。

你以为最可怕的是那些完全没想到的坑。但真正烧钱的，是这些"看到才认得"的标准，拖到写代码阶段才浮现。

因为 spec 一点点变动，就能让代码实现天差地别，而 agent 很难把之前的改动干净地退回去。所以要趁做原型、改起来还便宜的时候，把它们先逼出水面。

## 动手之中：让它一路记账

计划做得再足，未知的未知照样潜伏。agent 做着做着，可能撞到代码里一个边界情况，被迫改道。

所以我会让 Claude Code 一边做，一边记一个临时的 implementation-notes 文件。

规矩很简单：一旦撞上边界、被迫偏离原计划，就选那个最保守的方案，把这次偏离记到"Deviations"那一栏底下，然后接着往前走。

这样等下一轮再来，你手里就有一份"它当时到底为什么这么决定"的账本。

## 动手之后：考过了，才准合并

活儿做完，别急着合并。

一次长会话下来，Claude 做成的事，往往比你以为的多得多。光扫一眼代码 diff，你只能看个大概，因为很多行为都依赖那些你没细看的既有代码路径。

我的做法是：让它先给我足够的上下文，再就这次改动，出一份小测验来考我。我只有考满分，才 merge。

你可能觉得这有点自虐。但它其实是在逼你，把这次改动真正吃进脑子里，而不是稀里糊涂点下合并。

## 这套方法真跑起来是什么样

说了这么多，看一个把它整个跑通的例子最实在。Fable 的发布视频，整段是用 Claude Code 剪出来的。而剪它的那个人，此前对视频剪辑完全是外行，谈不上任何专业。

他是怎么开始的？从他已经知道的那一点点出发。他知道 Claude 能用代码剪视频、能转录，但不确定准不准。

于是他先让 Claude 给他讲明白：Whisper 这类转录到底怎么工作，自己能不能靠它，精确地把那些"呃""嗯"和长停顿切掉。

他还想要画面上的字幕，跟自己说话的节奏严丝合缝地对上，又拿不准做不做得到。那就让 Claude 先拿一份转录做一个原型出来，验证这条路走不走得通。

最后那一下最见功夫。视频画面看着有点发闷，他知道这是调色的问题，可他根本不懂调色。

他一开始想让 Claude 出几个版本让他挑。挑着挑着他才反应过来：我连"好的调色是什么样"都不知道，我拿什么挑？

于是他掉头，改成让 Claude 先教他调色——先把这个未知补上，再谈选择。

你注意到没有，这整个过程里，他没有一次是"把活儿甩给 AI"。恰恰相反，他一路在主动补齐自己的未知。人的判断力是被拉满的，不是被省掉的。

## 说清你不知道的那部分

把这些串起来，会看到一件反常识的事：模型越强，认知负担不是被卸下，而是被推回到你身上。

它不是"一句话出活"的捷径。模型越强，你反而要花更多时间去定义未知、写实现计划、做盲区扫描、考过测验才敢合并。

以前的问题是"模型会不会做"，现在的问题是"你有没有说清你不知道自己不知道的那部分"——最贵的 bug，藏在你从来没写下来的那句话里。

而每一次讲解、每一次头脑风暴、每一次面试、每一个原型、每一份参考，本质上都是同一件事：趁改动还便宜的时候，把你原本不知道的东西先挖出来。你这一次学到的，会变成你下一次的地图。

还要说一句公道话：这些技法是一个工具箱，不是一张一步步照抄的清单。不用每次都全套上，什么时候用哪一招，靠的是你自己的判断。照单全收，反而是误用。

## Closing

所以，下一个项目开始的时候，别急着写那份看起来天衣无缝的 prompt。先问 Claude 一句：帮我找找，我这次有哪些未知。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
