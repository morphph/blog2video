# 官方删了 80% 提示词，效果没变差

## Hook

一份系统提示词，被删掉了超过百分之80，评测成绩一点没掉。

动手的是 Anthropic 自己，被删的是 Claude Code 的系统提示词。

我读完这篇官方复盘，最在意的其实不是那个数字。是他们删掉的到底是什么东西。因为你的 CLAUDE.md 里，很可能正装着同一批东西。

## 先分清楚 prompt 和 context

要看懂他们删了什么，要先把两个词分开。

你在对话框里敲的那句话，是 prompt。它是一次性的，可以写得非常具体，因为你知道自己这次想要什么。

但模型真正看到的，远远不止这一句。系统提示词、Skill、CLAUDE.md、记忆，全都会被拼进去。这一整包东西叫 context，组织它的手艺叫上下文工程。

难点在于，context 是跨所有请求通用的。你不知道用户下一句会问什么，所以你没法写得具体。你只能写规则。

## 删掉的不是信息，是互相打架的规则

官方的原话是，他们发现自己在过度约束 Claude Code。约束来自三个地方：系统提示词、Skill，以及用户自己的请求。

他们回头去读自家内部的使用记录，看到了这样一幅画面。同一次请求里，一边写着「文档该留就留」，另一边写着「不要加注释」。两句话同时递到模型面前。

模型当然分得清用户想要什么。但在动手之前，它必须先把这一堆互相覆盖、互相矛盾的指令想清楚，才能决定该听谁的。

这句话是全文的题眼。规则真正吃掉的，不是你的上下文长度，是模型的判断力预算。

所以删掉百分之80 而评测不掉分，一点都不神奇。被删掉的本来就不是信息，是冲突。

## 那些老规则，官方当初就知道它有代价

你可能会问，既然有害，当初为什么要写？

因为当初的模型确实需要。Claude Code 刚推出的时候，官方最怕的是最坏情况，比如模型自作主张删掉你的文件。所以他们会给出特别强硬的指引，哪怕这个指引并不总是对的。

老的系统提示词里有这么一段：代码里默认不写注释，绝不写多段的 docstring 或者多行注释块，最多一行；也不要主动生成计划、决策、分析这类文档。

这条规则的问题在于，它在一部分场景里就是错的。用户可能有自己的偏好，特别复杂的代码本来就该配多行注释。

真正让我停下来的，是原文紧接着的半句话。他们说，当年不加这层护栏，模型写出来的注释在很多情况下都是错的，所以这个代价「我们只能接受」。

也就是说，这条规则从来就没被当成真理。它是官方明知有损失、还是买下的一份保险。

模型换代之后，保险到期了。而你今天从教程里、从别人的仓库里、从旧版官方文档里抄来的规则，抄的往往正是这类为上一代模型定制的保单。

## 删规则不等于留白

这里有个特别容易读歪的地方。删掉那整段禁令之后，新的系统提示词并没有留空。

它换成了一句话：写出来的代码要读着像它周围的代码——注释密度、命名、写法，都跟着现场走。

指令还在。只是从「我替你决定」，变成了「你去看现场，自己决定」。

这就是整篇文章的方法论。不是少给指引，是把绝对命令换成相对锚点。

## 最反直觉的一条：别给例子了

接下来这条，是全文最反直觉的。

给工具用法举例子，曾经是 tool use 的第一守则。几乎所有中文提示工程教程，今天还在这么教。

官方现在的判断是：给例子，反而会把新模型锁死在一个特定的探索空间里。你给了三个例子，它就在这三个例子的形状里打转。

那用什么替代？答案不是空白，是接口设计。想清楚你的工具、脚本、文件到底给了模型哪些参数，这些参数能不能更会表达。

官方举的是 Claude Code 自己的 Todo 工具。状态这个字段被定义成三个枚举值：pending、in progress、completed。

不用举例，枚举值本身就在告诉模型该怎么用。再配一句约束——同一时刻只保留一个 in progress——期望行为就说完了。

用接口的形状，代替用法的示例。这个思路迁移性极强。你写脚本、定 schema、设计 API 的时候，都用得上。

## 工具越来越多，上下文反而更省

第三条是渐进式披露。

Claude Code 早期专注编码，所以系统提示词里塞了大量关于怎么做代码审查、怎么验证的细节。这些内容不是每次都用得上，但用得上的时候特别关键。

后来他们把验证和代码审查整个搬了出去，各自做成一个 Skill，让模型需要的时候自己去调。

工具也是同一招。Claude Code 有一部分工具是延迟加载的：模型必须先用 ToolSearch 搜到完整定义，才能调用它。

这个设计解开了一个死结。直觉上，工具越多，工具定义占的上下文就越多，能力和成本是绑死的。而延迟加载把「默认加载」变成了「按需检索」，两者就脱钩了。

工具可以更多，不用的时候一个 token 都不占。

顺带说一句，早期模型有个毛病，它更容易听 context 末尾的指令，而不是开头的。所以当年的做法是系统提示词里写一遍、工具描述里再写一遍。现在这些说了两遍的地方被删掉了，用法只留在工具描述里。

## 你的长文件不该写成百科全书

同一招原样适用于你的 CLAUDE.md 和篇幅很大的 Skill。

官方点名了一个常见迷思。很多人觉得，这些文件必须写成百科全书，把所有可能用到的规范全塞进去。不然模型根本找不到。

正确的做法不是写得更少，是拆成一棵树。让每一部分，在它该被读到的那一刻才被读到。

## 给模型的参考资料，可以丰富得多

还有一条变化，我觉得被严重低估了。

过去在计划模式里，Claude Code 高度依赖 markdown 文件。把计划写成文件存下来，模型随时回头查；把规格文档存进代码库，也是同一个套路。

但现在模型能处理的参考资料，复杂度高了很多。

一份 spec 可以是一个 HTML 格式的 artifact。可以是一整套详细的测试用例。也可以是另一个代码库里、你想让它移植的那个函数。

它甚至可以是一份评分标准，用来让模型去校验你在某个领域的品味。

原文里有一句，我建议你直接记下来：一份 HTML 的设计稿，通常比一段文字描述、或者一张截图，产出的结果更好。

原因不难理解。代码是模型最熟的那门语言。你给它代码形态的高保真材料，它读到的是明确指令；你给它一张图，它读到的是需要猜的东西。

## 那你的 CLAUDE.md 到底该怎么写

讲到这里，落到你手上真正能改的地方。

系统提示词这一层，基本轮不到你。它跟产品上下文绑得很死。除非你在自建 agent harness，那这一层反过来是最值得花时间的地方。

CLAUDE.md 保持轻量。用一小段说清楚这个仓库是做什么的，剩下的 token 全部花在坑上。

什么叫坑？比如你们把所有类型定义都堆在一个文件里，别的地方一个都不放。这种反直觉的约定，模型自己看不出来，必须你告诉它。

反过来，看一眼文件结构就能知道的事，一句都不要写。

Skill 就当成一份轻量的索引，让模型在需要的时候找得到东西。别把它写成一份事事都要管的规范。

官方也把这套判据做成了一个命令。在 Claude Code 里敲斜杠 doctor，它会帮你给 Skill 和 CLAUDE.md 做一次瘦身。

## 先别急着清空你的 CLAUDE.md

说了这么多删，我必须把边界交代清楚。这是这期最容易被听歪的地方。

那个百分之80，带着三重限定。删的是 Claude Code 自己的系统提示词；适用的是 Claude Opus 5 和 Claude Fable 5 这一代模型；测的是 Anthropic 自己的编码类评测。

三个条件缺一个，结论就未必成立。原文自己也说了，对更老的模型，没有那些护栏，注释在很多情况下会写错。删护栏这件事，是有模型条件的。

第二，官方给 Skill 的建议留了一个例外：别写得过度约束，除非是极其重要的领域。什么算极其重要，文章一个判据都没给。

也就是说，删到哪一层，这个最难的决定，风险还是你自己扛。

第三，「没有可测量的损失」，不等于「没有损失」。评测只覆盖它覆盖的那部分。约束被删掉之后，模型在写作口吻、文档偏好、危险操作边界上会有什么变化，这次没有数据。

还有一个代价，官方说得很轻。过去用井号热键把内容写进 CLAUDE.md，存了什么是一份你能读、能改、能审的明文。现在改成模型自动决定哪些记忆值得留。省事了，但可见和可控也一起没了。

## Synthesis

把这一整篇拉远了看，它讲的其实不是「提示词可以少写」。

恰恰相反。上下文工程比以前更重要了，只是形状变了。从「写规则」，变成了设计接口、安排加载时机、给出高保真的引用。

规则这个东西，本质上是你替模型做决定。模型弱的时候，你替它决定是划算的。模型强到某个程度之后，你替它做的每一个决定，都在挤掉它本来能做得更好的那次判断。

所以这一整篇，可以压成一句话：上下文工程的关键，不是把你知道的都写进去，而是把模型自己能判断的那部分删掉。

说得再狠一点——为弱模型写的规则，会在强模型身上变成 bug。

## Closing

最后给你一个今晚就能做的动作。

打开你的 CLAUDE.md，逐条问两个问题。第一，这条规则，模型看一眼代码库能不能自己知道？能，就删掉。第二，这条规则，跟文件里别的地方会不会打架？会，就只能留一条。

但更该问的是第三个问题：这条规则，当初是抄谁的，为哪一代模型写的？

规则会过期。而过期的规则不会报错。它只会让模型在动手之前，先多花一次判断力，来伺候你。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
