# 我为什么不再读 AI 写的 markdown

[SLIDE 1: cover] (0:00 - 0:30)

Anthropic Claude Code 团队的工程师 Thariq，悄悄换了个工作习惯——他不再让 Claude 写 markdown 了。所有的 plan、spec、PR review、研究报告，全部切到 HTML。这条推贴出来，三天 3.4M 阅读，1.3 万人收藏。但这事跟你想的"格式偏好"不是一回事。今天不聊怎么让 Claude 写 HTML，只聊一件事——当 AI 越来越强，你怎么不被它替代决策。

[SLIDE 2: image] (0:30 - 1:30)

我读完这篇的时候，第一句让我停下来的不是什么技术论点。是一句很朴素的自白。

作者说：超过 100 行的 markdown 文件，我自己其实读不进去。我也没办法让公司里任何人去读它。

这句话说的不是 markdown 不好，是 markdown 被 AI 的产能撑爆了。

以前你写一份 spec，可能两百行就到头了，因为是你一个字一个字敲的。现在 Claude Code 一秒钟给你产一份八百行的实施计划。语法没问题、结构也清楚。但你打开的瞬间，脑子里就一句话：算了，滑到底直接 approved。

这才是问题。不是 AI 写得不好，是你开始不读 AI 写的东西了。

[SLIDE 3: image] (1:30 - 2:35)

作者的反应特别简单。换 HTML。

听起来像个表面动作对吧？格式而已。但我读到这里有个直觉：能让 Anthropic 内部团队成员悄悄改习惯的事，背后不是"换个后缀名"这么简单。

第一个理由是信息密度。markdown 能干的，HTML 都能干。markdown 干不了的，HTML 还能干。表格、SVG 插画、CSS 设计稿、流程图、甚至嵌一个 canvas。Claude 能读进去的几乎所有信息，HTML 都能高效表达出来。

还有一个让我笑出来的反例。在没有 HTML 可用的时候，Claude 会在 markdown 里干什么？画 ASCII 图。更荒诞的是，它会用 unicode 字符去模拟颜色——拿方块字符近似一个色板。一个被压在 markdown 里的模型，在用字符估计 RGB 值。

[SLIDE 4: principle] (2:35 - 3:35)

但我读到第三段才意识到，密度不是真正的论点。

作者很轻地说了一句：你的 spec、报告、PR writeup，如果是 HTML 的，别人真的去读它的概率，会高得多得多。

注意这个用词。不是"读得更高效"，是"读这件事真的会发生"。

markdown 文件你得下载、得有个 viewer、邮件里只能当附件挂着。HTML 你扔到 S3 上，发个链接，同事点开就看，手机上还能响应式地重新排版。

这一下我才明白他在说什么。他不是在比格式的能力上限，他是在比格式的触达率。一份没人打开的 plan，写得再细致也是零。HTML 在他眼里的核心价值，是把"被阅读"这件事的概率从 30% 拉到 80%。

[SLIDE 5: principle] (3:35 - 5:00)

接下来这段，是这篇博客真正反直觉的地方。我第一次读的时候没反应过来，回过头才意识到他在讲一件大事。

我们一直默认 HTML 是个"输出"——就是 Claude 写完给你看的成品。是只读的，是终点。

但 Thariq 不是这么用的。他让 Claude 给他做一个动画原型，里面带 sliders，带 knobs，让他用鼠标拖着调缓动曲线、调颜色、调时长。调到他满意了，按一个 "copy as prompt" 按钮，所有当前参数被打包成一段 prompt，他粘回 Claude Code 里，让 Claude 把这套配置写进真正的产品代码。

你看出来了吗。HTML 在这里根本不是输出格式。它是 Claude Code 的输入界面。

这就把整个讨论维度抬起来了。chat 输入框打字这种事，能描述的状态太有限了。颜色、缓动、cron 表达式、正则、裁剪区域——这些东西用嘴说说不清楚。但你给 AI 一个一次性的可视化界面去操作，操作完再把状态序列化回 prompt，整个反馈环就闭合了。

HTML 不是更好看的 markdown。HTML 是 chat 输入框的外接 GUI。

[SLIDE 6: principle] (5:00 - 6:20)

顺着这个思路，作者抛出了一个概念：throwaway editor，一次性编辑器。

举两个例子。30 个 Linear ticket 要重排优先级，他让 Claude 做一个 HTML 文件，每个 ticket 是一张可拖拽的卡片，分到 Now、Next、Later、Cut 四列里。AI 先按猜测排好，他用鼠标调整，最后一个 "copy as markdown" 按钮，把最终顺序连同每档的一句话理由导出来。

还有一个。系统 prompt 调优界面。左边可编辑的 prompt，变量槽位高亮。右边三个示例输入，模板实时渲染结果。底部一个 token 计数器、一个 copy 按钮。

注意这个限定词。不是产品。不是可复用工具。不是要测试、要部署、要维护的东西。就是为这一份数据、这一次任务，做一个用完就扔的界面。

工程文化里我们被训练了几十年的"DRY"——不要重复造轮子——在这里被反过来用了。当生成成本接近零的时候，DRY 这个原则的前提就消失了。一个能在两分钟内被生成出来的 UI，做成可复用的反而更贵。

throwaway editor 是个新的设计 primitive。它只在 AI 时代成立。

[SLIDE 7: image] (6:20 - 7:30)

中间还有个隐藏问题，作者顺手答了。

你可能会想，那为什么不在 ClaudeAI 网页版或 Claude Design 里做这些 HTML？为什么非得是 Claude Code？

他给了一个很直接的答案：context ingestion。Claude Code 能读你的 file system、你的 MCP（比如 Slack、Linear）、你的浏览器、你的 git history。

听起来像顺嘴一提，但这其实是分水岭。一个无根的 HTML 设计稿和一个带着你整个项目语境的 HTML 报告，是两个东西。他写这篇文章里那些示意图，是怎么来的？他让 Claude Code 翻遍他的代码文件夹，把所有以前生成过的 HTML 文件都找出来、分类、归组，然后做了一个总览页。这事 ClaudeAI 干不了——它根本读不到他的本地文件。

context 是 Claude Code 跟其他 Claude 产品的根本差别。HTML 在这里不是终点，是 context 流转的载体。

[SLIDE 8: checklist] (7:30 - 8:50)

读到这里我必须暂停一下夸节奏。因为这篇博客最让我尊重的部分，是作者主动列出来的代价。

第一，慢。HTML 比 markdown 生成慢 2 到 4 倍。这是每次等待从 30 秒变成两分钟。作者直接说 results are worth it，但他没装作没有这个成本。

第二，版本控制是噩梦。HTML 的 diff 噪声极大，你改一个字，整块标签可能重排。git diff 看不出实际改了什么。

第三，token 消耗高得多。HTML 标签开销比 markdown 大一个数量级。他的缓解理由是 Opus 4.7 的 1MM context window 大到让这点开销不再敏感。但你听得出来，这其实是把成本转嫁给了模型容量。

还有第四，默认产出可能丑。需要你自己建一份公司内部的设计系统 HTML 当参考。

他完全可以把 HTML 写成一个新发现的银弹。但他没有。他在文章里几次主动说"我有点担心有人把这个变成一个 /html skill"——他反对工具化，反对把这件事简化成一个咒语。这是很成熟的工程姿态。

[SLIDE 9: quote] (8:50 - 9:55)

读到 FAQ 我以为博客快结束了。结果在最后一节，作者轻描淡写地点破了真正的核心。

他说，所有上面这些话归根到底是想说：用 HTML 让我感觉自己 in the loop with Claude。

他原话：我曾经开始害怕，因为我不再深入读那些 plan，我就只能放手让 Claude 自己做选择。

我读到这一句的时候，前面所有的论点全部对上了。

100 行 markdown 没人读，是表象。读不进去意味着什么？意味着你按 approved 的时候根本不知道在批准什么。这等于把判断权外包给了 AI。

HTML 信息密度高、好分享、好交互、有 sliders 让你调参——这些机制全部指向同一件事：把人重新拉回那个决策的瞬间。让你看得见、点得动、调得了、改得动。

throwaway editor 的 "copy as prompt" 按钮，不是个 UI 巧思，是个权力移交的动作。AI 准备好初稿，你来做最后一道判断，再把判断推回去。

这不是格式之争。这是一个工程师在跟 AI 协作的过程里，对自己说：我不能只剩下按 approved 的功能。

[SLIDE 10: principle] (9:55 - 11:25)

我读完这篇博客最大的感受是：它表面在讲 HTML，真正在讲一种 AI 时代的人本主义焦虑。

模型变得比人写得快、想得宽、覆盖得全的时候，一个工程师真正需要捍卫的，不是写代码的能力，是 stay in the loop 的能力——是仍然在驾驶座上的资格。

而 stay in the loop 不是靠喊口号实现的，是靠每一个具体的小动作。比如选一个让你愿意打开的格式。比如做一个让你能用鼠标干预的界面。比如在 plan 里嵌入你能调的旋钮。比如在每个一次性 UI 末尾放一个 "copy as prompt" 按钮，把权力交还给你自己。

100 行的 markdown 让你滑到底直接 approved，HTML 让你停下来读一段。这两秒的差别，就是你和 AI 之间谁在做决策的差别。

当 AI 写得比你读得快，"读得进"就是你保留判断权的最后一道闸。HTML 不是更好的输出格式，HTML 是把人重新按回驾驶座的机制。

[SLIDE 11: summary] (11:25 - 13:05)

回过头看，这件事对我们任何一个跟 AI 协作的人都成立。不是只有 Claude Code 团队在面对这个问题。你让 ChatGPT 写一个长方案、让 Cursor 重构一大块代码、让 Gemini 做一份调研——只要 AI 的产能超过了你阅读和判断的速度，你就开始面临同一个分岔口。

下次让 AI 给你产 plan 的时候，问自己一个问题：这个东西我会真的打开来读吗？如果答案是不会，那别管它写得多好——你已经把判断权交出去了。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
