# 你的 Agent 到 Level 几了？

## Hook

你的 Agent 是 Level 几？这是 Google 工程总监 Antonio Gullí 在他 453 页的新书《Agentic Design Patterns》里抛出的诊断题。我读完发现一个不太愉快的答案——大多数人天天说自己在"用 Agent"，但他们用的根本是 Level 0：裸 LLM，没有工具、没有记忆、不会行动。书里说得很直白，Level 0 的东西，不算 Agent。

## 四级分层，是一把诊断尺

这本书最让我坐不住的，不是它讲了 21 种设计模式，也不是 Springer 这种学术出版社，是它在开头就把"Agent"这个词的边界切得很干净。

Level 0，裸 LLM。你打开 ChatGPT 网页版问它今年奥斯卡最佳影片是哪部，它只能猜。没有工具、没有记忆、不会自主行动。书里直接说，这一档不属于 Agent。

Level 1，工具使用者。用户问"最近有什么新剧"，Agent 自己判断这条信息不在训练数据里，主动调搜索工具去查。关键词是"自己判断"——不是你告诉它去搜，是它意识到该搜。这一步是 Agent 真正的门槛。

Level 2，战略思考者。会规划，会做 Context Engineering，会自我反思干完活回头审一遍。

Level 3，多 Agent 协作。一个项目经理 Agent 协调一群专才 Agent，像搭团队。

我读到这里第一反应是，把这四级当镜子照一下手上那些"AI 应用"。能照出来的事实是——大多数所谓"在用 Agent"的人，要么卡在 Level 0，要么勉强爬到 Level 1。这个诊断尺一拿出来，行业里很多浮夸的叙述瞬间安静下来。

## Level 1 到 Level 2，才是真正的死亡跳跃

为什么大多数 Agent 不好用？不是模型不行，是它根本没爬过 Level 1 到 Level 2 这一级台阶。

这一跳里最被低估的概念，叫 Context Engineering。书里给出的定义跟很多人理解的不一样——它不是堆信息，是裁剪、降噪、打包。

举个书里的例子。Agent 要在两个地点中间找一家咖啡店。它先调地图工具，拿回一堆原始数据——经纬度、距离矩阵、营业时间、评分。Agent 不会把这一坨直接喂给下一步，而是自己判断"下一步只需要街道名"，把数据裁成一个干净的短列表，再交给本地搜索工具。每一步都在主动做信息降噪。

书里那句原话我想念出来——"要让 AI 达到最高准确率，必须给它短小、聚焦、有力的上下文。" Context Engineering 干的就是这件事：管的不是你怎么问，是问之前 Agent 眼前摆着什么。Prompt 是台词，Context 是布景。布景错了，台词再好也演不出来。

## Producer 和 Critic，必须是两个人格

Level 2 的另一个核心能力，叫 Reflection。简单说就是 Agent 干完活后自己审一遍。

但书里给出了一条很硬的规则——Producer 和 Critic，必须用两个不同的 system prompt。不是同一个 Agent 自己审自己，是要造一个跟它对立的人格来挑刺。

这条规则乍听有点学究气，实际上是这本书我觉得最值钱的一句话。同一个 persona 审自己写的东西，盲区是会被继承的。你让同一个 LLM 先写代码再审查它自己写的代码，它大概率会说"挺好的"。"挺好的"是默认输出。

书里的代码示例很直白。Producer 的 prompt 是"你是 Python 开发者，写计算阶乘的函数，处理边界条件和异常"。Critic 的 prompt 是"你是吹毛求疵的高级工程师，逐行审查 Bug、风格、遗漏的边界条件；完美就输出 CODE_IS_PERFECT，否则列出所有问题"。然后一个循环：写、审、改、再审，直到 Critic 满意或者达到最大迭代次数。

这里有一个容易被忽略的代价。每一轮反射都是一次新的 LLM 调用，迭代越多越贵；而且上下文窗口会被前几版代码和批评意见挤满，实际可用的推理空间反而在缩水。书里的最大迭代次数默认设 3 次，一旦 Critic 满意就停。不要追求完美——追求完美会被 token 反噬。

## 别急着上 Multi-Agent

我观察过一个怪现象——很多团队听说 Multi-Agent 概念之后，第一反应是去搭 5 个、6 个 Agent 互相通信的复杂系统，花 80% 的时间在调协议、调路由。这本书的立场恰恰相反：先别急着上 Multi-Agent。

书里画了六种通信拓扑，但真正常用的就三种。单 Agent，任务能拆成互不依赖的子问题，各干各的，最简单。对等网络，Agent 之间直接通信没有中心节点，容错好但协调成本高，容易乱。Supervisor，一个调度 Agent 管一群干活 Agent，层级清晰好管理，但 Supervisor 本身是单点故障也是性能瓶颈。

任务越拆越碎，通信成本会反过来吞掉并行带来的收益。书里给出的判断是——绝大多数你以为需要 Multi-Agent 的场景，其实一个 Level 2 单 Agent 加上 Producer-Critic 和 Context Engineering 就够了。Level 3 是留给那种真正跨领域、多阶段、需要并行分工的任务。

换句话说，大多数人 Agent 不好用，不是 Agent 数量不够，是一个都没调到 Level 2。

## 第五个未来假设，最离谱也最值得记住

书末尾抛了五个关于 Agent 未来的假设。前四个还算合理推演——通用型 Agent、深度个性化主动发现、具身智能、Agent 成独立经济实体。

第五个把我看震了，叫"变形 Multi-Agent"。

你只声明一个目标——"做一个卖精品咖啡的电商生意"。系统自己决定：先生出"市场研究 Agent"和"品牌 Agent"。跑一轮数据之后，系统自己判断品牌 Agent 不够用了，把它拆成三个——Logo 设计、建站、供应链。建站 Agent 后来成了瓶颈，系统再自动复制三个并行版本同时做不同页面。整个过程中，系统还在不停地调优每个 Agent 的 prompt。

这跟 Karpathy 的 AutoResearch 还不一样。Karpathy 是你写一个 program.md 定义目标和指标，按启动；人类在循环外面，但团队是固定的。这本书更激进——连团队怎么组建、怎么重组，都交给系统。人类只声明"要什么"，剩下的全是系统自我演化。

作者也承认这条目前还停留在假设层面，没有成熟的工程实现。但你只要去想象一下这个画面——一个会自己拆分自己、自己复制自己、自己改自己 prompt 的 Agent 群——就会意识到，今天我们讨论的所有 Multi-Agent 拓扑都还只是这条路上的第一公里。

## Synthesis

读完整本书，我最大的收获不是任何一个模式，是那把诊断尺本身。

以前听到有人说"我的 Agent 不好用"，我会问"哪里不好用"。现在我会先问一句——你的 Agent 到 Level 几了？这一问下去，问题立刻从模糊的"效果不好"变成具体的"我连 Level 1 都没爬到"或者"我卡在 Level 1 上不去 Level 2"。一旦问题被定位到具体的层级，下一步该做什么就清楚了。

你以为你在用 Agent，其实大多数人连 Level 1 都没到——问题从来不是模型不行，是你根本没让它走出聊天框。

## Closing

如果今天只带走两件事，我建议你做这两件：

第一，给你现在的 Agent 加一个 Critic。Producer 和 Critic 用两个完全对立的 system prompt，迭代次数封顶 3 次。一次额外的 LLM 调用，往往换来翻倍的输出质量。

第二，开始做 Context Engineering，不是 Prompt Engineering。回头看你写给 Agent 的指令文件，如果全是"你要怎么做"的规则，缺少"你现在面对什么环境"的上下文，把后者补上。Context Engineering 才是 Level 1 跳到 Level 2 的真正杠杆。

至于 Multi-Agent，先放一放。把单 Agent 做到 Level 2，已经能覆盖你 80% 的场景。

AI 世界很吵，精读一篇，胜过刷一百条。我们下期再见。
