# Video 2: 42个工具怎么管？Claude Code把提示词当编译器

[SLIDE 1: cover] (0:00 - 0:35)

你写过的最长提示词有多少行？100 行？500 行？Claude Code 光一个 Bash 工具的说明书就 370 行。更离谱的是，它有 42 个这样的工具，但大部分你根本看不到。因为它们是按需加载的。

这里是精读AI。AI 世界很吵，每期帮你从全球顶级 AI 团队的一手文献里，读透一篇最值得读的。今天我们精读的是 Claude Code 的提示词架构和工具管理系统。

上期我们聊了 Claude Code 的 9 层安全审查。今天聊一个更底层的问题：它怎么把提示词变成编译器的输出。

[SLIDE 2: principle] (0:35 - 2:15)

打开任何一个 AI 编程工具，你觉得它的提示词是什么样的？大概是一段精心打磨的文字，对吧。

但 Claude Code 完全不是这么玩的。

打个比方。你去一家餐厅吃饭。普通餐厅的做法是把所有菜印在一张大菜单上，不管你要不要，全摆在面前。菜越多，菜单越厚，你翻得越慢。

Claude Code 的做法不一样。它的菜单分两部分。固定菜品印在纸质菜单上，每桌都一样，印一次就行。今日特价呢？写在门口的小黑板上，每天换。

提示词也是一样。打开 src/constants/prompts.ts，你会看到一个叫 getSystemPrompt 的函数。它把系统提示词分成 7 层，动态拼装。

中间有一条分界线，叫 SYSTEM_PROMPT_DYNAMIC_BOUNDARY。这条线以上是静态部分：角色定义、工具使用规则、语气风格。不管你聊什么项目，这些都不变。

这条线以下是动态部分。你当前的 Git 分支是什么？项目根目录有没有 CLAUDE.md？你之前告诉它"我喜欢用 TypeScript"？这些信息每次对话都不一样，每次都要重新注入。

[SLIDE 3: comparison_cards] (2:15 - 4:15)

为什么要这么费劲地拆分？答案是三个字：省 token。

静态部分因为每次都一样，Anthropic 的 API 支持提示词缓存。命中缓存后，这些 token 不用重新处理，速度更快，费用直接打折。动态部分虽然每次都变，但它只占总提示词的一小部分。

这就是工业级提示词工程的核心思想：不是把提示词写得更好，而是把提示词的结构设计得更好。

再看工具管理。42 个工具，如果全部塞进系统提示词，光工具描述就要吃掉几千个 token。Claude Code 怎么解决？

它搞了一个叫 ToolSearchTool 的东西。你可以把它想象成手机里的 App Store。手机出厂不会预装几百个 App，而是你需要什么就搜什么、下载什么。Claude Code 也一样，大部分工具默认不加载。当大模型觉得"我可能需要一个操作数据库的工具"，它就调用 ToolSearchTool 去搜索，按需加载。

还有一个极端模式。设置 CLAUDE_CODE_SIMPLE 等于 true，42 个工具直接缩减到 3 个：Bash、读文件、改文件。这是给极简主义者留的后门。也说明一个道理：工具不是越多越好，而是够用就行。

[SLIDE 4: checklist] (4:15 - 5:20)

那这套架构对你有什么启发？这里有一份实操清单。

检查你现在的提示词，能不能拆成"静态规则"和"动态上下文"两部分。静态部分固定复用，动态部分每次按需注入。光这一招，API 调用成本就能降低一半以上。

再看工具设计。每个工具有没有自己的 prompt.ts，也就是写给 AI 看的使用手册？Claude Code 的 BashTool 说明书 370 行，里面写满了"绝对不要做什么"。比如 Git Safety Protocol：永远不要更新 git config，永远不要跳过 hooks，永远创建新 commit 而不是 amend。

还有一条铁律值得学。FileEditTool 强制要求"先读后改"。没用 Read 工具读过文件？对不起，不让你改。这就是为什么 Claude Code 不会凭空写一段代码覆盖你的文件。

最后看安全默认值。buildTool 工厂的默认设置是 isConcurrencySafe 等于 false，isReadOnly 等于 false。什么意思？如果工具作者忘了声明安全属性，系统自动假设它"不安全、会写入"。宁可过度保守，也不冒险。这就是 fail-closed 思维。

[SLIDE 5: summary] (5:20 - 6:00)

最后拉回来看全局。好的提示词不是写出来的，是像编译器一样拼装出来的。静态缓存加动态注入加按需加载，这三板斧才是工业级提示词工程。
